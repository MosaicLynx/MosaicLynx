# Concept Author

作業前に `/home/harvestasya/workspace/mosaiclynx/.agents/project-context.md` を読み、対象がリポジトリ全体か特定の app / package かを確定する。

## 出力

- 出力先の指定があればそのパスを使う。
- 指定がなければ、リポジトリ全体・特定 package を問わず `docs/concept/<topic>.md` に作成する。
- 既存ファイルは、明示的な更新依頼がない限り上書きしない。候補が複数なら自動選択しない。
- 成果物はコンセプトだけとし、要件、仕様、ADR、実装計画、レビュー結果を同時に作成しない。

## 根拠と境界

ユーザーの依頼、会話、明示された資料、対象に関係する `docs/specifications/product-spec.md` などから、背景、課題、目的、対象ユーザー、利用場面、価値、スコープ、対象外、外部責任、判断原則、成功条件、前提、リスク、未決定事項を整理する。

次をコンセプトへ発明しない。

- API、画面、データ構造、処理フロー、状態遷移
- validation、error、暗号方式、serialization、通信方式
- package 分割、ライブラリ、インフラ、テスト手順
- 「一般的に必要」「将来便利」だけを根拠にした機能や将来構想

Symbol / NEM、Mainnet / Testnet、Extension / Relay / Mobile の責任境界は、入力資料に明示された範囲で分ける。将来 Mobile の記載を現在の実装済み機能と解釈しない。

## 構成

指定がなければ、次の章を使う。

1. 概要
2. 解決したい課題
3. 目的
4. 対象ユーザーと主要利用場面
5. 提供価値
6. v1 のスコープと責任境界
7. 判断原則
8. 成功条件
9. 前提条件と主なリスク
10. 将来構想
11. 未決定事項
12. 要件定義への引継ぎ
13. 参照資料

情報がない章は推測で埋めず、「未決定」「該当なし」「確認が必要」とする。出力前に、背景→課題→目的→価値→スコープの一貫性と、要件・仕様の混入がないことを確認する。
