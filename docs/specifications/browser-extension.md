# MosaicLynx ブラウザ拡張機能仕様

## 1. 目的と規範性

本書は、MosaicLynx ブラウザ拡張機能を、Web アプリケーション / dApp からの要求を受け付け、利用者が確認・承認した場合だけ wallet-core に署名を依頼するローカル署名主体として実装するための外部動作契約を定める。

ブラウザ拡張機能は信頼されたウォレット文脈である。ただし、Web ページ、Provider、注入された橋渡し、コンテンツスクリプト、SDK が渡す要求、オリジン、アカウント、表示メタデータおよび呼び出し元の自己申告は信頼されたではない。ブラウザが観測した呼び出し元文脈、拡張機能が管理する許可、信頼された UI、署名対象の意味上の内容検査および wallet-core の暗号学的な境界を分離する。

本書の `MUST`、`MUST NOT`、`SHOULD` および `MAY` は、[interfaces.md](./interfaces.md) の規範語に従う。本書はブラウザ拡張機能固有の適用を定めるが、共通識別子、対象範囲、オリジン、要求 / 応答、署名状態、エラー、チェーン固有のシリアライズおよび wallet-core の意味を再定義しない。

共通受信境界は [インターフェース §12.0](./interfaces.md) の上限のあるスナップショット / 通常のデータ正規化 / 不変 DTO を使用し、検証後の外部プロパティ再読み取りを禁止する。正式コア統合は [wallet-core 統合](./wallet-core-integration.md)、メッセージ期限切れ / テキスト形式はインターフェース §9.4、連署署名の任意対象範囲 / 結果 / 不明 / 配送はインターフェース §9.6.1 を正本とする。Relay はコアを呼ばず平文の正規化 / 意味を担わない。署名主体だけがコアを呼ぶ。

## 2. 適用範囲と判断権限

### 2.1 対象範囲

本書の対象は次のローカルパスである。

```text
Web アプリケーション / dApp
        ↓ 信頼されていないページ入力
ページに公開する Provider / 注入された橋渡し
        ↓ 信頼されていない通信経路境界
コンテンツスクリプト
        ↓ ブラウザが提供する送信者文脈
拡張機能特権を持つホスト
        ↓ 信頼されたウォレット UI / 許可 / 承認
wallet-core
        ↓ 暗号学的な境界
署名済み結果
```

対象には Provider 露出、呼び出し元 / オリジンとの結び付け、接続、許可、公開アカウント情報公開、要求受け入れ判定、内容検査、承認、認証、wallet-core 呼び出し、応答対応付け、並行処理、タイムアウト、キャンセルおよび拡張機能ライフサイクルを含む。

対象外には SDK の実装、Relay HTTP / 保存領域 / 暗号化、モバイルアプリ、wallet-core の内部実装、ブラウザ基盤 / バンドラー / UI 基盤、保存領域エンジン、Chrome API ラッパー、CSS およびテスト基盤を含む。対象外の責任は既存判断権限または下位実装へ委譲し、本書から新しいエンドポイント、通信上のフィールド、エラーコード、署名基本機構またはトークンモデルを追加しない。

### 2.3 初回提供範囲

- 初回ブラウザ拡張機能マイルストーンの対象ブラウザは Chrome である。最低バージョン、配布チャネル、マニフェストバージョンおよびリリース構成は未確定部分を勝手に固定しない。
- ブラウザ拡張機能はローカル Provider 経路を提供する。モバイル Relay をローカル要求の自動代替経路として使用しない。
- Mainnet 署名対応能力は、現在のリリースと適用中のリリース / 根拠ポリシーの判定条件を満たした信頼された署名主体 / リリースセキュリティ判断権限だけが有効化できる。判定条件が未達成または判定不能な場合は Mainnet 署名を無効 / 利用不能とし、利用可能・成功可能と報告しない。ブラウザ Provider と SDK は判定条件評価器または判断権限ではない。Testnet 専用で安全に継続できる場合は、Mainnet 判定条件失敗だけを理由に Testnet 署名まで停止しない。

## 5. Provider 契約

### 5.1 公開名称、バージョン、メソッド

Provider のページに公開するグローバル名前は `window.mosaicLynx` とする。Provider API の必須主要バージョンは `2` であり、SDK / 受け渡しの既存互換性規則に従う。Provider の `version` は実装バージョンの情報であり、自己申告だけで信頼、オリジン、許可または署名判断権限を証明しない。`apiVersion` は Provider API 互換性判定に使用するが、対応できない主要を格下げ、旧操作または別通信経路へ変換しない。

以下は SDK の公開 API ではなく、Web ページと拡張機能の Provider 境界の契約である。SDK の `connect()`、`signTransaction()`、`signData()` 等は [sdk.md](./sdk.md) の責任範囲で Provider を利用し、Provider が SDK の代替判断権限になることはない。

Provider は、[interfaces.md](./interfaces.md)、[sdk.md](./sdk.md)、[web-transaction-handoff-spec.md](./web-transaction-handoff-spec.md) および本書の整合したページに公開する公開操作意味を、実装で提供可能な範囲で公開する。現行 `@mosaiclynx/provider-api` の操作構造は実装根拠であり、公開フィールド / 結果の判断権限ではない。公開操作の詳細は §5.2 に従い、新しいメソッド、イベントまたはフィールドを追加しない。

| Provider メソッド / イベント                              | 意味                                                                                                                                   |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `connect({ chain, network })`                             | 指定対象範囲の公開アカウント情報公開と Origin-scoped 許可を利用者へ要求する。署名承認、所有責任証明、認証または permanent 認可ではない |
| `disconnect()`                                            | 現在の呼び出し元文脈に対応する接続 / 許可の終了を要求する。既存署名結果を取り消したことを意味しない                                    |
| `getAccounts()`                                           | 現在のオリジン / 接続対象範囲でページに公開可能なアカウント投影を取得する。キャッシュの存在は最新許可または署名認可の証明ではない      |
| `getActiveAccount(scope)`                                 | 指定対象範囲の公開有効なアカウント投影を取得する。未接続または確認不能は成功として扱わない                                             |
| `signTransaction(params)`                                 | 既存受け渡し / SDK のトランザクション署名要求を拡張機能の受け入れ判定、内容検査、承認、認証および wallet-core 境界へ渡す               |
| `signMessage(params)`                                     | 既存構造化メッセージ署名契約に従う `MESSAGE_SIGN` 要求を処理する。生の任意のメッセージ署名ではない                                     |
| `cosignTransaction(params)`                               | 既存 Provider / SDK 対応能力の範囲で `COSIGNATURE_SIGN` を処理する。公開範囲が未確定のチェーン / 対象は利用可能にしない                |
| `on(event, listener)` / `removeListener(event, listener)` | 既存 Provider イベント契約に従って公開状態変更を通知する。イベントを承認、認証、所有責任または署名成功の証明にしない                   |

Provider の既存イベント名は `accountsChanged` と `disconnect` である。`accountsChanged` はページに開示可能なアカウント投影が変更、無効化または接続対象範囲から外れたことを通知し、内部アカウント / プロファイル ID、秘密情報、許可詳細または署名結果を含めない。`disconnect` は接続文脈の終了・失効・喪失を通知し、署名が未実行だったこと、署名が失敗したことまたは結果が存在しないことを表明しない。

Provider の厳密な JSON / RPC エンベロープ、通信上のシリアライズ、リスナー配送、Provider ソフトウェアバージョンの許容範囲および対応能力 advertisement の厳密なフィールドは、上記の整合した公開契約を実装へ対応付ける下流実装境界の責任とする。内部表現の差分をページに公開する公開契約の判断権限にせず、新しい Provider メソッド、イベント、フィールドまたは API バージョンを追加しない。

### 5.2 Provider 操作構造

Provider のページに公開する TypeScript メソッド / 結果構造の規範の正本は、[interfaces.md](./interfaces.md)、[sdk.md](./sdk.md)、[web-transaction-handoff-spec.md](./web-transaction-handoff-spec.md) および本書の整合した公開契約である。現行 `@mosaiclynx/provider-api` の TypeScript 構造は実装根拠にとどまり、そのままページに公開する規範的な契約として使用しない。現行パッケージの `MosaicAccount.id`、`MosaicAccount.profileId`、署名 params の `accountId`、修飾のないな署名済み結果との差分は下流実装同期の対象であり、本書は既存実装に合わせて内部 ID、内部選択子または旧結果構造を復活させない。実装が満たす論理的な入出力は次のとおりである。

| 操作                | 入力                                                                                                       | 成功した結果                                                                                                                        |
| ------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `connect`           | `MosaicScope`（`chain`、`network`）                                                                        | 指定対象範囲で許可された `PublicAccountIdentity` の readonly 収集                                                                   |
| `disconnect`        | なし                                                                                                       | `void`。現在の呼び出し元の接続 / 許可を終了する                                                                                     |
| `getAccounts`       | なし                                                                                                       | 現在の呼び出し元に公開可能な `PublicAccountIdentity` 収集                                                                           |
| `getActiveAccount`  | `MosaicScope`                                                                                              | 対象範囲に対応する `PublicAccountIdentity` または `undefined`                                                                       |
| `signTransaction`   | 対象範囲、hex ペイロード、既存契約の任意 `expectedSignerPublicKey`                                         | Handoff-compatible な既知の署名済み結果または署名主体が生成した `RESULT_UNKNOWN`                                                    |
| `signMessage`       | 対象範囲、既存構造化されたメッセージの目的、ノンス、issuedAt、期限切れ、ペイロードおよび既存任意フィールド | Handoff-compatible な既知の署名済み結果または署名主体が生成した `RESULT_UNKNOWN`                                                    |
| `cosignTransaction` | チェーン固有のな親 / ペイロード、分離された等、既存契約のフィールド                                        | `MosaicLynxSigningResult<MosaicLynxCosignature>`。Symbol と NEM の対象 / 結果構造を混同しない。アカウントは信頼された文脈で解決する |

上表のページに公開する入力、アカウントレコード、返却値およびイベントペイロードに、`profileId`、内部 `accountId`、ウォレットストア ID、鍵枠、内部経路選択参照またはそれらを代替する内容を解釈しないハンドルを含めない。アカウントの公開投影は §10.1 の `PublicAccountIdentity` に限る。アカウントの利用者選択が必要な場合は信頼された署名主体 UI / 署名主体が所有する文脈で解決し、ページから受け取った選択子を認可、所有責任、鍵選択または署名主体識別情報の判断権限としない。

Provider の内部 RPC メソッド名（`permissions_connect`、`permissions_disconnect`、`account_list`、`account_getActive`、`sign_message`、`sign_transaction`、`cosign_transaction`）を使用する実装は、これらをページへ新しいエンドポイントとして公開せず、既存 Provider API のメソッド意味へ対応付ける。要求 / 応答は requestId と操作の一対一対応付けを持ち、成功結果のペイロード、署名主体、アカウント、対象範囲、対象および呼び出し元は特権を持つホストが検証したものに限る。

Provider のページメソッド署名に requestId を追加して新しい公開エンベロープを作ることはしない。特権を持つホスト / 橋渡しは既存の共通要求識別情報を内部で保持し、メソッド呼び出し、応答、保証決済およびページ配送を一つの論理的な要求に相関付ける。相関できない応答はページに成功として返さない。

Provider-native アカウントレコードを内部で使用する場合、その内部レコードはページに公開するアカウントレコードとして公開しない。特権を持つホスト / 署名主体内部の経路選択参照は現在のブラウザ呼び出し元、許可、対象範囲、プロファイル内の文脈、アカウントおよび期待される署名主体から対象を解決するためだけに使用し、ページ入力、ページ返却、許可判断権限、所有責任証明、アカウントの利用認可または鍵選択判断権限として扱わない。

### 5.2.1 署名主体が生成した署名結果

Provider のページに公開する署名結果と、Provider から SDK アダプターへ渡す内部表現は、[web-transaction-handoff-spec.md §5.2.1、§7.2](./web-transaction-handoff-spec.md) および [sdk.md §5](./sdk.md) の意味を保持しなければならない。厳密な Provider 通信上のフィールドは既存 Provider 契約に委譲するが、修飾のないな `SignedTransaction` / `SignedMessage` だけを返して既知の成功と結果不明、または配送処理結果の区分を区別できない契約としてはならない。

- 既知の署名済み結果は署名結果 `SUCCEEDED` と、同じ結果に付随する署名主体が生成した `deliveryDisposition`（`PENDING`、`DELIVERED` または `DELIVERY_UNKNOWN`）を保持する。SDK アダプターは同じ結果と処理結果の区分を `MosaicLynxSigningResult<T>` の `outcome: 'succeeded'` 分岐へ意味不変に渡す。
- 署名主体が署名生成自体の成否を安全に確定できない場合だけ `RESULT_UNKNOWN` を保持する。この分岐は署名済み結果と配送処理結果の区分を持たず、SDK アダプターは `outcome: 'resultUnknown'` へ意味不変に渡す。
- Provider、保証決済、コンテンツスクリプト、ページ配送、ブラウザライフサイクル、SDK アダプターまたは通信経路完了は、`RESULT_UNKNOWN`、`PENDING`、`DELIVERED`、`DELIVERY_UNKNOWN` を生成、推測、確定または別の意味へ書き換えない。通信経路やページへの応答が完了したことだけで `DELIVERED` としない。

`RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` はエラーコードではない。連署署名の公開結果共用体は既存の `OPEN-BEX-006` および上流の未決を維持し、本節はそれを確定しない。

### 5.2.2 Provider 収集と SDK / 受け渡し有効な投影

Provider の `connect` / `getAccounts` が扱うアカウント収集はブラウザ固有のな公開許可 / 情報公開投影であり、許可集合そのものや SDK / 受け渡しの公開応答要素数とは別である。Provider は収集を保持・返却できるが、その収集を SDK `connect(scope)` の結果として暗黙に返してはならない。

SDK / 受け渡しの `connect(scope)`、`getActiveAccount(scope)` および `refreshActiveAccount(scope)` が dApp へ返すアカウントは、既存受け渡しの `MosaicLynxActiveAccount` と共通の `PublicAccountIdentity` に対応する単数公開識別情報である。

この有効な投影は、信頼されたブラウザホストが現在のブラウザ呼び出し元、現在のプロファイル、現在の許可、現在の有効なアカウントおよび validated `Scope` を照合して導出する。現在の有効なアカウントが現在の許可の対象であり、対象範囲とアドレス / publicKey のチェーン固有の検証を満たす場合だけ、SDK / 受け渡しの単数応答として返す。Provider 収集の大きさ、配列順序、先頭アカウント、dApp 提供されたの `accountId`、表示名前または古くなった cached アカウントは選択判断権限ではない。`expectedSignerPublicKey` は署名主体期待値の制約であり、内部アカウント選択子ではない。

| 状態                       | ブラウザ Provider 収集                                                                        | SDK / 受け渡しの公開応答                                                                                                                                                                                 | 適用する既存意味                                                  |
| -------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| アカウント 0件             | 空収集。公開可能な有効な投影はない                                                            | `connect(scope)` は単数アカウントを解決せず、既存受け渡し §10 の `NOT_CONNECTED` 対応付けに従う。`getActiveAccount` / `refreshActiveAccount` は `undefined`                                              | empty 収集をアカウントの識別情報の成功値へ昇格しない              |
| アカウント 1件             | 1件の `PublicAccountIdentity`                                                                 | そのアカウントだけを単数有効な投影として返す                                                                                                                                                             | `Scope`、許可、プロファイルおよびチェーン固有の識別情報を検証する |
| 複数許可アカウント         | 許可された収集を保持する                                                                      | 現在の有効なアカウントが収集に含まれ、validated 対象範囲と一致する場合だけ、その一件を返す。解決できない場合は単数成功を返さず、既存 `NOT_CONNECTED` 対応付け / `undefined` に従う。配列順序で選択しない | 収集、許可集合、有効なアカウントを混同しない                      |
| 有効なアカウント変更       | 現在の許可に含まれる新しい投影として再計算し、既存 `accountsChanged` イベントの範囲で通知する | `refreshActiveAccount(scope)` は再照会した新しい単数投影を返す。保留中の要求は既存のアカウント / context-change 意味に従う                                                                               | dApp がアカウント変更を直接指定しない                             |
| 許可失効                   | 失効後の収集を返し、有効なが対象外なら有効な投影を返さない                                    | cached アカウントを成功として使用せず、`refreshActiveAccount` は `undefined`。接続・署名の失敗は既存受け渡し / SDK エラー対応付けに従う                                                                  | 失効後に古い認可を再利用しない                                    |
| `refreshActiveAccount`     | 信頼されたホストが現在の状態を再照会する                                                      | 新鮮な単数アカウントまたは `undefined`。署名承認は作成しない                                                                                                                                             | キャッシュ、イベント配送、過去の応答は判断権限ではない            |
| 古くなった有効なアカウント | 収集 / 有効な状態の古くなった値を成功投影として使用しない                                     | `getActiveAccount` / `refreshActiveAccount` は `undefined`、`connect` は既存受け渡しエラー対応付けに従い成功アカウントを返さない                                                                         | 古くなったアカウントから別アカウントへの自動代替経路をしない      |

モバイル Relay パスも同じ `MosaicLynxActiveAccount` の単数 SDK / 受け渡し応答を使用する。Provider 収集の存在はモバイルまたは SDK の公開応答要素数を変更しない。上表で明示した `NOT_CONNECTED`、`undefined` および既存受け渡し / SDK エラー対応付け以外の empty-account エラー、選択規則、別名または応答ラッパーを本書で追加しない。

### 5.2.3 `signMessage` / `signData` アダプター対応付け

ブラウザページに公開する `signMessage` は Provider 固有のアダプターメソッドであり、独立した論理的な署名操作や別のメッセージプロトコルではない。各呼び出しは、既存共通の要求識別情報を一つだけ持つ `signData` 要求と、共通の論理的な操作 `MESSAGE_SIGN` へ一対一で対応付ける。

| 対応付け項目               | ブラウザ Provider                                                                                                                                                   | SDK / 受け渡し / 共通の判断権限                                                                                                                                                |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ページに公開するメソッド   | `signMessage(params)`                                                                                                                                               | Provider 固有のメソッド。SDK が dApp に公開するメソッドは `signData(params)`                                                                                                   |
| SDK メソッド               | Provider 呼び出しを `signData` 要求として振り分け                                                                                                                   | `signData(params)` → `signData` 受け渡し操作                                                                                                                                   |
| 共通の論理的な操作         | `MESSAGE_SIGN`                                                                                                                                                      | `interfaces.md §9.1` / `signing-protocol.md` の正規論理的な操作                                                                                                                |
| 要求識別情報               | Provider 呼び出しと underlying 要求を一つの既存 `requestId` に相関。ページメソッドに新しい requestId フィールドを追加しない                                         | `requestId` は要求 / 応答の一対一対応付け鍵。`operation`、オリジン / 呼び出し元、対象範囲、アカウント、対象とともに検証する                                                    |
| 構造化されたメッセージ対象 | ブラウザで観測した正規オリジン、`Scope`、固定ドメイン `mosaiclynx.message.v1`、目的、ノンス、issuedAt、期限切れおよびペイロードからなる同一の構造化されたメッセージ | `StructuredMessage` / `SignedData` と受け渡しの既存の `RelayDataSigningRequest` に従う。生の任意のバイト列、表示不能メッセージ、別ドメインまたは別通信上のスキーマへ変換しない |
| データ / ペイロード        | Provider の構造化されたメッセージペイロードの `encoding` / `value` を、内容を変えずにメッセージ署名データとして渡す                                                 | SDK `signData` の `data` と受け渡し `payload` は同じ論理的なメッセージ内容を表す。両方をページ契約の別入力として同時に要求しない                                               |
| 期待される署名主体         | 任意 `expectedSignerPublicKey` がある場合だけ公開署名主体期待値として渡す。`accountId`、`accountIds`、`activeAccountId`、鍵枠、`recipientPublicKey` は渡さない      | 署名主体が actual 署名主体と完全一致を検証し、不一致は既存 `SIGNER_MISMATCH` 対応付け。省略時のアカウント / 鍵解決は信頼された署名主体の現在の文脈に委譲する                   |
| 成功した結果               | Provider 固有の表現が存在する場合も既知の署名済みデータと署名主体が生成した処理結果の区分を保持する                                                                 | 受け渡し `dataSigned` / `SUCCEEDED` / `signedData` / `deliveryDisposition` → SDK `MosaicLynxSigningResult<SignedData>` の `outcome: 'succeeded'`、`result`、同じ処理結果の区分 |
| エラー                     | Provider 内部エラーをページに公開する契約へそのまま昇格しない                                                                                                       | 受け渡し §10 と `interfaces.md §10` の既存具体的な / 論理的なエラー対応付け。新しい Provider エラーコード、別名または代替経路を追加しない                                      |
| `RESULT_UNKNOWN`           | Provider / ページライフサイクル / 保証決済から生成・推測しない                                                                                                      | 信頼された署名主体が生成した `resultUnknown` / `RESULT_UNKNOWN` を署名済み結果、errorCode、deliveryDisposition なしで SDK の `outcome: 'resultUnknown'` へ意味不変に渡す       |
| `deliveryDisposition`      | Provider、ページ配送、通信経路完了から生成・推測・書き換えない                                                                                                      | 既知の署名済み結果に付随する署名主体が生成した `PENDING`、`DELIVERED` または `DELIVERY_UNKNOWN` を同じ値で保持する。`RESULT_UNKNOWN` 分岐には付けない                          |

`signMessage` は `signData` / `MESSAGE_SIGN` の構造化されたメッセージ意味に必ず従い、トランザクション署名、任意の生バイト列署名または内容を確認しない署名への代替経路として扱わない。正規メッセージは [インターフェース §9.4](./interfaces.md) に従い、Provider request.messageExpiresAt を message.expiresAt に明示対応付けし要求単位の expiresAt と区別する。両フィールドの二重送信・独自別名は拒否する。上記以外の結果、エラー、不明および配送対応付けはモバイル Relay パスと同じである。

### 5.3 検出と対応能力

SDK は Provider の存在、必須メソッド、`apiVersion` 主要 `2`、必要対応能力および現在の実行環境互換性を確認してローカル経路を選択する。`window.mosaicLynx` の存在、グローバル名、アイコン、自己申告のオリジン、自己申告の対応能力、アカウントキャッシュまたは `version` だけを信頼アンカーとしない。

- 不正な形式の、メソッド欠落、偽の / 競合する、非対応主要、不明操作、判定不能な対応能力は Provider 利用不能 / 未対応のとして扱う。
- 互換性のあるローカル Provider が存在する場合にだけ拡張機能経路を選択する。互換性のない Provider を不在とみなしてリモート代替経路しない。
- Provider 拒否、検証失敗、タイムアウト、Vault ロック、文脈変更、結果不明または承認失敗の後に別通信経路、生の署名または別操作へ自動代替経路しない。
- 対応能力は接続、アカウント / アドレス情報公開、トランザクション署名、メッセージ署名、連署署名署名、対応済みのチェーン / ネットワーク、ローカル / リモート等の対応可能性であり、許可、アカウント所有責任、ロック解除、認証、承認または成功ではない。
- 対応能力識別子、対応能力集合、対応能力バージョン、協議オブジェクトおよび互換性対応表は [interfaces.md §5.6](./interfaces.md) の未決を維持する。ブラウザ拡張機能独自の識別子を追加しない。

### 5.4 Provider エラー境界

Provider、特権を持つ RPC、SDK および wallet-core のエラー定義の正本を混同しない。境界ごとの判断権限は次のとおりである。

| エラー層                                   | 判断権限 / ブラウザ拡張機能の扱い                                                                                                                                         |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 共通の論理的なエラー分類                   | [interfaces.md](./interfaces.md) の共通のエラーモデル。検証、未対応の、許可、利用者拒否等の論理的な意味を定める。                                                         |
| 署名結果 / 終端意味                        | [signing-protocol.md](./signing-protocol.md)。`REJECTED`、`FAILED`、`EXPIRED`、`CANCELLED`、`INVALIDATED`、`RESULT_UNKNOWN` 等の署名ライフサイクルの意味を定める。        |
| SDK / 受け渡し具体的な公開エラー           | [web-transaction-handoff-spec.md §10](./web-transaction-handoff-spec.md) の `MosaicLynxSDKErrorCode`。ページ / SDK 境界で公開できる具体的なコードの唯一の判断権限とする。 |
| Provider / 特権を持つ RPC / 通信経路固有の | 特権を持つホストと内部通信経路の境界に限定する implementation-specific コード。ページに公開する公開コードまたは受け渡しエラーコードの追加集合として扱わない。             |
| wallet-core 内部エラー                     | wallet-core 契約。ストア、バインディング、暗号学的な警告 / エラーの内部詳細をページに公開するエラーへ露出しない。                                                         |

現行 Provider パッケージに存在する `UNAUTHORIZED_ORIGIN`、`INVALID_MESSAGE`、`NONCE_REUSED`、`UNSUPPORTED_CHAIN`、`ACCOUNT_NOT_FOUND`、`RESOURCE_LIMIT` 等の `ProviderErrorCode` は、Provider / 特権を持つ RPC 内部のコードとしてだけ扱う。これらをそのまま受け渡し / SDK 公開エラーコードとして公開したり、追加集合として扱ったりしてはならない。特権を持つ境界は、既知の失敗原因を共通の論理的な分類と受け渡し §10 の既存具体的なコードへ正規化し、ページに公開する Provider / SDK アダプターへ Provider 固有のコードを転送しない。

不明、不正な形式のまたは受け渡し §10 に対応付けられない Provider / RPC コードは、成功、署名済み結果または新しい公開コードに変換せず安全側での終了とする。公開エラーが必要な場合の catch-all は受け渡し §10 の既存 `INTERNAL_ERROR` に限り、生のコードや内部詳細を露出しない。`RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` はこのエラーモデルに含めず、§5.2.1、§12 および §22 の結果 / 配送意味で表現する。

SDK に返る具体的なエラーは [web-transaction-handoff-spec.md §10](./web-transaction-handoff-spec.md) の判断権限に従う。ページ文脈に返すエラーにスタック追跡、特権を持つブラウザ API 詳細、filesystem パス、ウォレットストアエラー、暗号学的な内部詳細、秘密情報、内部アカウント / プロファイル ID または生の原因を含めない。

## 6. Provider 露出と注入境界

Provider の露出経路は、ページ文脈、注入されたスクリプト、コンテンツスクリプトおよび拡張機能特権を持つ文脈を分離する。具体的なスクリプト配置、メッセージ API、基盤、バンドラー、CSP、マニフェスト許可および Chrome API 呼び出し順は下位実装へ委譲する。

- ページ文脈と注入されたスクリプトは Web アプリケーションと同じ信頼されていない境界である。Provider オブジェクトが存在するだけで呼び出し元を信頼されたとみなさない。
- コンテンツスクリプトはページから受け取ったペイロード、オリジン、アカウント、チェーン、ネットワーク、表示メタデータおよび要求識別情報を特権を持つホストへ渡す前に、既存プロトコルの構造上の検証を行う。ただしコンテンツスクリプトの検証は特権を持つホストの最終検証を代替しない。
- 特権を持つホストは browser-provided 送信者 / 文書文脈を検証し、page-provided オリジンと一致しない要求を接続・署名へ進めない。
- ページ、注入されたスクリプト、コンテンツスクリプトは秘密鍵、ニーモニック、プロファイルパスワード、復号されたウォレットストア、アカウントの内部参照、許可判断、承認状態、認証状態または wallet-core ハンドルを取得・操作できない。
- リモート実行ファイルコード、page-provided HTML / Markdown、ページ CSS、dApp コールバックおよびページイベントで信頼された承認 UI、署名認可または秘密情報境界を変更できない。
- Provider 置き換え、重複 Provider、拡張機能再読み込みおよび文脈消失は、既存要求の応答受信者と承認との結び付けを再検証する理由となる。古い Provider オブジェクトを現在の判断権限として再利用しない。

## 7. オリジン / 呼び出し元結び付け

### 7.1 判断権限の区別

オリジン / 呼び出し元に関して、次を同一視してはならない。

| 値                                                        | 判断権限                                                                                                  |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 要求ペイロード内のオリジン                                | ページが提供する信頼されていない入力。結び付けの候補情報に過ぎない                                        |
| SDK-observed オリジン                                     | SDK が `window.location.origin` 等から得る補助情報。ブラウザの最終判断権限ではない                        |
| page-provided オリジン / アプリラベル                     | 信頼されていない。許可、UI のオリジンの信頼性判断、署名主体識別情報に使用しない                           |
| ブラウザで観測した送信者 / タブ / フレーム / 文書オリジン | 拡張機能が許可、要求、UI および応答に結び付けする判断権限                                                 |
| 許可オリジン                                              | 正規ブラウザで観測したオリジンと完全一致しなければならない。ページ自己申告で上書きしない                  |
| 信頼された UI のオリジン                                  | ブラウザで観測したオリジンから特権を持つホストが導出する。dApp ラベル、ファビコン、要約を判断権限にしない |

ブラウザ拡張機能は [interfaces.md §5.5](./interfaces.md) の正規オリジンを使用する。オリジンは方式、ホスト、ポートの正規文字列であり、パス、照会、フラグメント、表示名前およびファビコンを含めない。欠落、空、不正な形式の、観測値との不一致、フレーム / 文書を一意に結び付けられない場合は接続 / 署名を許可しない。

オリジンとの結び付けは、適用範囲に応じて少なくとも次を含む。

```text
ブラウザで観測したオリジン
+ 最上位の文書 / 閲覧文脈
+ 要求元のタブ / フレーム / 文書識別情報
+ 接続 / 許可対象範囲とリビジョン
+ プロファイル / アカウント / チェーン / ネットワーク
+ requestId / 操作 / 対応能力
+ 署名対象または構造化されたメッセージ文脈
+ 要求鮮度とプロトコル文脈
```

要求ペイロードのオリジンが観測されたオリジンと異なる場合、ペイロードの値を採用せず安全側に終了する。requestId だけ、接続済みだけ、Provider のコールバックだけまたはページのオリジン証明だけで呼び出し元真正性を成立させない。

### 7.2 最上位の、フレーム、タブ、ページ遷移

初回ブラウザ拡張機能マイルストーンでは、次を呼び出し元として受け付ける。

- 最上位の閲覧文脈の HTTPS オリジン。
- 開発用途に限る任意ポートの `http://localhost`、`http://127.0.0.1`、`http://[::1]`。

通常の HTTP、`file:`、`data:`、内容を解釈しないオリジン、ブラウザ内部ページ、他の拡張機能オリジンおよび iframe / 子フレームは受け付けない。iframe サポートを暗黙に追加しない。

要求は最上位のオリジン、要求元の文書、タブ識別情報、フレーム識別情報（該当する場合）および文書世代に結び付けする。ブラウザ / 拡張機能が最上位のと要求元のフレームの関係、文書識別情報またはページ遷移後の現在の文脈を安全に一意化できない場合、署名を許可せず安全側での終了とする。

同じタブの再読み込み、same-Origin ページ遷移、オリジン間のページ遷移、フレーム置き換え、タブ終了またはポップアップ / window 文脈の変更で、要求の呼び出し元結び付けと承認継続性を再検証する。新しい文書や別オリジンへ古い承認、署名済み結果、許可または応答コールバックを配送しない。これらのブラウザイベントは署名生成または署名主体側の配送処理結果の区分の成否を単独では決定しない。

### 7.3 共通の四条件署名認可

署名認可は、同一の署名主体が所有するプロファイル内のセキュリティ文脈に対する、一つの要求 / 厳密な署名対象の短寿命な許可である。次の4条件が、同じ文脈に対して互いに独立してすべて成立した場合だけ `AUTHORIZED` として扱う。

1. 認証。
2. 署名可能な状態へのロック解除。
3. 対象プロファイル / チェーン / ネットワーク / アカウントに対するアカウントの利用認可。
4. 利用者による明示的な承認。

次の関係を維持する。

- 認証 ≠ 署名可能な状態へのロック解除
- 署名可能な状態へのロック解除 ≠ アカウントの利用認可
- アカウントの利用認可 ≠ 利用者による明示的な承認
- 利用者による明示的な承認 ≠ 認証

4条件は、少なくとも次の同一結び付け文脈に結び付ける。

```text
要求識別情報
+ ブラウザで観測したオリジン
+ 文書 / タブ / フレーム文脈
+ プロファイル / プロファイル内のセキュリティ文脈
+ 許可 / リビジョン
+ アカウント
+ チェーン / ネットワーク
+ 操作
+ 対応能力 / バージョン
+ 厳密な署名対象
+ 内容検査結果
+ 期限切れ / 鮮度
```

接続、許可、アカウント情報公開、選択済みのアカウント、Provider 利用可能性、対応能力、通常の `UNLOCKED`、過去の認証、パスワード検証、ウォレットストア検証、wallet-core 対応能力、ページ / SDK 状態、Provider 応答または通信経路完了は、4条件のいずれの代替にもならない。許可の存在はアカウントの利用認可を、選択済みのアカウントはアカウントの利用認可を、`every-signature` またはその他の認証は残りの条件を包含しない。

4条件または結び付け文脈のいずれかが欠落、古くなった、失効済み、ロック済み、変更された、mismatched、不明または無効化済みなら、署名主体は安全側での終了とし、`AUTHORIZED`、`SIGNING` または `SUCCEEDED` へ進めず wallet-core を呼び出さない。認証 UI、ロック解除 API および内部実装方式は本書で固定しない。

## 8. 接続

### 8.1 接続フロー

`connect({ chain, network })` は、指定対象範囲の公開アカウント情報公開と Origin-scoped 許可を利用者へ要求する。概念フローは次のとおりである。

```text
Provider 要求
  → ブラウザ呼び出し元 / オリジン / 対象範囲検証
  → 既存の許可照会
  → 信頼された接続 UI
  → 明示的な利用者許可または拒否
  → 公開アカウント投影と接続応答
```

接続が成功するには、ブラウザで観測したオリジン、最上位の文書文脈、対象範囲、プロファイル、選択されたアカウント集合および許可リビジョンを対応付けられること、ならびに利用者の明示操作が必要である。未許可オリジンからの検証可能な要求は接続要求としてのみ扱い、署名 UI へ進めない。

接続 UI は少なくとも正規 / Punycode 表現の要求元のオリジン、対象範囲、プロファイル / アカウントの公開識別情報および許可対象を利用者が区別できる形で表示する。具体的配置、文言、選択 UI は下位 UI 仕様へ委譲する。

### 8.2 接続の意味と公開情報

接続成功は次を意味しない。

- アカウント所有責任証明またはアカウントの制御証明
- permanent 認可、端末認証または署名承認
- ウォレットロック解除、プロファイルパスワードの検証、署名ごとの認証
- トランザクション / メッセージの承認、署名、署名成功またはアナウンス成功

公開できる情報は [interfaces.md §5.3](./interfaces.md) のアカウントの公開識別情報と、既存の Provider / SDK が許可する非秘密の補助表示値に限る。秘密鍵、ニーモニック、ウォレットストア識別子、内部アカウント / プロファイル ID、鍵枠、パスワード、認証情報および秘密情報メタデータをページへ公開しない。

### 8.3 永続化、再接続、接続解除

許可の永続化、セッションレコードおよび保存領域エンジンは既存モデルと下位実装へ委譲する。ただし次を必須とする。

- 再接続は現在のブラウザ呼び出し元、現在の文書、許可対象範囲、リビジョン、プロファイル、アカウント、チェーン / ネットワークを再確認する。過去のキャッシュ、承認、認証、セッションまたは結果を無条件に復元しない。
- `isConnected()`、`getAccounts()` および `getActiveAccount()` は署名承認を作成せず、現在の公開状態を返すだけである。
- `disconnect()` / 許可失効後は cached アカウント、保留中の要求、承認、認証および署名認可を新しい要求に利用しない。
- 接続解除は過去に開始した不可逆な署名の結果を利用者拒否、未署名またはキャンセルに変換しない。
- 有効なアカウント、許可、プロファイル、対象範囲または呼び出し元文脈が変更された場合、`accountsChanged` / `disconnect` イベントは既存イベント契約の範囲で通知する。イベント配送は状態判断権限ではない。

## 9. 許可モデル

### 9.1 許可付与の結び付け

アプリケーション管理下の許可は、[interfaces.md §8](./interfaces.md) の `PermissionGrant` 論理的なモデルを使用する。

```text
オリジン + プロファイル + 対象範囲(チェーン, ネットワーク) + 許可済みのアカウント集合 + リビジョン
```

`profileId`、`accountIds`、リビジョン等の内部レコードはページ / SDK / Relay に公開しない。許可の対象は接続と公開アカウント情報公開であり、署名承認、認証、アカウント所有責任または鍵判断権限を含まない。

### 9.2 許可付与、リビジョン、失効

- オリジン、プロファイル、対象範囲、許可済みのアカウント集合および許可リビジョンは要求受け入れ判定と署名認可に結び付けする。
- 許可の対象範囲、アカウント集合、プロファイル対応またはリビジョンが変更・失効された時点で、対応するセッション、保留中の要求、承認、認証および署名認可を無効化する。
- 許可の存在だけ、古いリビジョンだけ、アカウントキャッシュだけまたは Provider イベントだけでは `AUTHORIZED` に進めない。
- 許可を別オリジン、別プロファイル、別対象範囲、別アカウント、別操作または別対応能力へ拡張しない。
- 許可期限切れ、独立 `permissionId`、`revokedAt`、端末間の同期および厳密な永続的な保存領域は上流未決を維持する。ブラウザ拡張機能が期限値や新しい失効トークンを独自に定義しない。

### 9.3 接続許可と署名認可

接続許可は、署名要求を信頼された内容検査、承認、認証、署名可能な状態へのロック解除、アカウントの利用認可または wallet-core 署名へ自動的に通す判断権限ではない。各署名要求は、§7.3 の4条件を同一のプロファイル内の文脈に対して独立に満たさなければならない。プロファイルが要求する `every-signature` は認証の条件を満たすためのものであり、他の3条件を代替しない。

## 10. 公開アカウント、プロファイル、アカウント / ネットワーク選択

### 10.1 公開アカウントの識別情報

ページに公開するの公開アカウントは、共通契約に従い次の意味を持つ。

```ts
interface PublicAccountIdentity extends Scope {
  address: string;
  publicKey: string;
}
```

全フィールドは必須で、チェーン固有の形式、長さ、チェックサム、ネットワークおよび公開鍵の整合を特権を持つホスト / チェーン統合が確認する。表示名前等が既存契約にある場合も補助表示に限り、署名主体識別情報、認可または所有責任証明の根拠にしない。

ページへ公開してはならないものは、秘密鍵、ニーモニック、ウォレットストア識別子、内部 `accountId`、内部 `profileId`、鍵枠、パスワード、復号されたストア、導出された暗号化鍵、認証秘密情報および署名内部秘密情報である。

特権を持つホスト / 署名主体が内部でアカウントを解決するためにアカウントの内部参照を使用する場合も、それは経路選択の内部参照に限る。アカウントの内部参照はページ入力、ページ返却、許可判断権限、所有責任証明、アカウントの利用認可、鍵選択判断権限またはアカウントの公開識別情報ではない。トランザクション署名の対象アカウントは、ペイロード、期待される署名主体、現在の許可、プロファイル内の文脈、チェーン / ネットワークおよび必要な署名主体役割から特権を持つホスト / 署名主体が解決する。複数の許可アカウントから利用者の選択が必要なメッセージ / 連署署名等では、信頼された署名主体 UI / 署名主体が所有する文脈で選択し、内部参照をページへ出さない。

### 10.2 プロファイル、アカウント、チェーン / ネットワーク

- プロファイルネットワークは [profile-account-spec.md](./profile-account-spec.md) に従い、作成後に暗黙変更しない。
- Symbol と NEM は別のチェーン固有のアカウント / 鍵識別情報として扱う。同じニーモニック、プロファイルまたは索引を理由に秘密鍵、アドレス、公開鍵、スキーマまたは署名バイト列を共用しない。
- 要求の対象範囲、プロファイル、選択アカウント、有効なアカウント、ペイロード署名主体、期待される署名主体、チェーン / ネットワーク対応能力およびリリース判定を相互に照合する。
- 誤ったチェーン、誤ったネットワーク、誤ったプロファイルまたは誤ったアカウントの要求に対して、対象を自動切替、暗黙接続、別アカウントへの代替経路または古い承認の移送を行わない。
- `expectedSignerPublicKey` が指定された場合は、対象チェーンの形式を検証し、実際の署名主体と完全一致させる。一致しない場合は既存具体的なエラー定義の正本に従い成功を返さない。

## 11. 署名要求受け入れ判定

### 11.1 受け入れ判定の必須検証

Provider、SDK、Web アプリケーション、ノードまたは Relay が既に検証した要求でも、特権を持つホストは信頼された承認フローに入れる前に再検証する。少なくとも次を確認する。

- Provider API / プロトコルバージョン、操作、必須対応能力および現在のローカル経路互換性
- requestId の形式、一対一対応付け、重複 / リプレイ、要求鮮度
- createdAt、expiresAt、適用されるメッセージ / トランザクション / 親期限切れ
- ブラウザで観測したオリジン、最上位の文書、タブ / フレーム / 送信者文脈および page-provided オリジンとの一致
- 許可のオリジン、プロファイル、対象範囲、許可済みのアカウント集合、リビジョンおよび現在の接続
- プロファイルロック / ロック解除状態、選択アカウント、期待される署名主体、署名主体役割、チェーン / ネットワーク
- ペイロードの型、エンコーディング、サイズ、構造上の有効性、完全性、正規入力条件
- 要求に対応する操作と対象の組み合わせ、対応能力、世代 / ライフサイクル文脈
- 要求が過去に終端状態、キャンセル、拒否、期限切れ、文脈消失または結果不明になっていないこと

検証の一部でも欠落、不正な形式の、不明、期限切れ、古くなった、不一致、未対応のまたは判定不能であれば、通常の署名承認フローへ進めない。ページが提示した `Origin`、アカウント、チェーン、ネットワーク、要約、ラベル、受信者名前、数量テキスト、説明またはメッセージ表示テキストを最終判断権限としない。

### 11.2 検証順序と境界

概念的な処理順は次のとおりである。

```text
RECEIVED
  → エンベロープ / 識別子 / 鮮度
  → ブラウザ呼び出し元 / オリジン / 文書
  → 許可 / プロファイル / アカウント / 対象範囲
  → 操作 / 対応能力
  → チェーン固有の対象解析 / 正規検証
  → 信頼された内容検査
  → 承認 / 認証
```

この順序は、信頼されていない入力を信頼された UI、許可判断、wallet-core または署名認可に昇格させないための境界である。具体的な内部クラス、キュー、ロック、CAS、DB トランザクションおよびメッセージ通信経路は固定しない。

## 12. 署名ライフサイクル

### 12.1 共通状態

ブラウザ拡張機能は [signing-protocol.md §6](./signing-protocol.md) の状態集合を使用し、独自の公開署名状態遷移を追加しない。

```text
RECEIVED → VALIDATED → INSPECTED → AWAITING_USER → AUTHORIZED → SIGNING → SUCCEEDED

終端:
REJECTED | FAILED | EXPIRED | CANCELLED | INVALIDATED | RESULT_UNKNOWN
```

`DELIVERY_UNKNOWN` は署名状態ではなく、`SUCCEEDED` した結果の配送処理結果の区分である。

| 状態             | ブラウザ拡張機能での意味                                                                                                                                                                                  |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RECEIVED`       | 受信したが信頼された要求として扱う前。署名不可                                                                                                                                                            |
| `VALIDATED`      | エンベロープ、呼び出し元、許可、セッション、対象範囲、アカウント、操作、対応能力、鮮度、完全性を検証済み。署名不可                                                                                        |
| `INSPECTED`      | 対象全体を解析 / 検証 / 内容検査し、信頼された確認モデルを生成済み。署名不可                                                                                                                              |
| `AWAITING_USER`  | 拡張機能管理 UI で確認・拒否を待つ。認証 / 認可は未成立                                                                                                                                                   |
| `AUTHORIZED`     | 同一の署名主体が所有するプロファイル内のセキュリティ文脈に対して認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認の4条件が独立して成立した短寿命状態。署名前再検証が必要 |
| `SIGNING`        | 4条件と結び付け文脈を再検証した対象を wallet-core 契約へ渡している状態。自動再実行不可                                                                                                                    |
| `SUCCEEDED`      | 4条件が成立した同一文脈において、wallet-core 結果と要求、対象、署名主体、アカウント、対象範囲、操作の対応を検証済みの状態                                                                                 |
| `REJECTED`       | 利用者の明示拒否。検証失敗やタイムアウトをこの状態に変換しない                                                                                                                                            |
| `FAILED`         | 失敗が確定した終端状態。署名成功として返さない                                                                                                                                                            |
| `EXPIRED`        | 要求または適用される対象 / メッセージ文脈の期限切れ                                                                                                                                                       |
| `CANCELLED`      | 署名を開始せず処理を終了できたキャンセル                                                                                                                                                                  |
| `INVALIDATED`    | 呼び出し元、許可、ライフサイクル、対象、完全性等の結び付けが失われた状態                                                                                                                                  |
| `RESULT_UNKNOWN` | 信頼された署名主体が署名生成自体の成否（署名済み / 未署名の）を安全に確定できない状態。UI、ページ、Provider、通信経路またはライフサイクルイベントだけではこの状態にしない                                 |

### 12.2 ブラウザ固有の状態との分離

ポップアップ未決、UI フォーカスされている、認証要求画面表示されている、Provider 接続済み、サービスワーカー稼働中の、タブ有効な等はブラウザ固有の運用上の状態であり、`AUTHORIZED`、`SIGNING`、`SUCCEEDED` または利用者拒否の代替ではない。ブラウザ固有の状態を追加する場合も、共通署名結果、承認との結び付けおよび終端状態の意味を変更しない。

## 13. 信頼された内容検査と内容を確認しない署名

### 13.1 内容検査判断権限

署名前の内容検査は拡張機能の特権を持つホストとチェーン統合が、実際の署名対象バイト列 / 構造化されたメッセージから行う。信頼された UI が表示する確認モデルは、署名へ渡す対象と同じ正本となるデータから導出し、表示用に別の再計算・補完・丸め・変換を持たない。

次は表示判断権限ではない。

- Web アプリケーション / dApp の要約、ラベル、受信者名前、数量テキスト、説明、Markdown、HTML、アイコン、brand 名前
- SDK や Provider が任意に追加した人が読める要約
- ノード、Relay、外部メタデータ、ハッシュ照会、名前サービスまたはリモート API の補助情報

補助メタデータを表示する場合も、署名対象から得た正本となる値と区別し、検証・許可・署名主体識別情報の判断権限に使わない。取得不能な補助情報を理由に対象の意味を推測しない。

### 13.2 内容を確認しない署名の禁止

次の対象は、警告のみ、生の署名、一般的な署名、代替経路署名、ハッシュのみ承認または利用者責務の表示で承認可能にしてはならない。

- 解析、フィールド検証、正規 reserialization または署名主体検証ができないもの
- チェーン、ネットワーク、アカウント、署名主体役割、受信者、資産影響、許可影響、メッセージ内容等のセキュリティに関わるフィールドを表示できないもの
- 不明型 / バージョン、未対応の形式、途中で切れた / 末尾の / non-canonical ペイロード
- 外側だけで埋め込み / 内部 / 親全体を確認できないもの

内容検査、表示、承認との結び付けまたは結果検証を安全に完了できない場合は安全側での終了とし、既存エラー定義の正本に従って終端失敗とする。

## 14. トランザクション署名

### 14.1 チェーン互換性への委譲

ブラウザ拡張機能はトランザクションバイト列、ハッシュ、署名形式、世代ハッシュ、チェーンシリアライズ、アドレス、ネットワーク定数またはトランザクションスキーマを独自定義しない。[chain-compatibility-spec.md](./chain-compatibility-spec.md) の固定 SDK、許可リスト、デコード / encode、フィールド検証、正規等価性、署名検証およびハッシュ契約をそのまま使用する。

現行の対応候補はチェーン互換性仕様の許可リストに限る。例として Symbol は `TransferTransactionV1`、`AggregateCompleteTransactionV2`、`AggregateBondedTransactionV2` および対応する full-parent 連署署名、NEM は `TransferTransactionV1/V2`、`MultisigTransactionV1` および対応する `CosignatureV1` である。具体的な型、バージョン、埋め込み件数、フィールド、フィクスチャおよびリリース判定はチェーン互換性仕様を更新せずに拡張しない。

拡張機能は次を実施する責任を持つ。

1. ペイロードのエンコーディング、サイズ、チェーン / ネットワーク、期待される署名主体および未署名 / 署名済み条件を検証する。
2. 対象チェーンの正本 decoder で全フィールドをデコードする。
3. 予約済みの、長さ、整数、アドレス、mosaic、メッセージ、署名、ネットワーク、署名主体およびスキーマ条件を検証する。
4. 正本 serializer で再構成したバイト列と入力バイト列をバイト単位で一致する比較する。
5. 全セキュリティに関わるフィールドから内容検査モデルを生成し、信頼された UI へ表示する。
6. wallet-core 結果を正本検証者 / ファクトリーで検証し、元ペイロード、対象ダイジェスト / ハッシュ、チェーン、ネットワーク、署名主体およびアカウントと対応付ける。

ノードメタデータ、手数料 multiplier、未確定別名解決、外部照会または dApp の表示文字列で入力バイト列の意味を置き換えない。

## 15. アグリゲート、連署署名、部分トランザクション、NEM マルチシグ

### 15.1 Symbol アグリゲート

Symbol アグリゲート完了 / Bonded は外側トランザクションだけで承認を作らない。外側フィールド、トランザクションハッシュ、全埋め込みトランザクション、埋め込み署名主体、受信者、資産 / 数量、手数料、期限、ネットワーク、既存の署名 / 連署署名、期待される署名主体および署名主体役割を一つの対象文脈として解析、内容検査、表示および結び付けする。

埋め込みトランザクション、トランザクションハッシュ、既存連署署名、正規順序、資産影響または役割を安全に確認できない場合は署名しない。Bonded / 部分トランザクションであることだけを根拠にノードから親を取得・補完しない。

### 15.2 連署署名

`COSIGNATURE_SIGN` の署名対象は分離された連署署名バイト列、ハッシュまたは要約単体ではなく、選択済みの連署者と完全な親トランザクションの関係である。親全体、埋め込み / 内部内容、既存署名 / 連署署名、対象ハッシュ、選択済みのアカウント、期待される署名主体、役割、チェーン / ネットワークおよび重複条件を確認できる場合だけ処理する。

既存連署署名、親不在、ハッシュのみ、親と分離された対象の不一致、開始主体 / 連署者役割不一致または公開対象範囲が未確定の場合は、通常トランザクション署名、生の署名、外部照会または警告のみへ代替経路しない。

### 15.3 部分トランザクションと NEM マルチシグ

部分トランザクションは共通の第三の署名操作ではなく、チェーン / ネットワークまたは受け渡し上の未完成文脈である。親、埋め込み / 内部、既存の署名、期待される署名主体、期限切れおよび影響を確認できない部分トランザクションは署名しない。

NEM マルチシグ / 連署署名は Symbol アグリゲート / 連署署名に変換しない。NEM 固有の decoder、役割、内部トランザクション、手数料 / 資産影響、親整合性および署名主体検証を [chain-compatibility-spec.md](./chain-compatibility-spec.md) と [signing-protocol.md](./signing-protocol.md) に従って行う。NEM と Symbol の鍵、アドレス、ハッシュ、シリアライズおよび承認対象を共通化しない。

## 16. 構造化メッセージ署名

`signMessage()` / SDK `signData()` は既存の構造化されたメッセージ契約と `MESSAGE_SIGN` 意味を使用する。ブラウザ拡張機能は新しい生のメッセージ、任意のバイト列、別ドメイン、別通信上のスキーマまたは代替経路署名を追加しない。

メッセージ署名対象は少なくとも次へ結び付けする。

```text
mosaiclynx.message.v1
+ ブラウザで観測した正規オリジン
+ アカウント
+ チェーン / ネットワーク
+ 目的 / ドメイン
+ ノンス
+ issuedAt / 期限切れ
+ requestId / 要求期限切れ
+ 呼び出し元文脈
+ ペイロードエンコーディングとバイト列
```

- オリジンはページが自己申告した値ではなくブラウザで観測した値から導出する。
- ノンスの再利用、要求期限切れ、メッセージ期限切れ、issuedAt の範囲、目的、ペイロードエンコーディングおよび Unicode / hex 条件は既存プロダクト / インターフェース / 受け渡し契約を検証する。
- 信頼された UI と署名バイト列は同一の構造化されたメッセージから導出する。UI 表示用の別メッセージ、要約または変換を署名対象にしない。
- 生の任意のメッセージ、表示不能なメッセージ、不明形式または内容検査できないペイロードを警告のみで署名しない。
- request.messageExpiresAt → 正規 message.expiresAt の対応はインターフェース §9.4 に固定される。要求単位の expiresAt は別。

## 17. 信頼された承認 UI

### 17.1 表示契約

署名ごとに拡張機能が管理する信頼された承認 UI を表示し、利用者が少なくとも次を確認できるようにする。

- 要求元の正規オリジン。dApp ラベル、アイコン、ファビコン、ページ title とは別に表示する
- 選択済みの署名アカウントの公開識別情報、必要な署名主体役割
- チェーン / ネットワーク
- 操作（トランザクション、アグリゲート、連署署名、NEM マルチシグまたは構造化されたメッセージ）
- トランザクション / 親 / 埋め込み / 内部 / メッセージの全セキュリティに関わる内容
- 資産 transfer、手数料 / 数量、受信者、許可 / 判断権限変更、メッセージ内容等の確認可能な影響
- 期待される署名主体、既存の署名 / 連署署名、未対応の / 警告 / 検証不能の状態
- 承認と拒否の明示操作

UI 配置、CSS、コンポーネント基盤、window / ポップアップ / 側パネルの選択、ローカライズ、アクセシビリティおよび文言は下位 UI 仕様へ委譲する。ページ DOM、ページ CSS、リモート HTML / Markdown、dApp-provided 表示テキストまたは spoofable ブランド表示で信頼された UI の意味を変更できない。

### 17.2 承認と認証

承認は一つの論理的な署名対象に対する single-use の利用者による明示的な承認である。これだけでは署名認可を成立させない。承認との結び付けは [signing-protocol.md §5.3](./signing-protocol.md) に従い、適用範囲で呼び出し元 / オリジン、文書文脈、requestId、セッション、操作、許可リビジョン、プロファイル、アカウント、チェーン / ネットワーク、対応能力、対象、内容検査結果、署名主体役割、期限切れおよび鮮度を含む。

同じ承認を次へ流用してはならない。

- 別要求、別ペイロード、別対象、別アカウント、別オリジン、別ネットワーク / チェーン
- 重複要求、再試行、different 署名主体役割、different 連署者
- 古くなった許可、新規文書、新規 Provider、新規世代

プロファイル `UNLOCKED` は署名可能な状態へのロック解除または署名認可を自動的に意味しない。接続、許可、アカウント情報公開、選択済みのアカウント、Provider 利用可能性、対応能力、過去の認証、パスワード検証、ウォレットストア検証、wallet-core 対応能力または信頼された UI の表示だけで署名してはならない。認証、署名可能な状態へのロック解除、アカウントの利用認可および利用者による明示的な承認は、同一のプロファイル内の文脈に対する独立した4条件であり、`every-signature` 認証もその一つだけを満たす。ブラウザ固有の OS 生体認証 API、パスワード要求画面実装、ロック解除 API、代替経路および頻度上限は独自に固定しない。

## 18. 署名前再検証と wallet-core 境界

### 18.1 署名前再検証

`AUTHORIZED → SIGNING` 直前に、現在値と承認レコードの次を再検証する。

- ブラウザで観測したオリジン、送信者、タブ、フレーム、文書、ページ遷移文脈
- requestId、操作、プロトコル / 対応能力文脈、要求 / メッセージ期限切れ
- 現在の接続、許可対象範囲、許可リビジョン、プロファイル、選択済みのアカウント
- チェーン / ネットワーク、期待される署名主体、署名主体役割、Mainnet リリース対応能力
- トランザクション / 親 / 埋め込み / 内部 / メッセージペイロード、ダイジェスト、ハッシュ、正規バイト列、内容検査結果
- 認証の要求固有の有効性と結び付け
- 署名可能な状態へのロック解除の現在の有効性と結び付け
- 対象プロファイル / チェーン / ネットワーク / アカウントに対するアカウントの利用認可の現在の有効性と結び付け
- 利用者による明示的な承認の対象対象、内容検査結果および結び付け
- 応答受信者、Provider インスタンス、現在のライフサイクル / 世代文脈

上記4条件または結び付け文脈の一つでも不一致、古くなった、欠落、期限切れ、失効済み、ロック、文脈消失、対象変更または検証失敗があれば旧認可 / 承認を使わず、既存署名プロトコルの `INVALIDATED`、`EXPIRED`、`FAILED` 等の適用可能な終端意味に従う。対象を自動修正、アカウント / ネットワークを自動切替、ペイロードを再構成または再承認なしに再署名しない。

### 18.2 wallet-core 呼び出し

wallet-core を呼び出す前に、特権を持つホストが信頼された検証、信頼された内容検査、認証、署名可能な状態へのロック解除、対象アカウントに対するアカウントの利用認可および利用者による明示的な承認の4条件を、同一のプロファイル内の文脈で完了・再確認する。wallet-core へ Web アプリケーションの生の要求、ページ要約、ページ提供されたアカウント選択子または未検証ペイロードをそのまま渡して署名判断権限を委譲しない。4条件または結び付け文脈が一つでも確認不能なら wallet-core を呼び出さない。

wallet-core には既存の承認済み対象、解消済み内部鍵参照および必要なチェーン固有の結び付けだけを既存バインディング契約で渡す。wallet-core の厳密な API、Rust / WASM 関数名前、FFI、鍵枠、KDF、ウォレットストア、ゼロ化および暗号学的な基本機構は本書で定義しない。wallet-core 結果はホストが要求 / 対象 / 署名主体 / 対象範囲と独立に検証し、検証できない警告、エラー、部分トランザクション結果または応答を成功として返さない。

### 18.3 Mainnet リリース / 根拠判定条件

Mainnet 署名対応能力は、現在のリリースと適用中のリリース / 根拠ポリシーを満たしたことを信頼された署名主体 / リリースセキュリティ判断権限が確認した場合にだけ有効化する。[interfaces.md §7.4](./interfaces.md)、[signing-protocol.md](./signing-protocol.md) および [CR-NFR-006](../requirements/requirements.md) の判定条件意味を適用し、ブラウザ Provider / SDK は判定条件評価器、リリース判断権限または判定条件の代替ではない。

次のいずれも Mainnet 判定条件の成立を証明しない。

- `Scope.network === 'mainnet'`。
- Provider 利用可能性、Provider 対応能力、SDK 利用可能性または接続。
- 許可、アカウント情報公開、通常のロック解除、wallet-core 対応能力またはページ / SDK 状態。
- テスト成功、署名済み結果、Provider 応答、応答配送成功または通信経路成功。

判定条件が欠落、無効な、期限切れ、不整合の、検証不能のまたは不明の場合、Mainnet 署名対応能力は無効 / 利用不能とし、成功可能と推測しない。判定条件失敗 / 不明を理由に自動再試行、自動再署名、代替の Provider、Relay またはモバイル代替経路を行わない。Mainnet 判定条件失敗だけで Testnet 要求を Mainnet 要求へ変換したり、独立した Testnet 署名を不必要に停止したりしない。Testnet 専用で安全に継続できるかは Testnet の独立した条件で判断する。

根拠スキーマ、評価器アルゴリズム、信頼された鍵形式、ビルド展開 / ロールバックおよびリリース補助ツールは [ADR 0001](../adr/0001-mainnet-evidence-lite.md)、[Mainnet リリース証跡](../release/mainnet-release-evidence.md) および [根拠ポリシー](../evidence/evidence-policy.json) の判断権限に委譲し、本書で再定義しない。

## 19. 秘密情報処理

次の情報はページ文脈、Provider、SDK、コンテンツスクリプト、URL、通知、クリップボード、ログ、遠隔計測データ、エラー、診断情報、Relay または Web アプリケーションへ渡さない。

- 秘密鍵、ニーモニック、シード、プロファイルパスワード、認証秘密情報
- 復号されたウォレットストア、導出された暗号化鍵、ウォレットストア平文、鍵枠の秘密情報
- 署名内部秘密情報、wallet-core ハンドル、認証情報、セッション秘密情報
- 秘密を復元できる内部メタデータ、生の例外、秘密を含む要求 / 承認オブジェクト

復号された秘密情報は wallet-core が必要とする境界に限定し、拡張機能の長期保存、ページに公開するオブジェクト、要求キャッシュ、承認レコードまたは診断情報に保持しない。ロック、異常終了、再起動、拡張機能再読み込み、安全でない更新、文脈消失、プロファイル切り替えまたはライフサイクル discontinuity が起きた場合は、未確認の復号された秘密情報 / 認可を継続利用しない。

## 20. 拡張機能ライフサイクル

### 20.1 ライフサイクル消失の基本規則

次のライフサイクルイベントは、要求 / 承認 / 認証 / 署名可能な状態へのロック解除 / アカウントの利用認可 / 署名 / 応答対応付けの継続性を再評価する契機である。

- バックグラウンド / サービスワーカー再起動または停止
- 拡張機能再読み込み、更新、ブラウザ再起動
- ポップアップ / 承認 window 終了、フォーカス消失、タブ終了、ページ / 文書終了または破棄
- ページページ遷移、再読み込み、オリジン変更、フレーム破棄 / 置き換え
- Provider 接続解除 / 置き換え、応答チャネル消失、コンテンツスクリプト置き換え、文書世代変更
- プロファイル切り替え、アカウント変更 / 削除、ネットワーク / チェーン変更
- ロック、許可失効、許可リビジョン変更、wallet-core 文脈消失

安全に現在の呼び出し元、許可、対象、承認、認証、署名可能な状態へのロック解除、アカウントの利用認可、プロファイル / アカウント、プロトコル文脈および応答受信者を再構築できない場合、古い認可を再利用せず、署名生成が未開始なら既存のキャンセル、無効化または適用可能な失敗意味に従う。ブラウザライフサイクルイベント、Provider 接続解除または応答チャネル消失自体は `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` の根拠ではない。署名生成開始後も、終了 / ライフサイクルイベントだけから `RESULT_UNKNOWN` を推測せず、信頼された署名主体が世代結果自体を独立に確定できない場合だけ署名プロトコルの意味を適用する。4条件の一つでも再構成・再確認できない場合は wallet-core を呼び出さない。再構築できないことを、署名未実行、利用者拒否または署名失敗の証明にしない。

### 20.2 サービスワーカー / バックグラウンド再起動

MV3 等のサービスワーカー / バックグラウンドの具体実行環境 API、keep-alive、永続的な保存領域、復旧プロトコルは固定しない。ただし再起動後に次を推測で復元してはならない。

- 保留中の要求、`AUTHORIZED` 承認、認証成功、署名可能な状態へのロック解除、アカウントの利用認可、`SIGNING` 状態、wallet-core 操作
- 現在の送信者 / タブ / フレーム / 文書、許可リビジョン、プロファイル / アカウント、要求対象
- 署名済み結果、応答対応付け、配送状態、署名結果

再起動前の認可を安全に再構成できない場合は無効化する。`SIGNING` 中にプロセス消失、wallet-core 呼び出し中断または結果バッファー消失が発生した場合も、そのイベント自体から `RESULT_UNKNOWN` を生成せず、信頼された署名主体が世代結果自体を独立に確定できない場合だけ署名プロトコルの `RESULT_UNKNOWN` 意味を使用する。同じ対象を自動再署名しない。信頼された署名主体が既知の署名済み結果を既に確定して保持している場合は、その結果をライフサイクルイベントにより `RESULT_UNKNOWN` へ変更しない。署名主体自身がその既知の結果の配送処理結果の区分を確定できない場合だけ、`SUCCEEDED + DELIVERY_UNKNOWN` として署名結果と分離する。ライフサイクル消失、Provider 接続解除、Provider 応答消失、ページ配送失敗、受領確認欠如またはタイムアウトだけでこの処理結果の区分を生成しない。

## 21. ページ遷移、タブ、フレーム、Provider 変更

要求中にオリジン変更、same-Origin 再読み込み、オリジン間のページ遷移、タブ終了、フレーム置き換えまたは Provider 置き換えが生じた場合、現在のブラウザ呼び出し元文脈と要求の結び付けを再検証する。

- 旧文書の承認を新規文書、新規オリジン、新規フレームまたは別タブに移さない。
- 旧文書へ返すべき応答を配送できなくても、その事実から `DELIVERY_UNKNOWN` を生成せず、別文書の要求に適用しない。
- フレームが破棄され、最上位の / フレーム relationship を一意に確認できない場合は署名を継続しない。
- ポップアップ / 承認 window 終了、タブ終了、ページ / 文書終了、Provider 接続解除または応答チャネル消失は、そのイベント自体では `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` の原因にならない。署名生成未開始なら既存のキャンセル、無効化または適用可能な失敗意味に従い、世代開始後は信頼された署名主体が世代結果自体を確定できない場合だけ `RESULT_UNKNOWN` とする。既知の署名済み結果は既知の結果のまま保持し、ページ / Provider へ返せないことだけでは `DELIVERY_UNKNOWN` にしない。
- page-provided requestId やコールバックオブジェクトが残っていても、新しい文書の呼び出し元証明、許可または承認として再利用しない。

## 22. 応答世代、対応付け、配送

### 22.1 応答結び付け

Provider 応答は元の要求と一対一に対応し、少なくとも次の組を検証する。

```text
requestId
+ 操作
+ ブラウザで観測したオリジン / 呼び出し元文脈
+ タブ / フレーム / 文書文脈
+ セッション / ライフサイクル / プロトコル文脈
+ 対象範囲
+ アカウント / 署名主体 / 署名主体役割
+ 対象 / ダイジェスト / ハッシュ / 構造化されたメッセージ文脈
+ 要求と対象期限切れ
```

応答受信者、Provider インスタンス、文書または呼び出し元文脈が一致しない応答は成功として適用しない。遅延した、重複、mismatched、再送された、古くなった、不明操作、誤った対象範囲、誤ったアカウント、誤った署名主体または誤った対象の応答は破棄し、別要求 / オリジン / タブ / フレームへ配送しない。

### 22.2 署名結果と配送処理結果の区分

- 既知の署名済み結果の署名結果は `SUCCEEDED` であり、`PENDING`、`DELIVERED` または `DELIVERY_UNKNOWN` の署名主体が生成した `deliveryDisposition` を同じ結果に付随させる。`deliveryDisposition` は署名状態ではない。
- `RESULT_UNKNOWN` は信頼された署名主体が署名生成自体の成否を安全に確定できない場合だけに用いる。署名済み結果と配送処理結果の区分を持たず、通常のエラー、署名失敗または未署名へ変換しない。ポップアップ / 承認 window 終了、タブ / ページ終了、Provider 接続解除、SDK タイムアウト、応答欠如またはライフサイクル消失だけではこの結果を生成・推測しない。
- `DELIVERY_UNKNOWN` は信頼された署名主体が既知の署名済み結果を保持し、署名主体側の配送処理結果の区分自体を安全に確定できない場合だけに用いる。`RESULT_UNKNOWN`、署名失敗またはエラーコードへ変換しない。ページ / Provider 配送失敗、応答消失、受領確認欠如、タイムアウト、タブ終了または通信経路失敗だけではこの処理結果の区分を生成・推測しない。
- Provider ページに公開する結果、Provider → SDK アダプター、保証決済、コンテンツスクリプト、ページ配送、Provider 接続解除、ブラウザライフサイクル、Relay 応答、HTTP 状態または通信経路完了は、これらの意味を生成、推測、確定または書き換えない。応答がページに届いたことだけで `DELIVERED` としない。
- Provider → SDK アダプターは [web-transaction-handoff-spec.md §5.2.1、§7.2](./web-transaction-handoff-spec.md) に従い、既知の結果と同じ処理結果の区分を `MosaicLynxSigningResult<T>` の `outcome: 'succeeded'` 分岐へ、署名主体が生成した `RESULT_UNKNOWN` を `outcome: 'resultUnknown'` 分岐へ意味不変に渡す。SDK アダプターはこれらを生成しない。

信頼された署名主体が既知の署名済み結果を保持している場合、UI、タブ、ページ、Provider または応答チャネルの終了 / 消失によって `RESULT_UNKNOWN` または `DELIVERY_UNKNOWN` へ変換しない。既存の確定済みの結果復旧意味が適用される場合に限り、既存結果の再送、再配送、取得または照会として扱い、再署名、新規署名、代替の署名主体 / Provider、Relay / モバイル代替経路または通信経路切り替えと混同しない。具体的な復旧 API / ポリシーは既存判断権限と OPEN-BEX-004 に委譲し、本書で追加しない。

## 23. 要求並行処理、重複、リプレイ

複数 dApp、複数オリジン、複数タブ、same-Origin の複数文書および複数保留中の承認を独立した要求として扱う。

- 各要求は独立した requestId、呼び出し元文脈、許可リビジョン、プロファイル、アカウント、対象範囲、操作、対象、内容検査モデル、承認、認証、期限切れおよび結果受信者を持つ。
- 同じオリジンであること、同じアカウントであること、同じペイロードであることまたは同じ許可であることだけで承認 / 認証 / 結果を共有しない。
- 別オリジンの要求を一つの承認、アカウント選択、許可、応答チャネルまたはコールバックに混在させない。
- 重複 / リプレイ要求は second 署名を行わず、既存ライフサイクル / エラー定義の正本に従って終端にする。重複応答 / コールバックも一度だけ適用する。
- アカウント変更、ロック、接続解除、許可失効、プロファイル切り替えが一つの要求に影響しても、別要求の対象、承認、アカウントまたは結果を上書きしない。
- キュー、前面 UI の選択、同時数上限、公平性、シリアライズの厳密なポリシーは未確定の下位実装へ委譲する。ただしグローバル singleton 承認や曖昧な一括処理承認を暗黙に導入しない。

## 24. タイムアウト、キャンセル、不明結果

### 24.1 タイムアウトとキャンセルの区別

次を別の事実として扱う。

| 事象                                                                             | ブラウザ拡張機能の意味                                                                                                                                                                                                   |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| SDK ローカルタイムアウト                                                         | SDK が待機を終了した事実。署名成功、未署名または拒否を意味しない                                                                                                                                                         |
| Provider 要求タイムアウト / 要求期限切れ                                         | 要求を `EXPIRED` 等の適用可能な終端状態とし、古い承認を再利用しない                                                                                                                                                      |
| 利用者拒否                                                                       | `REJECTED`。明示的な利用者拒否に限る                                                                                                                                                                                     |
| 承認 UI 終了 / タブ終了 / ページ終了                                             | 終了イベント自体では `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` にしない。署名生成未開始なら既存のキャンセル、無効化または適用可能な失敗意味。開始後は信頼された署名主体が世代結果自体を確定できない場合だけ `RESULT_UNKNOWN` |
| 明示的なキャンセル                                                               | `SIGNING` 前に安全に終了できた場合は `CANCELLED`。署名未実行の証明に自動変換しない                                                                                                                                       |
| ロック / 許可失効 / 文脈変更                                                     | 旧認可を無効化。別アカウント / 対象範囲へ移さない                                                                                                                                                                        |
| wallet-core / 拡張機能異常終了                                                   | 異常終了イベント自体では `RESULT_UNKNOWN` にしない。信頼された署名主体が世代結果自体を確定できない場合だけ `RESULT_UNKNOWN`。自動再署名しない                                                                            |
| 署名主体が既知の署名済み結果を保持し署名主体側の配送処理結果の区分を確定できない | `SUCCEEDED + DELIVERY_UNKNOWN`。ページ / Provider 配送、通信経路、応答消失またはライフサイクルの事実だけで生成せず、署名エラー / 利用者拒否 / 未署名としない                                                             |

具体的タイムアウト値、再試行間隔、キュー永続化、復旧 API および既存の結果取得は SDK / 受け渡し / プラットフォーム未決を維持する。タイムアウト / キャンセル後の再試行が許可される場合も、新しい requestId、新鮮なエンベロープ、再検証、新しい承認および認証を要求する。

既存 Provider メソッド集合に含まれないキャンセルエンドポイント / メソッドを本書から追加しない。Provider 要求のキャンセルは、既存 SDK / 署名プロトコル / 受け渡しのライフサイクル契約、呼び出し元文脈消失または接続解除意味を通じて扱い、キャンセルを署名未実行や利用者拒否の証明にしない。

### 24.2 キャンセルと署名の境界

`SIGNING` 前のキャンセルは署名を開始せず `CANCELLED` とする。`SIGNING` 中のキャンセルは終了 / キャンセルイベント自体から `RESULT_UNKNOWN` を推測せず、信頼された署名主体が世代結果自体を確定できない場合だけ署名プロトコルの意味を適用する。`SUCCEEDED` 後のキャンセルは確定した署名を取り消さず、既存結果配送意味に従う。既知の署名済み結果がある場合、ページ / Provider への配送不能だけから `DELIVERY_UNKNOWN` を生成しない。

## 25. アカウント / プロファイル / 許可変更

次の変更は保留中の要求、承認、認証、応答受信者および cached 公開状態の再評価対象である。

- 有効なアカウントの変更、アカウントの削除または置き換え
- プロファイル切り替え、プロファイル削除、プロファイルロック / ロック解除、署名可能な状態へのロック解除の変更
- チェーン / ネットワーク変更またはプロファイル対象範囲の変更
- 許可失効、許可対象範囲 / アカウント集合 / リビジョン変更
- vault ロック、wallet-core ストア置き換え、セキュリティ事故、認証またはアカウントの利用認可の失効

旧アカウントの承認、認証、署名可能な状態へのロック解除、アカウントの利用認可、鍵参照、保留中の結果または応答を新規アカウント / プロファイル / 対象範囲へ移さない。署名が既に不可逆な段階に進んでいる場合、許可失効 / 接続解除の発生だけから利用者拒否、未署名またはキャンセルを推測しない。結果不明は署名プロトコルの意味を維持する。

## 26. 拡張機能更新と互換性

拡張機能更新 / 再読み込みで Provider API バージョン、プロトコル、対応能力、シリアライズ、wallet-core バインディングまたは許可モデルが変化する場合、保留中の要求 / 承認を旧バージョンから現在の契約へ推測変換しない。

- 既知の互換性のあるバージョン / 対応能力の検証ができない場合は利用不能 / 未対応のまたは無効化とする。
- 不明フィールド、不明列挙型、不明バージョン、未対応の操作、未対応のチェーン / ネットワーク、変更された対象エンコーディングは安全側での終了とする。
- 更新後のプロファイル、アカウント、許可、ウォレットストア、署名対応能力の対応を安全に検証できない場合、署名可能状態を継続しない。
- official 配布、完全性、依存関係、現在のリリース、Mainnet リリース / 根拠判定条件および更新 / ロールバックポリシーはリリース / セキュリティ判断権限へ委譲する。拡張機能更新 / 実行環境状態、Provider / SDK 利用可能性または対応能力は Mainnet 判定条件を評価・代替しない。
- 更新互換性を理由に明示的な承認、オリジンとの結び付け、秘密情報の分離、内容を確認しない署名禁止、応答対応付けまたは安全側での終了を弱めない。

## 27. エラー定義の正本とページエラー露出

### 27.1 判断権限

| エラーの範囲                               | 判断権限 / ブラウザ拡張機能の扱い                                                                                                                                         |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 共通の論理的なエラー分類                   | [interfaces.md](./interfaces.md) の共通のエラーモデル。検証、未対応の、許可、利用者拒否等の論理的な意味を定める。                                                         |
| 署名結果 / 終端意味                        | [signing-protocol.md](./signing-protocol.md)。`REJECTED`、`FAILED`、`EXPIRED`、`CANCELLED`、`INVALIDATED`、`RESULT_UNKNOWN` 等の署名ライフサイクルの意味を定める。        |
| SDK / 受け渡し具体的な公開エラー           | [web-transaction-handoff-spec.md §10](./web-transaction-handoff-spec.md) の `MosaicLynxSDKErrorCode`。ページ / SDK 境界で公開できる具体的なコードの唯一の判断権限とする。 |
| Provider / 特権を持つ RPC / 通信経路固有の | 特権を持つホストと内部通信経路の境界に限定する implementation-specific コード。ページに公開する公開コードまたは受け渡しエラーコードの追加集合として扱わない。             |
| wallet-core 内部エラー                     | wallet-core 契約。ストア、バインディング、暗号学的な警告 / エラーの内部詳細をページに公開するエラーへ露出しない。                                                         |

ブラウザ拡張機能は内部エラーを新しい SDK 公開エラー分類体系、コード、別名または再試行ポリシーとして追加しない。既存判断権限に対応しない内部詳細は公開エラーに昇格させず、安全な既存失敗対応付けまたは必要な上流未決として扱う。

### 27.2 公開エラーの最小化

ページに公開するエラーは必要最小限の既存公開契約に正規化し、スタック追跡、拡張機能内部パス、ブラウザ API 詳細、生のウォレットストアエラー、暗号学的な基本機構、秘密情報、認証情報、プロファイル ID、アカウント ID、生の承認、全体ペイロード、ノード / Relay 内部詳細を含めない。

エラー応答は署名結果、承認、認証、オリジン検証、アカウント所有責任またはセッション存在を過剰に推測できる詳細を返さない。Provider 固有の / 特権を持つ RPC コードはこのページに公開する境界を越えず、既知の失敗原因だけを受け渡し §10 の既存公開コードへ正規化する。不明または対応付け不能なコードは成功にせず安全側での終了とし、必要な公開 catch-all は受け渡し §10 の `INTERNAL_ERROR` に限る。ブラウザ拡張機能はエンドポイント固有のな新しい公開コードを再定義しない。

## 28. 診断情報、ログ出力、フィッシング対策

### 28.1 診断情報 / ログ出力

診断情報は安全性の補助であり、オリジンの信頼性判断、許可判断権限、承認判断権限または署名結果検証者ではない。必要最小限の正規化済みイベント、操作分類、非秘密情報の要求処理結果の区分、公開エラー分類およびライフサイクル分類だけを記録する。

次をログ、警告、例外、遠隔計測データ、異常終了報告書または診断コールバックへ出力しない。

- 秘密鍵、ニーモニック、パスワード、復号されたウォレットストア、導出された鍵、認証秘密情報
- セッション秘密情報、認証情報、wallet-core ハンドル、生の承認 / 認可
- 不要な全体トランザクション / メッセージ / 署名済みペイロード、全体機微なフィールドまたは復元可能な生の要求
- 内部アカウント ID、プロファイル ID、鍵枠、filesystem パス、スタック追跡、ブラウザ特権を持つ API 詳細

ペイロードダイジェスト、requestId、対象範囲、正規オリジンまたは公開アドレスを診断情報へ含める場合も、既存プライバシー / ログ出力契約の最小範囲に限定し、秘密情報や署名判断権限と結び付けて外部へ公開しない。

### 28.2 フィッシング対策

信頼された拡張機能 UI はページ UI と識別可能な Extension-managed 文脈で表示し、要求元のオリジン、アカウント、チェーン / ネットワーク、操作および影響を明示する。dApp ラベル、ファビコン、アイコン、ページ title、リモートブランド表示、HTML / Markdown、ページ CSS または user-supplied 要約を要求元のオリジンや信頼された署名主体識別情報の代替にしない。

具体的ブランド表示、window 設計、phishing 警告表現および OS UI 統合は上流で未確定なら独自追加しない。

## 29. セキュリティ上の不変条件

ブラウザ拡張機能は次を常に維持する。

1. ページ入力、Provider、SDK、コンテンツスクリプト、ノード、Relay および外部 API は信頼されていないである。
2. 呼び出し元文脈はブラウザで観測した送信者、最上位の文書、タブ / フレーム、オリジンおよびライフサイクル文脈に結び付けする。
3. 接続許可は承認ではなく、許可は署名判断権限を含まない。
4. 認証、署名可能な状態へのロック解除、アカウントの利用認可および利用者による明示的な承認は、同一の署名主体が所有するプロファイル内のセキュリティ文脈に対する独立した4条件である。認証 ≠ 署名可能な状態へのロック解除、署名可能な状態へのロック解除 ≠ アカウントの利用認可、アカウントの利用認可 ≠ 利用者による明示的な承認、利用者による明示的な承認 ≠ 認証を維持する。
5. 接続、許可、アカウント情報公開、選択済みのアカウント、Provider 利用可能性、対応能力、通常の `UNLOCKED`、過去の認証、パスワード検証、ウォレットストア検証、wallet-core 対応能力またはページ / SDK 状態を4条件の代替にしない。
6. 信頼された内容検査と全セキュリティに関わるフィールドの表示が署名前に完了する。
7. 内容を確認しない署名、ハッシュのみ承認、要約のみ承認、ノード照会補完および生の代替経路を許可しない。
8. 一つの承認は一つの論理的な署名対象に対する single-use 認可である。
9. 古くなった、期限切れ、重複、再送された、キャンセル済み、失効済み、終端または lifecycle-lost 状態を再利用しない。
10. `AUTHORIZED → SIGNING` 直前と wallet-core 呼び出し前に、4条件と要求識別情報、ブラウザで観測したオリジン、文書 / タブ / フレーム、プロファイル、許可 / リビジョン、アカウント、チェーン / ネットワーク、操作、対応能力 / バージョン、厳密な対象、内容検査結果および期限切れ / 鮮度の結び付け文脈をすべて再確認する。いずれかが不成立なら wallet-core を呼び出さず安全側での終了とする。
11. 秘密鍵、ニーモニック、ウォレットストア平文、パスワード、認証秘密情報、認証情報および署名内部秘密情報をページ / Provider / SDK / Relay へ露出しない。
12. 応答対応付けは requestId だけに依存せず、呼び出し元、文書、操作、対象範囲、アカウント、対象およびライフサイクル文脈を検証し、失敗時は安全側での終了とする。
13. 既知の署名済み結果は `SUCCEEDED` と署名主体が生成した `PENDING` / `DELIVERED` / `DELIVERY_UNKNOWN` を保持し、`RESULT_UNKNOWN` は署名済み結果 / 配送処理結果の区分なしで表現する。Provider、SDK、保証決済、通信経路またはページ配送はこれらを生成・推測・書き換えない。
14. `RESULT_UNKNOWN` の不確実性または `DELIVERY_UNKNOWN` の後に自動再署名、代替の Provider、Relay / モバイル代替経路を行わない。
15. ページ遷移、タブ / フレーム置き換え、Provider 置き換え、ロック、許可リビジョン、プロファイル / アカウント変更、再起動および更新後に古くなった承認を継続しない。
16. 署名結果、利用者拒否、キャンセル、通信経路配送、応答 receipt、接続成功および認証成功を混同しない。

## 30. 対象範囲境界と委譲事項

本書は security-sensitive な観測可能な動作を固定するが、次を実装方式として固定しない。

- SDK 実装、Provider 通信経路、RPC / イベントシリアライズ、注入されたスクリプト配置、コンテンツスクリプトメッセージプロトコル
- Chrome API 名、マニフェストの完全な JSON、許可名、CSP、ブラウザ API ラッパー、最低ブラウザバージョン
- React / Vue / Svelte、状態管理、バンドラー、ファイル配置、保存領域エンジン、キュー / ロック / CAS / DB トランザクション
- wallet-core 厳密な API、Rust / WASM / FFI、KDF、AEAD、鍵導出、ウォレットストア形式、秘密情報バイトライフサイクル
- UI コンポーネント、CSS、設計システム、window / 側パネル、OS 生体認証 API、ローカライズ、テスト基盤
- 許可期限切れ、永続的なセッション復旧、並行処理 upper 結び付いた、タイムアウト / 再試行間隔、Provider 選択対応表

## 31. 適合性 / 受け入れ条件

ブラウザ拡張機能実装は、少なくとも次を検証可能でなければならない。

1. `window.mosaicLynx` の Provider API 主要 `2`、必須メソッド、対応能力および互換性を確認し、互換性のない / 不正な形式の Provider を安全に扱う。
2. ページ / 注入された / コンテンツスクリプトと特権を持つホストを分離し、ページ入力が信頼された呼び出し元、許可、承認または秘密情報へ昇格しない。
3. ブラウザで観測した最上位のオリジン、文書、タブ / フレーム文脈と要求を結び付けし、自己申告のオリジン、iframe、未対応のオリジン、ページ遷移後の古くなった要求を拒否する。
4. `connect()`、公開アカウント情報公開、許可、有効なアカウント、接続解除 / 失効および各署名承認を別の意味として扱う。
5. `Scope`、プロファイル内のセキュリティ文脈、アカウント、期待される署名主体、チェーン / ネットワーク、対応能力 / バージョン、期限切れ、requestId、重複 / リプレイおよび対象構造を署名前に再検証し、アカウント選択子を認可判断権限として扱わない。
6. `RECEIVED → VALIDATED → INSPECTED → AWAITING_USER → AUTHORIZED → SIGNING → SUCCEEDED` と全終端状態を署名プロトコルに従って扱い、`AUTHORIZED` は同一文脈の認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認の4条件がすべて成立した場合だけ作成する。独自の危険な状態を追加しない。
7. 信頼された UI がブラウザで観測したオリジン、アカウント、チェーン / ネットワーク、操作、全対象内容、署名主体役割、影響、警告および承認 / 拒否を表示し、ページ要約を判断権限にしない。
8. Symbol / NEM トランザクション、アグリゲート、連署署名、NEM マルチシグおよび構造化されたメッセージを各判断権限に従って全体検証し、不明 / 内容検査できない / 未対応の / 生の代替経路を署名しない。
9. `AUTHORIZED → SIGNING` 直前に呼び出し元、要求識別情報、許可 / リビジョン、プロファイル内の文脈、アカウント、対象範囲、チェーン / ネットワーク、操作、対応能力 / バージョン、厳密な対象、内容検査結果、期限切れ / 鮮度および4条件すべてを再検証する。欠落、古くなった、失効済み、ロック済み、変更された、mismatched、不明または無効化済みは安全側での終了とする。
10. 認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認の4条件と結び付け文脈を確認できた承認済み対象に限って wallet-core を呼び出し、結果を元要求、対象、署名主体、アカウント、チェーン / ネットワークおよび操作と検証する。
11. 並行する要求、重複コールバック、遅延した / 古くなった / mismatched 応答、same-Origin 複数の tabs、許可失効、ロック、アカウント変更および Provider 置き換えを要求間で混同しない。
12. 既知の署名済み結果の `SUCCEEDED` と署名主体が生成した `PENDING` / `DELIVERED` / `DELIVERY_UNKNOWN`、および署名済み結果 / 配送処理結果の区分を持たない `RESULT_UNKNOWN` を相互に誤変換せず、SDK タイムアウト、通信経路完了、ページ応答配送またはライフサイクル消失からこれらを推測せず、自動再署名しない。
13. サービスワーカー / バックグラウンド再起動、拡張機能更新、ブラウザ再起動、ページ遷移、タブ / フレーム破棄後に旧承認、認証、署名可能な状態へのロック解除、アカウントの利用認可、署名状態、応答対応付けまたは秘密情報を推測復元しない。
14. ページに公開するエラーは受け渡し §10 の既存公開コードに限り、Provider / 特権を持つ RPC の内部コードを転送せず、不明コードを成功にしない。診断情報、ログ出力、events、キャッシュおよび URL に秘密情報、認証情報、内部 ID、スタック追跡、生のウォレットストアエラーまたは不要な全体ペイロードを露出しない。
15. Mainnet 署名対応能力は現在のリリースと適用中のリリース / 根拠ポリシーを満たした信頼された署名主体 / リリースセキュリティ判断権限だけが有効化し、Provider / SDK 利用可能性、対応能力、接続、許可、アカウント情報公開、通常のロック解除、wallet-core 対応能力、テスト成功、署名済み結果、Provider 応答または通信経路 / 応答配送成功を判定条件の代替にしない。判定条件が欠落、無効な、期限切れ、不整合の、検証不能のまたは不明の場合は無効 / 利用不能とし、Testnet 専用の安全な継続を不必要に停止しない。

## 32. 未決課題

本書で上流未決事項を独自に確定しない。以下の残存する未決をブラウザ拡張機能の実装開始前または関連下位仕様で解消する。`OPEN-BEX-001` は上流共通契約を本書へ反映したことで解消済みであり、残存する未決には含めない。

### 解消済み: OPEN-BEX-001 — 公開アカウント投影と内部経路選択

上流の共通契約により、ページに公開するのアカウントの識別情報は §10.1 の `PublicAccountIdentity` に限定する。`profileId`、内部 `accountId`、ウォレットストア ID、鍵枠および内容を解釈しない内部経路選択ハンドルはページに公開するフィールド、ページ入力、許可判断権限、所有責任証明、アカウントの利用認可または鍵選択判断権限ではない。必要なアカウントの内部参照は特権を持つホスト / 署名主体内部の経路選択に限り、トランザクション署名の対象アカウントはペイロード、期待される署名主体、許可および現在のプロファイル内の文脈から解決する。複数の許可アカウントの選択は信頼された署名主体 UI / 署名主体が所有する文脈で行う。

### OPEN-BEX-002: Provider 検出、対応能力、複数の Provider

- **問題:** 複数の Provider、偽の / 競合する Provider の選択ポリシー、対応能力識別子 / 協議、Provider バージョン互換性対応表および明示的な選択 API が未確定である。
- **影響:** 検出、`isAvailable()`、接続、all 署名操作、Provider 置き換え。
- **本書の扱い:** API 主要 `2` の既存互換性、不正な形式の / 互換性のないの安全側での終了および自動代替経路禁止だけを適用する。新しい選択 API、対応能力 ID またはバージョン規則を追加しない。
- **戻すべき上流:** [sdk.md OPEN-SDK-001、OPEN-SDK-002](./sdk.md)、[SDK 設計 §7、§18](../design/sdk.md)、[interfaces.md 未決](./interfaces.md)。

### OPEN-BEX-003: フレーム、呼び出し元証明、オリジン正規化

- **問題:** ブラウザ固有のな最上位の / 要求元のフレームの厳密な観測、文書識別情報、オリジン正規化、iframe サポートの将来範囲および複数の window ポリシーが未確定である。
- **影響:** 接続、許可結び付け、信頼された UI、ページ遷移、応答配送。
- **本書の扱い:** 初回マイルストーンは上流要件どおり最上位の呼び出し元とし、iframe / 子フレームを暗黙に許可しない。安全に一意化できなければ安全側での終了とする。
- **戻すべき上流:** [browser-extension.md BR-004、BR-008](../requirements/browser-extension.md)、[ブラウザ拡張機能設計 §7、§19](../design/browser-extension.md)、ブラウザ固有の下位仕様。

### OPEN-BEX-004: 許可期限切れ、セッション永続化、復旧

- **問題:** 許可期限切れ、独立失効識別子、セッション永続化、バックグラウンドライフサイクル復旧、保留中の要求の保持および既存結果の取得ポリシーが未確定である。
- **影響:** 再接続、サービスワーカー再起動、許可リビジョン、タイムアウト、`RESULT_UNKNOWN`、`DELIVERY_UNKNOWN`。
- **本書の扱い:** 旧認可の推測復元、自動再署名、古くなったセッションの再利用を禁止する。具体タイムアウト、保存領域、復旧 API を追加しない。
- **戻すべき上流:** [interfaces.md §8](./interfaces.md)、[signing-protocol.md OPEN-006](./signing-protocol.md)、[SDK 設計 §13、§21](../design/sdk.md)、ブラウザライフサイクル下位仕様。

### OPEN-BEX-005: 認証、UI、更新互換性

- **問題:** ブラウザ固有の認証実装、信頼された UI ホスト、厳密な UI / アクセシビリティ、更新移行 / ロールバック、Provider バージョン遷移およびブラウザサポート対応表が未確定である。
- **影響:** `AWAITING_USER`、`AUTHORIZED`、ロック / ロック解除、再起動、更新、Mainnet リリース対応能力。
- **本書の扱い:** `every-signature`、明示的な承認、信頼された UI、安全側での終了および旧認可非再利用だけを確定する。OS API、UI 基盤、更新移行を固定しない。
- **戻すべき上流:** [profile-account-spec.md](./profile-account-spec.md)、[security-design.md §7、§14、§16](../design/security-design.md)、[browser-extension.md BR-012、BR-013](../requirements/browser-extension.md)、リリースポリシー。

### OPEN-BEX-006: 公開アグリゲート / 連署署名対象範囲

- **問題:** full-parent 内容検査と安全な連署署名意味は確定しているが、Provider / SDK v1 の必須 / 任意対応能力、対応チェーン、公開結果フィールドおよび操作対象範囲が未確定である。
- **影響:** Provider 対応能力、`cosignTransaction()`、Symbol アグリゲート、NEM マルチシグ / 連署署名、リリース判定。
- **本書の扱い:** 全体確認できない対象を拒否する。部分トランザクション、ハッシュのみ、要約のみまたは NEM / Symbol の暗黙変換を追加しない。
- **戻すべき上流:** [sdk.md OPEN-SDK-004](./sdk.md)、[signing-protocol.md OPEN-005](./signing-protocol.md)、[chain-compatibility-spec.md](./chain-compatibility-spec.md)、Provider / プラットフォーム署名対象範囲。

上記未決を理由に、接続許可を署名承認とすること、オリジンの信頼性判断を SDK / ページへ移すこと、内容を確認しない / 生の署名、秘密情報 API、新規エラーコード、自動再署名または安全条件を満たさない継続復旧を導入してはならない。
