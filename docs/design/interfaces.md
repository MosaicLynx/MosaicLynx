# MosaicLynx 共通データモデル・インターフェース基本設計

## 1. 目的

本書は、MosaicLynx を構成する SDK、ブラウザ拡張機能、モバイルアプリ、Relay、チェーン固有の統合および `symbol-nem-wallet-core`（以下 `wallet-core`）の間で共有する境界言語を定義する。各境界で何を受け取り、何を返し、どの主体が検証・判断するかを、通信経路や実装型から独立した概念モデルとして整理する。

本書の対象は、署名要求、署名結果、アカウント、チェーン / ネットワーク、署名前確認の概要および境界エラーである。ブラウザ拡張機能とモバイルアプリは共通の署名主体として扱うが、現在のワークスペースにモバイルアプリの実装は存在しない。モバイルに関する記述は、既存要件およびアーキテクチャで定義された責任境界を示すものであり、実装済みであることを示さない。

## 2. 適用範囲と位置づけ

正式 wallet-core ファサード 0.2.0 の API / DTO / エラー / 三つのバックエンドと秘密情報の許容範囲の正本は [wallet-core 統合仕様](../specifications/wallet-core-integration.md) とする。コア ID の内部対応と事前準備済みの内容を解釈しないストアを用い、秘密を取得する初期設定 / エクスポートを現行対象にしない。

本書は [アーキテクチャ設計](./architecture.md) を共通データモデルとインターフェース境界の観点から補足する基本設計書である。[セキュリティ設計](./security-design.md) が定める秘密情報、信頼境界、承認および安全側での終了の原則を前提とし、署名の処理順や状態遷移は [署名フロー基本設計](./signing-flow.md) に委譲する。

SDK と Web アプリ、ブラウザ拡張機能、モバイルアプリ、Relay の受け渡し契約は [SDK 要件](../requirements/sdk.md)、[ブラウザ拡張機能要件](../requirements/browser-extension.md)、[モバイルアプリ要件](../requirements/mobile-app.md)、[Relay 要件](../requirements/relay.md) および [Web トランザクション受け渡し仕様](../specifications/web-transaction-handoff-spec.md) と整合させる。Symbol / NEM 固有の解釈は [チェーン互換性仕様](../specifications/chain-compatibility-spec.md) に、プロファイル / アカウントの詳細は [プロファイル / アカウント仕様](../specifications/profile-account-spec.md) に従う。

本書でいう「インターフェース」は、データの意味、責任および検証の境界を指す。特定の通信方式、公開 API、DTO または画面を意味しない。

## 3. 設計原則

### 3.1 通信方式に依存しない

共通データモデルは、`window.postMessage`、WebExtension メッセージ通信、HTTP、WebSocket、ディープリンク、Relay 通信経路などの個別通信経路を前提にしない。各アダプターは通信経路の入力を共通の概念モデルへ変換し、通信経路固有のメタデータや失敗を共通の意味へ対応付ける。ただし、変換によって要求の意味、署名対象または安全条件を変更してはならない。

### 3.2 プラットフォームに依存しない

共通モデルはブラウザ拡張機能、モバイル、SDK の特定実装、OS API、UI ツールキットまたは保存領域 API に依存しない。拡張機能のブラウザ文脈やモバイルの受け渡し文脈のようなプラットフォーム固有情報は、共通の `caller context` または `signing context` へ境界情報として渡すが、具体的な取得方式は各プラットフォームの責任とする。

### 3.3 チェーンとネットワークの分離

`Chain` は Symbol または NEM のような対象チェーンを示し、`Network` はそのチェーン上の Mainnet / Testnet などのネットワーク文脈を示す。両者を一つの `networkId` だけで表現することを前提にしない。アプリケーションプロファイルは一つのチェーンと一つのネットワークに固定され、要求、アカウント、プロファイル、署名対象および結果は、適用されるチェーンとネットワークの組み合わせを保ったまま扱う。Symbol と NEM の両方を利用する場合は、チェーンごとに別プロファイル内の文脈を使用する。

具体的な列挙型、数値 ID、ネットワーク定数、アドレス規則およびトランザクションスキーマは本書で定めない。Symbol と NEM の導出、署名バイト列、アドレス、トランザクションの意味を共通規則へ暗黙に変換してはならない。

### 3.4 秘密情報の分離

秘密鍵、ニーモニック、シード、復号済みウォレットストア秘密情報および署名用秘密情報は wallet-core のみが扱い、MosaicLynx は取得・保持しない。プロファイルパスワードは信頼された署名主体の現在の操作限りとする。特に `Account`、`SigningRequest`、`SigningResponse`、`TransactionSummary` および `Error` は秘密情報を含まない公開・境界モデルとする。

`wallet-core` はソフトウェア鍵に対応する暗号学的な公開識別情報（公開鍵、アドレス、鍵識別情報）、秘密情報の処理、ウォレットストア、チェーン固有の鍵および生バイト署名の正本である。MosaicLynx アプリケーション / 署名主体は要求元、表示、承認、アカウントの選択および処理の調整を担い、wallet-core 内部の秘密処理や暗号学的な識別情報を再実装しない。

### 3.5 安全側での終了

要求、呼び出し元、許可、チェーン、ネットワーク、アカウント、トランザクション型、署名方式、期限、完全性または署名結果を確認できない場合、推測して処理しない。未知のバージョン、操作、形式、トランザクション型、メッセージ形式、ネットワークまたは署名文脈は、対応可能であることを確認できない限り安全側に終了する。Relay の配送成功や UI の表示成功だけを署名成功とみなさない。

### 3.6 ローカルでの導出

署名判断に必要なトランザクションの意味、アカウントの公開識別情報、チェーン / ネットワークの整合性および `TransactionSummary` は、可能な限り署名主体が検証済みの対象から導出する。外部要求元が提供した表示文言、名称、アイコン、要約またはメタデータを、そのまま署名判断の根拠にしない。

### 3.7 バージョン管理可能性

要求、応答およびプロトコルコンセプトは、将来の互換性確認と対応能力協議ができる概念的なバージョン文脈を持つ。具体的なバージョンフィールドの型、番号体系、互換性規則および通信上の表現は下位仕様へ委譲する。受信側が要求された意味を解釈できないバージョンは、未知フィールドの推測や別操作への代替経路で処理しない。

## 4. コンポーネント境界

基本的な経路は次のとおりである。

```text
Web アプリ / dApp
      │ 公開 SDK / 橋渡し
      ▼
署名主体（ブラウザ拡張機能またはモバイルアプリ）
      │ 承認済み対象のみ
      ▼
wallet-core
```

モバイル経路では、Relay はモバイル署名主体の前段にある内容を解釈しない通信経路である。

```text
Web アプリ / SDK
      │ 要求 / 応答の E2E 受け渡し
      ▼
Relay ───────────────► モバイル署名主体 ─────► wallet-core
  内容を解釈しない配送検証・表示・承認秘密処理・署名
```

### 4.1 境界ごとの責任

| 境界                           | 主な生成主体 / 利用主体                                                       | 境界で受け渡す概念                                                                                                                                      | 主な検証器 / 信頼された判断権限                                                                                                                                   |
| ------------------------------ | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Web アプリ ↔ SDK               | Web アプリが SDK を呼び、SDK が MosaicLynx へ要求する                         | 対応能力、公開アカウント、SigningRequest、SigningResponse、エラー                                                                                       | SDK は入力・対応付け・通信経路差異を扱う。最終的な署名判断と意味上の検証は署名主体                                                                                |
| SDK ↔ 署名主体                 | SDK / 橋渡しが要求を生成・配送し、署名主体が消費して応答を返す                | SigningRequest / SigningResponse / エラー                                                                                                               | 署名主体が受信要求を署名主体内のプロファイル文脈と結び付けし、呼び出し元、許可、対象、チェーン / ネットワーク、アカウント、承認、結果を検証する信頼された判断権限 |
| Web アプリ ↔ ブラウザ拡張機能  | Web アプリは外部要求元、拡張機能はブラウザ文脈を観測する署名主体              | SDK 要求、ブラウザ呼び出し元文脈、公開結果                                                                                                              | 拡張機能の特権を持つ層がブラウザ観測情報、プロファイル内の文脈および要求の対応を最終確認する。Web アプリの自己申告は判断権限ではない                              |
| Relay ↔ モバイル               | Relay は内容を解釈しないエンベロープを搬送し、モバイルが要求 / 応答を検証する | E2E 受け渡し、セッション / 世代の通信経路文脈、内容を解釈しない要求 / 応答                                                                              | Relay は構造・配送だけを検証する。モバイル署名主体が完全性、意味、表示、承認および署名の判断権限                                                                  |
| ブラウザ拡張機能 ↔ wallet-core | 拡張機能が承認済み署名対象を渡し、wallet-core が署名結果を返す                | 承認済み生の対象、プロファイルに結び付いたアプリケーションアカウント文脈、検証済み暗号学的な識別情報、チェーン / ネットワーク文脈、署名 / 結果 / エラー | 拡張機能が呼び出し元・プロファイル・アカウントの利用認可・利用者の意図と対象の一致を判断権限とし、wallet-core が暗号学的な識別情報・秘密処理・生の署名の判断権限  |
| モバイル ↔ wallet-core         | モバイルアプリが承認済み対象を渡し、wallet-core が署名結果を返す              | ブラウザ拡張機能と同じ共通概念。具体的なバインディング / OS 統合は別設計                                                                                | モバイルアプリが呼び出し元・プロファイル・表示・承認の判断権限、wallet-core が暗号学的な識別情報・秘密処理・生の署名の判断権限                                    |

各境界の生成主体は、受け渡しに必要な情報を提供する責任を持つが、受信側の検証を省略させる権限を持たない。`trusted authority` は全データを無条件に信頼するという意味ではなく、その境界で特定の判断を最終的に担う主体を示す。

ここでいうネットワーク文脈の生成主体は、チェーン / ネットワークを要求へ申告または通信経路する SDK、Web アプリ、dApp または受け渡しクライアントと、ペイロード・プロファイル・アカウントと照合して署名主体内のな信頼された文脈を導出する署名主体 / チェーン固有の統合に限る。Relay とブロックチェーンノードは、ネットワークメタデータの信頼されていないな搬送元・観測元または候補提供元にはなり得るが、ネットワークモデルを生成・確定・上書きする判断権限ではない。

### 4.2 コンポーネント別の受け取りと返却

- **SDK** は Web アプリの公開操作を論理的な要求へ変換し、署名主体から受け取った応答を元要求に対応付けて返す。秘密情報、最終承認、トランザクションの意味解釈および生の署名は扱わない。
- **ブラウザ拡張機能** は SDK / Provider とブラウザが観測した呼び出し元文脈を受け取り、特権を持つ層でプロファイル内の文脈とともに検証した後、確認領域と wallet-core アダプターへ渡す。返すのは検証済みの成功結果または分類された失敗であり、秘密情報ではない。
- **モバイルアプリ** は Relay または別の外部受け渡しから内容を解釈しないな要求を受け取り、アプリ自身のプロファイル内の文脈、検証済み受け渡し送信元、表示および認証で再検証する。現在のワークスペースには実装がなく、OS API、受信方式およびホストバインディングは下位設計に委譲する。
- **Relay** は E2E で保護されたエンベロープと最小限の通信経路メタデータを受け取り、期限・サイズ・セッション / 世代・重複など通信経路上の条件を検証して配送する。ネットワークを決定・上書きせず、署名主体のネットワーク検証を代替しない。署名判断、意味解釈、承認または署名結果の生成を返す主体ではない。
- **wallet-core** はホストから渡された契約上の入力を受け取り、ソフトウェア鍵の暗号学的な識別情報、ストア・鍵・秘密情報・生の署名の処理結果またはエラー / 診断情報を返す。利用者の呼び出し元、アプリケーションプロファイル / アカウント関連付け、UI、許可、アカウントの利用認可または署名意図を判断しない。

Relay やブロックチェーンノードから得られるネットワークメタデータは、接続・観測または補助情報であり、署名主体がそのまま信頼された文脈として採用するものではない。署名主体 / チェーン固有の統合がペイロード、アカウント、プロファイルおよび対象チェーンと照合し、必要なネットワーク文脈を自ら検証する。ノード検出、ノード選択、チェーン検証またはネットワーク fingerprinting の方式は本書で定めない。

## 5. 信頼境界

### 5.1 信頼の扱い

外部入力は、暗号化されていても、構造検証済みでも、意味上の信頼を得たとは扱わない。境界を越えるたびに、受信側が自分の責任範囲を検証する。

| データまたは主体                                            | 署名主体から見た扱い                                                       | 必要な扱い                                                                                                   |
| ----------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Web アプリ、dApp、SDK、Provider、コンテンツスクリプト       | 信頼されていない                                                           | 要求、呼び出し元結び付け、許可、期限、対象および完全性を検証する                                             |
| ブラウザが観測した送信者 / オリジン / 文書文脈              | ブラウザが観測した事実として利用可能。ただしペイロードの正しさを証明しない | 特権を持つ層が要求と対応付け、タブ / フレーム / 文書ライフサイクルを含めて検証する                           |
| Relay、Relay メタデータ、ノード、外部 API                   | 信頼されていない / 補助情報                                                | Relay は構造・配送だけを担当し、署名主体が E2E 完全性、意味、鮮度および結果を再検証する                      |
| モバイルのディープリンク / App Link / OS 受け渡しメタデータ | 信頼されていない                                                           | モバイルアプリが呼び出し元、セッション、完全性、期限および要求の対応を検証する                               |
| `TransactionSummary`                                        | 署名主体が対象から導出した場合のみ確認用に利用                             | 外部要約を署名可否の根拠にせず、ペイロードとの不一致は安全側での終了                                         |
| 署名主体の確認 UI と承認記録                                | 利用者の署名判断に関する信頼された判断権限                                 | 承認対象、プロファイル、アカウント、チェーン / ネットワーク、呼び出し元、4条件、文脈および対象に結び付けする |
| wallet-core の署名結果                                      | 暗号学的な識別情報・秘密処理・暗号結果の信頼された判断権限                 | ホストがプロファイル、対象、アカウント、チェーン / ネットワーク、操作、4条件および要求対応付けを検証する     |

`wallet-core` のバインディングは、API / データ所有責任の境界であり、WASM、JavaScript、ネイティブホストまたは OS から秘密情報が自動的に隔離されることを意味しない。ホスト側の一時的な秘密情報のライフサイクルは、wallet-core 外部契約と各プラットフォーム設計の責任である。

## 6. 共通データモデル

以下は論理モデルであり、JSON プロパティ名、具体的な型、エンコーディングまたは通信上のフィールドの確定ではない。モデルに含める情報は、対象操作に適用される範囲で扱う。

### プロファイル内のセキュリティ文脈

アプリケーションプロファイルと、そのプロファイルに固定されたプロファイルチェーン / ネットワークは、公開要求 / 応答フィールドではない署名主体内のなセキュリティ文脈とする。プロファイル ID を SDK、Relay またはその他の公開通信上のスキーマに追加することは要求しない。ここでいうアプリケーションプロファイルは、wallet-core のプロファイル / ストアと同一の責任単位ではなく、wallet-core の内部プロファイル / ストアをアプリケーションプロファイルの判断権限として扱わない。

アプリケーションアカウント、許可、有効なアカウント、承認および署名認可は、所属プロファイルの固定されたチェーン / ネットワークと一致しなければならない。異なるチェーンのアカウント、許可または認可を同一プロファイル内の文脈へ関連付けず、両チェーンを利用する場合はプロファイル内の文脈自体を分離する。

アプリケーション / 署名主体は、プロファイル / アカウント関連付け、有効なプロファイル、許可およびアカウント選択を所有する。署名主体は、次のすべてを同じプロファイル内の文脈に結び付けして検証・再確認する。

- 要求、呼び出し元 / 送信元文脈、セッションおよび許可文脈。
- 承認、認証、署名可能な状態へのロック解除およびアカウントの利用認可。
- アカウント、チェーン / ネットワーク、操作、署名対象、鮮度および wallet-core 呼び出し。
- wallet-core 結果、結果検証、応答受信者および応答配送文脈。

ブラウザのタブ / フレーム / 文書文脈と、モバイルの検証済み受け渡し送信元は、この呼び出し元 / 送信元文脈の一部として同じ要求文脈に結び付ける。プロファイル切り替え、プロファイルロック、有効なプロファイル文脈消失、プロファイル / アカウント関連付け変更、許可失効、アカウント切り替え、チェーン / ネットワーク変更または呼び出し元 / 送信元文脈変更が発生した場合、影響する保留中の要求、承認、認証、アカウントの利用認可および結果配送文脈を失効させる。失効した文脈、プロファイル A の承認 / 認証 / 認可 / 結果をプロファイル B に流用してはならず、古い応答受信者へ結果を配送してはならない。

要求識別情報、通信経路セッション、Relay 世代または SDK インスタンスはこの署名主体内の文脈の判断権限ではなく、その代替にもならない。

### 6.1 ネットワーク

`Network` は、対象チェーン上のネットワーク文脈を表す。ネットワークは単独でチェーンを意味せず、常に `Chain` と組み合わせて扱う。

概念上、次の情報を持つ。

- 対応するチェーン（Symbol または NEM）。
- Mainnet / Testnet などのネットワーク役割。
- 対象を一意に識別し、ペイロード、アカウント、プロファイルと照合するためのネットワーク識別情報。
- そのネットワークに対応するアドレス、トランザクションおよび署名規則を適用するための文脈。

ネットワーク文脈を要求へ申告または通信経路する生成主体は SDK、Web アプリ、dApp または受け渡しクライアントとする。Relay とブロックチェーンノードはネットワークメタデータの信頼されていないな搬送元・観測元または候補提供元にはなり得るが、ネットワークモデルを生成・確定・上書きする生成主体 / 判断権限ではない。署名主体 / チェーン固有の統合がペイロード、選択アカウント、プロファイルおよび対象チェーンと照合して署名主体内のなネットワーク文脈を確定する。未確定、誤ったネットワークまたはチェーンとネットワークの不一致は署名へ進めない。

### 6.2 アカウント

`Account` は、アプリケーションアカウント文脈と wallet-core の暗号学的な識別情報を署名主体 / チェーン固有の統合が検証済みで対応付けた公開投影である。アプリケーションアカウント文脈または wallet-core 識別情報のいずれか単独を共通 `Account` の判断権限とせず、両者の内部スキーマを共通モデルへ取り込まない。

概念上、次の公開情報を持つ。

- チェーンとネットワーク。
- アドレスおよび公開鍵。
- 利用者が識別するための表示情報。

表示情報は署名判断に必要な事実と区別する。公開鍵とアドレスは wallet-core の暗号学的な識別情報を用い、チェーン、ネットワークおよび選択状態を含む対応関係は署名主体 / チェーン固有の統合が検証した値を使う。dApp へ公開するアカウントは利用者が許可した公開情報に限る。

アカウントに関する判断権限は責任ごとに分離する。

| 判断権限                    | 正本となる判断                                                                                                                                                                                                                |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `wallet-core`               | ソフトウェア鍵に対応する暗号学的な公開識別情報、公開鍵、アドレス、鍵識別情報、ストア / 秘密情報処理および生の署名。                                                                                                           |
| アプリケーション / 署名主体 | アプリケーションプロファイルにおけるアカウント関連付け、アカウント選択、表示、許可、アカウントの利用認可および有効なプロファイル / アカウント文脈。アカウント / 許可はプロファイルの固定チェーン / ネットワークと一致させる。 |
| チェーン固有の統合          | 期待される署名主体、署名対象、チェーン / ネットワーク、アドレス / 公開鍵と wallet-core 識別情報の整合性検証。                                                                                                                 |

この分離により、アプリケーションは wallet-core 識別情報から独立した暗号学的な識別情報を発明せず、wallet-core の内部鍵参照をアプリケーションレベルの認可として扱わない。外部要求元のアカウント自己申告、内部鍵参照または wallet-core の署名成功は、アカウントの利用認可の判断権限ではない。

#### 公開識別情報と内部参照

`Account` は、コンポーネント境界を安全に通過させ得る **アカウントの公開識別情報** を表す。チェーン、ネットワーク、アドレス、公開鍵、利用者向けの表示情報など、公開して問題のない識別情報を含む。一方、署名主体 / アプリケーションがプロファイル、許可または wallet-core の鍵枠を内部で解決するための **アカウントの内部参照** は、`Account` の公開識別情報と同一視しない内部文脈である。

アカウントの内部参照について、次を原則とする。

- 秘密鍵そのものではない。
- 秘密鍵、ニーモニック、シードまたは復号された秘密情報を導出可能な情報ではない。
- 外部 Web アプリ、dApp または要求元が任意指定して直接鍵を選択できる対応能力ではない。
- 署名主体の信頼境界内で、現在のプロファイル、許可、アカウントの識別情報および署名文脈と照合して解決・検証する。
- 外部へ公開する必要がない場合は、SDK の公開結果、Relay、dApp または Web アプリへ渡さない。

内部参照の形式、永続化方法および鍵枠との対応は下位設計へ委譲する。外部要求元が提示した参照は、署名主体が補助情報として検証できる場合を除き、アカウント選択や認可の判断権限とは扱わない。

`Account` に次を含めない。

- 秘密鍵
- ニーモニック
- シード
- プロファイルパスワード
- 復号されたウォレットストア秘密情報
- それらを復元できる秘密情報または秘密情報の代替値

アカウントは、選択されたことだけで署名権限を意味しない。署名ごとにプロファイル内の文脈、呼び出し元、許可、チェーン、ネットワーク、対象および明示的承認と対応付ける。Symbol / NEM のチェーン固有のアカウント / 鍵識別情報を一つの共通秘密鍵識別情報として扱わない。

### 6.3 SigningRequest

`SigningRequest` は、一つの署名判断に必要な要求文脈、呼び出し元、セッション、プロファイル内の文脈、操作、アカウント、チェーン、ネットワークおよび署名対象を結び付けた論理単位である。トランザクション署名とメッセージ署名を同じ名前で曖昧に扱わず、`request type` または操作により署名の意味と検証経路を区別する。

#### 含める概念

- **要求識別情報 / 対応付け**: 要求と応答を対応付け、重複・差し替え・別要求への流用を検出する識別情報。
- **バージョン**: 要求モデル / プロトコルコンセプトの解釈に必要なバージョン文脈。
- **要求型 / 操作**: トランザクション、メッセージ、または下位仕様で定義された署名操作の意味。連署署名、アグリゲート、マルチシグの公開範囲は各チェーン / SDK 仕様に従い、未確定の操作をここで追加しない。
- **チェーン / ネットワーク**: 署名対象とプロファイル / アカウントが属する対象。チェーンとネットワークは別々に確認する。
- **プロファイル内のセキュリティ文脈**: アプリケーションプロファイル、固定プロファイルチェーン / ネットワーク、有効なプロファイル / アカウント関連付けおよび署名主体内のな許可 / 認可文脈。公開要求フィールドではない。
- **署名対象 / トランザクションペイロード**: 実際に署名するトランザクション、アグリゲート、連署署名対象、メッセージまたはチェーン固有の対象。表示用要約ではなく、署名の入力となる対象そのものを指す。
- **オリジン / 要求元 / 呼び出し元文脈**: Web ではブラウザが観測したオリジン・タブ / フレーム / 文書等、モバイルでは検証済み受け渡し送信元等。外部が記載した名称だけで検証済み呼び出し元とはしない。
- **有効期限 / 鮮度**: 要求の作成時点、期限、ノンス、世代等、鮮度とリプレイ防止に必要な概念。具体的な表現や期間は下位仕様へ委譲する。
- **アカウント選択情報**: 利用者が選択または許可したアカウントの公開識別情報、期待される署名主体、選択要求または署名主体内のな内部参照。内部参照は署名主体 / アプリケーション内部の解決用文脈であり、外部 SigningRequest、SDK 公開 API、Relay または dApp 向け応答の公開識別情報と同一視しない。要求元が任意のアカウントへ切り替える権限を持つことを意味しない。
- **署名文脈**: セッション、許可対象範囲、プロトコル / 対応能力、トランザクション文脈、メッセージの目的 / ドメイン / ノンス等、対象操作の署名判断に必要な文脈。プロファイル、アカウント、チェーン / ネットワーク、承認、認証、署名可能な状態へのロック解除およびアカウントの利用認可と同じ文脈に結び付けする。
- **受け渡し参加者 / 受信者文脈**: 適用される受け渡しにおける意図した受信者 / 参加者、必要な端末または署名主体内の識別情報、受け渡しセッション / 世代、および応答チャネル / 方向。公開フィールドの追加を意味せず、要求 / 応答の相関と受信者の正当性を確認するための概念文脈とする。

#### 生成・消費・検証

SDK、Web アプリまたは受け渡しクライアントは要求の生成主体である。Relay は要求の意味上の生成主体ではなく、内容を解釈しない通信経路である。ブラウザ拡張機能またはモバイル署名主体は要求の利用主体であり、同時に呼び出し元、プロファイル内の文脈、許可、チェーン / ネットワーク、アカウント、対象、鮮度および対応能力の検証器である。署名主体は、同一プロファイル内の文脈に対する共通署名判定条件を成立・再確認した場合だけ wallet-core を呼び出し、署名可否についての信頼された判断権限となる。

署名主体は要求に含まれる自己申告値を検証前に信頼せず、必要な文脈と `TransactionSummary` を対象から導出する。要求が不完全、期限切れ、重複、改ざん、未対応の、誤ったネットワーク、誤った署名主体または解析不能である場合は署名しない。

署名主体は署名前検証でプロファイル内の文脈、認証、署名可能な状態へのロック解除、対象プロファイル / チェーン / ネットワーク / アカウントに対するアカウントの利用認可および利用者による明示的な承認の成立を確認し、wallet-core 呼び出しと結果検証に同じ文脈を引き継ぐ。これらの条件を要求の公開自己申告フィールドで成立させることはない。

#### 並行する要求分離

各 `SigningRequest` は独立したセキュリティ / ライフサイクル単体とする。複数要求が同時に存在する場合も、各要求は少なくとも次の文脈を独立して保持し、別要求と共有・合成・流用しない。

- 要求識別情報、呼び出し元 / 送信元文脈、ブラウザのタブ / フレーム / 文書またはモバイルの受け渡し送信元。
- セッション、許可文脈、アプリケーションプロファイル、アカウント、チェーン / ネットワーク、操作、署名対象および鮮度。
- 承認、認証、署名可能な状態へのロック解除、アカウントの利用認可、wallet-core 結果、応答受信者および配送状態。

要求 A の呼び出し元、プロファイル / アカウント、承認、認証、認可、対象または結果を要求 B に使ってはならない。遅延した / 古くなった結果は元要求以外へ再対応付けせず、元の応答受信者が有効でない場合も別要求へ配送しない。requestId 単独、通信経路セッション、Relay 世代または SDK インスタンスはこの分離のセキュリティ判断権限ではない。ブラウザの複数タブ / フレームとモバイルの複数ディープリンク / Relay 受け渡しを同じ原則で分離する。具体的なキュー、ロック、状態遷移および並行処理アルゴリズムは下位設計へ委譲する。

### 6.4 SigningResponse

`SigningResponse` は SigningRequest に対する処理結果であり、署名が生成されたか、利用者が拒否したか、処理が失敗したか、または処理結果自体を確定できないかを区別する。要求 / 応答の配送成否は、署名生成の成否とは別の通信経路結果として扱う。

#### 結果の状態

- **成功**: 署名主体が同一呼び出し元、プロファイル、アカウント、チェーン / ネットワーク、操作、対象および鮮度文脈に対して4条件を成立・再確認した後、承認済み対象を wallet-core で処理し、返された署名結果とその文脈を検証できた状態。
- **利用者拒否済み**: 利用者が明示的に拒否した状態。署名成功ではなく、署名結果を伴わない終端結果とする。
- **失敗**: 検証、未対応の、セキュリティ、認証、wallet-core、ネットワークまたは内部処理などにより処理失敗が確定した状態。単に配送状態や処理結果を確定できない場合を `failed` に畳み込まず、通信経路 / Relay 失敗や `RESULT_UNKNOWN` とも区別する。
- **`RESULT_UNKNOWN`（結果不明）**: 署名主体が処理した可能性、署名した可能性または利用者が判断した可能性はあるが、成功、利用者拒否済み、失敗のいずれかを安全に確定できない状態。成功として返さず、同一要求の自動再署名を行わない。

`DELIVERY_UNKNOWN` は SigningResponse の結果状態ではなく、要求または応答の配送処理結果の区分である。送信後の接続断、peer からの配送確認不能または応答配送完了の確認不能など、配送状態を確定できない場合を示す。署名生成が確定済みなら、概念上は `success` と `DELIVERY_UNKNOWN` を併記できるが、同じ対象の再署名を開始せず、既存結果の再送・照会だけを候補とする。要求の配送が不明な場合も、未送信・失敗と推測して同じ要求を自動再送しない。

`RESULT_UNKNOWN` は処理結果そのものの不明、`DELIVERY_UNKNOWN` は配送状態の不明であり、処理失敗が確定した `failed` と同一視しない。これらの状態からの再送、再照会、冪等性および再試行の具体的な契約は下位プロトコル設計へ委譲する。

#### 含める概念

- 元要求識別情報 / 対応付け、呼び出し元 / 送信元文脈、プロファイル内の文脈および鮮度。
- 操作、署名主体識別情報、アカウント、チェーン、ネットワーク、承認、認証、署名可能な状態へのロック解除およびアカウントの利用認可の検証済み文脈。
- 適用される受け渡しの意図した受信者 / 参加者、端末または署名主体内の識別情報、セッション / 世代、応答チャネル / 方向、および応答配送文脈。
- 成功の場合に限る署名、署名済みトランザクション、連署署名または対象操作に対応する結果。
- トランザクション / アグリゲート / 親 / マルチシグ識別情報、メッセージ識別情報、対象ダイジェスト等、元対象と結果を独立検証するための結果メタデータ。
- 利用者拒否済み、キャンセル済み、期限切れまたは失敗の場合のエラー / 失敗意味。詳細な秘密情報や不要な内部状態は含めない。

署名主体は wallet-core の返却値をそのまま外へ転送せず、同じプロファイル内の文脈、呼び出し元 / 送信元文脈、対象および4条件の成立文脈との対応を結果検証で確認してから応答を生成する。SDK は応答を元要求とその応答受信者へ相関付けて Web アプリへ返す。遅延した / 古くなった結果を別要求へ返してはならない。dApp は通信経路の成功だけを信頼せず、受け取った署名 / 署名済みペイロードを元要求と独立に検証する。具体的な署名表現、署名済みペイロード、ハッシュおよび連署署名の形式は下位仕様へ委譲する。

#### キャンセルと終端結果

キャンセルは SigningRequest に対するライフサイクル操作であり、同じ要求識別情報と、適用される呼び出し元 / 送信元、セッション / 世代、受信者 / 参加者、チャネル / 方向、操作、対象および鮮度の結び付け文脈に対してだけ発行・検証する。キャンセルの発行主体は、該当するライフサイクル境界の判断権限（利用者、dApp、署名主体、プラットフォームまたは通信経路）に限り、SDK のローカル待機終了だけでは署名主体側のキャンセル完了を意味しない。具体的な API、受領確認フィールドおよび通信経路は下位仕様へ委譲する。

キャンセルの共通結果は、少なくとも次の意味を失わない。キャンセル要求の受理、拒否または既に終端であることを、同じ要求識別情報に対する受領確認 / 終端応答として扱う。署名開始前にキャンセルが受理され、署名を開始していないことを署名主体が確定できる場合は `CANCELLED` とする。`SIGNING` と競合し、署名生成自体の成否を確定できない場合は `RESULT_UNKNOWN` とし、署名が生成されていないと推測しない。署名生成の不成立を確定できる場合だけ `CANCELLED` とする。既知の署名成功後のキャンセルは既存結果を取り消さず、応答配送が不明なら `SUCCEEDED` と `DELIVERY_UNKNOWN` を維持する。期限切れ、タイムアウト、利用者拒否済みおよび確定失敗はキャンセルと自動変換しない。

`CANCELLED`、`RESULT_UNKNOWN`、`SUCCEEDED + DELIVERY_UNKNOWN` およびその他の終端結果は相互に潰さず、終端状態を再発、同じ要求の再認証・再署名または自動再署名の根拠にしない。

### 6.5 TransactionSummary

`TransactionSummary` は、署名主体の確認 UI 等で利用する、人間が署名対象を判断するための概要である。これは署名対象を表現する補助的な導出されたモデルであり、署名対象の真正性を証明するモデルではない。

対象に適用可能な範囲で、次の概念を含み得る。

- トランザクション型、バージョン、チェーン、ネットワーク。
- 送信者、期待される署名主体、受信者。
- 数量、mosaics / 資産、手数料。
- メッセージ、期限、鮮度。
- アグリゲート、埋め込み / 内部トランザクション、親、マルチシグ文脈。
- 連署署名要求、既存署名 / 連署署名。
- 権限・メタデータ・名前空間・アカウント状態等の変更。
- 警告、未検証の補助情報および署名主体が確認できない事項。

署名主体は署名対象をチェーン固有のに解析 / 検証し、確認に必要な情報を可能な限り対象から導出して要約を生成する。Web アプリ、SDK、Relay、ノードまたは外部 API が提供した要約、表示文言、アプリ名、アイコンまたは説明だけを信頼して署名してはならない。外部要約と実ペイロードが不一致の場合は、安全側に失敗する。必要な情報を解析・表示できない場合、警告の表示だけで迂回せず署名しない。

トランザクション型ごとの完全な表示項目、画面配置、警告の文言およびアグリゲート / マルチシグの表示規則は、本書の下位にあるチェーン固有の / プラットフォーム仕様で定める。

### 6.6 エラー

`Error` は、コンポーネント境界を越えて安全に失敗の意味を伝えるための概念モデルである。公開される分類は、再試行や利用者への案内を安全に判断できる粒度とし、秘密情報、復号データ、秘密鍵、ニーモニック、パスワード、生のペイロードの不要なダンプ、内部スタック追跡を含めない。

エラーの意味は、広い分類へ集約しても下表の区別を失わない。各行は主な発生責任境界を示す概念上の追跡先であり、具体的な公開コード、番号、スキーマ、retryability またはタイムアウトを定めるものではない。

| 失敗の意味                                    | 意味                                                                                                                                                         | 主な発生責任境界                             |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------- |
| 無効な要求                                    | 要求、呼び出し元 / 送信元、文脈、ペイロード、対象、アカウントまたはチェーン / ネットワークの不正・不整合で、署名判断の入力として受け付けられない。           | 署名主体 / 各アダプター                      |
| 未対応の                                      | 操作、トランザクション型、メッセージ形式、バージョン、チェーン / ネットワークまたは対応能力が対象外、未対応または解釈不能である。                            | 署名主体 / チェーン固有の統合 / 対応能力境界 |
| 利用者拒否済み                                | 利用者が信頼された UI で署名を明示的に拒否した。署名結果を伴わない。                                                                                         | 署名主体の信頼された UI                      |
| キャンセル済み                                | 利用者、dApp、署名主体、プラットフォームまたは通信経路が処理を取り消した。利用者が拒否したことを意味しない。                                                 | 要求ライフサイクル境界                       |

| 認証失敗                                      | 利用者認証または要求固有の認証が成立しない、失敗する、または確認できない。                                                                                   | 署名主体の認証境界                           |
| アカウントの利用認可失敗                      | 対象プロファイル / チェーン / ネットワークにおける対象アカウントの利用認可が成立しない、失効した、または確認できない。                                       | アプリケーション / 署名主体                  |

| ロック済み / 署名可能な状態へのロック解除失敗 | 署名主体がロック済み、または署名可能なロック解除文脈を成立・維持できない。通常の `UNLOCKED` や wallet-core パスワード / ストア検証の成功だけでは解消しない。 | 署名主体ホスト / ライフサイクル境界          |
| リプレイ / 重複                               | 使用済み、重複、遅延、衝突または過去文脈の要求として拒否された。                                                                                             | 署名主体 / Relay / 各アダプター              |
| wallet-core 失敗                              | ウォレットストア、ソフトウェア鍵、バインディング、秘密情報処理または wallet-core の署名契約が失敗した。                                                      | wallet-core 境界                             |
| 署名失敗                                      | 署名主体の署名処理の調整、対象結び付けまたは結果検証が署名成功を確定できず処理失敗が確定した。wallet-core 失敗と区別する。                                   | 署名主体 / wallet-core 境界                  |
| 通信経路失敗                                  | 要求 / 応答の通信経路、接続または配送処理が失敗した。署名結果を意味しない。                                                                                  | SDK / プラットフォームアダプター             |

`RESULT_UNKNOWN` は署名生成そのものの結果を成功、利用者拒否済み、キャンセル済みまたは確定失敗のいずれとも安全に判定できない状態であり、主に署名主体と wallet-core 呼び出しの境界で発生し得る。`DELIVERY_UNKNOWN` は確定済み結果または要求 / 応答が受信者へ届いたかを判定できない配送処理結果の区分であり、主に SDK、プラットフォームアダプターまたは Relay の配送境界で発生し得る。`RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` はエラーの確定失敗とも、互いとも同一視しない。

利用者拒否とキャンセル済み、期限切れと無効な要求、認証失敗とアカウントの利用認可 / 許可失敗、ロック済みと wallet-core 失敗、wallet-core / 署名失敗と通信経路 / Relay 失敗は、利用者案内、状態保持および安全な分岐のために意味上区別する。確定失敗、`RESULT_UNKNOWN` または `DELIVERY_UNKNOWN` のいずれも自動再署名の根拠にしない。原因を確認せず `USER_REJECTED`、`CANCELLED`、`FAILED`、`RESULT_UNKNOWN` または `DELIVERY_UNKNOWN` の間で自動変換しない。

## 7. インターフェース責務

### 7.1 SDK ↔ 署名主体

SDK は Web アプリの操作を SigningRequest として組み立て、署名主体が検証できる呼び出し元、セッション、許可、プロファイル内の文脈、チェーン / ネットワーク、アカウント、対象および鮮度の文脈を維持して渡す。プロファイル内の文脈は公開プロファイルフィールドの自己申告ではなく、署名主体が有効なプロファイルから解決する。署名主体は SDK の自己申告を最終判断権限とせず、受け取った要求を検証し、署名主体管理の確認 UI で承認・拒否を取得し、共通4条件を再確認したうえで wallet-core と連携して SigningResponse を返す。

SDK は通信経路の差異を隠蔽し得るが、署名主体の承認、意味上の内容検査、署名ごとの認証、秘密情報処理または安全側での終了を代替しない。SDK が受け取った応答は対応付け、状態、署名 / 署名済みペイロードの対応を確認してから Web アプリへ返す。

### 7.2 Web アプリ ↔ ブラウザ拡張機能

Web アプリは外部要求元として SDK / Provider を通じて要求する。Web アプリが提示するオリジン、アプリ名前、要約、アカウント、ネットワークまたは署名方式は、ブラウザ拡張機能にとって信頼されていない入力である。

ブラウザ拡張機能の特権を持つ層は、ブラウザが観測した送信者、オリジン、タブ / フレーム / 文書文脈と要求を同一呼び出し元文脈として対応付け、有効なプロファイル / アカウント、接続許可、チェーン / ネットワーク、期限、対象および操作を検証する。コンテンツスクリプト、Provider およびページ文脈は経路選択 / 橋渡しの境界であり、秘密情報を保持せず、呼び出し元、プロファイルまたはアカウントの利用認可の最終判断権限ではない。

拡張機能は自ら管理する確認領域で、対象から導出した要約を表示し、明示的な承認または拒否を取得する。返却された応答は Web アプリが独立に検証すべきものであり、拡張機能から返ったことだけで署名の正当性を証明したとは扱わない。

### 7.3 Relay ↔ モバイル

SDK / 受け渡しクライアントは Relay を通じてモバイルに渡す要求 / 応答を E2E のエンベロープとして扱う。Relay はエンベロープの構造、サイズ、期限、セッション / 世代、認証および状態遷移など、意味を解釈しない通信経路条件だけを検証し、必要な範囲で一時的に配送する。

Relay は署名要求の内容を独自判断で変更しない。トランザクション / メッセージの意味を解釈せず、表示、利用者の承認・拒否、署名可否、署名、アナウンスまたはノード選択を担わない。Relay から届いたデータはモバイルがすべて信頼されていない入力として再検証する。

モバイル署名主体は検証済み受け渡し送信元、呼び出し元、受け渡しセッション、要求完全性、期限、有効なプロファイル / アカウント、チェーン / ネットワーク、対象、要約、許可および対応能力を検証し、アプリ自身の UI と認証で承認を取得する。Relay の配送成功、メタデータまたは状態復旧だけで承認済み・署名済みとみなしてはならない。プロファイル内の文脈と受け渡し送信元が同じ要求文脈に結び付けされない場合は処理しない。具体的な E2E エンベロープ、HTTP / Redis、ディープリンクおよび世代の形式は [受け渡し仕様](../specifications/web-transaction-handoff-spec.md) と Relay の下位設計へ委譲する。

### 7.4 ブラウザ拡張機能 ↔ wallet-core

ブラウザ拡張機能は、共通4条件とプロファイル内の文脈に結び付けされた利用者承認済み対象、アプリケーションアカウント文脈および検証済み wallet-core 暗号学的な識別情報を、固定された wallet-core 外部契約に従ってアダプターへ渡す。署名前に確認した対象と渡す生の対象の一致、プロファイル、チェーン / ネットワーク、期待される署名主体、署名主体識別情報、操作、許可、アカウントの利用認可および4条件の成立状態を拡張機能が再確認する。

wallet-core はウォレットストア、鍵識別情報、秘密情報の処理、チェーン固有の鍵および生バイト署名を担い、結果、エラーまたは診断情報を返す。wallet-core に呼び出し元の信頼、利用者の UI 承認、dApp 許可、トランザクションの利用者向け意味解釈を委譲しない。

拡張機能は wallet-core の結果を同じプロファイル内の文脈、対象、アカウント、チェーン / ネットワーク、4条件の成立文脈および要求対応付けに対応付けて検証し、検証不能な結果は成功として返さない。バインディング、FFI、WASM / ネイティブ、秘密情報バイトの一時ライフサイクル、具体的な入力 DTO は wallet-core の外部契約と後続設計で決定する。

### 7.5 モバイル ↔ wallet-core

モバイルアプリと wallet-core の責任分担は、ブラウザ拡張機能と同じ共通境界を持つ。モバイルアプリは外部要求の受信、プロファイル / アカウント関連付け、有効なプロファイル / アカウントの表示・選択、チェーン / ネットワーク、確認 UI、利用者認証、承認対象の結び付け、OS 統合およびライフサイクルを担う。wallet-core は暗号学的な公開識別情報、秘密情報、ウォレットストア、鍵識別情報および生の署名を担う。モバイルアプリは共通4条件と検証済み受け渡し送信元を同じ要求文脈に結び付けして再確認する。

OS の Keychain / Keystore / 安全な Enclave / StrongBox 等の保護能力を wallet-core の責任と同一視しない。モバイルのプロセス、バックグラウンド、再起動または OS 終了で文脈が失われた場合、古い承認を無条件に復元して wallet-core を呼び出さない。具体的なバインディングホスト統合、OS 保護およびバックアップ / 移行は [モバイルアプリ要件](../requirements/mobile-app.md) と既存の未決事項に従う。

### 7.6 SDK ↔ MosaicLynx の共通インターフェースコンセプト

SDK が MosaicLynx に対して要求する共通の概念接点は、次の範囲に限定する。

- 対応対応能力とチェーン / ネットワークの確認。
- 接続、許可された公開アカウントの取得、接続解除または許可撤回。
- トランザクション署名とメッセージ署名の SigningRequest 生成・受け渡し。
- SigningResponse の成功、利用者拒否済み、キャンセル済み、期限切れ、失敗、`RESULT_UNKNOWN` の区別、および要求 / 応答の配送結果。
- キャンセル要求 / 受領確認と、署名前・`SIGNING` 中・既知成功後の結果優先順位。キャンセルの具体 API、通信上のスキーマおよび並行処理は下位仕様へ委譲する。
- 受け渡しの意図した受信者 / 参加者、端末または署名主体内の識別情報、セッション / 世代、応答チャネル / 方向の要求 / 応答結び付け。受信者、端末、チャネル、世代または方向の不一致は安全側での終了とする。
- 無効な要求、未対応の、認証失敗、アカウントの利用認可失敗、許可失敗、ロック済み / 署名可能な状態へのロック解除失敗、リプレイ / 重複、wallet-core / 署名失敗、通信経路 / Relay 失敗、内部失敗の意味を失わない安全な結果。
- `RESULT_UNKNOWN`（署名生成結果の不明）と `DELIVERY_UNKNOWN`（結果配送処理結果の区分の不明）の分離。いずれも失敗の詳細や自動再署名の根拠へ暗黙変換しない。

これらは Web アプリから観測できる共通の意味であり、各操作の API 名、戻り値の通信上の形式、通信経路選択、トランザクション組み立て、アナウンス、ノードアクセスまたは UI を本書で確定するものではない。SDK アダプターはプラットフォーム間で意味をそろえるが、プラットフォーム固有の呼び出し元検証や署名主体の最終判断を抽象化の中に隠して省略してはならない。

## 9. セキュリティ考慮事項

詳細は [共通セキュリティ設計書](./security-design.md) に委譲する。本書における共通インターフェースの適用上、次を維持する。

- 秘密情報を要求、応答、アカウント、要約、エラー、通信経路、URL、ログ、警告、診断または外部 UI に含めない。
- 署名主体が対象全体を解析・検証・表示できない場合は署名しない。未知のトランザクション型、メッセージ形式、チェーン / ネットワーク、署名方式を警告だけで許可しない。
- 接続許可、セッション、ロック解除済み状態、対応能力、Relay 配送成功または過去の認証を、署名ごとの承認・認証の代替にしない。
- `1 request = 1 confirmation = 1 authentication = 1 signing operation` の対応を維持し、別要求、別プロファイル、別アカウント、別チェーン / ネットワーク、別操作または別対象に文脈を流用しない。
- 要求や文脈の変化、プロファイルライフサイクル消失、リプレイ、重複、結果不明を検出した場合は、古い認可を再利用せず安全側に終了する。
- 意図した受信者 / 参加者、端末または署名主体識別情報、セッション / 世代、応答チャネル / 方向が要求 / 応答結び付けと一致しない場合は、配送成功にかかわらず安全側に終了して終端する。Relay / 通信経路の受領確認は承認、署名成功または配送完了の代替ではない。
- `USER_REJECTED`、`SIGNING_FAILED`、`RESULT_UNKNOWN` および `DELIVERY_UNKNOWN` を成功または相互に別の状態へ変換しない。確定失敗、`RESULT_UNKNOWN` または `DELIVERY_UNKNOWN` の後に同一要求を自動再実行・再署名せず、自動代替経路で安全境界を迂回しない。具体的な再送・再照会は下位プロトコル設計へ委譲する。

### 9.1 共通署名判定条件不変条件

署名主体は、同一の呼び出し元、プロファイル、アカウント、チェーン / ネットワーク、操作、署名対象および鮮度文脈に対して、次の4条件をすべて成立させ、署名直前に再確認した場合に限り、承認済み対象を wallet-core へ渡し、結果検証を通過した成功結果を生成できる。

1. 認証。
2. 署名可能な状態へのロック解除。
3. 対象プロファイル / チェーン / ネットワーク / アカウントに対するアカウントの利用認可。
4. 利用者による明示的な承認。

4条件の成立責任は署名主体 / アプリケーションホストにあり、要求の公開自己申告フィールドで成立させない。対応能力はサポート、利用可能性またはプロトコル互換性を表すだけであり、認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認または署名判断権限を意味しない。接続、許可、セッション、通常の `UNLOCKED`、前回認証、SDK 状態、Provider 状態、Relay メタデータ / 配送、dApp 自己申告、wallet-core パスワード / ストア検証および wallet-core 署名結果も4条件の代替ではない。

署名前検証と結果検証は、同一の4条件と結び付け文脈が継続していることを確認する。いずれかの条件または文脈が未成立、失効、ロック済み、古くなった、不明または不整合である場合、署名主体は wallet-core を呼び出さず、成功結果も返さない。

### 9.2 並行する要求セキュリティ上の不変条件

各要求は独立したセキュリティ / ライフサイクル単体であり、複数要求の間で呼び出し元 / 送信元、プロファイル、アカウント、許可、承認、認証、署名可能な状態へのロック解除、アカウントの利用認可、対象、wallet-core 結果または応答受信者 / 配送状態を共有・合成・流用しない。ブラウザの複数タブ / フレーム / 文書とモバイルの複数ディープリンク / Relay 受け渡しにも適用する。要求識別情報、通信経路セッション、Relay 世代または SDK インスタンスは分離のセキュリティ判断権限ではなく、遅延した / 古くなった結果を別要求へ再対応付けしてはならない。

## 10. バージョン管理 / 拡張性

要求、応答および受け渡しコンセプトはバージョン文脈により、受信側が解釈可能な契約かを確認できるようにする。バージョン管理の基本方針は次のとおりである。

- バージョンの意味、対応可能な操作、チェーン / ネットワーク、メッセージ形式および対応能力を受信側が確認する。
- 対応能力はサポート、利用可能性またはプロトコル互換性の確認に限り、認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認または署名判断権限の成立を表さない。
- 必須の意味を解釈できないバージョン、不明操作、不明形式または互換性のない対応能力は安全側での終了とする。
- 追加情報を無視できるかどうかは、意味を変えず安全に無視できることを下位仕様で確認する。未知フィールドを理由なく意味解釈したり、別のフィールドへ代替したりしない。
- 新しいバージョンや操作の追加で、チェーン / ネットワークの区別、秘密情報の分離、要約とペイロードの一致、明示承認および結果対応付けを弱めない。
- バージョン差異や対応能力不一致を、別の署名操作、生の署名または通信経路へ暗黙に代替経路しない。

具体的なバージョンフィールド、番号体系、前方互換性 / 後方互換性、非推奨化、対応能力協議および移行は [SDK 要件](../requirements/sdk.md)、受け渡し仕様、チェーン固有の仕様および各プラットフォームの下位設計で決定する。

## 11. 下位設計への委譲

本書で定めた概念モデルを実装可能な契約へ落とす際、次を下位設計・仕様へ委譲する。

- JSON プロパティ、JSON スキーマ、TypeScript インターフェース、Rust struct、DTO、CBOR スキーマ。
- JSON / CBOR 等のエンコーディング、バイナリの所有権、hex / Base64 の選択およびバイト列の表現。
- SDK の具体的 API 名、Provider 契約、呼び出し元結び付け、通信経路選択およびエラー対応付け。
- ブラウザ拡張機能のメッセージイベント、`window.postMessage`、Chrome API、サービスワーカー、保存領域、具体的な UI。
- モバイルのディープリンク / 普遍的な Link / App Link / Intent、OS API、安全な保存領域、認証、ライフサイクル、画面およびホストバインディング。
- Relay の HTTP エンドポイント、REST / WebSocket メッセージ、内容を解釈しないエンベロープ、E2E 暗号方式、TTL、Redis、認証、保存領域、頻度上限および通信上のプロトコル。
- wallet-core の Rust / バインディング API、FFI、WASM / ネイティブ、ウォレットストア、秘密情報ライフサイクル、暗号処理、鍵導出および署名バイト列。
- Symbol / NEM のトランザクション型、バージョン、スキーマ、正規化、ハッシュ、署名バイト列、アグリゲート / マルチシグ / 連署署名の完全な解析範囲。
- トランザクション型ごとの完全な TransactionSummary、確認 UI、警告および表示順。
- エラーコードの完全な catalogue、番号体系、公開文言、retryability および通信経路状態。

## 12. 対象外

本書は次を決定しない。

- 完全な JSON スキーマ、JSON プロパティの完全な定義、TypeScript インターフェース、Rust struct または CBOR スキーマ。
- JSON / CBOR のエンコーディング詳細、hex / Base64 の選択。
- HTTP エンドポイント、REST API、WebSocket メッセージ形式、Relay 通信上のプロトコルまたはディープリンク URI スキーマ。
- ブラウザ拡張機能のメッセージイベント名、`window.postMessage` の具体的形式。
- エラーコードの完全な一覧・番号体系。
- トランザクション型ごとの完全な解析仕様、完全な確認 UI 仕様。
- Plugin 基盤、一般的なメッセージ bus、RPC 基盤、通信経路プロトコルの新規導入。
- SDK API の詳細設計、UI 詳細設計、wallet-core 内部 API の再設計。

これらの対象外は、共通の責任境界、信頼、検証および安全側での終了の原則を省略できることを意味しない。

## 13. 既存の未決事項

本書は新しい未決事項を追加しない。次の既存の未決事項は、共通モデルの意味を変えずに下位工程で解決する。

- SDK の具体的なバージョンポリシー、呼び出し元 / オリジンとの結び付け、通信経路選択、トランザクション組み立ておよびアグリゲート / 連署署名の公開範囲（[SDK 要件の未決事項](../requirements/sdk.md#15-未決事項)）。
- モバイルの受信方式、OS 保護と wallet-core バインディング、プロセスライフサイクル、バックアップ / 移行（[モバイルアプリ要件の未決事項](../requirements/mobile-app.md#7-スマホアプリ固有の未決事項)）。
- アプリケーション / コア識別情報対応付け、三つのバックエンド、エラー対応付けは Wallet-core 統合で確定済み。OS 保護・移行と将来秘密情報を含まない初期設定は別の後続契約を必要とする。
- Relay 障害時の外部から観測できる失敗境界と、結果不明後の既存結果の照会・再配送契約（[Relay 要件の未決事項](../requirements/relay.md#9-relay-固有の未決事項)）。
- Symbol / NEM の対応トランザクション型 / バージョン、アグリゲート / マルチシグ / 連署署名、メッセージ形式の公開範囲と表示受け入れ条件。

これらが未決であっても、秘密情報の分離、署名主体による意味上の検証、利用者の明示承認、要約と実ペイロードの一致、Relay の非署名責任および安全側での終了の原則は変更しない。
