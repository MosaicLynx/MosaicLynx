# MosaicLynx Concept Sheet

## 1. 概要

MosaicLynx は、Symbol / NEM の dApp を利用する一般ユーザーが、署名要求の内容と対象ネットワークを確認したうえで、安全に署名できる環境を提供する Signer（署名機）である。

最初にブラウザ拡張機能で中核価値を提供し、その後 Android アプリ、iOS アプリ、Relay へ段階的に展開する。4つの段階を全体 v1 のマイルストーンとし、Relay 完了を全体 v1 完了の基準とする。

本書は、要件定義・設計・実装へ進む前に、プロジェクトの目的、対象、責任境界、制約、未決事項を固定するためのコンセプトである。

### v1、milestone、release の定義

- `MosaicLynx v1` は、ブラウザ拡張機能、Android アプリ、iOS アプリ、Relay の4つの milestone 全体を指す。
- 実施順序は次の順で固定する。
  1. ブラウザ拡張機能
  2. Android アプリ
  3. iOS アプリ
  4. Relay
- 各 milestone は、MosaicLynx v1 全体とは別の個別 milestone / release 単位として扱える。
- Relay milestone の完了を、MosaicLynx v1 全体の完了とする。
- `Extension MVP` などの名称は個別 release を指す場合があり、MosaicLynx v1 全体と同義にはしない。

## 2. 背景

Symbol / NEM の dApp は、トランザクションやメッセージへの署名を利用者へ求める。署名には秘密情報が必要だが、その秘密情報を Web ページや dApp に渡すことはできない。また、利用者は署名する対象、チェーン、ネットワーク、発生し得る結果を確認してから承認する必要がある。

既存資料では、Chrome 拡張機能、スマートフォンアプリ、SDK、Relay がそれぞれ異なる責任を持つ前提が示されている。一方、一般ユーザーが複数の提供形態をまたいで同じ安全な署名判断を行えること、dApp 開発者が提供形態の違いを個別に扱わずに済むことは、コンセプトとして整理する必要がある。

## 3. 解決する課題

### 中心課題（課題仮説）

一般ユーザーは dApp から署名を求められた際、秘密情報を Web ページへ渡さずに、何へ署名するのか、どのチェーン・ネットワークが対象なのか、署名によって何が起こり得るのかを判断しにくい可能性がある。

その結果、利用者が次のいずれかを選ばざるを得なくなる可能性がある。

- 署名対象を十分に理解しないまま承認する。
- 秘密情報を dApp や Web ページへ渡す危険な手段へ依存する。
- 正当な dApp の利用であっても、判断できずに利用を中断する。

MosaicLynx は、署名要求を理解・確認できる範囲を示し、利用者が確認して承認または拒否できる Signer を提供する。提供形態の違いを dApp 開発者が個別に扱わずに済むことは、一般ユーザーの一貫した安全な署名体験を支える付随価値として扱う。

現在の利用者調査、問い合わせ、事故記録などによる実証が十分でない部分は、検証前の課題仮説として扱う。

### 付随する課題仮説

- dApp 開発者が、ブラウザ拡張機能、Android アプリ、iOS アプリ、Relay の違いを個別に扱うと、統合や利用者体験が分断される。
- 署名処理、利用者の承認、チェーン固有の理解、秘密情報の保管を同じ責務として扱うと、責任境界を説明しにくくなる。
- Symbol と NEM、Mainnet と Testnet を同じ意味として扱うと、誤った対象への署名につながる。

## 4. コンセプト

MosaicLynx は、一般ユーザーに対して、dApp の署名要求を安全に確認・承認または拒否できる署名環境を提供する。秘密情報を dApp から分離し、ブラウザ拡張機能、スマートフォンアプリ、Relay の提供形態が変わっても、利用者の明示的な判断と責任境界を維持する。

dApp 開発者が提供形態の違いを個別に扱わず、一般ユーザーへ一貫した署名体験を提供できる接点を持つことを支える。

## 5. 想定利用者

### 第一対象：一般ユーザー

Symbol / NEM dApp を利用し、要求されたメッセージやトランザクションへ署名する個人利用者を第一対象とする。

一般ユーザーにとっての中心的な価値は、署名機の内部構造や提供形態を過度に意識せず、提示された署名対象を確認して自分の意思で承認または拒否できることである。

### 主要な協力者：dApp 開発者

dApp へ MosaicLynx を組み込み、提供形態の違いを個別に実装せず、一般ユーザーへ一貫した署名体験を提供したい開発者を主要な協力者とする。dApp 開発者の統合容易性は独立した最終目的ではなく、一般ユーザーの安全な署名判断を支える条件として扱う。

### 提供を支える関係者：運用者

公開 build、release evidence、公開環境を管理する運用者を、提供を支える関係者とする。運用者向けの監査・統制機能を v1 の中心価値には含めない。

### 初期対象としない利用主体

組織利用、カストディ利用、企業向けの監査・統制を第一対象とはしない。将来どの範囲まで保証するかは、将来検討事項として保留する。

## 6. 主な利用シナリオ

### 6.1 一般ユーザーが dApp から署名を求められる

一般ユーザーが Symbol / NEM dApp を利用し、トランザクションまたはメッセージへの署名を求められる。MosaicLynx は、利用者が署名判断を行える形で要求を受け付ける。

### 6.2 一般ユーザーが署名対象を確認する

利用者は、署名機が確認可能と判断した対象と、チェーン・ネットワークなど判断に必要な情報を確認する。内容を理解できない要求や、対象範囲外の要求は署名へ進めない。

### 6.3 一般ユーザーが承認または拒否する

利用者は、自分の意思で署名を承認または拒否する。拒否、判断不能、対象外の場合に、署名結果を返さないことを安全な終了状態とする。

### 6.4 dApp が署名結果を利用する

dApp は受け取った署名結果を独立して確認し、必要なネットワーク処理を自らの責任で行う。MosaicLynx は、dApp に代わって announce や継続的な状態管理を行わない。

### 6.5 提供形態を段階的に広げる

ブラウザ拡張機能で最初の中核価値を確認した後、同じ責任境界を Android アプリ、iOS アプリへ広げ、最後に Relay を提供する。各段階は MosaicLynx v1 内の個別 milestone / release 単位として扱い、Relay milestone の完了を MosaicLynx v1 全体の完了とする。

## 7. 提供価値

| 対象               | 提供する価値                                                                     |
| ------------------ | -------------------------------------------------------------------------------- |
| 一般ユーザー       | 秘密情報を dApp や Web ページへ渡さず、署名の意思決定を自分で行える。            |
| 一般ユーザー       | 署名対象、チェーン、ネットワークを確認し、意図しない署名を避けやすくなる。       |
| dApp 開発者        | 署名手段の違いを個別に扱わず、一般ユーザーへ一貫した署名体験を提供しやすくなる。 |
| プロジェクト運用者 | Signer、提供形態、Relay、ネットワーク処理の責任を分けて説明・管理できる。        |

一般ユーザーの安全な署名判断を最優先とし、dApp 開発者と運用者への価値はその実現を支えるものとして扱う。

## 8. コンセプト上の主要機能

コンセプトを成立させるために、MosaicLynx は少なくとも次の能力を持つ。

- dApp からの署名要求を受け付けられる。
- 署名要求を、利用者が判断できる範囲で理解・確認できる。
- 利用者が署名要求を明示的に承認または拒否できる。
- 署名に必要な秘密情報を dApp、Web ページ、Relay へ公開せずに扱える。
- Symbol / NEM と Mainnet / Testnet を曖昧にせず、対象を区別して扱える。
- 承認できない要求、理解できない要求、対象範囲外の要求を安全に終了できる。
- dApp が署名手段の違いを個別に扱わず、共通の署名接点を利用できる方向性を提供できる。
- ブラウザ拡張機能、Android アプリ、iOS アプリ、Relay の段階的な提供において、Signer の責任境界を維持できる。
- dApp が受け取った署名結果を独立して確認できる前提を提供できる。

各能力の外部要求、受け入れ条件、提供方式は要件定義・仕様化で決定する。

## 9. 対象範囲

MosaicLynx が責任を持つ範囲は次のとおりとする。

- 一般ユーザーが dApp の署名要求を確認し、承認または拒否するための Signer の責任。
- 署名に必要な秘密情報を、dApp、Web ページ、Relay から分離して扱う責任。
- 署名要求を理解・確認できる範囲と、確認できない要求を拒否する責任。
- Symbol / NEM と Mainnet / Testnet を区別した署名体験を提供する責任。
- ブラウザ拡張機能、Android アプリ、iOS アプリ、Relay を段階的に整備する全体 v1 の方向性。
- 各提供形態において、利用者の明示的な承認と秘密情報保護を共通の中心原則として維持する責任。

最初の中核価値はブラウザ拡張機能で検証する。Android アプリ、iOS アプリ、Relay は同じ中核価値を広げる後続の v1 マイルストーンとする。

## 10. 非対象範囲

次の事項は、MosaicLynx のコンセプト上の責任範囲に含めない。

- 残高、履歴、トークン、ネームスペースなどの資産管理。
- 署名済みトランザクションの announce、ノード選択、継続的なネットワーク状態管理。
- 利用者の確認を省略した自動署名、永続的な署名許可、理解できない要求のブラインド署名。
- ハードウェアウォレット、コールドウォレット、企業カストディと同等の保証。
- 組織向け監査・統制・カストディ保証を前提とした v1 の提供。
- dApp そのものの企画、開発、運営、利用者獲得。
- Relay による署名対象の意味解釈、署名、ネットワーク処理、長期保管。
- 詳細な API、データ形式、通信方式、暗号方式、状態遷移、実装ライブラリ、テスト手順。
- 「将来便利そう」という理由だけで追加する機能。

組織向け保証の最終的な対象範囲は将来検討事項として保留し、上記の初期非対象範囲を将来の恒久的な禁止事項とは解釈しない。

## 11. 基本原則

### 一般ユーザーの安全な判断を最優先する

機能の便利さや対応範囲の拡大より、一般ユーザーが署名対象を理解し、意思を持って承認または拒否できることを優先する。

### 秘密情報と dApp の責務を分離する

dApp、Web ページ、Relay に秘密情報を公開しない。署名に必要な秘密情報を扱う責任の所在を曖昧にしない。

### Signer は検証・提示・署名判断を支える

利用者へ理解できない raw data の判断を一方的に委ねず、Signer が確認できる範囲を明確にする。確認できない要求は、便利な代替経路で通さない。

### 利用者の明示的な承認を必要とする

署名は、利用者が提示された対象と影響を確認して承認した場合だけ行う。

### チェーンとネットワークを明示的に分ける

Symbol と NEM、Mainnet と Testnet を同じ意味として扱わない。共通化は責任の重複を減らす範囲に留める。

### 外部責任と独立検証を尊重する

dApp は受け取った署名結果を独立して確認し、announce など署名後の処理を担う。MosaicLynx は dApp の責任を肩代わりしない。

### 迷った場合は安全側に倒す

要求の理解、対象の確認、認証、復元に確信がない場合は、署名や復元を進めない。

## 12. 制約

- 最初の提供形態は Chrome 拡張機能とする。Android アプリ、iOS アプリ、Relay は後続の v1 マイルストーンとする。
- 現在のワークスペースに Mobile アプリの実装が存在することを前提にしない。Mobile は計画上の提供形態として扱う。
- Symbol / NEM のチェーン差異と Mainnet / Testnet のネットワーク差異を、要件・仕様・提供形態で明示的に扱う。
- Mainnet は、プラットフォームごとに必要な release evidence、セキュリティ確認、承認が整うまで一般利用可能にしない。未達成時は Testnet 専用とする。
- dApp の署名結果検証とネットワーク処理は外部責任であり、MosaicLynx の責任範囲へ自動的に取り込まない。
- Relay はスマートフォンアプリへ署名要求を受け渡す基盤として扱うが、署名対象の意味解釈や署名そのものの責任を担わない。
- 一般ユーザーを第一対象とし、組織利用やカストディ用途を初期の成功条件にしない。
- 具体的なプラットフォーム機能、公開契約、対応範囲、完了条件は、承認済み要件・仕様なしに追加しない。
- 本コンセプトの MosaicLynx v1、milestone、release の整理を上位のプロダクト方針として扱う。既存仕様書に異なる release 境界の表現がある場合は、後続の要件・仕様整理で本方針に整合させる。

## 13. セキュリティ・プライバシー

### 守る情報

秘密鍵、Mnemonic、Profile password、backup の平文、署名に使う秘密情報、利用者の承認判断を保護対象とする。署名対象やアカウントに関する情報も、必要な範囲を超えて外部へ公開しない。

### 信頼しないもの

dApp、Web ページ、外部からの署名要求、Relay、ネットワークから受け取る入力を、検証前から信頼しない。既存実装、SDK の利便 API、テスト結果だけをプロトコル上の正しさの根拠にしない。

### 責任境界

- Signer は、署名要求を理解・確認できる範囲を判断し、利用者が判断できる情報を提示し、署名前後の要求と結果の対応を保つ責任を持つ。
- 利用者は、Signer が確認・提示した対象と影響を確認し、承認または拒否する責任を持つ。
- dApp は、受け取った署名結果を独立して確認し、必要なネットワーク処理を行う責任を持つ。
- Relay は、スマートフォンアプリへの受け渡しを担うが、署名対象を解釈したり秘密情報を扱ったりする責任を持たない。

具体的な脅威モデル、暗号方式、保存方法、入力検証、通信仕様は要件定義・設計・仕様で決定する。コンセプト段階で安全性の保証範囲を過大に表現しない。

## 15. 未決事項

ここでいう OPEN は、MosaicLynx v1 またはその後続工程において、適切な時期に確認・決定する必要がある事項を指す。

### OPEN-001：中心課題の実在性と現在の回避方法

- 論点: 一般ユーザーが署名対象と秘密情報の境界を判断しにくいという課題が、どの場面でどの程度発生しているか。また、現在どのような手段で回避されているか。
- 未決の理由: 利用者調査、問い合わせ、事故記録、既存署名手段との比較などによる十分な実証がまだないため。
- 決定時期: 要件定義開始時までに、既存手段、想定利用場面、課題仮説を可能な範囲で確認する。十分に確認できない部分は検証前の課題仮説として維持し、必要に応じて要件定義中および初期 milestone でも継続して検証する。OPEN-001 が未完了であることだけを理由として、要件定義全体を停止しない。ただし、未確認の内容は確認済みの事実として扱わない。

### OPEN-002：一般ユーザーが必要とする確認情報

- 論点: 一般ユーザーが署名判断を完了するために、どの情報を確認できる必要があるか。
- 未決の理由: コンセプトでは必要性を示すに留め、表示内容や確認粒度を仕様として先取りしないため。
- 決定時期: 要件定義・利用者検証の段階。

### OPEN-003：4つのマイルストーンの個別完了条件

- 論点: ブラウザ拡張機能、Android アプリ、iOS アプリ、Relay が、それぞれ何を提供できれば個別 milestone / release を完了し、次段階へ進めるか。
- 未決の理由: 実施順序と Relay 完了を MosaicLynx v1 完了とする方針は決まっているが、各段階の外部要求、個別完了条件、次段階へ進む条件、必要な依存関係は未定義である。
- 決定時期: 要件定義の開始時。

### OPEN-005：Mainnet 一般公開の詳細条件

- 論点: release evidence、セキュリティ確認、承認をどの証拠で満たしたと判定するか。
- 未決の理由: Mainnet は証跡・承認ゲートを通過するまで有効化しない方針だが、詳細な受け入れ条件は要件・リリース設計の対象である。
- 決定時期: 各プラットフォームの Mainnet 公開前。

### 将来検討事項

ここでいう FUTURE は、現在は意図的に対象外としており、MosaicLynx v1 の進行・完了や現在の要件定義を妨げない事項を指す。

#### FUTURE-001：組織向け監査・統制・カストディ保証の範囲

- 論点: 一般ユーザー向け提供の後、組織利用、監査、統制、カストディに対してどこまで保証するか。
- 現在の扱い: 組織利用、監査、統制、カストディ保証は MosaicLynx v1 の初期対象外とし、v1 の完了条件には含めない。現在の要件定義の開始・完了を妨げる blocker ともしない。
- 検討時期: 将来の組織向け展開を検討する際に改めて判断する。現在は具体的な機能、要件、保証範囲を決定しない。

## 16. 次フェーズ

本コンセプトシートの承認後、OPEN-001〜OPEN-003およびOPEN-005を確認し、一般ユーザーの中核価値、dApp 開発者が利用しやすい共通の署名接点、各 milestone の責任境界、外部責任、受け入れ可能な成功条件を要件定義へ引き継ぐ。OPEN-001 の確認が完了していない場合も、検証前の課題仮説を明示したまま要件定義を開始できるものとする。
