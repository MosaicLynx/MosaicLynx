# MosaicLynx SDK 要件定義書

## 1. 文書の目的と位置付け

本書は、MosaicLynx を外部アプリケーションおよび Web アプリケーションから利用するための SDK に固有の要求を定める。SDK は MosaicLynx 本体の署名主体ではなく、外部アプリケーションと MosaicLynx の接続・連携を安全かつ一貫した形で扱う統合層として位置付ける。

本書は [MosaicLynx 共通要件](./requirements.md) を SDK の適用範囲へ具体化する補足要件である。署名主体の署名可否、利用者確認、秘密情報の処理および Relay の受け渡し責任を SDK へ移すものではない。

本書で定めないものは、公開 API の型・関数・クラス、データ形式、URL、RPC または WebSocket のメッセージ、ディープリンク形式、暗号アルゴリズム、暗号パラメータ、状態遷移、パッケージ分割、ビルド構成および実装ライブラリである。これらは、承認済み要件を満たす後続の仕様・設計で定める。

### 1.1 要求の表記

- **MUST**: SDK の対象範囲に含まれる場合、満たさなければならない要求。
- **MUST NOT**: SDK が指定された行為または状態を成立させてはならない要求。
- **SHOULD**: 原則として満たすべき重要な要求。満たせない場合は理由と影響を記録する。
- **MAY**: v1 の成立条件ではないが、他の要求に反しない範囲で許容される事項。

## 2. SDK の位置付けと対象利用者

### 2.1 SDK が解決する課題

外部アプリケーションが MosaicLynx を利用する際、ブラウザ拡張機能、将来のモバイルアプリ、Relay など提供形態ごとの差異を個別に実装すると、接続、要求の受け渡し、結果の解釈、失敗処理および安全境界が分断される。SDK はこの統合上の差異を、署名主体の安全条件を弱めない範囲で吸収する。

SDK が提供する価値は、外部アプリケーションが次を一貫して扱えることである。

- MosaicLynx の利用可能性と対応能力を確認する。
- 利用者が許可した公開アカウントとチェーン / ネットワークの文脈を扱う。
- 署名要求を適切な MosaicLynx の提供形態へ渡す。
- 成功、利用者拒否、未対応および安全側の失敗を区別する。
- 署名結果を元の要求との対応を含めて確認し、外部アプリケーションへ返す。

### 2.2 対象利用者と責任主体

| 主体                        | SDK 要件上の位置付け                                                                                                                         |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 一般ユーザー                | SDK の直接利用者ではない。MosaicLynx 側の確認領域で署名対象を確認し、要求ごとに承認または拒否する。                                          |
| dApp / 外部アプリケーション | SDK の主要な利用者。要求を生成し、SDK の結果を受け取り、必要な検証・ネットワーク処理を行う。                                                 |
| dApp 開発者                 | 主要な統合者。提供形態ごとの差異を個別に扱わず、MosaicLynx の共通連携を利用する。                                                            |
| ブラウザ拡張機能            | SDK が接続する署名主体の一つ。要求元、許可、表示、承認、署名および拡張機能内の秘密情報境界を管理する。                                       |
| モバイルアプリ              | 将来マイルストーンの署名主体。外部要求の検証、表示、利用者の承認、署名および端末側の秘密情報境界を管理する。                                 |
| Relay                       | モバイル連携時の受け渡し基盤。SDK は必要なクライアント側連携を行い得るが、Relay サーバーは署名、意味解釈、承認および秘密情報処理を担わない。 |
| wallet-core                 | 鍵管理、ウォレットストア、秘密情報を使用する暗号処理および生の署名の正本。SDK はこの責務を代替しない。                                       |

## 3. スコープ

### 3.1 SDK が責任を持つ範囲

SDK は、承認済みの MosaicLynx 連携契約が提供する範囲で、次を責任範囲とする。

- 外部アプリケーションから MosaicLynx への接続・連携の抽象化。
- MosaicLynx の利用可能性、対応能力および互換性の確認。
- 外部アプリケーションの要求を、署名主体が検証・確認できる要求として生成または受け渡すこと。
- ブラウザ拡張機能、モバイルアプリ、Relay などの提供形態差異を、共通の意味が保たれる範囲で吸収すること。
- 公開アカウント情報、要求結果および署名結果の受信・解釈・正規化。
- 要求と結果、要求元、接続・署名文脈、チェーン / ネットワークの対応確認。
- 利用者拒否、未対応、接続失敗、期限切れ、Relay 障害その他の失敗分類の正規化。
- 署名結果を外部アプリケーションが独立して検証できる状態で返すこと。
- 連携に必要な最小限の非秘密診断情報を扱うこと。

SDK は、上記を実現するために必要なクライアント側のアダプターまたは受け渡し処理を持ち得る。ただし、具体的な通信経路、プロトコルおよび暗号方式を本書で固定しない。

### 3.2 SDK が原則として責任を持たない範囲

SDK は、次を責任範囲に含めない。

- 秘密鍵、ニーモニック、プロファイルパスワード、復号済み Vault または署名用秘密情報の要求、永続保存、管理または外部公開。
- wallet-core の鍵管理、ウォレットストア、秘密情報を使用する暗号処理、生の署名およびその失敗処理の代替。
- MosaicLynx の承認 UI、署名対象の最終表示、利用者に代わる承認・拒否判断。
- ブラウザ拡張機能本体、モバイルアプリ本体、Vault、プロファイル、アカウント管理およびプラットフォーム固有の認証。
- Relay サーバーの実装、運用、長期保管、署名対象の意味解釈、署名、承認またはアナウンス。
- Symbol / NEM ノード、ノード選択、署名済みトランザクションのアナウンス、残高・履歴その他の継続的なネットワーク状態管理。
- Symbol SDK / NEM SDK に代わる汎用ブロックチェーン SDK または、根拠のないチェーン共通化。
- 組織向け監査、カストディ、永続的な包括署名許可およびユーザー確認を省略する自動署名。
- 独自の RPC 基盤、通信経路基盤または、外部アプリケーションから指定された任意 Relay の運用。

トランザクション組み立ての便利機能を SDK の必須責任とするかは未決であり、`SDK-OPEN-004` で扱う。いずれの場合も、SDK がアナウンスまたはノード管理を担うことはない。

## 4. 前提・制約

- MosaicLynx の実施順序はブラウザ拡張機能、Android、iOS、Relay である。SDK は最初のブラウザ拡張機能連携を優先し、モバイル / Relay 連携は対応するマイルストーンの成立を前提とする。
- モバイル対応を定義する要求は、将来マイルストーンの統合要求として扱う。
- MosaicLynx の共通要件はトランザクション署名とメッセージ署名を共通の署名能力として定めている。SDK v1 も両方を必須操作として扱う。具体的な操作名、メッセージ形式、通信上の契約および対応マイルストーンの実現方法は後続仕様で定める。
- Symbol と NEM、Mainnet と Testnet は SDK の全ての要求・結果で明示的に区別する。SDK は一方のチェーン / ネットワークを他方へ暗黙に変換しない。
- Mainnet 対応能力は適用される Mainnet リリース判定を満たす署名主体 / ビルドの能力だけを扱い、SDK が判定条件を迂回して Mainnet 対応能力を有効化してはならない。判定条件が未達成または判定不能でも、安全な利用不能 / 未対応のとして扱えることを優先する。
- wallet-core の責任境界は、MosaicLynx アプリケーションの表示・承認・処理の調整と混同しない。SDK はアプリケーションや wallet-core の責任を外部アプリケーションへ移さない。
- 外部アプリケーションが受け取った署名結果の独立検証と、必要なネットワーク処理は外部アプリケーションの責任である。SDK が検証補助を行っても、その責任を肩代わりしない。
- 本書で未決とした事項は、API やプロトコルの詳細を推測して確定する根拠としては扱わない。

## 5. SDK の利用モデル

外部アプリケーションから MosaicLynx を利用する概念フローを次に示す。具体的な関数名、URL、データ形式、メッセージ形式および状態遷移は定めない。

1. 外部アプリケーションが、MosaicLynx の利用可能性と必要な操作 / チェーン / ネットワークの対応能力を確認する。
2. 必要に応じて、外部アプリケーションが接続・公開情報の利用を要求し、MosaicLynx 側で利用者が許可する。
3. 外部アプリケーションが、自身の責任で用意したトランザクションまたはメッセージの署名要求を SDK へ渡す。
4. SDK が要求の文脈、許可状態、対応能力および受け渡し経路を確認し、対応する MosaicLynx へ要求を渡す。
5. ブラウザ拡張機能またはモバイルアプリが、外部入力を検証し、署名対象、チェーン、ネットワーク、アカウントおよび確認可能な影響を利用者へ提示する。
6. 利用者が要求ごとに承認または拒否する。SDK、外部アプリケーションまたは Relay が利用者の判断を代行してはならない。
7. MosaicLynx 側が、明示的な承認とその他の安全条件を満たした場合だけ署名し、結果または拒否・失敗を返す。
8. SDK が応答の要求対応、完全性、チェーン / ネットワーク / アカウントおよび対応する対応能力を確認し、正規化した結果または安全側の失敗を外部アプリケーションへ返す。
9. 外部アプリケーションが結果を独立して検証し、必要なアナウンスやネットワーク処理を自ら行う。

Relay を経由する場合も、Relay は受け渡しの一部に留まり、最終的な検証・表示・承認・署名はモバイルアプリが担う。Relay の受け渡し成功だけを署名成功の根拠にしてはならない。

## 6. 機能要求

### SDK-FR-001 利用可能性と対応能力の判定

**MUST** SDK は、外部アプリケーションが、利用可能な MosaicLynx の接続方式、対応操作、対応チェーン / ネットワークおよび互換性を判定できる能力を提供しなければならない。

利用可能性は、単なる Provider、アプリまたは Relay の存在を署名可能性・接続済み・アプリ導入済みと同一視してはならない。判定不能、対応経路なし、非対応バージョンおよび未対応操作は、成功や接続済みとして報告してはならない。

根拠: コンセプト §8、共通要件 CR-007、CR-012。整合確認: `docs/specifications/web-transaction-handoff-spec.md` §5.3、§6。下流: SDK 仕様、Provider 互換性、プラットフォーム対応能力判定。

### SDK-FR-002 接続と許可の要求

**MUST** SDK は、外部アプリケーションが指定したチェーン / ネットワークの公開連携を要求でき、MosaicLynx 側で利用者が許可した結果だけを受け取れるようにしなければならない。

接続許可と各署名要求の利用者承認は別の責任として維持し、接続済みであることだけを署名承認として扱ってはならない。未接続状態から署名を行うための暗黙接続を成立させてはならない。

根拠: コンセプト §5、§6.3、§11、共通要件 CR-003、CR-009。整合確認: `docs/specifications/product-spec.md` §11、§16、`docs/requirements/browser-extension.md` BR-003〜BR-005、`docs/requirements/mobile-app.md` MR-002〜MR-004。下流: 拡張機能 / モバイルの接続契約、SDK 仕様。

### SDK-FR-003 公開アカウントと接続文脈

**MUST** SDK は、許可された範囲に限り、外部アプリケーションが署名者の公開アカウントの識別情報と、そのアカウントに対応するチェーン / ネットワークの接続文脈を確認できるようにしなければならない。

内部のプロファイル ID、アカウント ID、ウォレットストアの識別子その他の内部管理情報を、外部アプリケーションへ公開することを必須としてはならない。公開情報の取得やキャッシュの存在を、署名時の認可または最新状態の証明として扱ってはならない。

独立したノード状態、残高、履歴またはブロックチェーンネットワーク状態を取得する SDK 機能は本要求に含めない。チェーン / ネットワーク文脈をどの公開情報契約で提供するかは下流仕様で定める。

根拠: コンセプト §5、§7、§11、共通要件 §4.2、CR-005、CR-009。整合確認: `docs/specifications/product-spec.md` §15、§16、`docs/specifications/profile-account-spec.md`。下流: Provider / モバイル公開識別情報契約、SDK 仕様。

### SDK-FR-004 切断・許可撤回の連携

**MUST** SDK は、外部アプリケーションが現在の連携を終了するための契約を、対応する MosaicLynx の許可・状態管理と矛盾しない形で利用できるようにしなければならない。

切断または許可撤回後の公開アカウント情報を新しい署名要求の認可に利用してはならない。プロファイル切替、チェーン切替、ロック、ロック解除または認証の操作を、外部アプリケーションが SDK 経由で利用者の確認なしに実行できるようにしてはならない。

根拠: コンセプト §6.3、§11、共通要件 CR-009、CR-011。整合確認: `docs/specifications/product-spec.md` §11、§16、`docs/specifications/web-transaction-handoff-spec.md` §5。下流: Provider / モバイル許可契約。

### SDK-FR-005 署名要求の生成・受け渡し

**MUST** SDK は、外部アプリケーションの署名要求を、署名主体が要求元、許可状態、署名対象、チェーン / ネットワーク、アカウントおよび有効性を検証できる形で MosaicLynx 側へ受け渡さなければならない。

ブラウザの実オリジンとブラウザ文脈を観測・検証する最終責任はブラウザ拡張機能 / ブラウザプラットフォーム側にある。SDK は dApp が自己申告した呼び出し元またはオリジン文字列を検証済みオリジンとして扱ってはならず、拡張機能が検証した保証を超える呼び出し元識別情報を表明してはならない。モバイル / Relay では、受け渡しセッションと要求元との対応を最終的に検証する責任はモバイルアプリ / プラットフォーム側にある。SDK は契約上必要な結び付け情報を受け渡し得るが、その情報の存在だけで呼び出し元の真正性を保証してはならない。Relay は呼び出し元識別情報の最終検証主体ではない。

要求元の対応または受け渡しが検証できない場合、SDK は署名成功、呼び出し元検証済み、検証済みオリジンまたは接続済みとして報告してはならない。接続済みという事実は呼び出し元真正性の代替にならない。

根拠: コンセプト §6.1、§13、共通要件 CR-001、CR-NFR-001、CR-NFR-008、CR-NFR-009。整合確認: `docs/requirements/browser-extension.md` BR-003、BR-004、`docs/requirements/mobile-app.md` MR-002、`docs/requirements/relay.md` RR-001、`docs/specifications/web-transaction-handoff-spec.md` §7。下流: SDK 要求契約、プラットフォーム呼び出し元結び付け、受け渡し仕様。

### SDK-FR-006 トランザクション署名の連携

**MUST** SDK は、承認済みの MosaicLynx 共通能力に含まれるトランザクション署名要求を、外部アプリケーションから署名主体へ渡し、利用者の明示的承認後に得られた結果を受け取れるようにしなければならない。

署名主体が対応範囲内のトランザクション全体、チェーン / ネットワーク / アカウント、資産移動、権限変更その他の確認可能な影響を解析・提示できない場合、SDK は未対応または安全側の失敗を成功として扱ってはならない。SDK が自ら署名を実行したり、署名主体の確認を省略する代替経路を提供したりしてはならない。

アグリゲート、マルチシグおよび連署署名を含むトランザクション関連操作は、対応するチェーンアダプターと署名主体が全体・親子関係・署名対象を安全に検証・提示できる場合だけ、その操作の意味を保って受け渡さなければならない。未対応の場合は通常のトランザクション署名またはメッセージ署名へ暗黙に変換してはならない。連署署名を SDK v1 の必須公開能力とするかは `SDK-OPEN-002` で扱う。

根拠: コンセプト §6.1、§6.2、§8、§11、共通要件 CR-002、CR-004、CR-005、CR-007-TX。整合確認: `docs/specifications/product-spec.md` §12、`docs/specifications/chain-compatibility-spec.md`、`docs/specifications/web-transaction-handoff-spec.md` §2、§7。下流: SDK 署名仕様、チェーン固有の署名契約、拡張機能 / モバイル承認仕様。

### SDK-FR-007 メッセージ署名の連携

**MUST** SDK は、MosaicLynx 共通要件で承認されたメッセージ署名を SDK v1 の必須操作として、トランザクション署名と区別された要求として署名主体へ渡し、利用者が実際に署名するメッセージの内容、用途および適用されるチェーン / ネットワーク / アカウントの文脈を確認できるようにしなければならない。

SDK は、利用者が理解できない生バイト列、未対応形式または表示不能なメッセージを、警告だけで署名へ進める API や暗黙代替経路を提供してはならない。表示・承認されたメッセージと実際の署名対象が一致しない場合、署名成功を返してはならない。

SDK v1 がメッセージ署名を必須で扱うことは確定事項であり、未対応メッセージ署名をトランザクション署名、生の署名または別のメッセージ形式として成功扱いにしてはならない。具体的なメッセージ操作の名称、形式、通信上の契約、API 型および受け渡しの詳細は後続仕様で定める。

根拠: コンセプト §2、§3、§6、§8、§11、共通要件 CR-007-MSG、CR-004、CR-NFR-003、CR-NFR-009。整合確認: `docs/requirements/browser-extension.md`、`docs/requirements/mobile-app.md`、`docs/requirements/relay.md`、`docs/design/architecture.md` §2、§5.2、`docs/specifications/product-spec.md` §16、`docs/specifications/web-transaction-handoff-spec.md` §2、§5。下流: メッセージ署名仕様、Provider / モバイル操作契約、テスト仕様。

### SDK-FR-008 署名結果の受信・対応確認

**MUST** SDK は、受信した署名結果が、元の要求、要求元、署名者、アカウント、チェーン、ネットワークおよび必要な署名主体指定に対応していることを確認できなければ、署名成功として返してはならない。

SDK が結果の形式や署名を検証した場合でも、外部アプリケーションが結果を独立して検証できる前提を維持しなければならない。Relay または Provider が成功応答を返したことだけを正当性の根拠にしてはならない。

根拠: コンセプト §6.4、§7、§9、§11、共通要件 CR-006、CR-NFR-009、CR-NFR-012。整合確認: `docs/requirements/relay.md` RR-002、RR-005、RR-007、`docs/specifications/web-transaction-handoff-spec.md` §7、§13。下流: 結果契約、SDK 検証仕様、dApp 統合指針。

### SDK-FR-009 通信経路差異の抽象化

**MUST** SDK は、対応するブラウザ拡張機能直接連携、モバイルアプリ連携および Relay を介した連携について、外部アプリケーションが共通の意味を持つ接続・署名・結果・失敗の契約を利用できるようにしなければならない。トランザクション署名とメッセージ署名の正常な署名結果は、通信経路によらず同じ操作の意味を保たなければならない。

外部アプリケーションに通信経路固有の秘密情報、Relay 認証情報、内部アカウント ID、任意 Relay の指定またはプラットフォーム内部状態を要求してはならない。外部アプリケーションが利用可能な通信経路を個別に選択しなければ署名できない設計を v1 の必須条件としてはならない。

各通信経路の利用可能性、提供マイルストーン、呼び出し元検証および UI 差異を、同一の危険な意味へ変換してはならない。利用者拒否、不一致 / 完全性 / 呼び出し元 / リプレイ失敗および結果不明を自動再試行または別通信経路代替経路で迂回しないことは確定事項とする。具体的な選択順序、利用者が明示的に選択する代替経路の可否、利用不能 / 接続失敗 / タイムアウト時の扱いおよび将来の第三者通信経路の追加方針は `SDK-OPEN-003` で扱う。

根拠: コンセプト §3、§4、§6.5、§8、共通要件 CR-007、CR-011、CR-AC-015。整合確認: `docs/design/architecture.md` §3、§5.5、`docs/specifications/web-transaction-handoff-spec.md` §1、§6、`docs/requirements/relay.md`。下流: 通信経路アダプター仕様、拡張機能 / モバイル / Relay 契約。

### SDK-PLAT-003 モバイルアプリ / Relay との連携

受け渡しセッションと要求元との対応を最終的に検証する責任はモバイルアプリ / プラットフォーム側にある。Relay は呼び出し元識別情報の最終検証主体ではなく、Relay の配送成功だけを呼び出し元検証成功として扱ってはならない。SDK は契約上必要な結び付け情報を受け渡し得るが、その存在だけで呼び出し元の真正性を保証してはならない。モバイルアプリが未提供、未対応または対応能力を満たさない場合、SDK はその状態を利用可能・署名成功として扱ってはならない。Relay はモバイルアプリの代わりに扱ってはならない。

根拠: コンセプト §1、§6.5、§9、§12、共通要件 CR-011、OPEN-003。整合確認: `docs/requirements/mobile-app.md` MR-002、MR-003、MR-004、MR-012、`docs/requirements/relay.md` RR-001〜RR-009、`docs/specifications/web-transaction-handoff-spec.md` §1、§6、§7。下流: モバイル受け渡し / Relay 仕様、モバイルマイルストーン受け入れ。

### SDK-PLAT-004 実行環境の境界

**MUST** SDK は、対象として宣言していない実行環境、ブラウザ文脈またはサーバー側の文脈で、利用可能・呼び出し元検証済み・署名可能であると誤認させてはならない。

ブラウザのオリジン、利用者有効化、ページライフサイクルまたはモバイルアプリの導入状態を必要とする連携を、Node.js その他のサーバー側の実行環境で同じ保証があるように扱ってはならない。Node.js、Web ワーカー、SSR、非ブラウザ実行環境を正式対応対象とするかは `SDK-OPEN-005` で決定する。

根拠: コンセプト §11、§12、共通要件 CR-NFR-001、CR-NFR-008。整合確認: `docs/requirements/browser-extension.md` BR-004、BR-007、BR-008、`docs/specifications/web-transaction-handoff-spec.md` §5.3、§11、`docs/design/architecture.md` §3、§6。下流: 実行環境サポート対応表、呼び出し元結び付け仕様。

**MUST** SDK の配布物は、外部のリモートコード、未検証の動的スクリプトまたは利用者が認識できない実行時取得コードに依存して、署名要求・結果処理の安全性を成立させてはならない。

## 11. エラーモデル要求

### SDK-ERR-001 外部から区別可能な失敗分類

**MUST** SDK は、少なくとも次の失敗分類を、署名成功および互いに意味の異なる失敗から区別できるようにしなければならない。

| 分類                                     | 外部アプリケーションが判断できる必要があること                                                                      |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 利用者拒否                               | 利用者が承認しなかったこと。自動再試行や別通信経路への切替を成功の代わりに行わない。                                |
| 利用不能                                 | 対応する MosaicLynx、Provider、モバイルアプリまたは通信経路が利用できないこと。                                     |
| 接続 / 許可失敗                          | 接続失敗、未接続、許可不足または接続対象範囲不一致であること。                                                      |
| タイムアウト / 期限切れ / キャンセル済み | 要求期限、キャンセルまたはライフサイクルによって完了しなかったこと。                                                |
| 無効な要求                               | 入力形式、対象、エンコーディング、サイズまたは検証条件が不正であること。                                            |

| 不一致 / 完全性失敗                      | 呼び出し元、オリジン、アカウント、チェーン、ネットワーク、要求 / 結果対応、完全性またはリプレイ検証に失敗したこと。 |
| Relay / 通信経路失敗                     | Relay、通信または受け渡しの失敗であり、署名結果が不明または得られなかったこと。                                     |
| 内部失敗                                 | SDK、Provider、モバイルアプリ、wallet-core または依存コンポーネントの内部失敗であること。                           |

成功は、要求、操作、署名主体、アカウント、チェーン、ネットワーク、対応付けおよび署名主体が確認・承認した対象との対応を確認でき、外部アプリケーションが署名結果を独立検証できる正常完了であることを表す。

具体的なエラーコード、例外クラス、メッセージ文言、HTTP 状態、再試行回数および再試行間隔は定めない。

根拠: コンセプト §6.3、§13、共通要件 CR-010、CR-012。整合確認: `docs/requirements/relay.md` RR-004、RR-NFR-002、`docs/specifications/web-transaction-handoff-spec.md` §10。下流: SDK エラー仕様、開発者文書、契約テスト。

## 12. 非機能要求

### SDK-NFR-001 安全性優先の信頼性

**MUST** SDK は、可用性、利便性または再試行の成功率を高めるために、要求検証、承認、結果対応、チェーン / ネットワーク整合性、秘密情報保護または呼び出し元検証を緩和してはならない。

Relay、Provider、モバイルアプリまたはネットワークが利用できない場合に連携が完了しないことは許容するが、失敗を署名成功としてはならない。

根拠: コンセプト §11、§13、共通要件 CR-010、CR-NFR-006、CR-NFR-010、CR-NFR-011。整合確認: `docs/requirements/relay.md` RR-010、RR-011、`docs/adr/0001-mainnet-evidence-lite.md`。下流: 失敗 / リリース仕様。

### SDK-NFR-002 相互運用性

**MUST** SDK は、承認済みの Provider、モバイルアプリ、Relay、チェーンアダプターおよびチェーン互換性の契約と相互運用できなければならない。Symbol と NEM の差異、Mainnet と Testnet の差異および署名結果の検証可能性を、提供形態の差異によって失わせてはならない。

根拠: コンセプト §8、§11、共通要件 CR-005、CR-006、CR-NFR-005。整合確認: `docs/specifications/chain-compatibility-spec.md`、`docs/specifications/web-transaction-handoff-spec.md`、`docs/design/architecture.md` §2、§6。下流: 相互運用性仕様、固定ベクター / 差分テスト仕様。

### SDK-NFR-003 通信経路間の契約検証可能性

**MUST** SDK の共通契約は、ブラウザ拡張機能直接連携と、提供開始後の対応するモバイル / Relay 連携を個別に検証できなければならない。トランザクション署名とメッセージ署名の正常な署名結果、成功に至らない結果および安全側失敗が、通信経路により別の操作の意味へ変化しないことを確認できなければならない。

モバイル / Relay の提供開始前は、実装済み検証結果が存在するものとして報告してはならない。検証が完了していない状態で、検証済み、確認済み、保証済みまたは対応済みであるかのように報告してはならない。

根拠: コンセプト §6.5、§14、共通要件 CR-007、CR-011、CR-AC-009、CR-AC-015。整合確認: `docs/specifications/web-transaction-handoff-spec.md` §14、`docs/design/architecture.md` §5.5。下流: SDK 契約テスト、プラットフォーム E2E テスト、マイルストーン受け入れ。

### SDK-NFR-004 配布・更新時の安全性

**MUST** SDK の配布および更新は、対応する公開契約、依存関係、対応能力、署名結果検証および呼び出し元 / Relay 境界を利用者に誤認させる状態を作ってはならない。互換性または Mainnet 対応能力を確認できない更新後は、署名成功を継続してはならない。

具体的なパッケージリリース、成果物、SBOM、証跡、展開およびロールバック手順はリリースポリシーと後続仕様で定める。

根拠: コンセプト §12、§14、共通要件 CR-NFR-006、CR-011。整合確認: `docs/specifications/product-spec.md` §17.4、§19、`docs/adr/0001-mainnet-evidence-lite.md`。下流: リリース準備状態、Mainnet 根拠、更新互換性仕様。

### SDK-NFR-005 テスト可能性と安全な可観測性

**MUST** SDK の主要契約は、正常系だけでなく、不正な形式の入力、未対応の機能、誤ったチェーン / ネットワーク、利用者拒否、タイムアウト、キャンセル、文脈変更、応答不一致、リプレイ、Relay 失敗および秘密情報漏えいの不成立を検証できる形で定義されなければならない。

**SHOULD** SDK は、通信経路選択、要求開始、応答受信および失敗分類など、秘密情報を含まない最小限の診断を提供できるようにすべきである。診断の有無や出力が署名可否・秘密情報保護の境界を変えてはならない。

根拠: コンセプト §14、共通要件 CR-AC-001〜CR-AC-016、CR-NFR-001〜CR-NFR-012。整合確認: `docs/specifications/web-transaction-handoff-spec.md` §12、§14、`docs/specifications/chain-compatibility-spec.md` §7、`docs/adr/0001-mainnet-evidence-lite.md`。下流: SDK テスト仕様、リリース証跡、セキュリティレビュー。

本書では、SDK の uptime、秒単位の遅延、同時実行数、再試行回数または実行環境ごとの性能目標を定めない。必要性と測定方法は、対象マイルストーンとリリースポリシーで判断する。

## 15. 未決事項

### SDK-OPEN-002：アグリゲート / マルチシグ / 連署署名の SDK 公開範囲

- 論点: トランザクション署名に含まれるアグリゲート / マルチシグの扱いと、連署署名を独立した SDK 操作として v1 の必須能力に含めるか。
- 未決の理由: プロダクト / チェーン互換性は全体解析・確認を要求し、既存受け渡し仕様は連署署名の契約を記載するが、共通要件は独立した連署署名対応能力の v1 範囲を明示していないため。
- 影響: SDK-FR-006、公開操作、チェーンアダプターの検証契約、モバイル / Relay 受け渡し、受け入れフィクスチャ。
- 決定時期: SDK 仕様とチェーン互換性の対応範囲を確定する前。対応しない操作は対応能力で未対応とし、通常署名へ変換しない。
- 根拠: 共通要件 CR-007-TX、`docs/specifications/product-spec.md` §12、`docs/specifications/chain-compatibility-spec.md` §4、`docs/specifications/web-transaction-handoff-spec.md` §5、既存受け渡し契約。

### SDK-OPEN-003：通信経路選択、明示的代替経路および第三者連携

- 論点: 拡張機能 / モバイル / Relay の選択順、利用不能 / 接続失敗 / タイムアウト後の扱い、利用者による通信経路の明示的選択を許可するか、将来の第三者アプリ・第三者通信経路を単一契約へ含めるか。
- 未決の理由: SDK は通信経路差異を吸収する必要があるが、利用者の明示操作、利用者有効化、オリジン / 呼び出し元保証および安全側失敗への影響がプラットフォームごとに異なるため。
- 影響: SDK-FR-001、SDK-FR-009、SDK-PLAT-003、SDK-COMP-003、UX、Relay / モバイルマイルストーン。
- 決定時期: 各プラットフォームの受け渡し仕様と SDK 互換性対応表の確定時。
- 制約: 利用者拒否、不一致 / 完全性 / 呼び出し元 / リプレイ失敗および結果不明の後に、自動再試行または別通信経路代替経路で処理を迂回してはならない。dApp が Relay URL、認証情報または内部通信経路状態を任意指定して安全境界を変更できないことも、本要件の前提である。

### SDK-OPEN-004：トランザクション組み立ての責務

- 論点: SDK がトランザクション組み立ての補助処理または domain-specific 生成を提供するか、外部アプリケーションが Symbol / NEM SDK 等で構築したペイロードの受け渡しと結果検証に限定するか。
- 未決の理由: SDK の中心価値は署名連携であり、トランザクション組み立てを含めると Symbol / NEM SDK の代替やチェーン固有の所有責任を招く一方、dApp の統合容易性に影響するため。
- 影響: SDK スコープ、依存関係、公開パッケージ、チェーン互換性、API / 仕様、テストフィクスチャ。
- 決定時期: SDK 仕様で統合対象と依存責務を確定する前。
- 制約: SDK がノード、アナウンス、継続的なネットワーク状態を担わないことは確定している。

### SDK-OPEN-005：正式対応実行環境と配布形態

- 論点: ブラウザ ESM / TypeScript / JavaScript を初期対象とする範囲、Node.js、SSR、Web ワーカー、非ブラウザ実行環境、モバイルブラウザの正式サポート対応表、配布パッケージの互換条件。
- 未決の理由: Web 受け渡しはブラウザ文脈、オリジン、ページライフサイクルおよび利用者有効化に依存し得るが、全実行環境の保証範囲は既存要件で確定していないため。
- 影響: SDK-PLAT-001、SDK-PLAT-004、呼び出し元結び付け、配布、テスト対応表。
- 決定時期: SDK 配布 / 実行環境仕様と各プラットフォームマイルストーンの決定時。
- 根拠: コンセプト §6.5、共通要件 OPEN-003、`docs/specifications/web-transaction-handoff-spec.md` §1、§4、§5.3、`docs/design/architecture.md` §1、§6。

### SDK-OPEN-006：バージョン管理、後方互換性および非推奨化ポリシー

- 論点: SDK バージョンと MosaicLynx / Provider / Relay プロトコルバージョンの対応、保証する後方互換期間、バージョン不一致の扱い、非推奨の機能の告知・廃止・移行条件。
- 未決の理由: 既存仕様にはバージョン / 主要の方向性があるが、SDK パッケージ、Provider API、Relay プロトコル、モバイルアプリの横断的なリリースポリシーは一つの要件として確定していないため。
- 影響: SDK-COMP-001〜004、対応能力協議、リリース証跡、開発者移行。
- 決定時期: SDK 互換性仕様とリリースポリシーの確定時。
- 制約: 非対応または意味を維持できない機能を別操作へ利用者に知らせない格下げしないことは確定している。

### SDK-OPEN-007：呼び出し元 / オリジンとの結び付けの具体方式

- 論点: ブラウザ拡張機能のブラウザで観測したオリジン、モバイル / Relay の受け渡しセッション、必要に応じたオリジン証明を、SDK の共通契約へどの粒度で受け渡すか。
- 未決の理由: ブラウザ拡張機能 / ブラウザプラットフォームまたはモバイルアプリ / プラットフォームが最終検証主体であり、SDK がそれらの保証を超えないことは確定しているが、プラットフォーム間で同一の結び付け方式を採用する必要はないため。
- 影響: SDK-SEC-004、SDK-FR-005、SDK-PLAT-002〜004、Mainnet リリース判定、モバイル受け渡し。
- 決定時期: プラットフォーム固有の呼び出し元結び付けの具体方式を確定し、SDK の共通結果 / エラー契約へ反映する前。
- 制約: 外部アプリケーションが渡したオリジン文字列だけを認証根拠にしないこと、検証不能時に署名成功・呼び出し元検証済み・検証済みオリジン・接続済みを報告しないこと、保証範囲を越えて dApp の善性や非侵害を表示しないことは確定している。

## 16. 対象外

本書で SDK の対象外とする事項を明示する。

- 秘密鍵、ニーモニック、プロファイルパスワード、Vault 平文、ウォレットストアの秘密部分を SDK に入力させること。
- SDK が秘密情報を保管、復号、鍵導出または生の署名すること。
- SDK、Relay または外部アプリケーションが、利用者確認なしに署名すること。
- SDK が承認 UI、署名対象の最終解釈・提示、ユーザー拒否の代行を担うこと。
- ブラウザ拡張機能、モバイルアプリ、wallet-core または Relay サーバー本体を SDK に内包すること。
- Relay に署名、トランザクション / メッセージの意味解釈、秘密情報処理、アナウンスまたは長期履歴を担わせること。
- SDK に Symbol / NEM ノード、REST / WebSocket、アナウンス、残高・履歴・資産管理を担わせること。
- SDK を汎用ブロックチェーン SDK、Symbol SDK / NEM SDK の代替または自動トランザクション生成とみなすこと。トランザクション組み立て補助処理の最終範囲は SDK-OPEN-004 が決める。
- dApp が任意 Relay URL、認証情報、セッション秘密情報、内部アカウント ID または通信経路を指定して安全境界を変更すること。
- 未対応操作、不明形式、解析不能トランザクション / メッセージを生の署名、警告だけの承認または別操作へ代替経路すること。
- 組織向け監査・統制・カストディ、二者承認、ハードウェア署名主体、MPC を v1 SDK の完了条件とすること。
- SDK 要件書で API 型、クラス / 関数、メソッド署名、JSON スキーマ、URL、プロトコルフィールド、暗号方式、タイムアウト秒数、再試行アルゴリズム、内部状態遷移、パッケージ directory またはバンドラーを確定すること。

- `_sns/packages/symbol-nem-interchange-format/doc/requirements.md`、`_sns/packages/symbol-nem-interchange-format/doc/spec-format.md`、`_sns/packages/symbol-nem-interchange-format/doc/spec-api.md`: SNIF の形式・API と責務境界の整合確認資料。SNIF は通信経路非依存にデータと `id` / `replyTo` 等の対応付け情報を搬送できるが、リプレイ防止、鮮度、使用済み管理、セッション結び付け、呼び出し元 / オリジンの真正性、認証 / 認可、利用者承認、署名生成・検証およびトランザクション意味上の検証を担わない。SNIF を通信経路に用いる場合も、ブラウザ Provider、ディープリンク / App Link、Relay 固有の安全境界を SDK 要件から消去しない。MosaicLynx SDK が SNIF を使用すること自体は、本要件では確定しない。

### 18.3 下流引継ぎ

- SDK 仕様: 公開契約、要求・結果形式、対応能力、エラー、ライフサイクル、通信経路アダプターおよびバージョン管理。
- ブラウザ拡張機能 / Provider 仕様: オリジン、接続、許可、公開アカウント、承認および Provider 互換性。
- モバイルアプリ / Relay 仕様: モバイル受け渡し、呼び出し元結び付け、Relay の内容を解釈しない受け渡し、モバイル側の検証・承認・署名。
- チェーン互換性 / トランザクション内容検査仕様: Symbol / NEM、Mainnet / Testnet、トランザクション、メッセージ、アグリゲート / 連署署名の対応範囲。
- プラットフォーム / 実行環境 / 配布仕様: ブラウザ、Node.js その他実行環境のサポート対応表、配布および更新互換性。
- リリースポリシー / 根拠: Mainnet 対応能力、SDK 成果物、依存関係、互換性およびセキュリティ根拠。
- テスト仕様: 通信経路間の契約、エラー、不正な形式の入力、リプレイ、応答対応関係、プライバシーおよび秘密情報漏えい。
