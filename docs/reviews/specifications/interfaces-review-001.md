## 総評

本仕様は、共通データモデルとコンポーネント境界を、実装可能な契約粒度まで具体化できている。`requestId`、`sessionId`、`requestDigest`、時刻表現、Relay 受け渡しの期限、構造化されたメッセージノンス、Mainnet モバイルのオリジン証明および DNS / HTTPS 制約は、既存の [Web トランザクション受け渡し仕様](../../specifications/web-transaction-handoff-spec.md) と [プロダクト仕様](../../specifications/product-spec.md) に根拠がある。共通署名状態、承認との結び付け、`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN`、Relay の内容を解釈しない境界も [signing-flow.md](../../design/signing-flow.md)、[security-design.md](../../design/security-design.md) および既存 IF 指摘の解決内容と整合する。

ただし、SDK 公開エラーコードの一部が既存受け渡しと一致しない。対象仕様は `INVALID_MESSAGE` と `NONCE_REUSED` を「既存受け渡しで確定している」としているが、受け渡しの `MosaicLynxSDKErrorCode` 共用体には両方がない。このままでは共通応答の `errorCode` の許容集合がコンポーネント間で一意に定まらず、仕様として確定できない。

### IS-001: SDK エラーコードの仕様間の不整合

- **問題:** `interfaces.md` §10.2 の公開コード共用体は `INVALID_MESSAGE` と `NONCE_REUSED` を定義している。一方、既存受け渡し §10 の `MosaicLynxSDKErrorCode` はこれらを定義せず、`signData` のスキーマ / リプレイ関連失敗も既存の `INVALID_PARAMS`、`REQUEST_EXPIRED`、`INTERNAL_ERROR` 等へ整理されている。また受け渡し §7.2 の Relay 応答は同じ共用体を参照しているため、SDK、Relay 受け渡し、共通インターフェースのエラードメインが一致しない。
- **根拠:** 共通エラーコードは [web-transaction-handoff-spec.md](../../specifications/web-transaction-handoff-spec.md) §7.2、§10 で既存契約として定義され、対象仕様 §10.2 はその契約を参照すると記載している。構造化されたメッセージのノンス / 期限切れ / リプレイ要件自体は [product-spec.md](../../specifications/product-spec.md) §16〜§17 と [signing-flow.md](../../design/signing-flow.md) §14 に根拠があるが、それだけでは新しい公開エラーコードの追加根拠にはならない。
- **リスク:** 実装者が対象仕様に従えば受け渡しと異なるコードを返し、受け渡しに従えば対象仕様の応答共用体と異なるコードを返す。`INVALID_MESSAGE` / `NONCE_REUSED` を受信側が未対応のコードとして拒否する可能性、user-visible エラーの分類不一致、Relay 応答の相互運用不能が生じる。エラーコードの差異を利用者に知らせない代替経路で吸収すると、検証失敗やリプレイ失敗の意味が失われる。
- **推奨対応:** まず [web-transaction-handoff-spec.md](../../specifications/web-transaction-handoff-spec.md) と [docs/requirements/sdk.md](../../requirements/sdk.md) に戻し、構造化されたメッセージ検証 / ノンスリプレイの公開エラー分類とコード集合を承認する。その決定に合わせて `interfaces.md` §10.2、受け渡し §7.2 / §10、必要な SDK 契約テストを同じ変更として更新し、対象仕様には「既存受け渡しで確定」と書ける根拠を残す。新規コードを採用しない場合は対象仕様から両コードを除き、既存コードへの分類規則を明示する。いずれの場合も不明コードの安全でない代替経路は行わない。
- **上流へ戻す必要:** あり。公開エラーコードの判断権限とコンポーネント間の契約の決定が必要。
- **仕様内で修正可能:** 上流でコード集合を確定した後、`interfaces.md` の共用体、根拠リンク、エラー対応付けを同期する。

## セキュリティ / 信頼境界評価

- Web アプリケーション / SDK の自己申告をオリジンの信頼性判断とせず、ブラウザで観測した文脈またはモバイル受け渡しの検証済み文脈を最終結び付けとしている。
- 許可、セッション、プロファイル、アカウント、対象範囲、チェーン / ネットワーク、操作、対応能力、対象、要求識別情報を結び付けし、`requestId` 単独を認可としていない。
- Relay は内容を解釈しない通信経路として扱われ、復号、意味上の内容検査、承認、署名、wallet-core の責務を持たない。
- Signer 側の内容検査、信頼された UI、明示承認、署名前の再検証、wallet-core 結果の対応確認が共通検証順序に含まれる。
- `RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` を分離し、終端状態の再発、古くなった承認、重複署名、自動再署名を禁止している。
- 秘密情報資料、秘密鍵、ニーモニック、ウォレットロック解除秘密情報を共通外部インターフェースに公開しない責任分界が維持されている。

上記のセキュリティ / 信頼境界は適合している。IS-001 はエラー分類体系の相互運用性問題であり、現時点で秘密情報漏えいや承認迂回を直接生じさせる記述ではないが、安全側に終了する公開契約を一意にできないため `ERROR` とする。

## コンポーネント責務 / コンポーネント間の契約評価

§16 の責任表は、SDK、ブラウザ拡張機能、モバイルアプリ、Relay、wallet-core を適切に分離している。SDK は要求組み立て、振り分け、対応付け、エラー正規化に限定され、ブラウザ / モバイルがオリジン、許可、内容検査、承認、認証およびライフサイクルを担い、Relay は内容を解釈しない配送、wallet-core は秘密情報と暗号学的な処理を担う。`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` の境界も [interfaces-review-002](../design/interfaces-review-002.md) の解決内容と一致する。

共通対応能力の具体的協議、許可期限切れ、呼び出し元文脈およびアグリゲート / マルチシグの公開対象範囲は未決に残されている。未決事項を SDK、Relay または各ホストが独自に確定する構造にはなっていない。

## 追跡可能性評価

§17 は、要求・設計・本仕様の主要契約を追跡可能にしている。参照された IF-001〜IF-003 は [interfaces-review-001](../design/interfaces-review-001.md) で指摘され、[interfaces-review-002](../design/interfaces-review-002.md) で解決確認されているため、レビュー資料を製品要求の一次根拠として扱っているわけではない。一次根拠はコンセプト、要件、設計および既存仕様に置かれている。

指定された具体値については、以下を一次根拠として確認した。

- 要求 / セッション / ダイジェスト / タイムスタンプ / 5分期限 / Mainnet オリジン証明: [web-transaction-handoff-spec.md](../../specifications/web-transaction-handoff-spec.md) §7
- 構造化されたメッセージノンス / 期限切れ / リプレイ: [product-spec.md](../../specifications/product-spec.md) §16、§17、および [signing-flow.md](../../design/signing-flow.md) §14
- PermissionGrant のプロファイル / 対象範囲 / accountIds / リビジョン: [product-spec.md](../../specifications/product-spec.md) §15
- 信頼境界 / 責務 / 安全側での終了: [architecture.md](../../design/architecture.md)、[security-design.md](../../design/security-design.md)、[signing-flow.md](../../design/signing-flow.md)

## 未決 / 上流返却要否

- `OPEN-001`〜`OPEN-006` は、既存設計が未確定としている事項を本仕様でも保持している。これらを独自に確定していない点は適切。
- `IS-001` は未決のまま次工程へ持ち越すべきではない。公開エラーコードの判断権限を上流で決定し、受け渡しと本仕様を同期する必要がある。
- その他に、上流へ戻すべき未決事項、または仕様内だけで修正すべき追加指摘は確認されなかった。

## 基本設計粒度の評価

インターフェース / データモデル仕様として、共通型の意味、必須性、コンポーネント間の結び付け、検証順序、シリアライズ、エラー意味、互換性、ライフサイクルおよび追跡可能性が実装可能な粒度で定義されている。ブラウザ API、モバイル OS API、Relay の DB / キュー、SDK の具体クラス、wallet-core 内部暗号処理、チェーン固有のパーサー実装を不要に再定義していない。

また、`OPEN-001`〜`OPEN-006` によって、メッセージ有効期限フィールド、対応能力協議、共通のバージョン対応表、許可期限切れ / 失効、呼び出し元文脈、アグリゲート / マルチシグ対象範囲を適切な上流・下位契約へ委譲している。`IS-001` を解消すれば、下位実装・契約テストへ進める粒度に達している。
