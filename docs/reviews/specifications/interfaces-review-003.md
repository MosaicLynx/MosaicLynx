## 5. 要約

対象仕様は、アカウントの公開識別情報とアカウントの内部参照の分離、ブラウザ観測されたオリジンと自己申告のオリジンの分離、PermissionGrant の結び付け、Symbol / NEM と Mainnet / Testnet の分離、トランザクションと `MESSAGE_SIGN` の識別、requestId / 世代 / ダイジェスト、正規化、秘密情報の分離、受け渡し §10 の具体的なエラー定義の正本、Relay 内容を解釈しない境界、既知の結果の再送 / 取得 / 照会および基本的な再署名禁止を定義している。過去 `IS-001` の修正状態も維持されている。

しかし、最新要件 / 設計が後から確定した次のセキュリティ契約を、共通仕様から実装・検証可能な肯定形の不変条件として読み取れない。

- 認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認の4条件が独立した必須条件であること。
- プロファイル内のセキュリティ文脈が公開フィールドではなく、要求、承認、認証、アカウントの利用認可、wallet-core 呼び出し、結果、応答受信者 / 配送まで結び付けされること。複数要求の文脈を共有・流用しないこと。
- `RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` が Signer が生成した処理結果の区分であり、SDK / Relay / Provider / 通信経路状態から生成・推測・確定されないこと。
- セキュリティ失敗、不明、配送失敗、通信経路失敗から自動再試行 / 代替の経路により承認境界を迂回しないこと。
- Mainnet 対応能力が対応能力 / 接続 / Provider 状態ではなく、信頼された Signer とリリース / 根拠判定条件に従属すること。

これらは API ライブラリ、クラス、保存領域、OS API、具体再試行 loop を追加要求するものではなく、共通契約の意味・判断権限・安全側での終了条件の不足である。したがってレビュー判定条件 2、3、4、5、6、7 を阻害する `Critical` 指摘として、`SR-001`〜`SR-005` を採用する。

## 7. 必須の修正

### SR-001: 共通4条件の独立した署名判定条件が不足している

- **重要度 / 状態:** `Critical` / `New`
- **対象箇所:** `interfaces.md` §4（行69）、§8.1〜§8.3（行337〜363）、§12.1（行576〜588）、§13（行616〜641）、§15（行662〜675）。
- **確認できた事実:** 対象は Signer の認証、PermissionGrant、明示的な確認、署名前の `Authorization` 結び付けおよび `1 request = 1 confirmation = 1 authentication = 1 signing operation` を定めている。しかし `AUTHORIZED` は「明示承認と署名ごとの認証」の成立だけであり、署名可能な状態へのロック解除とアカウントの利用認可を同じ要求 / プロファイル / アカウント / チェーン / ネットワーク / 対象に対する独立条件として要求していない。`capability` がロック解除・認可・承認の代替でないことも明記されていない。
- **既存の根拠:** 共通要件 `requirements.md` §4.2 / `CR-016`、`architecture.md` §6.9、`security-design.md` の署名判定条件、`signing-flow.md` §8〜§9・§23、`design/interfaces.md` §9.1 は、認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認を独立した4条件とし、接続、許可、対応能力、通常の `UNLOCKED`、過去の認証および wallet-core のパスワード / ストア検証を代替にしないと定める。
- **発生条件:** 実装者が `PermissionGrant.accountIds` または選択済みのアカウントをアカウントの利用認可とみなし、通常の `UNLOCKED` または接続 / 対応能力を署名可能ロック解除とみなし、既存の認証と明示的な承認だけで `AUTHORIZED` / `SIGNING` へ進める場合に発生する。
- **問題・影響:** 接続許可、公開アカウント情報公開、通常のロック解除、対応能力、wallet-core ストア検証が署名判定条件を代替できる余地が残る。対象プロファイル / チェーン / ネットワーク / アカウントに対する権限が確認できない状態、または署名可能な状態へのロック解除が失効・不明な状態で署名 / 成功へ進む実装を排除できず、CR-016、セキュリティ判定条件、Signer 判断権限を弱める。
- **必要な最小修正または確認:** 新しい公開フィールドや accountId / 内容を解釈しないハンドルを追加せず、Signer が同一呼び出し元、プロファイル内の文脈、アカウント、チェーン / ネットワーク、操作、対象、鮮度に対して4条件をすべて成立・署名前に再確認し、いずれかが未成立・ロック済み・古くなった・不明・不整合なら wallet-core 呼び出しと成功を禁止する不変条件を、共通ライフサイクル、検証、応答結果に明記する。
- **完了条件 / 再確認方法:** トランザクション、連署署名、`MESSAGE_SIGN` の各操作について、接続、許可、対応能力、通常のロック解除、過去認証、wallet-core パスワード / ストア検証、Relay 配送が4条件の代替にならないことを対象本文だけで確認できること。4条件を満たした同一文脈の場合にだけ `AUTHORIZED`、`SIGNING`、`SUCCEEDED` が成立すること。

### SR-002: プロファイル内のセキュリティ文脈と要求単位分離が不足している

- **重要度 / 状態:** `Critical` / `New`
- **対象箇所:** `interfaces.md` §5.3（行111〜128）、§8.1〜§8.2（行321〜356）、§12.1（行576〜588）、§13（行627〜641）、§15（行667〜674）、§16（行677〜687）。
- **確認できた事実:** 対象は `PermissionGrant.profileId` と `accountIds` を内部参照とし、許可対象範囲 / リビジョンの変更時にセッション、未完了認可、古い承認を無効化すると定めている。一方、プロファイル ID を公開しない Signer 内のセキュリティ文脈の定義、プロファイル切り替え / プロファイルロック / 有効なプロファイル文脈消失 / Profile-Account 関連付け変更による承認・認証・アカウントの利用認可・結果配送の失効、および並行する要求間での文脈共有・流用禁止は明示していない。一般的な `context` / `INVALIDATED` の記載だけでは、どの状態を同じプロファイル文脈に結び付けするかが一意でない。
