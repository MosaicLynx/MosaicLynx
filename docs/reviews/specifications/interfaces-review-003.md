## 4. Review Result

`REVISE SPECIFICATION`

## 5. Summary

対象 Specification は、Public Account Identity と Internal Account Reference の分離、Browser observed Origin と self-declared Origin の分離、PermissionGrant の binding、Symbol / NEM と Mainnet / Testnet の分離、transaction と `MESSAGE_SIGN` の識別、requestId / generation / digest、canonicalization、secret isolation、Handoff §10 の concrete error authority、Relay opaque boundary、known result の resend / retrieval / lookup および基本的な re-sign prohibition を定義している。過去 `IS-001` の修正状態も維持されている。

しかし、最新 Requirements / Design が後から確定した次の security contract を、共通仕様から実装・検証可能な肯定形の invariant として読み取れない。

- Authentication、Signing-capable unlock、Account authorization、Explicit user approval の4条件が独立した必須条件であること。
- Profile-local security context が公開 field ではなく、request、approval、authentication、Account authorization、wallet-core call、result、response recipient / delivery まで binding されること。複数 request の context を共有・流用しないこと。
- `RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` が Signer-originated disposition であり、SDK / Relay / Provider / transport state から生成・推測・確定されないこと。
- security failure、unknown、delivery failure、transport failure から automatic retry / alternate route により承認境界を迂回しないこと。
- Mainnet capability が capability / connection / Provider state ではなく、trusted Signer と release / evidence gate に従属すること。

これらは API library、class、storage、OS API、具体 retry loop を追加要求するものではなく、共通 contract の意味・authority・fail-closed 条件の不足である。したがって Review Gate 2、3、4、5、6、7 を阻害する `Critical` finding として、`SR-001`〜`SR-005` を採用する。

## 7. Required Changes

### SR-001: 共通4条件の独立した署名 gate が不足している

- **Severity / Status:** `Critical` / `New`
- **対象箇所:** `interfaces.md` §4（行69）、§8.1〜§8.3（行337〜363）、§12.1（行576〜588）、§13（行616〜641）、§15（行662〜675）。
- **確認できた事実:** 対象は Signer の authentication、PermissionGrant、explicit confirmation、署名前の `Authorization` binding および `1 request = 1 confirmation = 1 authentication = 1 signing operation` を定めている。しかし `AUTHORIZED` は「明示承認と署名ごとの認証」の成立だけであり、Signing-capable unlock と Account authorization を同じ request / Profile / Account / Chain / Network / target に対する独立条件として要求していない。`capability` が unlock・authorization・approval の代替でないことも明記されていない。
- **既存の根拠:** 共通 Requirements `requirements.md` §4.2 / `CR-016`、`architecture.md` §6.9、`security-design.md` の署名 gate、`signing-flow.md` §8〜§9・§23、`design/interfaces.md` §9.1 は、Authentication、Signing-capable unlock、Account authorization、Explicit user approval を独立した4条件とし、connection、permission、capability、ordinary `UNLOCKED`、過去の認証および Wallet Core の password / Store validation を代替にしないと定める。
- **発生条件:** 実装者が `PermissionGrant.accountIds` または selected Account を Account authorization とみなし、通常の `UNLOCKED` または connection / capability を署名可能 unlock とみなし、既存の authentication と explicit approval だけで `AUTHORIZED` / `SIGNING` へ進める場合に発生する。
- **問題・影響:** 接続許可、公開 Account disclosure、通常の unlock、capability、wallet-core Store validation が署名 gate を代替できる余地が残る。対象 Profile / Chain / Network / Account に対する権限が確認できない状態、または signing-capable unlock が失効・不明な状態で signing / success へ進む実装を排除できず、CR-016、security gate、Signer authority を弱める。
- **必要な最小修正または確認:** 新しい公開 field や accountId / opaque handle を追加せず、Signer が同一 caller、Profile-local context、Account、Chain / Network、operation、target、freshness に対して4条件をすべて成立・署名前に再確認し、いずれかが未成立・locked・stale・unknown・不整合なら wallet-core call と success を禁止する invariant を、共通 lifecycle、validation、response result に明記する。
- **完了条件 / 再確認方法:** transaction、cosignature、`MESSAGE_SIGN` の各 operation について、connection、permission、capability、ordinary unlock、過去 authentication、Wallet Core password / Store validation、Relay delivery が4条件の代替にならないことを対象本文だけで確認できること。4条件を満たした同一 context の場合にだけ `AUTHORIZED`、`SIGNING`、`SUCCEEDED` が成立すること。

### SR-002: Profile-local security context と request 単位 isolation が不足している

- **Severity / Status:** `Critical` / `New`
- **対象箇所:** `interfaces.md` §5.3（行111〜128）、§8.1〜§8.2（行321〜356）、§12.1（行576〜588）、§13（行627〜641）、§15（行667〜674）、§16（行677〜687）。
- **確認できた事実:** 対象は `PermissionGrant.profileId` と `accountIds` を internal reference とし、permission scope / revision の変更時に session、未完了 Authorization、古い approval を無効化すると定めている。一方、Profile ID を公開しない Signer-local security context の定義、Profile switch / Profile lock / active Profile context loss / Profile-Account association change による approval・authentication・Account authorization・result delivery の失効、および concurrent request 間での context 共有・流用禁止は明示していない。一般的な `context` / `INVALIDATED` の記載だけでは、どの状態を同じ Profile context に binding するかが一意でない。
- **既存の根拠:** `design/interfaces.md` §6 は Profile-local context を公開 request / response field とせず、request、caller、session、permission、approval、Authentication、Signing-capable unlock、Account authorization、target、wallet-core call、result、recipient / delivery を同じ context に binding し、Profile switch / lock 等で失効させる。`signing-flow.md` §23、`security-design.md` §10.2 および最新 Design Review の DR-001 / DR-005 は同じ境界を確定している。
- **発生条件:** Signer が permission revision を再確認しても Profile switch / lock を別の context change として扱わない場合、または複数の active request に一つの approval、authentication、Account authorization、wallet-core result / recipient state を共有する場合に発生する。
- **問題・影響:** Profile A の approval、authentication、Account authorization、selected Account または known result が Profile B、別 request、別 Account、別 caller へ流用される余地がある。Profile lock、association change、process / context loss 後に古い signing context が再開され、wrong Profile / Account への signing または response misdelivery を許す可能性がある。
- **必要な最小修正または確認:** Profile ID や opaque handle を公開するのではなく、Signer-local Profile / Profile Network / Account association context を定義し、request〜approval〜authentication〜unlock〜Account authorization〜target〜wallet-core call〜result〜recipient / delivery に binding する。Profile switch / lock、association / Account / Chain / Network / caller / relevant permission / session change および context loss は影響 request を `INVALIDATED` とし、各 active request は独立した security / lifecycle unit として context を共有・合成・流用しないと明記する。
- **完了条件 / 再確認方法:** Profile A→B、Profile lock / unlock、Account switch、複数 tab / frame または複数 handoff の同時 request、遅延 response の各ケースで、古い approval / auth / authorization / result を再利用せず、別 recipient / request へ配送しないことを対象本文から検証できること。公開 Account Identity に internal ID を追加しないことも維持する。

### SR-003: `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` の authority と transport 分離が不足している

- **Severity / Status:** `Critical` / `New`
- **対象箇所:** `interfaces.md` §6.1〜§6.3（行172〜254）、§10.1〜§10.3（行487〜532）、§12.1（行576〜588）、§13（行616〜641）、§16（行677〜687）。
- **確認できた事実:** 対象は `RESULT_UNKNOWN` を signing generation の不明、`DELIVERY_UNKNOWN` を確定済み result の delivery disposition とし、自動 retry / 再署名や相互変換を禁止している。しかし、両者が Signer-originated であり Signer だけが成立させること、SDK / Provider / Relay / transport / page lifecycle が生成・推測・確定できないこと、SDK / Relay は transport category として意味不変に pass-through するだけであることが明記されていない。`RelayResponse` の concrete union（§6.3）にも両 disposition を保持する契約がなく、Handoff §10 への mapping が意味を縮退させてはならないという条件もない。
- **既存の根拠:** `signing-flow.md` §7.3〜§7.4・§19・§23、`sdk.md` Design §4.2・§15・§21、`relay.md` Design §13.3・§14・§25〜§29 は、Signer が signing generation result / known-result delivery disposition を確定し、SDK / Relay は timeout、Relay outage、response absence、disconnect、recipient offline、reconnect / delivery failure、page lifecycle loss から両者を生成・推測・確定しないと定める。`signing-protocol.md` §6.1・§19 も同じ semantic distinction を要求する。
- **発生条件:** SDK timeout、Relay outage、response absence、Provider disconnect、page lifecycle loss、recipient offline または delivery failure を `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` として作成する場合、または Signer の disposition を `failed` / Handoff `INTERNAL_ERROR` / transport error へ無断で縮退する場合に発生する。
- **問題・影響:** signing generation の成否、既知 result の配送成否、transport の可用性を誤分類し、dApp が誤った retry、re-sign、recovery または user guidance を選択する。特に既知 result の再配送と新しい signing operation が混同される。`§6.3` の union だけを実装すると、Signer-originated unknown を失わずに SDK へ渡す方法を実装者が推測しなければならない。
- **必要な最小修正または確認:** 新しい concrete public error code を発明せず、`RESULT_UNKNOWN` は signing generation 自体を確定できない trusted Signer のみ、`DELIVERY_UNKNOWN` は known signed result の delivery disposition を確定できない trusted Signer のみが成立させると明記する。SDK / Relay / Provider / transport は transport-level failure の分類と、Signer-originated disposition の request correlation 後の意味不変伝達だけを行う。timeout、outage、response absence、disconnect、offline、page lifecycle loss、delivery failure の列挙を含める。Handoff concrete response がこの区別を保持できない点は Handoff / downstream contract として upstream return し、Interfaces から独自 code を追加しない。
- **完了条件 / 再確認方法:** 上記 transport 事象から両 disposition を生成・推測・確定できないこと、Signer-originated disposition を `failed`、user rejection、transport error、相互の別 disposition へ変換しないこと、known result の recovery が resend / retrieval / lookup に限定されることを対象と下流 contract の組合せで検証できること。

### SR-004: security failure 後の automatic retry / fallback 禁止が不十分である

- **Severity / Status:** `Critical` / `New`
- **対象箇所:** `interfaces.md` §6.4（行256〜262）、§10.1（行489〜509）、§10.3（行521〜532）、§13（行616〜641）、§14.2（行653〜660）、§15（行667〜675）。
- **確認できた事実:** 対象は unknown operation / version / capability 等の別 operation・raw signing・別 transport・旧 protocol への fallback、user rejection 等の同一 request retry、`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` 後の再署名を個別に禁止する。しかし user rejection、permission denial、Account authorization failure、caller / Origin mismatch、integrity / replay failure、Chain / Network mismatch、transport failure、`RESULT_UNKNOWN`、`DELIVERY_UNKNOWN` の全てについて、alternate Provider / Signer / local / remote route への automatic fallback を包括的に禁止していない。`transport_failure` の retry 行も「Relay delivery を署名成功と扱わない」に留まり、新しい signing operation の条件を固定していない。
- **既存の根拠:** `architecture.md` §5.2、`signing-flow.md` §21・§23、`sdk.md` Design §17・§21、`relay.md` Design §25・§29、SDK 要件 `SDK-FR-009`〜`SDK-FR-010` は、security failure を別 route へ自動変換せず、明示 retry でも fresh request、fresh validation、4条件および explicit approval を必要とすると定める。
- **発生条件:** local Provider が拒否・不一致・unknown を返した後に remote Relay へ切り替える、Relay failure 後に local Signer へ切り替える、Provider A failure 後に Provider B / Signer B へ同一 intent を自動送信する、または transport failure を新しい署名 retry として扱う場合に発生する。
- **問題・影響:** 利用者拒否、権限・認証・Account authorization、caller、integrity、replay、Chain / Network の security decision を alternate route が迂回できる。Signer が一度署名したか不明な request に対する重複署名、別 Account / Profile での署名、承認なしの再試行を防げない。
- **必要な最小修正または確認:** automatic retry / fallback を、対象の全 security failure、unknown、delivery / transport failure から禁止する invariant を追加する。transport reconnect / response redelivery と signing retry を分離し、known result は既存 result の resend / retrieval / lookup のみとする。新しい signing operation が利用者により明示的に開始される場合だけ、new request identity、fresh context、fresh validation、4条件および explicit approval を要求する。具体的な route、retry 回数、interval、API は下流へ委譲する。
- **完了条件 / 再確認方法:** user rejection、permission / Account authorization / authentication / unlock failure、caller / Origin、integrity、replay、Chain / Network、`RESULT_UNKNOWN`、`DELIVERY_UNKNOWN`、transport failure の各ケースで、別 route への自動送信・自動署名が発生しないことを matrix として対象本文から検証できること。

### SR-005: Mainnet release / evidence gate が common contract にない

- **Severity / Status:** `Critical` / `New`
- **対象箇所:** `interfaces.md` §5.1（行79〜97）、§5.6（行156〜168）、§7.2〜§7.3（行296〜317）、§12.2（行590〜604）、§14（行643〜660）、§16（行677〜687）、§18 OPEN-002（行712〜717）。
