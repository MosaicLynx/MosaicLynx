## 5. 要約

- Relay は内容を解釈しない / 信頼されていない通信経路であり、トランザクション / メッセージ意味、承認、認証、アカウントの利用認可、署名、Signer 結果、4条件および Mainnet 判定条件の判断権限を持たない。
- `transport status` は Relay の受理、保存、取得、受領確認、キャンセル、期限切れ、削除等の通信経路観測として定義され、Signer が生成した `deliveryDisposition` と同じ意味の Relay 内のフィールド / 状態として再利用されていない。
- `PENDING`、`DELIVERED`、`DELIVERY_UNKNOWN` は信頼された Signer が既知の署名済み結果に付与する配送 axis であり、Relay は値を生成、推測、変更または確認しない。受領確認 / `consumed`、取得、HTTP 2xx、削除および Relay 内の `delivered` は `DELIVERED` を意味しない。
- `RESULT_UNKNOWN` は信頼された Signer が署名生成自体の成否を確定できない場合だけ、`DELIVERY_UNKNOWN` は既知の署名済み結果を保持したまま Signer 側の配送処理結果の区分を確定できない場合だけ成立する。タイムアウト、ネットワーク / 保存領域失敗、状態消失、応答欠如、受領確認失敗等から Relay / SDK は生成しない。
- 既知の署名済み結果の復旧は再送、再配送、取得、照会に限定され、新しい署名 / 再署名と分離されている。Relay は自動再署名、ローカル / リモート、Provider、Signer の自動代替経路を開始・要求しない。
- 認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認の4条件と Mainnet リリース / 根拠判定条件は信頼された Signer / リリース判断権限の責任であり、Relay のセッション、トークン、世代、通信経路成功または利用可能性は代替にならない。Mainnet 判定条件失敗 / 不明でも安全な Testnet 専用操作の継続を不必要に妨げない。

## 9. 解消済みの指摘

### RLS-001 — 受領確認 / キャンセル意味

- **重要度 / 状態:** `Major` / `Resolved`
- **対象箇所:** `relay.md` §5.2、§8.2、§13.1、§13.2、§14.1、§15.1、§16.1
- **確認できた事実:** 受け渡し §9.6 の外形が妥当な受領確認 / キャンセルは常に `204 No Content` とし、状態変更は正しい endpoint-scoped `webToken`、対応セッション、`response_available` または適用可能な有効なライフサイクル、現在の世代 / ライフサイクル等を確認できる場合だけ行う。それ以外は状態を変更しない操作であり、不明セッション、トークン不一致、終端 / 削除、期限切れ、重複、世代不一致、状態消失を応答差異から露出させない。
- **上流根拠:** [`web-transaction-handoff-spec.md` §9.6](../../specifications/web-transaction-handoff-spec.md#96-受領確認とキャンセル)。
- **今回の判定:** `204` を変更成功、セッション存在、トークン有効性、署名成功、署名キャンセル成功、未署名またはアプリケーション処理成功と解釈しないことも各エンドポイントに明記されている。回帰なし。
- **完了条件 / 再確認方法:** §13.1 / §13.2 の HTTP 応答と状態変更の分離、§14.1 / §15.1 / §16.1 の状態を変更しない操作 / 状態消失意味が受け渡し §9.6 と一致すること。充足。

### SR-001 — 通信経路状態と Signer が生成した `deliveryDisposition`

- **重要度 / 状態:** `Critical` / `Resolved`
- **対象箇所:** `relay.md` §2.2、§7.2、§13.3、§14.1、§14.3、§20、§21、§22、§23
- **確認できた事実:** Relay 内のは `transport status` とし、`accepted`、`stored`、`available`、`retrieved`、`consumed` 等を通信経路ライフサイクル観測として扱う。一方、`deliveryDisposition` と `PENDING`、`DELIVERED`、`DELIVERY_UNKNOWN` は既知の署名済み結果に付随する Signer が生成したフィールドとして信頼された Signer に限定される。Relay は generate、推測、derive、昇格、格下げ、rewrite、正規化、統合、replace、confirm を行わない。
- **上流根拠:** [`interfaces.md` §10.3](../../specifications/interfaces.md#103-不明結果と配送処理結果の区分)、[`signing-protocol.md` §19.3](../../specifications/signing-protocol.md#193-配送処理結果の区分)、[`web-transaction-handoff-spec.md` §7.2](../../specifications/web-transaction-handoff-spec.md#72-論理応答)。
- **確認できた事実:** 暗号化された応答に処理結果の区分が含まれても Relay は内容を解釈しないバイト列 / エンベロープとして意味保持して中継する。`retrieved`、受領確認、`consumed`、HTTP 2xx、削除、`unavailable` または Relay 内の `delivered` は `DELIVERED` を意味しない。小文字の Relay 状態 `pending` と大文字の Signer 処理結果の区分 `PENDING` も別物である。
- **完了条件 / 再確認方法:** Relay / SDK が通信経路観測から `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` を生成・推測・確定せず、応答内の Signer が生成した値だけを意味不変にそのまま通過させるすること。§14.3、§20、§22 および事例 A〜E で充足。

### SR-002 — 4条件 / Mainnet 判定条件の Relay 判断権限を持たないこと

- **重要度 / 状態:** `Minor` / `Resolved`
- **対象箇所:** `relay.md` §4.2、§20、§21、§22、§23
- **確認できた事実:** 認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認は同一要求 / 対象 / プロファイル内の文脈に対する信頼された Signer の独立した必須条件と列挙され、Relay は評価、establish、意味上の検証、キャッシュ、復元、推測、substitute しない。セッション存在、参加者受け入れ判定、トークン、世代、要求 / 応答存在、保存済み / 利用可能、取得、受領確認、消費済み、通信経路成功および利用可能性も代替にならない。
- **上流根拠:** [`requirements.md` CR-016 / CR-AC-017](../../requirements/requirements.md#cr-016-署名可能状態の共通前提-signer-end-to-end)、[`interfaces.md` §7.4](../../specifications/interfaces.md#74-mainnet-署名対応能力判定条件)、[`signing-protocol.md` §21.1](../../specifications/signing-protocol.md#211-互換性)。
- **確認できた事実:** Mainnet 対応能力は信頼された Signer と現在のリリース / 根拠判定条件の成立時だけ有効であり、Relay は評価器、検証者、promoter、迂回仕組みではない。判定条件が欠落、無効な、期限切れ、不整合の、検証不能の、不明の場合の Mainnet 無効 / 利用不能は信頼された Signer / リリース判断権限が決め、Testnet 専用操作の安全な継続を妨げない。
- **完了条件 / 再確認方法:** §20 のセキュリティ上の不変条件、§21 のコンポーネントの責務、§22 の受け入れ / 事例 F および §23 の追跡可能性から、4条件と Mainnet 判定条件の Relay 判断権限を持たないことが独立に検証できること。充足。
