## 5. 要約

前回の `MSR-001`〜`MSR-003` は、今回の本文で完了条件を満たしている。

- `§1.1` は契約所有責任を基準に共通の契約の判断権限とモバイル固有の specialization を分離し、共通の競合はモバイル側で上書きせず未決 / 文書間の課題として扱うため、`MSR-001` は解消した。
- `§16` は観測可能性 / 補助的な出力と規範的な受け渡し応答を明確に分離し、既存契約が要求する公開結果を正常応答に含められる一方、秘密情報と観測可能性への無制限な複製を禁止しているため、`MSR-002` は解消した。
- `§9.3` と `§13.1` は `AUTHENTICATING` をモバイルアプリ内部だけのローカル UI / 認証内部手順と明示し、共通の厳密な状態、公開 / 通信上の / Relay / 永続的な状態、応答フィールドおよび SDK 契約から除外しているため、`MSR-003` は解消した。

ただし、全文再確認で `§18` のセキュリティ上の不変条件 17 に新しい主要指摘を確認した。`raw payload` を `external channel、Relay、SDK、log、diagnostics または persistent plain storage` へ漏らしてはならないという無限定な MUST は、共通の受け渡し / インターフェースが正常な署名済み応答に必須とする `SignedTransaction.payload` および `SignedData` の伝達と両立しない解釈を許す。`§16` の応答 exemption だけでは、`§18` の別の MUST を安全に限定できない。

## 7. 必須の修正

### `MSR-004`: `§18` の `raw payload` 禁止が規範的な署名済み応答と両立しない

- **重要度 / 状態:** `Major` / `New`
- **対象箇所:** [`mobile-app.md`](../../specifications/mobile-app.md) `§18` 項目 17、現在 657 行目。関連箇所は `§12.1` 403〜414 行目、`§16` 573〜595 行目。
- **発生条件・確認できた事実:** `§18` 項目 17 は、ニーモニック等の秘密情報と並べて `raw payload` を `external channel、Relay、SDK、log、diagnostics または persistent plain storage` へ漏らしてはならないと定める。`raw payload` は本仕様の用語表で定義されず、要求ペイロードのみを指すのか、署名済みペイロードを含むのかが限定されていない。
- **既存の根拠:** [`interfaces.md`](../../specifications/interfaces.md) §9.6 は `SignedTransaction` の必須公開フィールドとして `payload`、`hash`、`signerPublicKey` を定める。同仕様 §6.3 と [`web-transaction-handoff-spec.md`](../../specifications/web-transaction-handoff-spec.md) §7.2 は `signed` / `dataSigned` 応答に署名済み結果を必須とする。受け渡し §5.2.1 はその応答を SDK の公開署名結果として dApp へ伝達する。共通要件 `CR-008` / `CR-NFR-002` および署名プロトコル §20 は秘密情報と **不要な** 生のペイロードの露出を禁止するが、必須公開署名済み結果を禁止していない。`§16` は同じ対象本文でも規範的な応答を許可している。
- **問題:** `raw payload` を文字どおり適用すると、モバイルアプリが必須 `signedTransaction.payload` を SDK / 外部応答へ返せず、`signed` / `dataSigned` の応答共用体を実装できない。これを「未署名の要求ペイロード」などの意図として解釈する場合でも、対象本文はその区別を定めておらず、実装者が応答必須フィールドを禁止するか許可するかを推測する必要がある。`§16` の観測可能性境界はログ出力複製を限定する修正であり、`§18` の外部チャネル / SDK に及ぶ独立した MUST を解消しない。
- **影響:** 正常な公開応答、SDK / dApp との相互運用性、dApp の独立検証および追跡可能性が実装者ごとに分岐する。より緩い解釈では `raw payload` の秘密性・公開性の境界が曖昧なままになり、セキュリティ上の不変条件も検証不能になる。これは仕様の必須外部契約 / 相互運用性を妨げる主要課題である。
- **必要な最小修正または確認:** `raw payload` の意味と対象範囲を、共通の受け渡し / インターフェースが要求する正常応答の公開署名済み結果と衝突しない形で限定する。少なくとも必須 `signedTransaction.payload`、`SignedData` およびその他共通の契約が定める公開応答フィールドは正常応答として許可し、秘密情報、不要な生の要求 / ペイロード、エラー、ログ、診断情報、Relay メタデータ等の補助出力への複製は引き続き禁止することを本文上明確にする。具体的なフィールド名や応答構造は共通の仕様に委譲する。
- **完了条件・再確認方法:** `§18` 項目 17、`§12`、`§15`、`§16`、インターフェース §6.3 / §9.6 / §10.3、受け渡し §7.2 / §10 を再照合し、`signed`、`dataSigned`、`resultUnknown`、`rejected`、`failed` の共用体、必須公開署名済み結果、`deliveryDisposition` および秘密情報 / 観測可能性禁止が同時に成立することを確認する。SDK / dApp への必須応答と観測可能性 / 補助的な出力の複製を区別できることも確認する。

## 9. 解消済みの指摘

### `MSR-001`: 判断権限優先順位の自己矛盾 — 解消済み

`§1.1` は文書全体の順位ではなく契約所有責任を判断権限の基準とし、共通の要求 / 応答、フィールド、状態、エラー、署名結果、`RESULT_UNKNOWN`、`deliveryDisposition`、シリアライズ、チェーン / ネットワーク、プロファイル / アカウント、受け渡し、バージョン / 対応能力、リリース / 根拠を既存の各仕様 / ポリシーの判断権限とした。モバイルはライフサイクル、信頼されたホスト、プラットフォーム境界、モバイル検証、信頼された UI、追加のセキュリティ制限および安全側での終了条件を共通の契約と両立する追加制約として定めるだけで、上書き判断権限を持たない。共通との矛盾はモバイル側で選択せず、未決 / 文書間の課題とする。

`§12` の応答対応付け、`§13.1` の共通の厳密な状態、`§17` のリリース / 根拠判断権限、`§19` のエラー対応付け / 委譲 / 未決、`§21` の追跡可能性もこの境界と矛盾しない。よって前回の self-contradiction は解消した。

### `MSR-002`: 診断情報禁止が規範的な応答を禁止 — 解消済み

`§16` は観測可能性 / 補助的な出力をログ、警告、例外、診断情報、利用状況分析、遠隔計測データ、異常終了報告書、サポート出力、Relay メタデータ等に限定し、規範的な受け渡し応答および SDK / dApp へ伝える公開結果をその禁止対象から除外した。既存契約が定める場合に限り要求対応付け、署名済みトランザクション / データ、署名、ハッシュ、Signer 公開鍵、アカウントの公開識別情報、`deliveryDisposition` 等を正常応答に含められること、ただし応答共用体やフィールドを本書が新規発明しないことも明記した。秘密情報は正常応答にも含めず、公開結果を観測可能性へ複製することも許可していない。

`§12.1` の `signed` / `dataSigned` / `resultUnknown` / `rejected` / `failed` 対応付けはインターフェース §6.3、受け渡し §7.2、SDK の公開対応付けと整合する。この点について前回指摘は解消した。ただし `§18` の別の無限定な `raw payload` 禁止は `MSR-004` として別途残る。

### `MSR-003`: `AUTHENTICATING` のモバイルローカル内部手順境界 — 解消済み

`§9.3` は共通のライフサイクル表から `AUTHENTICATING` を除外し、`§13.1` は共通の厳密な状態図を `RECEIVED → VALIDATED → INSPECTED → AWAITING_USER → AUTHORIZED → SIGNING → SUCCEEDED` と明示した。そのうえで `AUTHENTICATING` を `AWAITING_USER` と `AUTHORIZED` の間のモバイルアプリ内部ローカル UI / 認証 / 利用者の立ち会い内部手順とし、共通の署名状態、公開状態、通信上の状態、応答フィールド、Relay 状態、永続的な状態、SDK 契約へシリアライズ / expose しないことを定めている。認証は四条件の一つとして維持され、ローカル失敗 / 古くなった / 失効済み / ロック済み / 文脈不一致では旧認証 / 認可を再利用しない。よって前回曖昧さは解消した。

## 10. 後続工程へ委譲する指摘

正式な未解消指摘の後工程委譲はない。`§19.3` に記録された既存未決は、仕様として未決定のまま下位判断権限へ委譲される事項であり、今回の新規指摘の代替や解消扱いにはしていない。

## 15. 残存リスクと未決定事項

- `MSR-004` が残る場合、モバイルが必須 `signedTransaction.payload` / `SignedData` を SDK / dApp へ返すことの可否が実装者ごとに分岐し、`signed` / `dataSigned` の相互運用性が成立しない。
- `MSR-001`〜`MSR-003` は解消済みだが、`§18` の別箇所に残った `raw payload` の対象範囲を明確化しなければ、秘密情報境界と規範的な応答境界の全体は閉じない。
- 現行公開モバイルビルドはリリース資料に従い Testnet 専用であり、本文とリリース判断権限に整合する。これは指摘ではない。
- `MOB-OPEN-*`、`MR-OPEN-*`、`CR-OPEN-*`、インターフェース / Relay / SDK の既存未決は、モバイルが安全下限を弱めず保持している。未決事項を convenience だけで閉じたり、モバイル固有のフィールド / エラー / 対応能力へ昇格させたりしてはならない。
- モバイルアプリの送信元 / 実行環境は現在のワークスペースに存在しないため、今回の判定は文書契約のレビューであり、実行環境が本文どおりであることの証拠ではない。
