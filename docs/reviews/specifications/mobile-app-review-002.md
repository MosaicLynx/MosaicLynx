## 5. Summary

前回の `MSR-001`〜`MSR-003` は、今回の本文で completion condition を満たしている。

- `§1.1` は contract ownership を基準に common contract の authority と Mobile-specific specialization を分離し、common conflict は Mobile 側で override せず OPEN / cross-document issue として扱うため、`MSR-001` は解消した。
- `§16` は observability / auxiliary output と normative Handoff response を明確に分離し、既存 contract が要求する public result を正常 response に含められる一方、secret と observability への無制限な複製を禁止しているため、`MSR-002` は解消した。
- `§9.3` と `§13.1` は `AUTHENTICATING` を Mobile App 内部だけの local UI / authentication substep と明示し、common exact state、public / wire / Relay / persistent state、response field および SDK contract から除外しているため、`MSR-003` は解消した。

ただし、全文再確認で `§18` の security invariant 17 に新しい Major finding を確認した。`raw payload` を `external channel、Relay、SDK、log、diagnostics または persistent plain storage` へ漏らしてはならないという無限定な MUST は、common Handoff / Interfaces が正常な signed response に必須とする `SignedTransaction.payload` および `SignedData` の伝達と両立しない解釈を許す。`§16` の response exemption だけでは、`§18` の別の MUST を安全に限定できない。

## 7. Required Changes

### `MSR-004`: `§18` の `raw payload` 禁止が normative signed response と両立しない

- **Severity / Status:** `Major` / `New`
- **対象箇所:** [`mobile-app.md`](../../specifications/mobile-app.md) `§18` item 17、現在 657 行目。関連箇所は `§12.1` 403〜414 行目、`§16` 573〜595 行目。
- **発生条件・確認できた事実:** `§18` item 17 は、Mnemonic 等の secret と並べて `raw payload` を `external channel、Relay、SDK、log、diagnostics または persistent plain storage` へ漏らしてはならないと定める。`raw payload` は本仕様の用語表で定義されず、request payload のみを指すのか、signed payload を含むのかが限定されていない。
- **既存の根拠:** [`interfaces.md`](../../specifications/interfaces.md) §9.6 は `SignedTransaction` の required public field として `payload`、`hash`、`signerPublicKey` を定める。同仕様 §6.3 と [`web-transaction-handoff-spec.md`](../../specifications/web-transaction-handoff-spec.md) §7.2 は `signed` / `dataSigned` response に signed result を required とする。Handoff §5.2.1 はその response を SDK の公開 signing result として dApp へ伝達する。共通 Requirements `CR-008` / `CR-NFR-002` および Signing Protocol §20 は secret と **不要な** raw payload の露出を禁止するが、required public signed result を禁止していない。`§16` は同じ対象本文でも normative response を許可している。
- **問題:** `raw payload` を文字どおり適用すると、Mobile App が required `signedTransaction.payload` を SDK / external response へ返せず、`signed` / `dataSigned` の response union を実装できない。これを「unsigned request payload」などの意図として解釈する場合でも、対象本文はその区別を定めておらず、実装者が response 必須 field を禁止するか許可するかを推測する必要がある。`§16` の observability 境界は logging 複製を限定する修正であり、`§18` の external channel / SDK に及ぶ独立した MUST を解消しない。
- **影響:** 正常な public response、SDK / dApp との相互運用性、dApp の独立検証および traceability が実装者ごとに分岐する。より緩い解釈では `raw payload` の秘密性・公開性の境界が曖昧なままになり、security invariant も検証不能になる。これは specification の required external contract / interoperability を妨げる Major issue である。
- **必要な最小修正または確認:** `raw payload` の意味と scope を、common Handoff / Interfaces が要求する正常 response の public signed result と衝突しない形で限定する。少なくとも required `signedTransaction.payload`、`SignedData` およびその他 common contract が定める public response field は正常 response として許可し、secret、不要な raw request / payload、error、log、diagnostics、Relay metadata 等の補助出力への複製は引き続き禁止することを本文上明確にする。具体的な field 名や response shape は common Specification に委譲する。
- **完了条件・再確認方法:** `§18` item 17、`§12`、`§15`、`§16`、Interfaces §6.3 / §9.6 / §10.3、Handoff §7.2 / §10 を再照合し、`signed`、`dataSigned`、`resultUnknown`、`rejected`、`failed` の union、required public signed result、`deliveryDisposition` および secret / observability 禁止が同時に成立することを確認する。SDK / dApp への required response と observability / auxiliary output の複製を区別できることも確認する。

## 9. Resolved Findings

### `MSR-001`: authority precedence の自己矛盾 — Resolved

`§1.1` は文書全体の順位ではなく contract ownership を authority の基準とし、common request / response、field、state、error、signing result、`RESULT_UNKNOWN`、`deliveryDisposition`、serialization、Chain / Network、Profile / Account、Handoff、version / capability、release / evidence を既存の各 Specification / policy の authority とした。Mobile は lifecycle、trusted host、platform boundary、Mobile validation、trusted UI、additional security restriction および fail-closed condition を common contract と両立する追加制約として定めるだけで、override authority を持たない。共通との矛盾は Mobile 側で選択せず、OPEN / cross-document issue とする。

`§12` の response mapping、`§13.1` の common exact state、`§17` の release / evidence authority、`§19` の error mapping / delegation / OPEN、`§21` の traceability もこの境界と矛盾しない。よって前回の self-contradiction は解消した。

### `MSR-002`: diagnostics 禁止が normative response を禁止 — Resolved

`§16` は observability / auxiliary output を log、warning、exception、diagnostics、analytics、telemetry、crash report、support output、Relay metadata 等に限定し、normative Handoff response および SDK / dApp へ伝える public result をその禁止対象から除外した。既存 contract が定める場合に限り request correlation、signed transaction / data、signature、hash、signer public key、public Account identity、`deliveryDisposition` 等を正常 response に含められること、ただし response union や field を本書が新規発明しないことも明記した。secret は正常 response にも含めず、public result を observability へ複製することも許可していない。

`§12.1` の `signed` / `dataSigned` / `resultUnknown` / `rejected` / `failed` mapping は Interfaces §6.3、Handoff §7.2、SDK の公開 mapping と整合する。この点について前回 finding は解消した。ただし `§18` の別の無限定な `raw payload` 禁止は `MSR-004` として別途残る。

### `MSR-003`: `AUTHENTICATING` の Mobile local substep 境界 — Resolved

`§9.3` は common lifecycle 表から `AUTHENTICATING` を除外し、`§13.1` は common exact state diagram を `RECEIVED → VALIDATED → INSPECTED → AWAITING_USER → AUTHORIZED → SIGNING → SUCCEEDED` と明示した。そのうえで `AUTHENTICATING` を `AWAITING_USER` と `AUTHORIZED` の間の Mobile App 内部 local UI / authentication / user-presence substep とし、common signing state、public state、wire state、response field、Relay state、persistent state、SDK contract へ serialize / expose しないことを定めている。Authentication は四条件の一つとして維持され、local failure / stale / revoked / locked / context mismatch では old Authentication / authorization を再利用しない。よって前回 ambiguity は解消した。

| Recovery / re-sign boundary          | **Pass**             | `§12.4`、`§14` が known result の resend / redelivery / retrieval / lookup と新しい signing generation を分離し、別 Account、Signer、Provider、transport への automatic fallback を禁止している。                                                                                                                                                       |
| Lifecycle / state loss / concurrency | **Pass**             | `§13`〜`§14` が background、suspend、resume、device lock、process termination、OS kill、crash、network / Relay failure、generation / Profile / Account / permission change、duplicate、replay、timeout、cancellation、local / remote mismatch を扱い、old approval / auth / unlock / authorization / target / secret を自動再利用しない。               |
| Common state set / `AUTHENTICATING`  | **Pass**             | `§9.3` と `§13.1` が common exact state set と Mobile local-only substep を明確に分離し、`AUTHENTICATING` を public / wire / Relay / persistent state にしない。                                                                                                                                                                                        |
| Secret boundary / wallet-core        | **Fail — `MSR-004`** | secret の外部・SDK・Relay・log・diagnostics・clipboard・notification・persistent plain storage への漏洩禁止と wallet-core delegation は維持されるが、`§18` item 17 が required public signed payload まで禁止し得る。                                                                                                                                   |

| Existing OPEN                        | **Pass — deferred**  | `§19.3` の `MOB-OPEN-001`〜`009`、`MR-OPEN-001`〜`008`、`CR-OPEN-001` / `002`、`OPEN-RELAY-003` / `004`、`OPEN-SDK-004` および common `OPEN-001`〜`006` への委譲は前回対象から追加・削除・close・意味変更されていない。各 OPEN は implementation choice と既存 authority で決める必要のある事項として妥当であり、安全下限を弱める根拠にはなっていない。 |
| Interoperability / traceability      | **Fail — `MSR-004`** | common Handoff / Interfaces の signed result を SDK / dApp へ伝える contract と、Mobile §18 の `raw payload` MUST の境界が一意でない。その他の主要 traceability は確認できる。                                                                                                                                                                          |

Adversarial check では、malicious dApp、forged external invocation、stale / tampered Relay response、replay、request / Account / Chain / Network substitution、Profile switch、resume after approval、process loss、result loss、duplicate、delayed response、Relay compromise、misleading notification、OS lifecycle interruptionを確認した。これらに対する request / target / context binding、fresh gate、trusted inspection、fail-closed、no automatic re-sign / fallback および Relay non-authority は維持されている。追加で、required signed payload が `§18` の `raw payload` 禁止に該当する場合の response union failure を確認し、`MSR-004` とした。

## 15. Remaining Risks and Open Decisions

- `MSR-004` が残る場合、Mobile が required `signedTransaction.payload` / `SignedData` を SDK / dApp へ返すことの可否が実装者ごとに分岐し、`signed` / `dataSigned` の interoperability が成立しない。
- `MSR-001`〜`MSR-003` は Resolved だが、`§18` の別箇所に残った `raw payload` の scope を明確化しなければ、secret boundary と normative response boundary の全体は閉じない。
- 現行公開 Mobile build は release 資料に従い Testnet-only であり、本文と release authority に整合する。これは finding ではない。
- `MOB-OPEN-*`、`MR-OPEN-*`、`CR-OPEN-*`、Interfaces / Relay / SDK の既存 OPEN は、Mobile が安全下限を弱めず保持している。未決事項を convenience だけで閉じたり、Mobile-specific field / error / capability へ昇格させたりしてはならない。
- Mobile App の source / runtime は現在の workspace に存在しないため、今回の判定は文書 contract の review であり、runtime が本文どおりであることの証拠ではない。

なし。対象 Specification、Requirements、Design、関連 Specification、ADR、source、test および前回レビュー成果物は変更していない。変更対象は本レビュー成果物だけである。

## 17. Final Decision

`REVISE SPECIFICATION`

`MSR-001`、`MSR-002`、`MSR-003` は解消した。新規 `MSR-004` は `Major` の blocking finding である。Critical はない。`§18` item 17 の `raw payload` と common normative response の境界を明確化し、Interfaces / Handoff の response union と secret / observability boundary を再照合するまで、Mobile App Specification は次工程へ進めない。
