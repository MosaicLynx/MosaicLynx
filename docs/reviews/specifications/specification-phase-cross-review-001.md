## 4. レビュー結果

`REVISE SPECIFICATION`

現行仕様は、安全性の中核である四つの条件、信頼された内容検査、wallet-core 境界、Relay の内容を解釈しない / 信頼されていない境界、`RESULT_UNKNOWN` と `deliveryDisposition` の基本分離、プロファイル / アカウント / チェーン / ネットワーク結び付け、Mainnet 安全側での終了を概ね共有している。

しかし、次の判定を妨げる文書間の課題が残っている。

- プロダクトの旧公開 API が共通の / 受け渡し / SDK / ブラウザ契約と競合し、内部アカウント選択子、別操作名、修飾のない結果、別フィールドを規範的なに見せている。
- Provider の `connect` 収集と SDK / 受け渡しの単数有効なアカウントの対応付けが定義されていない。
- ブラウザのポップアップ / タブ終了が、共通の規則の除外するライフサイクル消失から `RESULT_UNKNOWN` または `DELIVERY_UNKNOWN` を生成し得るように読める。
- 受け渡しが Node.js / Redis / Lua / Pub/Sub / Redis TTL を固定している一方、Relay 仕様は保存領域バックエンド / 配置構成を `OPEN-RELAY-002` として未決にしている。
- 受け渡し、プロダクト、プロファイル、チェーンに、主要契約を要件 → 設計 → 仕様へ逆追跡できる追跡可能性が不足している。
- 将来バックアップ対応能力について、プロダクトとプロファイルが暗号・削除契約を異なる粒度で規範化しているが、共通の未決 / 責任主体がない。

したがって、個別レビューの `READY` は維持したまま履歴として扱うが、仕様工程全体は実装へ移行できない。

## 7. 必須の修正

### `SPCR-001` — プロダクト公開契約の共通の契約への収束

- **対象箇所:** [`product-spec.md` §11.1 / §11.3 / §16](../../specifications/product-spec.md)、[`interfaces.md` §5.3 / §6.3](../../specifications/interfaces.md)、[`web-transaction-handoff-spec.md` §5.1 / §5.2](../../specifications/web-transaction-handoff-spec.md)。特にプロダクトの `accountId`、`accountIds`、`activeAccountId`、`recipientPublicKey`、`Account[]`、修飾のない `SignedMessage` / `SignedTransaction`。
- **事実 / 条件:** プロダクトは `accountId` を署名要求選択子として受け付け、`display name` を dApp へ返し、`signMessage` / `signTransaction` が修飾のない結果を返す構造を現在形で規範化している。共通の / 受け渡し / SDK は公開識別情報を `Scope + address + publicKey` に限定し、内部選択子を禁止し、`expectedSignerPublicKey` と `MosaicLynxSigningResult<T>` / `signData` を使用する。
- **既存の判断権限:** 共通の公開識別情報 / 応答 / エラー / 結果はインターフェース、具体的な SDK / 受け渡し API は受け渡しと SDK、Provider 境界はブラウザ拡張機能が責任主体。プロダクトはこれらを上書きしない。
- **課題 / 影響:** dApp、SDK、Provider、署名主体間で別フィールドと別結果意味が実装され得る。内部アカウント選択子によるアカウント差し替えを許し、`RESULT_UNKNOWN` / `deliveryDisposition` の公開意味を失う経路も生じる。
- **最小修正 / 確認:** プロダクトの現在の公開契約を共通の / 受け渡し契約に更新するか、旧構造を明確に historical / 非推奨の / 対象外として規範的な対象範囲から除外し、必要な移行判断を責任主体付き未決として記録する。新しい別名や選択子を追加して解消してはならない。
- **完了 / 再確認:** プロダクトの公開 API、アカウントフィールド、署名結果、具体的なエラーがインターフェース / 受け渡し / SDK / ブラウザの一つの対応付けへ収束し、`accountId` 等が外部判断権限でないことを横断レビューで再確認する。

### `SPCR-002` — アカウント応答の型・要素数対応付け

- **対象箇所:** [`web-transaction-handoff-spec.md` §5.1 / §5.2](../../specifications/web-transaction-handoff-spec.md) の `MosaicLynxActiveAccount` と単数 `connect()`、[`sdk.md` §5](../../specifications/sdk.md) の単数返却、[`browser-extension.md` §5.2](../../specifications/browser-extension.md) およびプロダクト §16 の収集返却、[`interfaces.md` §6.3](../../specifications/interfaces.md) の `connected.account: PublicAccountIdentity`。
- **事実 / 条件:** `MosaicLynxActiveAccount` と `PublicAccountIdentity` のフィールドは現状同型だが、Provider / プロダクトの `connect` は readonly 収集、SDK / 受け渡しは単数有効なアカウントである。複数の許可アカウントから SDK の返す一件を選ぶ判断権限、または収集を SDK へ公開する対応付けが定義されていない。
- **既存の判断権限:** 公開アカウントフィールドはインターフェース、SDK 公開返却は SDK / 受け渡し、Provider アダプター対応付けはブラウザ / 受け渡しの境界で定義する。プロファイル既定やページ選択子は判断権限ではない。

- **完了 / 再確認:** ブラウザ → SDK → dApp とモバイル → SDK → dApp のアカウント応答が同じ公開識別情報意味と明示的要素数対応付けを持つことを確認する。

### `SPCR-003` — ブラウザライフサイクルと不明意味の限定

- **対象箇所:** [`browser-extension.md` §21](../../specifications/browser-extension.md) のポップアップ / 承認 window 終了、§23 の `approval UI close / tab close`、および §20 / §22 の `RESULT_UNKNOWN` 限定。比較対象は [`interfaces.md` §10.3](../../specifications/interfaces.md) と [`signing-protocol.md` §6.2 / §19.3](../../specifications/signing-protocol.md)。
- **事実 / 条件:** ブラウザは「ポップアップ / 承認 window 終了」「タブ終了」で「署名成否が不明なら `RESULT_UNKNOWN`」、「確定結果の配送だけが不明なら `DELIVERY_UNKNOWN`」と記載している。一方共通の契約は SDK タイムアウト、Provider 接続解除、ページ / SDK / Relay ライフサイクル消失、応答欠如、配送失敗だけでは署名主体が不明を生成しないと明記する。
- **既存の判断権限:** `RESULT_UNKNOWN` は信頼された署名主体が署名生成自体を確定できない場合だけ、`DELIVERY_UNKNOWN` は信頼された署名主体が有効な署名済み結果を保持した上で配送処理結果の区分を確定できない場合だけ成立する。ブラウザ終了 / ページ配送自体は判断権限ではない。
- **課題 / 影響:** UI 終了またはページライフサイクルイベントだけで不明を生成できる解釈が残り、通信経路 / 利用者キャンセルと署名主体世代不確実性が混同される。既存結果復旧、再署名禁止および dApp のエラー処理が崩れる。
- **最小修正 / 確認:** ブラウザ固有の終了の記述を、信頼された署名主体が独立に確認した世代不確実性が存在する場合だけ不明とする条件へ限定する。一般的な終了、タブ終了、Provider 応答消失、ページ配送失敗は共通のキャンセル / 無効化 / 通信経路意味に従い、単独では不明を生成しない。
- **完了 / 再確認:** ブラウザの全終了 / 異常終了 / response-loss 表と共通の除外一覧を再突合し、署名主体のみのオリジンと確定済みの結果保持を確認する。

### `SPCR-004` — 受け渡しと Relay の保存領域判断権限の整合

- **対象箇所:** [`web-transaction-handoff-spec.md` §7.1 / §9.7](../../specifications/web-transaction-handoff-spec.md)、[`relay.md` §2.3 / §24 `OPEN-RELAY-002`](../../specifications/relay.md)、[`docs/design/architecture.md` §16〜§17](../../design/architecture.md)、[`docs/design/relay.md` §19.3](../../design/relay.md)。
- **事実 / 条件:** 受け渡しは自己ホスト MVP について Node.js Relay、非永続 Redis、Redis Lua、Redis Pub/Sub、Redis absolute TTL、RDB / AOF / volume / バックアップ無効化、HMAC 鍵を具体的に要求する。Relay 仕様は保存領域エンジン、スキーマ、キュー、ロック、CAS、ブローカー、クラスター、配置を対象外とし、バックエンド / 構成を `OPEN-RELAY-002` として未決にしている。アーキテクチャ / Relay 設計も具体バックエンドを委譲している。
- **既存の判断権限:** 受け渡しはエンドポイント、通信上の、認証情報、E2E、世代、TTL、HTTP のプロトコル判断権限。Relay の保存領域 / 配置選択は Relay 操作 / 設計判断権限に委譲され、現在 `OPEN-RELAY-002` である。
- **課題 / 影響:** 受け渡しを実装すると Relay 未決を暗黙に終了することになり、異なる保存領域 / 配置を選ぶ実装は受け渡し非準拠となる。プロトコル契約と実装選択が逆転し、工程境界も逸脱する。
- **最小修正 / 確認:** 受け渡しの具体的な Node.js / Redis 実装 paragraph をプロトコル要求から分離し、Relay 操作 / 設計の決定または既存未決へ戻す。論理状態、上限のある保持、状態消失、内容を解釈しない境界、セキュリティ上の不変条件は維持し、バックエンドを今回のレビューで決定しない。
- **完了 / 再確認:** 受け渡しと Relay のエンドポイント / 論理的なライフサイクルは一致し、バックエンド / 構成の判断権限と未決責任主体が一意であることを確認する。

### `SPCR-006` — 将来バックアップの対象範囲 / 暗号処理判断権限

### `SPCR-007` — `signMessage` / `signData` 操作対応付け

- **対象箇所:** [`browser-extension.md` §5.1 / §5.2](../../specifications/browser-extension.md) のページに公開する `signMessage`、[`sdk.md` §5.2](../../specifications/sdk.md)、[`web-transaction-handoff-spec.md` §2 / §5.2 / §7](../../specifications/web-transaction-handoff-spec.md)、[`interfaces.md` §6.4 / §9.4](../../specifications/interfaces.md)、[`mobile-app.md` §10.3](../../specifications/mobile-app.md)。
- **事実 / 条件:** 共通の論理的な操作、SDK、受け渡し、モバイル通信上のは `signData` / `MESSAGE_SIGN` を使用する。ブラウザページに公開する Provider は `signMessage` を使用するが、`signMessage` → `signData` の一対一操作対応付け、`data` / `payload` 対応付け、`expiresAt` / `messageExpiresAt`、結果対応付けが一つの表として定義されていない。ブラウザは「既存構造化されたメッセージ」とだけ記述し、受け渡しは SDK の `signData` を具体的なにする。
- **既存の判断権限:** 共通の操作 / 構造化されたメッセージはインターフェース、SDK 公開 API / 受け渡し応答は SDK / 受け渡し、Provider 固有のページメソッドはブラウザのアダプター境界。`messageExpiresAt` と `expiresAt` の競合は既存 `OPEN-001` であり、この指摘で終了しない。
- **課題 / 影響:** ブラウザ dApp と SDK / モバイルの操作、フィールド、期限切れ、エラー / 結果が別プロトコルとして実装され、メッセージ署名がトランザクション署名や生バイト列署名へ誤射影される可能性がある。
- **最小修正 / 確認:** Provider メソッドを `signMessage` とするなら、既存共通の `signData` への明示的アダプター対応付けとページに公開するフィールド / 結果 / エラー意味を定義する。正規操作を変更する場合はプロダクト / ブラウザ / SDK / 受け渡しの判断権限を同時に更新する。新しい別名や期限切れ変換を独断で追加せず `OPEN-001` を維持する。
- **完了 / 再確認:** 拡張機能とモバイルの両経路で、同一要求識別情報、`MESSAGE_SIGN`、構造化されたメッセージ、署名主体結果、配送 / 不明対応付けが一意になることを確認する。

### 追跡可能性不足

受け渡し、プロダクト、プロファイル、チェーンの各仕様は、上流へのリンクや相互参照は持つが、主要契約を要求 ID → 設計節 → 仕様節 → 責任主体 / 未決へ逆追跡する対応表を持たない。これは文書形式の問題に留まらず、今回発見したプロダクト旧式の契約、受け渡し保存領域競合、将来バックアップ divergence を判定条件前に検知できない直接原因となっている。`SPCR-005` の完了条件とする。
