## 5. 要約

対象本文は、モバイルホスト / 信頼された Signer を最終的な署名判断権限とし、外部入力を信頼されていないとして再検証する責任、信頼されたフォアグラウンド UI、認証・署名可能な状態へのロック解除・アカウントの利用認可・利用者による明示的な承認の独立した四条件、同一文脈への結び付け、チェーン / ネットワークの分離、Relay の内容を解釈しない境界、Signer のみの `RESULT_UNKNOWN` / `deliveryDisposition`、確定済みの結果復旧、ライフサイクル無効化、秘密情報の分離、Mainnet 安全側での終了および Testnet 専用継続を広く具体化している。これらの主要セキュリティ上の不変条件と失敗意味には、今回の照合で新たな欠落は確認しなかった。

一方、次の二点は実装者が同じ外部契約を一意に実装できない判定を妨げる課題である。

- `§1.1` は本仕様のモバイル固有の契約を共通仕様より上位に置く一方、直後に共通仕様の判断権限に従うと定めており、競合時の優先主体が自己矛盾する。
- `§16` はリテラルには署名済み応答の必須フィールド（署名済みペイロード、ハッシュ、公開鍵、requestId 等）を応答に含めることを禁止する。これは `§12.1` および受け渡し / インターフェースの署名済み応答共用体と同時には成立しない。

また、`AUTHENTICATING` は Mobile-only のローカル内部手順と読むことができるが、共通の状態集合を使用すると宣言した同じ節の状態図 / 表に共通の状態の一員のように置かれている。これは外部通信上の状態にしない境界を明示すべき軽微課題である。

## 7. 必須の修正

### `MSR-001`: `§1.1` の判断権限優先順位が自己矛盾している

- **重要度 / 状態:** `Major` / `New`
- **対象箇所:** [`mobile-app.md`](../../specifications/mobile-app.md) `§1.1`、特に 19〜26 行目
- **発生条件・確認できた事実:** 21 行目は「本仕様がモバイル固有のに明示する契約」を第一判断権限とする。22 行目は共通インターフェース、署名プロトコル、受け渡し、プロファイル / アカウント、チェーン互換性を第二順位とする。しかし 26 行目は共通契約との競合時に「共通仕様の判断権限に従う」と定める。13 行目も既存共通の契約を置き換えないと述べている。
- **既存の根拠:** [`interfaces.md`](../../specifications/interfaces.md) は共通の要求 / 応答、状態、結果 / 配送の共通契約を定義し、[`signing-protocol.md`](../../specifications/signing-protocol.md) は共通契約の重複箇所についてインターフェースとチェーン互換性を判断権限としている。受け渡しも Web 受け渡しプロトコルの具体契約を自身の判断権限としている。
- **問題:** モバイル固有の契約が共通の契約を合法的に specialize できる範囲と、共通の契約に矛盾した場合の優先順位が一意に決まらない。26 行目の例外を適用するのか、21 行目の一般順位を適用するのかが実装者から判定できない。
- **影響:** 応答フィールド、状態、エラー、バージョン、対応能力、メッセージフィールドおよびセキュリティ上の不変条件が競合したとき、実装・適合性テスト・下流 SDK / Relay の相互運用が異なる契約へ分岐し得る。これは判断権限境界と追跡可能性の判定を妨げる失敗である。
- **必要な最小修正または確認:** `§1.1` を、共通の契約の対象は共通の仕様が判断権限であり、本仕様はモバイル固有のな適用・制約・追加の安全下限だけを定め、共通の契約を上書きしないことが直接読める形へ修正する。共通資料間で未解決の差異は、既存未決または本仕様の委譲事項として明示し、モバイル固有の契約が上位になる一般順位を残さない。
- **完了条件・再確認方法:** `§1.1`、`§12`、`§13`、`§17`、`§19.3` および追跡可能性を読み合わせ、共通の要求 / 応答、状態、エラー、メッセージ、リリース判定に競合があった場合の判断権限が一通り同じ結果になることを確認する。特にインターフェース / 署名プロトコル / 受け渡しとの競合解決が一意であることを再レビューする。

### `MSR-002`: 診断情報の禁止列挙が規範的な応答を禁止している

- **重要度 / 状態:** `Major` / `New`
- **対象箇所:** [`mobile-app.md`](../../specifications/mobile-app.md) `§16` 573〜576 行目、および `§12.1` 403〜412 行目
- **発生条件・確認できた事実:** 573 行目は「ログ、例外、警告、診断情報、利用状況分析、遠隔計測データ、異常終了報告書、サポート出力、Relay メタデータ **または応答**」に次の情報を含めてはならないと定める。576 行目には `full request / response`、`payload`、`signed payload`、`raw transaction`、`message contents`、`hash`、`public key`、`address`、`requestId` 等が列挙されている。
- **既存の根拠:** 本文 `§12.1` はトランザクション / メッセージ署名成功時に `signedTransaction` / `signedData` と `requestId` / `requestDigest` を含む既存受け渡し応答を生成すると定める。[`interfaces.md`](../../specifications/interfaces.md) は応答の requestId / requestDigest と署名済み結果のペイロード、ハッシュ、signerPublicKey を必須とする。[`web-transaction-handoff-spec.md`](../../specifications/web-transaction-handoff-spec.md) §7.2 も同じ応答共用体を定義する。
- **問題:** `response` に修飾語がなく、禁止列挙が規範的な暗号化された応答とその平文結果フィールドにも適用される。したがって署名済み / dataSigned の成功応答を作れず、`§12.1` の成功契約と直接矛盾する。これは秘密情報を漏らさない要件とは別に、公開結果を返すための相互運用契約を消してしまう問題である。
- **影響:** 正常署名の結果が dApp / SDK へ返せず、受け渡し応答共用体、要求対応付け、署名済み結果検証、`PENDING` / `DELIVERY_UNKNOWN` を含む公開結果の運用が成立しない。禁止範囲を誤って実装すると成功パスが常に不適合になる。
- **必要な最小修正または確認:** 禁止対象をログ、例外、警告、診断情報、利用状況分析、遠隔計測データ、異常終了報告書、サポート出力および Relay メタデータ等の観測・補助出力へ限定し、既存受け渡しが要求する暗号化された応答と、その応答内で必要な公開署名済み結果 / 対応付けフィールドは除外する。`response` が診断情報応答等の別概念を意味する場合は、その限定を本文で明示する。秘密情報、セッション秘密情報、認証情報、復号されたストア等を応答に含めない境界は維持する。
- **完了条件・再確認方法:** `§12.1`、`§15`、`§16`、インターフェース §6.3 / §9.6 / §10.3、受け渡し §7.2 を再照合し、署名済み / dataSigned / resultUnknown / 拒否済み / 失敗の全共用体が禁止列挙と両立することを確認する。成功応答に必要な公開フィールドは許可され、秘密情報フィールドは引き続き禁止されていることを確認する。

## 8. 任意の改善

### `MSR-003`: `AUTHENTICATING` のモバイルローカル内部手順境界を明示する

- **重要度 / 状態:** `Minor` / `New`
- **対象箇所:** [`mobile-app.md`](../../specifications/mobile-app.md) `§13.1` 454〜478 行目、および `§9.3` 299〜301 行目
- **発生条件・確認できた事実:** 454 行目は `AUTHENTICATING` をモバイルの端末認証 / 利用者の立ち会い内部手順であり、新しい通信上の操作ではないと説明する。一方、同じ節は「既存署名プロトコルの状態集合を使用する」と宣言し、状態図、`State` 表、終端状態からの遷移禁止に `AUTHENTICATING` を含める。Relay 境界のモバイル / Signer 状態表にも同状態を含める。
- **既存の根拠:** [`interfaces.md`](../../specifications/interfaces.md) §13.1 および [`signing-protocol.md`](../../specifications/signing-protocol.md) §6.1 は共通の状態の厳密な集合を `RECEIVED → VALIDATED → INSPECTED → AWAITING_USER → AUTHORIZED → SIGNING → SUCCEEDED` とし、追加の共通の署名状態を定義しない。
- **問題:** 「通信上の操作ではない」だけでは共通の状態表現、公開ライフサイクル、シリアライズおよび適合性テストに含めないことが確定しない。モバイル実装がこれを共通状態として公開・保存・Relay メタデータ化すると、共通の厳密な状態集合と衝突する。
- **影響:** モバイルローカル UI ライフサイクルと共通署名ライフサイクルの境界が実装ごとに分かれ、状態シリアライズ、コンポーネント間のテスト、下流 SDK の状態処理に余分な状態が現れる可能性がある。直接の署名迂回や秘密情報漏えいは本文の他の不変条件が防止しているため、重要度は軽微とした。
- **必要な最小修正または確認:** `AUTHENTICATING` をモバイル内部の非通信上の・非公開・非共通の状態のローカル内部手順と明記し、共通の状態 / 応答 / Relay 状態 / 永続化にシリアライズしないことを確認する。共通の状態図とモバイル UI 内部手順図を分離する。

## 15. 残存リスクと未決定事項

- `MSR-001` を修正しない場合、モバイル固有のと共通の仕様の競合解決が実装者ごとに分岐する。
- `MSR-002` を修正しない場合、署名済み / dataSigned の正常受け渡し応答を返せない解釈が成立する。
- `MSR-003` を明示しない場合、モバイルローカル認証内部手順が共通の状態、公開応答または Relay 状態として漏れる可能性がある。
- モバイルアプリの送信元 / 実行環境は現在のワークスペースに存在しないため、今回の判定は文書契約のレビューであり、実行環境が本文どおりであることの証拠ではない。
- 現行公開モバイルビルドはリリース資料に従い Testnet 専用であり、これは本文とリリース判断権限に整合する状態であって、今回の指摘ではない。
- `MR-OPEN-*`、`CR-OPEN-*`、インターフェース / Relay / SDK の既存未決は、本文が安全下限を弱めずに保持している。これらを実装 convenience だけで閉じたり、モバイル固有の別名 / フィールド / エラー / 対応能力へ昇格させたりしてはならない。

## 16. 自動変更

なし。対象仕様、要件、設計、関連仕様、ADR、送信元、テストおよび過去レビュー成果物は変更していない。変更対象は本レビュー成果物だけである。

## 17. 最終判断

`REVISE SPECIFICATION`

`MSR-001` と `MSR-002` は `Major` の判定を妨げる指摘である。`MSR-003` は `Minor` の任意改善。重大指摘はない。判断権限優先順位と応答禁止を修正し、`AUTHENTICATING` のローカルのみ状態境界を明記した後、共通のインターフェース / 署名プロトコル / 受け渡しとの再レビューが必要である。
