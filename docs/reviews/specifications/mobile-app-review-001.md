## 4. Review Result

`REVISE SPECIFICATION`

## 5. Summary

対象本文は、Mobile host / trusted Signer を最終的な signing authority とし、外部入力を untrusted として再検証する責任、trusted foreground UI、Authentication・Signing-capable unlock・Account authorization・Explicit user approval の独立した四条件、同一 context への binding、Chain / Network の分離、Relay の opaque boundary、Signer-only の `RESULT_UNKNOWN` / `deliveryDisposition`、known-result recovery、lifecycle invalidation、secret isolation、Mainnet fail-closed および Testnet-only continuation を広く具体化している。これらの主要 security invariant と failure semantics には、今回の照合で新たな欠落は確認しなかった。

一方、次の二点は実装者が同じ external contract を一意に実装できない blocking issue である。

- `§1.1` は本仕様の Mobile-specific contract を共通 Specification より上位に置く一方、直後に共通 Specification の authority に従うと定めており、conflict 時の優先主体が自己矛盾する。
- `§16` は literal には signed response の必須 field（signed payload、hash、public key、requestId 等）を response に含めることを禁止する。これは `§12.1` および Handoff / Interfaces の signed response union と同時には成立しない。

また、`AUTHENTICATING` は Mobile-only の local substep と読むことができるが、common state set を使用すると宣言した同じ節の state diagram / table に common state の一員のように置かれている。これは外部 wire state にしない境界を明示すべき Minor issue である。

## 7. Required Changes

### `MSR-001`: `§1.1` の authority precedence が自己矛盾している

- **Severity / Status:** `Major` / `New`
- **対象箇所:** [`mobile-app.md`](../../specifications/mobile-app.md) `§1.1`、特に 19〜26 行目
- **発生条件・確認できた事実:** 21 行目は「本仕様が Mobile-specific に明示する契約」を第一 authority とする。22 行目は共通 Interfaces、Signing Protocol、Handoff、Profile / Account、Chain Compatibility を第二順位とする。しかし 26 行目は共通契約との競合時に「共通 Specification の authority に従う」と定める。13 行目も既存 common contract を置き換えないと述べている。
- **既存の根拠:** [`interfaces.md`](../../specifications/interfaces.md) は common request / response、state、result / delivery の共通契約を定義し、[`signing-protocol.md`](../../specifications/signing-protocol.md) は共通契約の重複箇所について Interfaces と Chain Compatibility を authority としている。Handoff も Web handoff protocol の具体契約を自身の authority としている。
- **問題:** Mobile-specific contract が common contract を合法的に specialize できる範囲と、common contract に矛盾した場合の優先順位が一意に決まらない。26 行目の exception を適用するのか、21 行目の一般順位を適用するのかが実装者から判定できない。
- **影響:** response field、state、error、version、capability、message field および security invariant が競合したとき、実装・conformance test・下流 SDK / Relay の相互運用が異なる契約へ分岐し得る。これは authority boundary と traceability の blocking failure である。
- **必要な最小修正または確認:** `§1.1` を、common contract の対象は common Specification が authority であり、本仕様は Mobile-specific な適用・制約・追加の安全下限だけを定め、common contract を上書きしないことが直接読める形へ修正する。共通資料間で未解決の差異は、既存 OPEN または本仕様の委譲事項として明示し、Mobile-specific contract が上位になる一般順位を残さない。
- **完了条件・再確認方法:** `§1.1`、`§12`、`§13`、`§17`、`§19.3` および Traceability を読み合わせ、common request / response、state、error、message、release gate に conflict があった場合の authority が一通り同じ結果になることを確認する。特に Interfaces / Signing Protocol / Handoff との conflict resolution が一意であることを再レビューする。

### `MSR-002`: diagnostics の禁止列挙が normative response を禁止している

- **Severity / Status:** `Major` / `New`
- **対象箇所:** [`mobile-app.md`](../../specifications/mobile-app.md) `§16` 573〜576 行目、および `§12.1` 403〜412 行目
- **発生条件・確認できた事実:** 573 行目は「log、例外、warning、diagnostics、analytics、telemetry、crash report、support output、Relay metadata **または response**」に次の情報を含めてはならないと定める。576 行目には `full request / response`、`payload`、`signed payload`、`raw transaction`、`message contents`、`hash`、`public key`、`address`、`requestId` 等が列挙されている。
- **既存の根拠:** 本文 `§12.1` は transaction / message signing 成功時に `signedTransaction` / `signedData` と `requestId` / `requestDigest` を含む既存 Handoff response を生成すると定める。[`interfaces.md`](../../specifications/interfaces.md) は response の requestId / requestDigest と signed result の payload、hash、signerPublicKey を required とする。[`web-transaction-handoff-spec.md`](../../specifications/web-transaction-handoff-spec.md) §7.2 も同じ response union を定義する。
- **問題:** `response` に修飾語がなく、禁止列挙が normative encrypted response とその plaintext result fields にも適用される。したがって signed / dataSigned の success response を作れず、`§12.1` の success contract と直接矛盾する。これは秘密情報を漏らさない要件とは別に、公開結果を返すための相互運用 contract を消してしまう問題である。
- **影響:** 正常 signing の結果が dApp / SDK へ返せず、Handoff response union、request correlation、signed result verification、`PENDING` / `DELIVERY_UNKNOWN` を含む公開 result の運用が成立しない。禁止範囲を誤って実装すると success path が常に不適合になる。
- **必要な最小修正または確認:** 禁止対象を log、例外、warning、diagnostics、analytics、telemetry、crash report、support output および Relay metadata 等の観測・補助出力へ限定し、既存 Handoff が要求する encrypted response と、その response 内で必要な public signed result / correlation fields は除外する。`response` が diagnostics response 等の別概念を意味する場合は、その限定を本文で明示する。秘密情報、session secret、credential、decrypted Store 等を response に含めない境界は維持する。
- **完了条件・再確認方法:** `§12.1`、`§15`、`§16`、Interfaces §6.3 / §9.6 / §10.3、Handoff §7.2 を再照合し、signed / dataSigned / resultUnknown / rejected / failed の全 union が禁止列挙と両立することを確認する。success response に必要な public fields は許可され、secret fields は引き続き禁止されていることを確認する。

## 8. Optional Improvements

### `MSR-003`: `AUTHENTICATING` の Mobile local substep 境界を明示する

- **Severity / Status:** `Minor` / `New`
- **対象箇所:** [`mobile-app.md`](../../specifications/mobile-app.md) `§13.1` 454〜478 行目、および `§9.3` 299〜301 行目
- **発生条件・確認できた事実:** 454 行目は `AUTHENTICATING` を Mobile の device authentication / user-presence substep であり、新しい wire operation ではないと説明する。一方、同じ節は「既存 Signing Protocol の state set を使用する」と宣言し、state diagram、`State` table、terminal state からの遷移禁止に `AUTHENTICATING` を含める。Relay boundary の Mobile / Signer state table にも同 state を含める。
- **既存の根拠:** [`interfaces.md`](../../specifications/interfaces.md) §13.1 および [`signing-protocol.md`](../../specifications/signing-protocol.md) §6.1 は common state の exact set を `RECEIVED → VALIDATED → INSPECTED → AWAITING_USER → AUTHORIZED → SIGNING → SUCCEEDED` とし、追加の common signing state を定義しない。
- **問題:** 「wire operation ではない」だけでは common state representation、public lifecycle、serialization および conformance test に含めないことが確定しない。Mobile 実装がこれを共通 state として公開・保存・Relay metadata 化すると、common exact state set と衝突する。
- **影響:** Mobile local UI lifecycle と共通 signing lifecycle の境界が実装ごとに分かれ、state serialization、cross-component test、下流 SDK の state handling に余分な state が現れる可能性がある。直接の signing bypass や secret leakage は本文の他の invariant が防止しているため、severity は Minor とした。
- **必要な最小修正または確認:** `AUTHENTICATING` を Mobile 内部の非 wire・非 public・非 common state の local substep と明記し、common state / response / Relay state / persistence に serialize しないことを確認する。common state diagram と Mobile UI substep diagram を分離する。
- **完了条件・再確認方法:** Mobile 本文、Interfaces、Signing Protocol、Handoff の state / response を読み合わせ、external contract に現れる state が common exact set だけであり、Mobile local substep が signing operation や Relay transport state に変換されないことを確認する。

## 10. Deferred Findings

既存 OPEN は、今回の対象本文が安全下限を固定したうえで exact implementation / public scope を独自に決定していない限り、未決事項として妥当である。今回、既存 OPEN を勝手に close すべきものは確認しなかった。

- `MR-OPEN-001` / `MOB-OPEN-001`: OS version、端末範囲、配布および milestone。Target は個別 platform / release matrix を残している。これは implementation choice だけでなく release scope の判断である。
- `MR-OPEN-002` / `MOB-OPEN-002`: 標準 verified HTTPS App Link 以外の route。現行 Handoff が標準 App Link と Mainnet proof を決めているため、残る OPEN は custom scheme、QR、share / Intent 等の追加経路であり、標準 route を未決へ戻すものではない。
- `MR-OPEN-003`、`CR-OPEN-001`、`CR-OPEN-002` / `MOB-OPEN-003`: wallet-core Binding、Native / WASM host integration、OS wrapping、secret byte lifecycle、migration の exact contract。Target は wallet-core の cryptographic authority と no reimplementation を固定し、方式を下位へ委譲している。
- `MR-OPEN-004` / `MOB-OPEN-004`: PIN、passcode、biometric、Profile password の具体的役割、fallback、retry、rate limit、再認証頻度、lock timeout。`every-signature` と bypass 禁止は既に固定されている。
- `MR-OPEN-005`、`OPEN-RELAY-003`、`OPEN-RELAY-004` / `MOB-OPEN-005`: pending retention、resume、known-result retention、resend / retrieval / lookup、client-facing transport mapping。Target は transport failure と result / delivery semantics を分離し、exact recovery API は決定していない。
- `MR-OPEN-006` / `MOB-OPEN-006`: Profile 全体 backup / restore、端末移行、一般 capability。Mainnet gate の evidence 条件と、一般 backup capability の提供範囲は Target でも分離されている。
- `MR-OPEN-007` / `MOB-OPEN-007`: screen capture、recording、recent-app preview、notification、clipboard、crash / diagnostics の platform policy。Target は秘密情報の非露出下限を固定し、platform-specific policy を委譲している。
- `MR-OPEN-008` / `MOB-OPEN-008`: platform matrix、capability report、runtime enforcement、Store と Mainnet capability の関係。Mainnet gate の存在、failure / unknown 時の disabled、Testnet-only continuation および release authority は既に決定済みである。
- `OPEN-006` / `OPEN-SDK-004` / `MOB-OPEN-009`: Aggregate、Partial、Symbol / NEM cosignature の public operation、supported scope、result contract。Target は full inspection と blind / raw fallback 禁止を固定するが、公開必須 capability は既存 OPEN のままである。
- Interfaces `OPEN-001`〜`OPEN-005`: structured message expiry field、capability / version negotiation、permission expiry / revocation identifier、caller context。Target `§10.3` と `§19.3` は field alias や独自 version / capability を発明せず、既存 authority へ戻している。`OPEN-001` の `expiresAt` / `messageExpiresAt` 差異を未決のまま保持している点は適切である。

上記 OPEN は実装前に必要な外部判断を含むが、本文が明示する no blind signing、four-condition gate、Relay non-authority、fail-closed、no automatic re-sign / fallback を緩和する根拠にはならない。未記録の security-critical OPEN としては、今回の照合で別の必須 blocker を確認しなかった。

## 15. Remaining Risks and Open Decisions

- `MSR-001` を修正しない場合、Mobile-specific と common Specification の conflict resolution が実装者ごとに分岐する。
- `MSR-002` を修正しない場合、signed / dataSigned の正常 handoff response を返せない解釈が成立する。
- `MSR-003` を明示しない場合、Mobile local authentication substep が common state、public response または Relay state として漏れる可能性がある。
- Mobile App の source / runtime は現在の workspace に存在しないため、今回の判定は文書 contract の review であり、runtime が本文どおりであることの証拠ではない。
- 現行公開 Mobile build は release 資料に従い Testnet-only であり、これは本文と release authority に整合する状態であって、今回の finding ではない。
- `MR-OPEN-*`、`CR-OPEN-*`、Interfaces / Relay / SDK の既存 OPEN は、本文が安全下限を弱めずに保持している。これらを implementation convenience だけで閉じたり、Mobile-specific alias / field / error / capability へ昇格させたりしてはならない。

## 16. Automatic Changes

なし。対象 Specification、Requirements、Design、関連 Specification、ADR、source、test および過去レビュー成果物は変更していない。変更対象は本レビュー成果物だけである。

## 17. Final Decision

`REVISE SPECIFICATION`

`MSR-001` と `MSR-002` は `Major` の blocking finding である。`MSR-003` は `Minor` の optional improvement。Critical finding はない。authority precedence と response prohibition を修正し、`AUTHENTICATING` の local-only state 境界を明記した後、common Interfaces / Signing Protocol / Handoff との再レビューが必要である。
