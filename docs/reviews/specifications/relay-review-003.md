## 4. レビュー結果

`REVISE SPECIFICATION`

現行本文は Relay を内容を解釈しない / 信頼されていない通信経路として設計し、受け渡し §9 のエンドポイント、認証情報、受領確認 / キャンセル、世代、保持、プライバシーおよび並行処理を概ね適切に定めている。RLS-001 の受領確認 / キャンセル `204 No Content` 状態を変更しない操作意味も解消済みである。

ただし、§3、§13.3、§14.1、§14.3 および §22.10 の Relay 内の “配送処理結果の区分” と、上流が署名主体が生成したフィールドとして予約する `deliveryDisposition` / `PENDING` / `DELIVERED` / `DELIVERY_UNKNOWN` の境界が一意でない。Relay が通信経路失敗から `DELIVERY_UNKNOWN` を作る、または受領確認 / 消費済みを `DELIVERED` として公開する読み方を排除できないため、現行のままでは公開結果意味と復旧意味を安全に実装できない。`SR-001` は重大とし、修正まで Ready としない。

加えて、四つの署名条件と Mainnet リリース / 根拠判定条件が Relay の非権限であることは上流・設計では確定しているが、Relay 本文のセキュリティ上の不変条件、受け入れ、追跡可能性で明示性が不足する。Relay に新しい判定条件や実装詳細を要求するものではなく、`SR-002` は軽微の同期・検証可能性指摘とする。

## 5. 要約

- Relay は要求 / 応答暗号化されたエンベロープを復号・意味解釈せず、アカウント、許可、オリジン、承認、認証、署名、結果有効性および Mainnet 根拠の判断権限を持たない。`appToken` / `webToken` と `sessionSecret` / 導出された E2E 資料も分離されている。
- 受け渡し §9 の世代、作成 / 取得 / 応答 / ポーリング、受領確認、キャンセル、HTTP 状態、期限切れ、サイズ、頻度上限、存在秘匿および一般的なエラー本文は本文と整合する。本文は受け渡し通信上の契約を新しいエンドポイントやトークンモデルとして拡張していない。
- RLS-001 は解消済みである。外形が妥当な受領確認 / キャンセルは常に `204 No Content`、状態変更は正しい endpoint-scoped `webToken`、対応セッション、現在の世代 / ライフサイクル等を確認できる場合だけ、その他は状態を変更しない操作である。`204`、削除、受領確認、キャンセルは署名結果、承認、署名キャンセル、未署名または署名主体側の配送成功を証明しない。
- 世代、再起動 / 状態消失、終端状態、重複 / リプレイ、応答競合、期限切れ / 削除、上限のある保持、観測可能性プライバシー、エラー定義の正本、自動再署名 / 代替経路禁止は概ね一貫している。旧状態 / 認証情報 / 承認 / 署名状態を復元しない契約も維持されている。
- `SR-001` は、Relay の通信経路状態と署名主体が生成した `deliveryDisposition` が同じ “配送処理結果の区分” 名で定義され、応答配送失敗を “不明” と扱う記述も残るため、署名主体のみの `DELIVERY_UNKNOWN` の生成禁止と受領確認 / 消費済み非同値性を本文から一意に検証できない点である。
- `SR-002` は、Relay が四条件または Mainnet 判定条件を所有しないことを、本文の受け入れ / 追跡可能性まで明示的に追跡できない点である。現在の本文に Relay がそれらを評価・代替する直接の記述はなく、内容を解釈しない境界の基本方向は維持されている。

## 7. 必須の修正

### SR-001 — Relay 内の配送状態と署名主体が生成した deliveryDisposition の境界

- **重要度:** 重大
- **状態:** 新規
- **対象箇所:** `relay.md` §3、§13.3、§14.1、§14.3、§22.10
- **課題:** §3 は “配送処理結果の区分” を Relay が要求 / 応答を配送した状態として定義する。§13.3 は Relay が `delivered` を報告できるとし、`DELIVERED`、`ACKNOWLEDGED`、`CONSUMED` を列挙する。さらに §14.1 は応答配送失敗を “配送処理結果の区分を失敗または不明” とし、§14.3 は Relay 失敗 / 応答配送から結果を判定できない場合に SDK / 署名主体が `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` 意味を使用すると記載する。これは、Relay 内の失敗 / 受領確認 / 消費済み状態を署名主体が生成した `DELIVERY_UNKNOWN` / `DELIVERED` として生成・推測・昇格できる余地を残す。
- **正本となる競合:** インターフェース §10.3、署名プロトコル §19.3、受け渡し §7.2 は `deliveryDisposition` を既知の署名済み結果に付随する署名主体側のフィールドとし、`PENDING`、`DELIVERED`、`DELIVERY_UNKNOWN` を SDK / Provider / Relay / 通信経路が生成・推測・変更してはならない。受け渡し §9.6 / SDK 受領確認・Relay `consumed` は署名主体側の配送処理結果の区分と同値ではなく、応答登録や受領確認から `DELIVERED` を成立させない。
- **必須明確化:** Relay 内の観測は `transport status` または同等の専用語へ改める。`deliveryDisposition`、`PENDING`、`DELIVERED`、`DELIVERY_UNKNOWN` は署名主体が生成した既知の署名済み結果のみが設定し、Relay の保存領域、取得、HTTP 成功、受領確認、`consumed`、タイムアウト、接続 / 再起動 / 状態消失、応答欠如、配送失敗から Relay が生成・推測・変更・確定しないと明記する。`RESULT_UNKNOWN` も同様に Relay が生成しないこと、既知の署名済み結果の `DELIVERY_UNKNOWN` は結果を保持すること、Relay 失敗後の復旧は既存結果の再送 / 取得 / 照会に限ることを本文の失敗 / 受け入れ / 追跡可能性に反映する。
- **工程境界:** これは実装方式、再試行秒数、保存領域スキーマまたは新しいエラー分類体系の要求ではなく、既存共通契約の外部名、判断権限、意味保存を一意にするための仕様修正である。

## 8. 任意の改善

### SR-002 — 共通の四つの条件 / Mainnet 判定条件の Relay 非権限の明示と追跡

- **重要度:** 軽微
- **状態:** 新規
- **対象箇所:** `relay.md` §4.2、§20、§21、§22、§23
- **課題:** 本文は承認、認証、署名、アカウント / 許可等を一般に Relay の責任外としているが、認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認の四条件を独立した署名主体判断権限として列挙していない。また Mainnet リリース / 根拠判定条件、欠落 / 無効な / 期限切れ / 不整合の / 検証不能の / 不明の安全側での終了、Testnet 専用継続および Relay 正常性 / 利用可能性 / 通信経路成功の非代替性が、受け入れ / 追跡可能性に現れない。
- **根拠:** 要件 `CR-AC-017`、`CR-NFR-006` / `CR-AC-008`、インターフェース §7.4 / §15、署名プロトコル §8 / §21.1、Relay 設計 §10.2 / §20 はこれらを確定済みの共通契約としている。本文 §20.2 の利用可能性非代替性と §21 のモバイル責務は方向として整合するため、現時点で Relay が判定条件評価器や四条件判断権限になっているとは判定しない。
- **推奨明確化:** §20、§22、§23 に、四条件は信頼された署名主体の独立した必須条件であり Relay のセッション / 参加者 / トークン / 世代 / 要求存在 / 通信経路成功では所有・検証・キャッシュ・復元・推測・代替できないことを短く追記する。Mainnet 判定条件は信頼された署名主体 / リリースセキュリティ判断権限の責務で、Relay は評価器 / 検証者 / 対応能力 promoter ではなく、Mainnet 判定条件失敗 / 不明から別経路、再署名、`RESULT_UNKNOWN`、`DELIVERY_UNKNOWN` または通信経路成功を生成しないこと、Testnet 専用の安全な継続を妨げないことを受け入れ / 追跡可能性に追加する。根拠評価器、信頼された鍵、SBOM、リリース補助ツールの詳細は追加しない。
- **処理結果の区分:** 現本文に直接の判断権限逆流はないため、`SR-002` は任意改善とし、レビュー判定条件を単独で不合格させない。

## 9. 解消済みの指摘

### RLS-001 — 受領確認 / キャンセル意味

現行 §5.2、§8.2、§13.1、§13.2、§14.1、§15.1 および §16.1 は受け渡し §9.6 の例外を明示している。メソッド、パス、ヘッダー、本文、プロトコル等の外形が妥当な受領確認 / キャンセルは、誤ったトークン、不明 / 削除済みセッション、終端 / 期限切れ状態、重複、世代不一致、再起動 / 状態消失を含め、常に `204 No Content` である。正しい endpoint-scoped `webToken`、対応セッション、現在の世代 / ライフサイクル、適用可能な状態を確認できた場合だけ一度の変更 / 削除を行い、それ以外は状態を変更しない操作とする。

`204`、受領確認、キャンセル、削除、`consumed` または `cancelled` は署名成功、署名失敗、署名キャンセル、未署名の、利用者承認、セッション存在、トークン有効性、署名主体側の配送成功の証明ではない。受領確認とキャンセルの競合も終端遷移を高々一度とし、遅延した応答、セッション間の、終端 reactivation を許さない。これは `relay-review-002.md` の判定を機械的に継承したものではなく、現行本文と受け渡し §9.6 を直接照合した結果である。

## 15. 残存リスクと未決定事項

- `SR-001` が修正されるまで、Relay 内の `delivered` / 不明観測と署名主体が生成した `deliveryDisposition` の誤マッピング、受領確認 / 消費済みからの誤った `DELIVERED` 生成、通信経路失敗からの誤った `DELIVERY_UNKNOWN` 生成を実装レビューで安全に排除できない。

- `response_available` からキャンセル可能な範囲の表記は受け渡しのライフサイクル明確化待ちであり、Relay が独自の状態分岐を発明しないことを前提に後続工程へ委譲とする。

## 17. 最終判断

`REVISE SPECIFICATION`

- **RLS-001:** `Resolved`。受領確認 / キャンセルの valid-shape `204`、条件付き変更、状態を変更しない操作、存在秘匿、終端 / 世代 / 状態消失意味に回帰はない。
- **SR-001:** `New / Critical`。Relay 通信経路観測と署名主体が生成した `deliveryDisposition`、`DELIVERY_UNKNOWN`、`DELIVERED`、`RESULT_UNKNOWN` の生成判断権限と意味保存を明示的に分離するまで判定を妨げる。
- **SR-002:** `New / Minor`。四つの条件と Mainnet リリース / 根拠判定条件の Relay 非権限、安全側での終了、Testnet 専用継続を受け入れ / 追跡可能性へ追跡する同期改善。直接の判断権限逆流は確認していない。

新規指摘は重大 1 件、主要 0 件、軽微 1 件である。Relay の内容を解釈しない / 信頼されていない通信経路境界、秘密情報分離、受領確認 / キャンセル意味、世代 / リプレイ / 保持 / プライバシー、自動再署名 / 代替経路に重大な回帰は確認していない。`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` の判断権限については SR-001 の重大な明確化不足が残る。Mainnet 判定条件と四条件判断権限が Relay に逆流する直接記述はないが、本文の明示追跡が不足している。仕様工程境界の逸脱は確認していない。

レビュー判定条件は 2〜6 が SR-001 により不合格であり、最終判断は `REVISE SPECIFICATION` とする。これは実装ビルド、実 Relay / モバイル、E2E、wallet-core またはリリース証跡評価器の検証済み判定ではない。
