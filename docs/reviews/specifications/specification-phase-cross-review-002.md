## 4. レビュー結果

`REVISE SPECIFICATION`

現行仕様は、次の安全上の中核については横断的に整合している。

- 認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認の四つの条件は、信頼された Signer の独立条件として同一要求 / 対象 / プロファイル / アカウント / チェーン / ネットワーク文脈に結び付けされている。
- ブラウザ拡張機能とモバイルアプリは対象から導出したデータを信頼された UI に表示し、dApp 要約、URL、通知、Relay メタデータ、ハッシュのみ、ノード照会を承認の代替にしていない。
- wallet-core は秘密情報 / 生の署名の判断権限、Relay は内容を解釈しない / 信頼されていない通信経路であり、Relay に Signer 判断権限、承認、意味上の内容検査、結果判断権限、Mainnet 判定条件判断権限はない。
- `RESULT_UNKNOWN`、`deliveryDisposition`、確定済みの結果復旧 / 再署名の分離は、各主要経路で同じ意味を保持している。

一方、次の判定を妨げる文書間の課題が残っている。

- 主要契約を要件 → 設計 → 仕様へ逆追跡する明示的な対応表がプロダクト、プロファイル、チェーン、受け渡しに存在せず、文書間の判断権限の検証可能性が不足している（`SPCR-005`）。
- モバイル / 受け渡しが、上流で未決の OS 保護、ハードウェア対応能力、直接の署名、バックアップ / 復元を現在のモバイル Mainnet 判定条件の具体条件として規範化している（`SPCR-008`）。
- インターフェースと受け渡しが同じ `RelayRequestBase` / `RelayResponse` を別の型名・別名・判断権限で定義し、共通のフィールド判断権限が一意に確定していない（`SPCR-009`）。
- プロダクトの Mainnet 根拠マニフェストが現在の Lite ポリシーの必須承認と一致せず、Lite と strict ポリシーの条件が同じ規範的なテキストに混在している（`SPCR-010`）。

従って、個別仕様の `READY` は履歴として維持するが、仕様工程全体は実装へ移行できない。

| 重要度 | 有効な新規 / 未決 / 再発 | 解消済み履歴 |
| ------ | -----------------------: | -----------: |
| 重大   |                        0 |            0 |
| 主要   |                        4 |            6 |
| 軽微   |                        0 |            1 |

有効な指摘は `SPCR-005`、`SPCR-008`、`SPCR-009`、`SPCR-010` である。`SPCR-001`〜`004`、`SPCR-006`、`SPCR-007` は現行本文との照合により解消済み履歴とした。

## 7. 必須の修正

### `SPCR-005` — 要件 → 設計 → 仕様追跡可能性の不足

### `SPCR-009` — インターフェースと受け渡しの具体的な要求 / 応答判断権限重複

- **対象箇所:** [`interfaces.md` §6.2 / §6.3](../../specifications/interfaces.md)、[`web-transaction-handoff-spec.md` §5.1 / §7.1 / §7.2](../../specifications/web-transaction-handoff-spec.md)、同受け渡し §1 の「Web受け渡しプロトコルは本書を適用する」という判断権限文。
- **事実 / 条件:** インターフェースは `RelayRequestBase`、`RelayOperation`、`RelayResponseBase`、`RelayResponse` を具体的な論理的な構造として定義し、`PublicAccountIdentity` / `DeliveryDisposition` を使用する。受け渡しは同じ `RelayRequestBase` と `RelayResponse` を再定義し、`MosaicLynxActiveAccount` / `MosaicLynxDeliveryDisposition` を使用する。受け渡しの応答共用体にはインターフェースの `RelayResponseBase` が現れず、両文書は同じ `mosaiclynx.relay.v1`、フィールド、結果を別宣言として記載している。両者の aliases が通信上の上・型上完全同一であること、共通のフィールドと Web-specific フィールドの境界、どちらが正規宣言かが明示されていない。
- **既存の判断権限:** インターフェースは共通の要求 / 応答 / フィールド判断権限を担い、受け渡しは Web 受け渡しの protocol-specific 具体的な契約と受け渡しエラーコードを担うという分担が本文に散在する。ただし、現在の declarations と受け渡し §1 の広い上書き文だけでは、実装者が一つの正規型 / フィールド判断権限を選べない。
- **課題 / 影響:** SDK、Provider、モバイル、Relay アダプターが同じ JSON 構造を偶然実装できても、公開 TypeScript 型、アカウントの識別情報、配送フィールド、追加フィールドの必須性およびバージョン管理について別契約を実装し得る。要求 / 応答契約の unique 判断権限という判定条件条件を満たさず、コンポーネント間の相互運用性と古くなった / 結果対応付けの検証基準が曖昧になる。
- **最小修正 / 確認:** 共通のフィールド / 型の正本の管理主体と、受け渡しが具体化してよい protocol-specific portion を明示する。インターフェースの共通の宣言を参照するなら、受け渡しの重複共用体を削除し、`MosaicLynxActiveAccount` / `MosaicLynxDeliveryDisposition` が共通の型の wire-identical 別名であることを明記する。別の分割を採用する場合も、両文書、SDK、ブラウザ、モバイル、Relay の判断権限表を同時に更新する。新しい別名、フィールド、正規化を今回追加しない。
- **完了 / 再確認:** requestId、requestDigest、操作、Signer、アカウントの識別情報、対象範囲、対象、期限切れ、署名済み結果、エラー、対応付け、配送フィールドの一つずつについて正規宣言と利用主体対応付けが一つになり、受け渡し / SDK / Provider / モバイル / Relay が同じ応答共用体を参照することを確認する。

### `SPCR-010` — プロダクト Mainnet 根拠マニフェストと現在の Lite ポリシーの承認条件不整合

- **対象箇所:** [`product-spec.md` §19 冒頭および `evidence-manifest.json` 記述](../../specifications/product-spec.md)、[`0001-mainnet-evidence-lite.md`](../../adr/0001-mainnet-evidence-lite.md)、[`evidence-policy.json`](../../evidence/evidence-policy.json)、[`mainnet-release-evidence.md` Lite ポリシー](../../release/mainnet-release-evidence.md)。
- **事実 / 条件:** プロダクト §19 の blockquote は Lite では二名承認等を `not-required` とする。一方、同 §19 のマニフェスト規範的な説明は `二名以上のsecurity/release承認者` を保持すると記載する。現在のポリシーは `mode: lite`、`requiredApprovals.release: 1`、`requiredApprovals.security: 0`、`allowSameApproverMultipleRoles: true` であり、リリース証跡も Lite は one リリース承認、strict-only 根拠は存在しない時 `not-required` とする。
- **既存の判断権限:** Mainnet 承認回数とポリシーパラメーターは ADR 0001、`evidence-policy.json`、Mainnet リリース証跡が判断権限であり、プロダクトはそれらを参照する。Mainnet 対応能力の安全側での終了と Testnet 専用継続は共通要求として維持する。
- **課題 / 影響:** 現在の Lite を実装・検証する主体が、プロダクトの二名記述を必須フィールドと解釈するのか、ポリシーのリリース 1 / セキュリティ 0 を適用するのか決められない。逆に strict 移行の条件が Lite に誤適用される可能性があり、Mainnet 判定条件の必須根拠 / 承認を一意に検証できない。
- **最小修正 / 確認:** プロダクトのマニフェスト要件を現在の `mode` / ポリシーパラメーターに条件付け、Lite と strict のフィールド / 承認要件を明確に分離する。または ADR / ポリシーを承認済みの新しい現在のポリシーへ更新してプロダクトと一致させる。今回のレビューでポリシーの値や strict 移行を変更しない。
- **完了 / 再確認:** 現在の Lite マニフェストがリリース承認 1、セキュリティ承認 0 のポリシーと矛盾なく検証でき、strict 移行の条件は現在の Lite を阻害しない形で明示され、ブラウザ / モバイル / SDK / Relay が同じリリース判断権限を参照することを確認する。

### 追跡可能性不足

主要契約の利用主体対応付けはインターフェース / 署名 / ブラウザ / モバイル / Relay / SDK に分散して存在するが、プロダクト、プロファイル、チェーン、受け渡しに同形式の requirement-to-design-to-spec 対応表がなく、文書全体の正本の管理主体、鏡像未決、工程境界を機械的・レビュー可能に確認できない。これは単なる文書形式ではなく、今回の `SPCR-008`〜`010` を実装前に検知・解消するための判定条件根拠の不足である。

## 15. 残存リスクと未決定事項

## 17. 最終判断

`REVISE SPECIFICATION`

有効な判定を妨げる主要指摘は `SPCR-005`、`SPCR-008`、`SPCR-009`、`SPCR-010`。文書間の矛盾 / 判断権限曖昧さが残っており、要件 → 設計 → 仕様追跡可能性と現在の Mainnet 契約の一意性も不足しているため、実装工程へ移行不可と判定する。

修正後は、少なくとも各指摘の完了条件を再確認し、10 仕様と上流ポリシーを同じリビジョンで横断再レビューすること。`READY` は、判定を妨げる指摘がなく、共通の判断権限、セキュリティ / 責務境界、Mainnet ポリシー、追跡可能性、外部契約、工程境界が全て一意かつ検証可能になった場合に限る。
