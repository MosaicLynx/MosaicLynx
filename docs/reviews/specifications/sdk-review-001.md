## 総評

SDK 仕様は、SDK を Web アプリケーション / dApp と信頼された Signer の間にある非特権統合層として定義し、Provider 検出、対応能力 / バージョン、接続 / 許可、公開アカウント、要求組み立て、応答対応付け、並行処理、タイムアウト / キャンセル、ローカル / リモート受け渡しおよびエラー正規化の責務を具体化している。

SDK が Provider の存在・対応能力・接続・公開アカウント・Relay 配送を承認や署名成功とみなさないこと、SDK がオリジンの信頼性判断、許可判断権限、信頼された表示、認証、生の署名または wallet-core の秘密情報境界を担わないことも明確である。オリジンとの結び付け、Signer 側検証、承認、署名ライフサイクル、結果不明、再署名禁止、Relay 内容を解釈しない境界および機微なエラー詳細非露出は上流契約と整合している。

また、公開 API、連署署名の任意 / 既存の契約、対応能力識別子、バージョン協議、許可ライフサイクル、タイムアウト / キャンセルの具体ポリシー、呼び出し元結び付けの具体的な仕組みは、受け渡し / インターフェース / 署名プロトコルの判断権限または未決へ適切に委譲されている。今回確認した問題は、`isAvailable()` の可用性条件が文書内および受け渡しの対応箇所で一意に定まらない点である。

## 判定

### REVISE 仕様

`isAvailable()` が Provider のないモバイル Relay 経路を利用可能と報告する条件と、モバイル Relay がリリース / 機能フラグにより無効な場合の扱いが一意に定まっていない。公開 API の外部契約と通信経路選択が食い違うため、修正後に次工程へ進める。

### SDK-001

- **重要度:** `ERROR`
- **状態:** `OPEN`
- **対象箇所:** `docs/specifications/sdk.md` §5.1 の `isAvailable()` 定義、§6.2 の「対応 Provider が存在しない場合は `isAvailable()` を `false`」という規則。関連して [Web トランザクション受け渡し仕様 §5.3](../../specifications/web-transaction-handoff-spec.md) と §6 のモバイル Relay 選択条件。
- **問題:** §5.1 は `isAvailable()` が「対応 Provider または既存の対応受け渡し条件」で `true` になると定め、受け渡し §5.3 も Provider がなくても対応モバイルブラウザと必要 Web API / 検証済み HTTPS App Link 条件があれば `true` と定めている。一方、対象 §6.2 は対応 Provider が存在しない場合に常に `false` とする。さらに対象 §6.2 / 受け渡し §6 はモバイル Relay 機能フラグおよび本番 v1.0.0 の受信アプリ公開前の無効条件を定めているが、これが `isAvailable()` の判定条件へ明示的に接続されていない。
- **根拠:** 受け渡し §5.3 の `isAvailable()` 条件、受け渡し §6 の通信経路自動選択、SDK 要件 `SDK-FR-001` / `SDK-PLAT-003` および対象 §5.1 / §6.2。受け渡しはアプリのインストール済みを保証しない一方、選択可能な受け渡し経路の条件を `true` の根拠としている。
- **リスク:** 実装者が、Provider のないモバイルブラウザで `true` を返す実装と常に `false` を返す実装のいずれも選べる。前者では本番で無効なモバイル Relay を利用可能と誤報し、後者では有効化されたリモート受け渡しを利用不能と誤報する。これにより `isAvailable()` と実際の通信経路選択、`UNAVAILABLE` の返却、SDK / dApp の UX およびサポート対応表の意味が不一致になる。Provider がある場合の拡張機能優先規則と、非対応 Provider を別経路へ利用者に知らせない代替経路しない規則にも影響する。
- **推奨対応:** 受け渡しを判断権限として、`isAvailable()` が `true` になる条件を「対応 Provider が選択可能」または「対象リリースでモバイル Relay が有効化され、対応実行環境 / Web API / 検証済み HTTPS App Link の条件を満たす」と一意に定義する。モバイル Relay の機能フラグ無効、本番リリース判定未達または受信アプリ未提供時は、アプリのインストール有無を断定せず、選択可能な受け渡し経路がないため `false` とするかどうかを受け渡し側で明示し、対象 §5.1 / §6.2 と一致させる。修正後も `isAvailable() = true` を接続、許可、承認、署名成功またはアプリのインストール済みの保証にしてはならない。
- **戻し先:** まず `docs/specifications/web-transaction-handoff-spec.md` §5.3 / §6 の可用性とリリース / 機能フラグの関係を確定し、その後 `docs/specifications/sdk.md` §5.1 / §6.2 を同期する。これは SDK 側だけで独自に決めるべき公開ポリシーではない。

## 重点確認結果

### 公開 API / Provider / 対応能力 / バージョン

`createMosaicLynxSDK`、`MosaicLynxSDKOptions`、`isAvailable()`、接続 / アカウント API、`signTransaction()`、`signData()` および `cosignTransaction()` の型と保証意味は受け渡し §5.1 を参照している。`cosignTransaction()` は既存公開契約の範囲として記述され、SDK v1 の必須対応能力、Symbol / NEM 共通対応能力またはチェーン固有の対象範囲として確定されていない。複数 Provider の選択ポリシー、対応能力識別子、バージョン協議の厳密な表現も未決に残っている。

Provider 検出はグローバルオブジェクトの存在、自己申告名前 / バージョン / オリジンまたは表示情報を信頼アンカーにせず、偽の / 不正な形式の / 競合する / 互換性のない Provider を安全側に扱う。Provider 検出、対応能力、接続、許可および承認の混同は確認されなかった。`SDK-001` はこの評価を変更するものではなく、利用可能性の定義と実際の通信経路選択条件の接続に限定される。

### 接続 / 許可 / 承認

接続、account/address 情報公開、署名要求、利用者承認、認証および署名を分離している。SDK は許可判断権限ではなく、公開アカウントキャッシュや接続状態を署名承認の代替にしていない。`connect()` の成功、`isConnected()`、`getActiveAccount()` および対応能力は署名承認やアカウント所有責任の証明ではない。

### 署名 / インターフェース / 署名プロトコル整合

`interfaces.md` の識別子、対象範囲、アカウントの識別情報、オリジン、要求 / 応答、タイムスタンプ / 期限切れ、シリアライズ、検証および共通のエラーモデルを再定義せず参照している。`signing-protocol.md` の Signer 判断権限、状態、承認との結び付け、署名前再検証、終端状態、`RESULT_UNKNOWN`、`DELIVERY_UNKNOWN`、リプレイ / 重複および自動再署名禁止も維持されている。

`signData()` は既存の構造化されたメッセージ / `SignedData` 契約を利用し、`messageExpiresAt` と `expiresAt` の未決差異を未決として保持している。アグリゲート / 連署署名 / 部分トランザクション / NEM マルチシグは共通操作や共通ペイロード構造に独自統合されていない。

### 要求 / 応答 / 並行処理 / 失敗

requestId、操作、Provider / セッション文脈、オリジン / 呼び出し元、対象範囲、アカウント、Signer、対象、ダイジェスト、プロトコル / 世代、期限切れおよび鮮度を応答対応付けに使用し、古くなった / 重複 / リプレイ / 遅延した / 別要求の応答を成功適用しない。複数要求、Provider 置き換え、接続解除、ページライフサイクル、タイムアウト、ローカルキャンセル、通信経路失敗、結果不明および配送不明を区別し、自動再署名、古い承認の再利用、別通信経路への利用者に知らせない代替経路を禁止している。

`SDK-001` を除き、実装時に意味が一意に定まらない要求 / 応答、タイムアウト / キャンセル、エラー正規化の矛盾は確認されなかった。

### エラー定義の正本 / 機微な詳細

共通の論理的な分類は `interfaces.md`、署名失敗 / 結果処理結果の区分は `signing-protocol.md`、具体的な SDK / 受け渡しエラーコードは受け渡し §10 を判断権限としている。`INVALID_MESSAGE`、`NONCE_REUSED` 等の新規公開エラーコード、独自別名または分類体系を追加していない。Relay HTTP 構造上の拒否と SDK 公開エラーも分離されている。内部スタック追跡、認証情報、秘密情報、トークン、URL、パーサー / OS / 暗号処理ライブラリ詳細を公開エラーや診断情報へ露出しない契約になっている。

## 信頼境界 / セキュリティ評価

適合。SDK は Web アプリケーション / dApp と同じ非特権文脈にあり、Provider 応答、Relay 配送、dApp 表示メタデータ、自己申告の / SDK-observed オリジンを信頼された判断権限としない。ブラウザ拡張機能 / モバイルアプリが信頼された呼び出し元文脈、許可、対象内容検査、信頼された UI、承認、認証および署名の最終判断権限を保持する。

SDK 侵害単独で秘密鍵、ニーモニック、ウォレットストア、端末認証データ、セッション秘密情報、Relay 認証情報または wallet-core 署名 API へ到達できない。Relay は内容を解釈しない通信経路のままであり、SDK は Relay を認可、意味上の検証器、承認または結果判断権限としない。未対応の、不正な形式の、不一致、リプレイ、文脈消失および互換性のないバージョンは安全側に終了して扱われる。

## 新規仕様混入の評価

主要な具体化は既存判断権限との整合を確認した。

- requestId の 128-bit CSPRNG / base64url、sessionId、requestDigest、タイムスタンプ / 期限切れ、構造化されたメッセージノンスは `interfaces.md` および受け渡しの既存契約に基づく。
- Mainnet モバイルの HTTPS / 443、originProof、DNS rebinding / private / 予約済みのアドレス拒否は受け渡し / インターフェースの既存契約に基づく。
- 対応能力 / 許可の意味分離、共通の検証、互換性およびエラー定義の正本は `interfaces.md`、`signing-protocol.md`、受け渡しおよび上流設計に基づく。
- `cosignTransaction()` の公開存在は受け渡しの既存の契約を参照し、必須対応能力・対応チェーン・マイルストーンを本書で確定していない。

したがって、`SDK-001` 以外に、上流で未決の事項を SDK 仕様側だけで新規確定した混入は確認されなかった。

## 仕様 / 実装境界の評価

公開型・保証意味、責務境界、検証、対応付け、ライフサイクル、エラー定義の正本および安全側での終了条件は実装可能な契約粒度にある。一方、Provider 選択ポリシーの厳密な構造、対応能力 / バージョン対応表、許可ライフサイクル、呼び出し元結び付けの具体的な仕組み、連署署名公開対象範囲およびタイムアウト / キャンセルの具体ポリシーは未決として適切に委譲されている。

`SDK-001` を解消すれば、実装者が `isAvailable()` の結果とモバイル Relay 選択条件について追加の公開ポリシーを推測する必要はなくなる。

## 未決事項の評価

対象 §21 の OPEN-SDK-001〜005 は、複数 Provider 選択、対応能力 / バージョン協議、タイムアウト / キャンセル / 通信経路失敗、連署署名公開対象範囲、実行環境 / 呼び出し元結び付け / リリース互換性に限定されている。これらを理由に接続を承認とみなすこと、オリジンの信頼性判断を SDK に移すこと、生の / 内容を確認しない署名、秘密情報 API または新規エラーコードを追加してはならないという制約も維持されている。

`SDK-001` は既存未決の単なる実装詳細ではなく、公開 `isAvailable()` の意味を確定するために受け渡し / リリースポリシーへ戻す必要がある論点である。

## 最終判定

- 指摘件数: `ERROR 1 / WARN 0 / NIT 0`
- 主要指摘: `SDK-001` — `isAvailable()` の Provider なし・モバイル Relay 有効化・本番リリース無効条件の不整合。
- 仕様内で修正可能な指摘: `SDK-001` の対象節の同期修正。ただし、先に受け渡し §5.3 / §6 の判断権限を確定する必要がある。
- 上流へ戻す必要がある指摘: `SDK-001`。受け渡しの利用可能性と機能フラグ / リリース利用可能性の関係を確定する。
- 最終判定: **REVISE 仕様**
- **SDK 仕様 READY:** 不可。`SDK-001` 解消後に再レビューする。
