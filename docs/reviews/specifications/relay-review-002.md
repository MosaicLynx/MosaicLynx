## RLS-001 の解消確認

前回指摘は、一般的な `404 Not Found` / 認可失敗規則と、受け渡し §9.6 の「外形が妥当な受領確認 / キャンセルは常に `204 No Content`、正しい Web トークンの場合だけ状態変更する」という個別契約が Relay 仕様内で競合していたことである。

今回の修正では、次を明示している。

- §5.2 のエンドポイント表で受領確認 / キャンセルの有効な要求に対する常時 `204 No Content` と条件付き削除を定義した。
- §8.2 で受け渡し §9.6 のエンドポイント固有の意味を一般的な `404` 規則より優先し、構造上の検証失敗だけを例外とした。
- §11.5、§13.1、§13.2、§14.1、§15.1、§16.1 でトークン不一致、不明 / 削除済み / 終端状態、競合、状態消失 / 再起動の HTTP 応答と変更を同期した。
- 受領確認は `response_available → consumed`、キャンセルは未完了の有効なセッションを `cancelled` として扱う場合に限って変更 / 削除し、それ以外は状態を変更しない操作とした。

したがって、前回指摘の実装分岐（`404` を返すか、受け渡しに従い `204` を返すか）は解消されている。

## 受領確認 / キャンセル応答対応表

「外形が妥当」とは受け渡し §9.6 がエンドポイント要求として扱うメソッド、パス、ヘッダー、本文、プロトコルその他の構造上の検証を満たすことを指す。外形不正の要求はこの対応表の対象外で、既存の受け渡し構造上のエラー契約に従う。

| 操作 / 条件                                                                                                                                                      | HTTP 応答                       | 状態変更                                                                                     |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- | -------------------------------------------------------------------------------------------- |
| 受領確認: 有効な構造、正しいエンドポイントの適用範囲 `webToken`、対応セッションが `response_available`、現在の世代 / ライフサイクルが有効                        | `204 No Content`                | `response_available → consumed` を一度だけ適用し、適用可能な Relay 状態を削除                |
| 受領確認: 誤ったトークン、不明セッション、削除済み / 消費済み / キャンセル済み / 期限切れ、重複受領確認、世代不一致、状態消失後に対象状態を確認不能              | `204 No Content`                | 状態を変更しない操作                                                                         |
| キャンセル: 有効な構造、正しいエンドポイントの適用範囲 `webToken`、対応する有効なセッション、現在のライフサイクルでキャンセルが適用可能                          | `204 No Content`                | セッションを `cancelled` として扱い、適用可能な Relay 状態を削除                             |
| キャンセル: 誤ったトークン、不明セッション、削除済み / キャンセル済み / 消費済み / 期限切れ、重複キャンセル、世代不一致、状態消失 / 再起動後に対象状態を確認不能 | `204 No Content`                | 状態を変更しない操作                                                                         |
| 受領確認 / キャンセル: 不正な形式の、誤ったメソッド、無効なパス / ヘッダー / 本文 / プロトコル等の構造上の失敗                                                   | 受け渡しの構造上のエラー契約    | 変更なし                                                                                     |
| 受領確認 / キャンセルの重複 / 競合（受領確認 vs 受領確認、キャンセル vs キャンセル、受領確認 / キャンセル vs 期限切れ / 削除 / 状態消失等）                      | 有効な構造なら `204 No Content` | 適用可能な論理的な遷移は一度だけ。競合側は状態を変更しない操作とし、終端状態を再活性化しない |

この対応表は、HTTP 応答の状態と状態変更の条件を分離し、受け渡し §9.6 の応答意味を受領確認 / キャンセルの両エンドポイントに一貫して適用している。

## 重点確認結果

### 受け渡し §9.6 との整合

適合。受け渡し §9.6 のメソッド、Bearer `webToken`、受領確認の `response_available → consumed`、キャンセルの未完了セッション終端処理、有効な要求への常時 `204 No Content`、正しい Web トークンの場合だけの状態変更および削除後の冪等 / 存在秘匿を Relay 仕様 §5.2、§8.2、§13.1、§13.2 が維持している。

### 受領確認意味

適合。受領確認の変更条件はエンドポイントの適用範囲、対象セッション、`response_available`、現在の世代 / ライフサイクルの全確認に限定されている。成功した変更は一度だけ `consumed` へ遷移し、重複受領確認、終端 / 削除済み状態、誤ったトークン、不明セッションおよび状態消失では変更しない。受領確認自体は応答の E2E 検証成功を前提とするが、Relay はその検証を行わず、受領確認 / `consumed` を署名成功として表明しない。

### キャンセル意味

適合。キャンセルの変更条件はエンドポイントの適用範囲、対応する有効なセッション、現在のライフサイクルおよびキャンセル適用可能性の全確認に限定されている。有効な構造の誤ったトークン、不明、終端 / 削除済み、重複、世代不一致および状態消失 / 再起動後の未確認状態は `204` の状態を変更しない操作であり、`cancelled` / 削除を適用しない。キャンセルは Relay オブジェクトの削除・無効化に限られ、Signer の署名キャンセル完了や未署名を表明しない。

### `204` と状態変更の分離

適合。受領確認 / キャンセルとも、有効な構造への `204` は変更の成功、セッションの存在、トークンの正しさ、署名成功、署名キャンセル成功、未署名またはアプリケーション処理成功を証明しない。変更は別の条件評価として規定され、確認不能時は状態を変更しない操作となる。

### 存在秘匿

適合。誤ったトークン、不明セッション、終端 / 削除済み / 期限切れ状態、重複、世代不一致および状態消失は、有効な構造であれば全て `204 No Content` に統一される。§8.2 と §14.1 は一般的な `404` / 認可失敗規則が受領確認 / キャンセルのエンドポイント固有の規則を上書きしないことを明示している。構造上の失敗のみがこの例外の対象外であり、トークン有効性やセッション存在の判定結果そのものとは分離されている。

### 重複 / 競合意味

適合。§13.1 / §13.2 は重複受領確認 / キャンセルを状態を変更しない操作とし、§15.1 は受領確認 vs 受領確認、キャンセル vs キャンセル、受領確認 / キャンセル vs 期限切れ / 削除 / 応答送信 / 状態消失 / 再起動の競合で適用可能な論理的な遷移を一度だけとする。CAS、Lua、ロック、キュー等の実装方式を固定せず、終端状態の再活性化、状態ロールバック、double 応答およびセッション間の配送を禁止する契約は維持されている。

### 状態消失 / 再起動 / 世代変更

適合。§16.1 は現在の世代への切替、旧有効な状態 / 認証情報 / 承認 / 署名認可の非復元、旧識別情報の再開禁止を維持する。対象状態を確認できない受領確認 / キャンセルは変更せず、有効な構造なら受け渡し §9.6 に従って `204 No Content` を返す。旧状態を HTTP 応答から推測させず、新鮮な世代 / 識別情報 / エンベロープ / クライアント側の検証 / 承認を要求するため、修正による externally 観測可能な意味の回帰はない。

### 一般 `404` / 認可失敗規則との関係

適合。§8.2 の一般則は「受け渡しの共通 `404` / エラー本文を使用するエンドポイント」に限定され、その直後に受領確認 / キャンセルのエンドポイント固有の例外が置かれている。§14.1 も認可、not found、終端、期限切れ、整合性失敗の各行で同じ優先関係を再確認している。受領確認 / キャンセルの有効な構造に `404` を返す解釈は残っていない。

### `204` の意味境界

適合。§13.1 / §13.2 / §13.3 / §14.3 および §20 は、Relay の受け入れ済み、保存済み、配送済み、acknowledged、消費済み、キャンセル済み、削除、`204` を署名承認、署名成功、署名キャンセル成功、未署名、`RESULT_UNKNOWN` または `DELIVERY_UNKNOWN` と同一視しない。`204` は通信経路操作の外形応答に限定されている。

### セキュリティ / 信頼境界

適合。今回の修正は既存の Relay の内容を解釈しない / 信頼されていない通信経路境界を維持し、トランザクション / メッセージの復号・意味解釈、承認、認証、署名、ウォレット、アカウント / 許可判断権限、E2E 秘密情報の受信・保持を追加していない。生のトークン、セッション秘密情報、暗号文、平文、不要な識別情報 linkage の非露出、安全側での終了、世代結び付け、終端再利用防止も維持されている。新しいエンドポイント、エラーコード、エラー分類体系、トークンモデル、署名結果または信頼判断権限は追加されていない。
