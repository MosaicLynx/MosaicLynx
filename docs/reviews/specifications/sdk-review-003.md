## 5. Summary

現行 SDK Specification は、前回 `SDK-001` の修正を維持し、現在の signing result / delivery semantics と多くの upstream contract を正しく反映している。しかし、Requirements と Interfaces / Signing Protocol で確定した Mainnet release / evidence gate を SDK 本文が明示していない。これは単なる実装詳細の不足ではなく、SDK の availability / capability / version / connection / permission / transport と Mainnet signing capability の authority を分離する public security contract の不足である。

- `SDK-001` は `Resolved`。`isAvailable()` は current Handoff route availability として local Provider route または条件を満たす Mobile Relay route の有無を表し、Provider がないだけで `false` にしない。availability は connection、permission、Account authorization、authentication、unlock、approval、Mainnet signing enabled、App installed または signing success を意味しない。
- SDK は Web Application / dApp と trusted Signer の間の non-privileged integration / orchestration layer であり、request construction、Provider discovery、capability / version check、dispatch、correlation、response validation、public result mapping、transport / local lifecycle、public error normalization を担う。Authentication、Signing-capable unlock、Account authorization、Explicit user approval、semantic signing decision、trusted confirmation、final target validation、raw signing、secret handling、result disposition decision は Signer authority のままである。
- `MosaicLynxSigningResult<T>` は Handoff と一致し、`signTransaction()` は `Promise<MosaicLynxSigningResult<SignedTransaction>>`、`signData()` は `Promise<MosaicLynxSigningResult<SignedData>>`。known result は `succeeded` で resolve し、Signer-originated `RESULT_UNKNOWN` は `resultUnknown` で resolve し、通常の rejection / failure は Handoff §10 の error で reject する。
- `RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` は SDK / Provider / Relay / transport / timeout / outage / response absence / reconnect / page lifecycle から生成・推測しない。known signed result の `PENDING`、`DELIVERED`、`DELIVERY_UNKNOWN` は Signer-originated disposition をそのまま保持し、Relay ACK / consumed state で `DELIVERED` に書き換えない。
- local Provider と Mobile Relay は同じ public result semantics を使用する。malformed / incompatible / conflicting Provider を trusted Signer とせず、security failure や signing 開始後の failure / unknown から local ↔ remote、Provider A ↔ B、Signer A ↔ B の automatic fallback、automatic re-sign を行わない。
- connection、permission、Account disclosure、capability、availability、signing Authorization、four conditions、signing success は分離され、Public Account は public address / publicKey 等に限定される。Origin の最終 authority、semantic inspection、approval、secret、Relay authority は SDK の外にある。
- 新規 `SR-001` は、`CR-NFR-006` / `SDK-AC-010` / `SDK-NFR-004` と Interfaces §7.4 / Signing Protocol §21.1 の Mainnet gate を SDK 本文 §6、§13、§16、§19〜§20 が反映していないことを指摘する。`isAvailable()`、SDK / Provider capability / version、connection、permission、Relay / App Link availability、wallet-core capability、test success、signed response は Mainnet gate の代替ではなく、gate の判定不能・失敗時は trusted Signer 側の unavailable / rejection を SDK が保持する、という normative clause と traceability が必要である。

## 7. Required Changes

### `SR-001`: Mainnet release / evidence gate の SDK contract への反映

- **Severity:** `Critical`
- **Status:** `New`
- **Location:** `docs/specifications/sdk.md` §6.2〜§6.4、§13、§16、§19〜§20。§6.2 の `release / product gate` は Mobile route availability の条件であり、Mainnet signing security gate ではない。対象本文には `Mainnet` の release / evidence gate、trusted Signer authority、非代替性、判定不能時の結果保持を表す記述がない。
- **Condition / fact:** 対象は `isAvailable()`、Provider / capability / version、connection / permission、Relay / App Link、wallet-core および signed response を個別に signing approval / success の代替にしないが、Mainnet signing capability についても同じく代替でないこと、current release / evidence gate を満たした trusted Signer だけが有効化することを定めていない。§19 の acceptance と §20 の traceability にも `CR-NFR-006`、`SDK-AC-010`、Mainnet release / evidence gate の確認項目がない。
- **Existing basis:** [共通 Requirements `CR-NFR-006`](../../requirements/requirements.md)、[SDK Requirements §SDK-PLAT-001〜005 / `SDK-AC-010` / `SDK-NFR-004`](../../requirements/sdk.md)、[Interfaces §7.4](../../specifications/interfaces.md)、[Signing Protocol §21.1](../../specifications/signing-protocol.md) は、Mainnet capability を current release / evidence gate を満たす trusted Signer に限定し、Scope、capability、Provider / SDK / Relay / OS / wallet-core state、test success、signed response を代替とせず、gate の missing / invalid / expired / inconsistent / unverifiable / unknown を fail-closed にすることを確定している。
- **Problem:** SDK 実装者が route availability、SDK / Provider capability、connection、permission、Relay availability または signed response の存在を Mainnet readiness と誤って扱う余地が残る。SDK が gate を評価する詳細実装を要求する必要はないが、SDK が gate を有効化・迂回せず、Signer-originated Mainnet unavailable / rejection を Handoff §10 の意味のまま返す境界が対象 contract から検証できない。
- **Impact:** Mainnet の security gate が SDK の可用性・互換性・transport 成功へ誤って委譲され、fail-open または Signer の Mainnet rejection の意味変換が起こり得る。`CR-NFR-006`、`SDK-AC-010`、`SDK-NFR-004` に反し、Review Gate 2、5、6、7 を満たせない。
- **Minimum fix / recheck:** 対象本文に、(1) Mainnet signing capability は current release / evidence gate を満たす trusted Signer だけが有効化する、(2) `isAvailable()`、SDK / Provider capability / version、connection、permission、Relay / App Link availability、wallet-core capability、test success、signed response は代替でない、(3) gate が missing / invalid / expired / inconsistent / unverifiable / unknown の場合は Signer 側が Mainnet を disabled / unavailable または Handoff §10 の対応 error とし、SDK はその意味を生成・緩和・迂回せず保持する、(4) Testnet-only の継続を妨げない、を normative に追加する。evidence schema / evaluator / trusted key / release tooling の詳細は Interfaces、ADR、release policy へ委譲したままでよい。§19 の acceptance、§20 の traceability、Case 15 をこの contract に追跡し、Gate 2、5、6、7 を再確認する。

## 9. Resolved Findings

### `SDK-001`: Resolved — `isAvailable()` と Mobile Relay route availability の整合

- **Severity:** Critical（旧レビューの `ERROR`）
- **初出:** `sdk-review-001`
- **過去状態:** `sdk-review-002` では `Resolved` とされていたが、その結論は自動継承せず、現行本文と Handoff を再照合した。
- **現在の確認:** SDK §6.2 は、compatible local Provider route が利用可能なら `isAvailable() = true` とし、Provider が存在しない場合も Handoff §5.3 の current release、feature flag、release / product gate、受信 App 提供状況、runtime、Web API、verified HTTPS App Link 条件を満たす Mobile Relay route があれば `true` とする。Provider 不在だけで `false` にせず、Provider が malformed / incompatible / conflicting / currently unselectable であっても absence として remote へ silent fallback しない。両 route がなければ `false` である。
- **意味の分離:** SDK §6.2、§7、§16 と Handoff §5.3 は availability を connected、permission granted、Account authorized、authenticated、unlocked、user approved、Mainnet signing enabled、signing succeeds、Mobile App installed と同一視しない。Handoff §5.3 の現行 product / release gate が route の公開可否を決めるため、App install の推測も行わない。
- **Case check:** compatible local Provider は `true`、Provider 不在で Mobile route が available は `true`、両方 unavailable は `false`、incompatible / malformed Provider は trusted route ではなく security failure を remote route へ silent fallback しない。従って同じ問題の回帰はなく、`SDK-001: Resolved` を維持する。

## 10. Deferred Findings

- `OPEN-SDK-005`: runtime、caller binding、release compatibility の具体方式。SDK が final Origin authority、platform API、release evaluator になることは確定していない。
- Interfaces `OPEN-001` 等の message expiry field、permission / revocation、caller proof、capability negotiation は upstream の未決として扱い、SDK が `expiresAt` と `messageExpiresAt` を独自 alias していないことを確認した。
