## 5. 要約

現行 SDK 仕様は、前回 `SDK-001` の修正を維持し、現在の署名結果 / 配送意味と多くの上流契約を正しく反映している。しかし、要件とインターフェース / 署名プロトコルで確定した Mainnet リリース / 根拠判定条件を SDK 本文が明示していない。これは単なる実装詳細の不足ではなく、SDK の利用可能性 / 対応能力 / バージョン / 接続 / 許可 / 通信経路と Mainnet 署名対応能力の判断権限を分離する公開セキュリティ契約の不足である。

- `SDK-001` は `Resolved`。`isAvailable()` は現在の受け渡し経路利用可能性としてローカル Provider 経路または条件を満たすモバイル Relay 経路の有無を表し、Provider がないだけで `false` にしない。利用可能性は接続、許可、アカウントの利用認可、認証、ロック解除、承認、Mainnet 署名有効、アプリインストール済みのまたは署名成功を意味しない。
- SDK は Web アプリケーション / dApp と信頼された署名主体の間の non-privileged 統合 / 処理の調整層であり、要求組み立て、Provider 検出、対応能力 / バージョン確認、振り分け、対応付け、応答検証、公開結果対応付け、通信経路 / ローカルライフサイクル、公開エラー正規化を担う。認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認、意味上の署名判断、信頼された確認、最終対象検証、生の署名、秘密情報処理、結果処理結果の区分判断は署名主体判断権限のままである。
- `MosaicLynxSigningResult<T>` は受け渡しと一致し、`signTransaction()` は `Promise<MosaicLynxSigningResult<SignedTransaction>>`、`signData()` は `Promise<MosaicLynxSigningResult<SignedData>>`。既知の結果は `succeeded` で解決し、署名主体が生成した `RESULT_UNKNOWN` は `resultUnknown` で解決し、通常の拒否 / 失敗は受け渡し §10 のエラーで拒否する。
- `RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` は SDK / Provider / Relay / 通信経路 / タイムアウト / 障害 / 応答欠如 / 再接続 / ページライフサイクルから生成・推測しない。既知の署名済み結果の `PENDING`、`DELIVERED`、`DELIVERY_UNKNOWN` は署名主体が生成した処理結果の区分をそのまま保持し、Relay 受領確認 / 消費済み状態で `DELIVERED` に書き換えない。
- ローカル Provider とモバイル Relay は同じ公開結果意味を使用する。不正な形式の / 互換性のない / 競合する Provider を信頼された署名主体とせず、セキュリティ失敗や署名開始後の失敗 / 不明からローカル ↔ リモート、Provider A ↔ B、署名主体 A ↔ B の自動代替経路、自動再署名を行わない。
- 接続、許可、アカウント情報公開、対応能力、利用可能性、署名認可、四つの条件、署名成功は分離され、公開アカウントは公開アドレス / publicKey 等に限定される。オリジンの最終判断権限、意味上の内容検査、承認、秘密情報、Relay 判断権限は SDK の外にある。
- 新規 `SR-001` は、`CR-NFR-006` / `SDK-AC-010` / `SDK-NFR-004` とインターフェース §7.4 / 署名プロトコル §21.1 の Mainnet 判定条件を SDK 本文 §6、§13、§16、§19〜§20 が反映していないことを指摘する。`isAvailable()`、SDK / Provider 対応能力 / バージョン、接続、許可、Relay / App Link 利用可能性、wallet-core 対応能力、テスト成功、署名済み応答は Mainnet 判定条件の代替ではなく、判定条件の判定不能・失敗時は信頼された署名主体側の利用不能 / 拒否を SDK が保持する、という規範的な clause と追跡可能性が必要である。

## 7. 必須の修正

### `SR-001`: Mainnet リリース / 根拠判定条件の SDK 契約への反映

- **重要度:** `Critical`
- **状態:** `New`
- **対象箇所:** `docs/specifications/sdk.md` §6.2〜§6.4、§13、§16、§19〜§20。§6.2 の `release / product gate` はモバイル経路利用可能性の条件であり、Mainnet 署名セキュリティ判定条件ではない。対象本文には `Mainnet` のリリース / 根拠判定条件、信頼された署名主体判断権限、非代替性、判定不能時の結果保持を表す記述がない。
- **条件 / 事実:** 対象は `isAvailable()`、Provider / 対応能力 / バージョン、接続 / 許可、Relay / App Link、wallet-core および署名済み応答を個別に署名承認 / 成功の代替にしないが、Mainnet 署名対応能力についても同じく代替でないこと、現在のリリース / 根拠判定条件を満たした信頼された署名主体だけが有効化することを定めていない。§19 の受け入れと §20 の追跡可能性にも `CR-NFR-006`、`SDK-AC-010`、Mainnet リリース / 根拠判定条件の確認項目がない。
- **既存の根拠:** [共通要件 `CR-NFR-006`](../../requirements/requirements.md)、[SDK 要件 §SDK-PLAT-001〜005 / `SDK-AC-010` / `SDK-NFR-004`](../../requirements/sdk.md)、[インターフェース §7.4](../../specifications/interfaces.md)、[署名プロトコル §21.1](../../specifications/signing-protocol.md) は、Mainnet 対応能力を現在のリリース / 根拠判定条件を満たす信頼された署名主体に限定し、対象範囲、対応能力、Provider / SDK / Relay / OS / wallet-core 状態、テスト成功、署名済み応答を代替とせず、判定条件の欠落 / 無効な / 期限切れ / 不整合の / 検証不能の / 不明を安全側に終了することを確定している。
- **問題:** SDK 実装者が経路利用可能性、SDK / Provider 対応能力、接続、許可、Relay 利用可能性または署名済み応答の存在を Mainnet 準備状態と誤って扱う余地が残る。SDK が判定条件を評価する詳細実装を要求する必要はないが、SDK が判定条件を有効化・迂回せず、署名主体が生成した Mainnet 利用不能 / 拒否を受け渡し §10 の意味のまま返す境界が対象契約から検証できない。
- **影響:** Mainnet のセキュリティ判定条件が SDK の可用性・互換性・通信経路成功へ誤って委譲され、安全条件を満たさない継続または署名主体の Mainnet 拒否の意味変換が起こり得る。`CR-NFR-006`、`SDK-AC-010`、`SDK-NFR-004` に反し、レビュー判定条件 2、5、6、7 を満たせない。
- **最小修正 / 再確認:** 対象本文に、(1) Mainnet 署名対応能力は現在のリリース / 根拠判定条件を満たす信頼された署名主体だけが有効化する、(2) `isAvailable()`、SDK / Provider 対応能力 / バージョン、接続、許可、Relay / App Link 利用可能性、wallet-core 対応能力、テスト成功、署名済み応答は代替でない、(3) 判定条件が欠落 / 無効な / 期限切れ / 不整合の / 検証不能の / 不明の場合は署名主体側が Mainnet を無効 / 利用不能または受け渡し §10 の対応エラーとし、SDK はその意味を生成・緩和・迂回せず保持する、(4) Testnet 専用の継続を妨げない、を規範的なに追加する。根拠スキーマ / 評価器 / 信頼された鍵 / リリース補助ツールの詳細はインターフェース、ADR、リリースポリシーへ委譲したままでよい。§19 の受け入れ、§20 の追跡可能性、事例 15 をこの契約に追跡し、判定条件 2、5、6、7 を再確認する。

- **現在の確認:** SDK §6.2 は、互換性のあるローカル Provider 経路が利用可能なら `isAvailable() = true` とし、Provider が存在しない場合も受け渡し §5.3 の現在のリリース、機能フラグ、リリース / プロダクト判定条件、受信アプリ提供状況、実行環境、Web API、検証済み HTTPS App Link 条件を満たすモバイル Relay 経路があれば `true` とする。Provider 不在だけで `false` にせず、Provider が不正な形式の / 互換性のない / 競合する / currently unselectable であっても欠如としてリモートへ利用者に知らせない代替経路しない。両経路がなければ `false` である。
- **意味の分離:** SDK §6.2、§7、§16 と受け渡し §5.3 は利用可能性を接続済み、許可 granted、アカウント認可済みの、認証済みの、ロック解除済み、利用者承認済み、Mainnet 署名有効、署名 succeeds、モバイルアプリインストール済みのと同一視しない。受け渡し §5.3 の現行プロダクト / リリース判定が経路の公開可否を決めるため、アプリ install の推測も行わない。
- **事例確認:** 互換性のあるローカル Provider は `true`、Provider 不在でモバイル経路が利用可能は `true`、両方利用不能は `false`、互換性のない / 不正な形式の Provider は信頼された経路ではなくセキュリティ失敗をリモート経路へ利用者に知らせない代替経路しない。従って同じ問題の回帰はなく、`SDK-001: Resolved` を維持する。

## 10. 後続工程へ委譲する指摘

以下は対象本文が明示的に未決として維持しており、未決の存在だけでは指摘としない。解消時に SDK の公開契約として再レビューする。

- `OPEN-SDK-001`: 複数 Provider の選択ポリシー。不正な形式の / 互換性のない / 競合する Provider を信頼された経路としない安全側境界は確定しているが、複数の互換性のある Provider の明示選択は未確定。
- `OPEN-SDK-002`: 対応能力 / バージョン協議、対応対応能力の識別子、互換性対応表。不明 / 未対応のは拒否 / 利用不能、利用者に知らせない格下げ不可という安全側だけが確定している。
- `OPEN-SDK-003`: タイムアウト / キャンセル / 通信経路失敗の具体的復旧ポリシー、再試行タイミング。SDK タイムアウト、通信経路失敗、キャンセルを署名主体結果、`RESULT_UNKNOWN`、`DELIVERY_UNKNOWN` に変換しないこと、同一要求の再利用・自動再署名をしないことは確定している。
- `OPEN-SDK-004`: 連署署名の v1 公開対象範囲。現行公開範囲と Symbol / NEM のチェーン固有の境界を維持し、`MosaicLynxSigningResult<T>` を連署署名に暗黙拡張していない。
- `OPEN-SDK-005`: 実行環境、呼び出し元結び付け、リリース互換性の具体方式。SDK が最終オリジンの信頼性判断、プラットフォーム API、リリース評価器になることは確定していない。
- インターフェース `OPEN-001` 等のメッセージ有効期限フィールド、許可 / 失効、呼び出し元証明、対応能力協議は上流の未決として扱い、SDK が `expiresAt` と `messageExpiresAt` を独自別名していないことを確認した。

ブラウザ拡張機能 / Provider の下流同期課題は、[ブラウザ拡張機能仕様](../../specifications/browser-extension.md) §5 の旧 `SignedTransaction` / `SignedMessage` 結果構造、旧 Provider エラーコード、`id` / `profileId` を含む内部選択子 / アカウント投影、および送信元パッケージの旧公開型である。現行 SDK / 受け渡し共通の契約は公開共用体、受け渡し §10 エラー定義の正本、公開アカウント境界を明確にしており、SDK がローカル Provider 応答をどのように共通の結果へアダプターするかも §5.4、§8、§15 で署名主体が生成した結果 / 処理結果の区分のそのまま通過させるとして意味が定まっている。このため責任主体はブラウザ拡張機能 / Provider 仕様と実装同期であり、SDK 指摘へ逆流させない。
