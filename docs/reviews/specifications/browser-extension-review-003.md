## 9. 解消済みの指摘

### SR-001 — アカウント投影 / 選択子判断権限

`PublicAccountIdentity` は §10.1 で `Scope`、`address`、`publicKey` のみに限定される。§5.2 はページに公開する入力、アカウントレコード、返却値、イベントペイロードに内部 ID / ハンドルを含めず、ページ提供された選択子を認可、所有責任、鍵選択または署名主体識別情報の判断権限にしない。複数アカウントの選択は信頼された署名主体 UI / 署名主体が所有する文脈で行う。`expectedSignerPublicKey` は §5.2、§10.2 の公開署名主体期待値であり、内部選択子ではない。`OPEN-BEX-001` も §32 で解消済みと明記されている。これはインターフェース §5.3、受け渡し §5.2 / §6.1、SDK §5 / §7 と整合する。

### SR-002 — Provider エラー定義の正本 / 対応付け

§5.4 と §27 は、Provider / 特権を持つ RPC / 通信経路固有のコードを内部境界に閉じ、共通の論理的な分類、署名プロトコル結果、受け渡し §10 の `MosaicLynxSDKErrorCode` および wallet-core 内部エラーを別層として扱う。現行 Provider パッケージの `INVALID_MESSAGE`、`NONCE_REUSED`、`UNAUTHORIZED_ORIGIN` 等を公開受け渡し / SDK コードの追加集合にせず、対応付け不能なコードは成功や新しい公開コードにせず、必要な catch-all は既存 `INTERNAL_ERROR` に限定する。これはインターフェース §10、署名プロトコル §16、受け渡し §10、SDK §5.2 / §5.4 と整合する。

### SR-003 — プロダクトメソッド構造同期

§5.1〜§5.2 の Provider 契約は SDK / 受け渡し / インターフェースの現在の構造を判断権限とし、プロダクト仕様 §16.1 の範囲を限定した `getActiveAccount` 省略および `cosignTransaction` 省略をブラウザ拡張機能の仕様へ逆流させていない。これは対象内で解消済みである。一方、プロダクト / Provider / SDK / 受け渡しの横断同期自体は責任主体を持つ下流 / 上流追加対応であり、本レビューの対象指摘ではない。

### SR-004 — 共通の四つの署名条件

§7.3 が4条件を同一の要求、呼び出し元、プロファイル内の文脈、アカウント、チェーン / ネットワーク、操作、厳密な対象、内容検査、期限切れに結び付けし、いずれかが欠落 / 古くなった / 失効済み / ロック済み / 変更された / mismatched / 不明 / 無効化済みなら `AUTHORIZED`、`SIGNING`、`SUCCEEDED` または wallet-core 呼び出しへ進まない。§12.1 の `AUTHORIZED`、§18.1 の署名前再検証、§18.2 の wallet-core 呼び出し前、§20 のライフサイクル、§24 のキャンセル、§29 の不変条件、§31.6 / §31.9 / §31.10 の受け入れ、§33 の追跡可能性が同じ意味を保持する。§7.3、§17.2、§29 は接続、許可、アカウント情報公開、通常の `UNLOCKED`、選択済みのアカウント、prior 認証、キャッシュまたは `every-signature` 単独成立を代替にしていない。

### SR-005 — Mainnet リリース / 根拠判定条件

§2.3 と §18.3 は現在のリリース / 適用可能な根拠ポリシーの判定条件を信頼された署名主体 / リリースセキュリティ判断権限の判断権限とする。Provider / SDK は判定条件評価器、リリース判断権限または代替ではない。§18.3 / §31.15 はネットワーク、Provider / SDK 利用可能性、対応能力、接続、許可、アカウント情報公開、通常のロック解除、wallet-core 対応能力、テスト成功、署名済み結果、Provider 応答、応答配送、通信経路成功を判定条件証明としない。SDK / Provider / プロトコルバージョン互換性および wallet-core 利用可能性は、§5.3、§18.1、§26 の実行環境 / 経路 / 結び付け条件であり、リリース証跡判定条件の判断権限ではない。判定条件の欠落、無効な、期限切れ、不整合の、検証不能の、不明は無効 / 利用不能とされ、自動再試行 / 再署名 / 代替の経路を行わず、独立した Testnet 専用署名は不必要に停止しない。根拠スキーマ、評価器、信頼された鍵、SBOM / 補助ツールはリリース判断権限へ委譲される。

### SR-006 — 署名結果 / 配送意味

§5.2.1、§22.2 は既知の署名済み結果を `SUCCEEDED` と署名主体が生成した `deliveryDisposition`（`PENDING`、`DELIVERED`、`DELIVERY_UNKNOWN`）の組として保持し、署名主体が署名生成自体を確定できない場合だけ `RESULT_UNKNOWN` とする。後者は署名済み結果、配送処理結果の区分、通常のエラーコードを持たない。§12.1、§20.2、§21、§24、§29、§31 は応答消失、ページ配送、通信経路完了、ライフサイクル消失から状態 / 処理結果の区分を推測せず、自動再署名しないことを確認できる。§5.2.1 / §22.2 は受け渡し §5.2.1 / §7.2、SDK §5.1 / §5.4 の `MosaicLynxSigningResult<T>` 対応付けを意味不変に適用する。確定済みの結果復旧は新しい署名ではなく、上流の既存結果の再送 / 再配送 / 取得 / 照会契約に限定され、未確定の復旧 API を本書で発明していない。Relay 受領確認 / 消費済み状態も署名主体側の処理結果の区分の判断権限ではなく、Relay 応答 / HTTP / 通信経路完了から処理結果の区分を生成しない。
