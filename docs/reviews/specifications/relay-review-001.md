## 総評

Relay 仕様は、Relay を内容を解釈しない / 信頼されていない通信経路に限定し、トランザクション / メッセージの解釈、承認、認証、署名、wallet-core、アカウントに関する判断権限および署名結果の判断を Relay から分離している。世代、セッション、参加者、方向、認証情報対象範囲、期限切れ、要求 / 応答識別情報を用いた経路選択、短期保持、終端削除、重複 / リプレイ、並行処理、再起動 / 状態消失、リソース制御、観測可能性および安全側での終了の契約も、要件、Relay 設計および受け渡しと概ね整合している。

ただし、受領確認 / キャンセルエンドポイントの認証失敗時・削除後の HTTP 応答が受け渡し §9.6 と一致していない。受け渡しは「外形が妥当な受領確認 / キャンセルには常に `204 No Content` を返し、正しい Web トークンの場合だけ状態を変更する」と定めている。一方、本仕様 §8.2 は認証情報不一致等を共通 `404 Not Found` とする一般則を置き、§13.1 / §13.2 は対象 webToken を検証した場合の `204` を記述している。この競合はサーバー実装とクライアントの存在秘匿・冪等性の解釈を一意にできないため、修正が必要である。

## 判定

### REVISE 仕様

受領確認 / キャンセルの HTTP 応答意味を受け渡し §9.6 と同期する `ERROR` 1件を解決するまで、次工程へ確定的に進めない。

### RLS-001: 受領確認 / キャンセルの応答意味不整合

- **重要度:** `ERROR`
- **状態:** `OPEN`
- **対象箇所:** [Relay 仕様 §8.2](../../specifications/relay.md#82-認可規則)、[§13.1](../../specifications/relay.md#131-受領確認)、[§13.2](../../specifications/relay.md#132-キャンセル)、[§14.1](../../specifications/relay.md#141-失敗分類)。比較対象は [Web トランザクション受け渡し仕様 §9.6](../../specifications/web-transaction-handoff-spec.md#96-受領確認とキャンセル)。
- **問題:** 受け渡し §9.6 は、受領確認 / キャンセルについて「外形が妥当な要求へ常に `204 No Content` を返し、正しい Web トークンの場合だけ状態を変更する」と定め、削除後の再試行でもセッションの存在やトークン一致を判別できない意味を要求している。一方、Relay 仕様 §8.2 は認証情報不一致、セッション不在、終端状態または期限切れを受け渡しの共通 `404 Not Found` で同一化する一般則を受領確認 / キャンセルにも適用し得る記述になっている。さらに §13.1 は「対象 webToken」が正しい場合の `204` を成功条件として記載し、§13.2 も webToken を検証して未完了セッションを変更する構造であるため、不正トークン・削除後・状態消失時に `204`（状態変更なし）なのか `404`／拒否なのかが一意に定まらない。§15.1、§16.1 の状態不整合時の受領確認 / キャンセル停止・拒否も、この受け渡しのエンドポイント固有の意味との関係が明示されていない。
- **根拠:** 受け渡し §9.6 は受領確認 / キャンセルの状態とトークン有効性に応じた状態変更を明示している。Relay 仕様 §5.1 は受け渡し §9 をエンドポイント、メソッド、状態、本文、認証情報の正本として参照し、§2.2 と §14.2 も受け渡し契約を再定義しないとしているため、Relay 側の一般的な 404 規則が受領確認 / キャンセルの個別契約を上書きしてはならない。
- **リスク:** 実装者が、不正トークンや削除済みセッションについて `404` を返す実装と、受け渡しに従って外形が妥当なら `204` を返す実装に分岐する。前者はトークン有効性、セッション存在、終端状態の差分を応答から推測可能にし、後者を想定する SDK の冪等受領確認 / キャンセルと相互運用できない。状態消失や並行するキャンセル / 受領確認でも応答意味が不一致になり、通信経路処理結果の区分と署名結果の境界をクライアントが誤解するおそれがある。
- **推奨対応:** 受け渡し §9.6 を受領確認 / キャンセルのエンドポイント固有の判断権限として明示する。外形が不正な要求だけは受け渡しが許す構造上のエラーとし、外形が妥当な受領確認 / キャンセルはトークン、セッションの存在、終端状態または削除済みかどうかを外部へ区別せず `204 No Content` とする。その場合も、正しい対象範囲の webToken と現行状態が確認できたときだけ、受領確認の `response_available → consumed` またはキャンセルの終端削除を適用する。§8.2 の共通 404 規則、§13.1 / §13.2 の条件付き表現、§14.1 の失敗表、§15.1 / §16.1 の状態消失文言をこの例外と矛盾しないよう同期し、HTTP 応答と状態遷移を明確に分離する。
- **上流へ戻す必要:** なし。受け渡し §9.6 が既にエンドポイント意味を確定しているため、Relay 仕様内の一般則・説明を受け渡しに合わせて修正すべきである。
- **仕様内で修正可能:** あり。受領確認 / キャンセルの応答対応表と状態消失 / 競合時の扱いを対象節へ反映する。

## 重点確認結果

### 設計 → 仕様 / 責任分界

Relay の責務はセッション / 参加者 / 世代ライフサイクル、経路選択、一時的な保持、エンドポイント受け入れ判定、構造上の検証、配送、受領確認 / キャンセル、期限切れ、リソース制御、観測可能性に限定されている。トランザクション / メッセージ解析、意味上の検証、要約、許可、承認、認証、署名、wallet-core および署名結果の推測は明示的に禁止され、Relay 設計と要件の責任境界を維持している。

受け渡しのエンドポイント、フィールド、認証情報、エンベロープ、世代、TTL、HTTP 状態、ポーリング、受領確認 / キャンセルは参照扱いであり、Relay 独自の公開 SDK API、署名操作、エラー分類体系、WebSocket、プッシュ、federated Relay、長期保存領域または自動代替経路は追加されていない。DB / Redis スキーマ、キュー、ロック、ブローカー、クラスター構成、配置の具体実装を未決としていることも、今回のレビュー範囲で要求された仕様 / 実装境界に適合する。

### Relay 信頼境界 / 内容を解釈しない通信経路

適合。Relay はインターネットに公開する入力、SDK / ブラウザ拡張機能、モバイルアプリ、永続化および運用者を信頼アンカーとせず、暗号化されたエンベロープを復号・改変・意味解釈しない。経路選択に使用する外側メタデータとサーバー側の状態、クライアント / Signer が最終検証する内部対応付け、AEAD、オリジン、アカウント、許可、承認および署名意味が分離されている。

Relay の受け入れ済み / 保存済み / 配送済み / 受領確認 / 消費済みを Signer の `VALIDATED`、`AUTHORIZED`、`SUCCEEDED` または利用者拒否と解釈しない。Relay 侵害単独で秘密鍵取得、E2E 復号、承認迂回、署名認可または無断署名へ到達しない境界も維持されている。

### セッション / 世代 / 認証情報

適合。`sessionId`、`requestId`、`generationId`、要求 / 応答識別情報、参加者役割、方向および通信経路認証情報が別の意味として定義され、識別子 knowledge 単独でセッション参加、メッセージ取得、応答注入またはセッション間のアクセスが成立しない。世代は非秘密の state-continuity 文脈であり、再起動、状態消失、永続化 corruption、インスタンス / クラスター継続性消失または運用上の無効化で旧状態を現在の状態として復元しない。世代の厳密な形式、保存領域バックエンド、再接続 API、再試行タイミングおよび運用上のリソースポリシーは未決に留められている。

`appToken` / `webToken` はエンドポイント認可、`sessionSecret` は E2E 秘密情報と分離され、生の認証情報、セッション秘密情報、導出された鍵、秘密鍵、ニーモニック、ウォレットストアおよび平文が Relay の API、ログ、診断情報、バックアップ、遠隔計測データまたは管理者表示へ露出しない。

### 経路選択 / 保持 / TTL

適合。セッション、役割、方向、世代、要求 / 応答識別情報、認証情報対象範囲、期限切れおよびライフサイクルの組み合わせで経路選択文脈を分離し、セッション間の / 受信者間の照会と終端状態再利用を禁止している。受け渡しの 5 分期限切れ、512 KiB 暗号化された HTTP 本文、作成頻度、long ポーリング、一時的な保持、終端削除、最大 24 時間の最小削除記録を参照しており、メッセージ履歴、バックアップ、分析用長期保存または再試行キューとして Relay を利用しない。

受け渡し §9.9 の自己ホスト MVP の具体的インフラ記述は、今回の Relay サーバー側の契約の判断権限（エンドポイント、フィールド、認証情報、TTL、HTTP 状態等）とは分けて扱った。Relay 仕様は保存領域エンジンや Redis スキーマを独自に再定義していない。

### 重複 / リプレイ / 並行処理

適合。重複作成、同じ / 競合する応答、repeated 取得 / ポーリング、重複受領確認、キャンセル競合、期限切れ競合、旧認証情報、古くなった世代、遅延した配送、再起動 / 状態消失を通信経路レベルの状態とクライアント側の対応付け / 完全性検証に分担している。Relay は厳密に一回のみ配送またはアプリケーション処理を保証せず、同一応答の競合上書き、終端状態の再活性化、状態ロールバック、セッション間の配送を防止する論理不変条件を要求している。

### 失敗 / 配送意味

`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN`、署名成功、利用者拒否、未署名および配送処理結果の区分を混同しない方針は適合している。不正な形式の、認可失敗、not found、期限切れ、古くなった世代、保存領域失敗、ネットワークタイムアウト、配送失敗、重複 / 競合の分類も、Relay が署名結果を生成しない責任分界と整合する。ただし、RLS-001 の受領確認 / キャンセルエンドポイント応答だけは受け渡し個別契約との同期が必要である。

### エラー定義の正本

適合。共通の論理的な分類はインターフェース仕様、署名結果と `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` は署名プロトコル、SDK / 受け渡しの具体的なコードと対応付けは受け渡し §10、Relay HTTP 構造上の拒否本文は `RELAY_REQUEST_REJECTED` とする判断権限分担を維持している。Relay 仕様は新しい公開 SDK エラーコード、署名結果または分類体系を追加していない。

### セキュリティ上の不変条件

RLS-001 を除き、次の不変条件は本文と整合する。

- Relay は署名判断権限、ウォレット、トランザクション検証器、アカウント / 許可判断権限、承認エンジンまたは信頼アンカーではない。
- Relay 認証、セッション受け入れ判定、保存領域、配送、受領確認、利用可能性は承認、認証、署名成功またはトランザクション安全性を意味しない。
- 秘密鍵、ニーモニック、プロファイルパスワード、ウォレットストア、sessionSecret、導出された鍵、署名秘密情報、生の認証情報、平文および不要な機微なメタデータを Relay 境界から露出しない。
- 期限切れ、消費済み、キャンセル済み、再送された、重複、古くなった、無効化済みまたは旧世代のオブジェクトを有効な受け渡しとして再利用しない。
- セッション間の / 受信者間の漏えい、応答差し替え、終端状態再利用および状態消失後の古くなった状態復元を許さない。
- 構造上の検証、世代整合性、経路選択完全性または shared-state 整合性を確認できない場合は安全側での終了とする。

### 追跡可能性 / 未決課題

Relay 要件 `RR-001`〜`RR-011`、`RR-NFR-*`、Relay 設計の責務・セッション・世代・内容を解釈しない境界・scaling・失敗方針、および受け渡し §7〜§9 の具体的な受け渡し契約への追跡可能性は確認できた。`OPEN-RELAY-001`〜`OPEN-RELAY-005` も世代形式、保存領域 / 配置、再接続、再試行対応付け、運用リソースポリシーに限定され、上流で未決の事項を勝手に確定していない。

### 基本設計・仕様粒度

Relay 実装者が追加判断せずに必要なサーバー側の通信経路契約を実装できるよう、エンドポイント責務、受け入れ判定、経路選択分離、ライフサイクル、保持、重複 / リプレイ、並行処理、失敗、リソース制御、プライバシーおよび受け入れ不変条件が定義されている。反面、具体的な保存領域 API、Redis 鍵、キューアルゴリズム、クラスター構成、配置、再試行間隔、metric 名または rate-limit の追加値を固定しておらず、実装詳細への過剰な踏み込みも確認されなかった。RLS-001 を解消すれば、下位実装・契約テストへ進められる粒度である。
