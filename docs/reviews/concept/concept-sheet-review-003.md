- 完了条件 / 再確認方法: 認証・ロック・アカウント認可を署名前提として明記し、下位設計へ委譲していることを確認し、完了とした。

## 11. 対象範囲と追跡可能性

- コンセプトの製品境界は、ブラウザ拡張機能 / Android / iOS を利用者向け署名主体、Relay を非署名の受け渡し基盤、SDK を dApp 側の連携接点として整理している。dApp による署名結果の独立検証と署名後のネットワーク処理も外部責任として維持されている。
- コンセプトの中心価値は一般ユーザーの安全な署名判断であり、dApp 開発者はそれを支える主要な協力者、運用者は提供を支える関係者として位置付けられている。組織利用・カストディ・企業向け監査統制は v1 の初期対象外である。
- Symbol / NEM と Mainnet / Testnet の区別、利用者の明示的承認、署名主体の認証・ロック・アカウント認可、秘密情報分離、Mainnet リリース判定、dApp の独立検証は、コンセプト内で製品上の原則として追跡できる。
- 対象コンセプトの根拠資料に要件 / 設計 / 仕様 / リリース資料が列挙されていること自体は問題ではない。今回確認した本文は、それらをコンセプトの正本または規範的な下流編集指示として扱っておらず、用語・責任境界・前提の確認資料として参照している。
- 要件定義以降へ委譲するのは、OPEN-001〜OPEN-003、OPEN-005 の決定と、各プラットフォーム / リリースの具体的な受け入れ条件、API、形式、方式、脅威モデルなどである。これらの詳細をコンセプトの合否条件へ逆流させていない。

## 12. ドメイン別の確認

- 課題・価値: 中心課題を検証前の仮説として扱い、一般ユーザーが署名対象・チェーン・ネットワーク・起こり得る結果を判断できる価値へつないでいる。課題仮説の未実証は OPEN-001 として明示されている。
- 対象ユーザー: 一般ユーザーが第一対象であり、dApp 開発者の統合容易性は一般ユーザーの一貫した署名体験を支える付随価値として整理されている。修正による優先順位の変更はない。
- v1 の境界: ブラウザ拡張機能、Android、iOS の署名主体と Relay の非署名マイルストーン、実施順序、個別リリースと全体 v1、Relay 完了の意味が区別されている。モバイルは計画上の後続提供形態であり、実装済み機能とは扱われていない。
- 責任境界: 署名主体、SDK、利用者、dApp、Relay、運用者の責任が混同されていない。Relay は署名せず、SDK は秘密情報・署名・最終承認を担わず、dApp は結果を独立検証する。
- 信頼境界 / セキュリティ: Web / dApp / SDK、外部要求、Relay、ネットワーク入力を検証前から信頼しない。署名主体 / 承認境界の保証範囲と外部完全侵害の非保証が整合している。認証・ロック・アカウント認可も概念前提に留まり、詳細方式は要求されていない。
