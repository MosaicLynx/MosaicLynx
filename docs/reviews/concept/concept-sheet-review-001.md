## 総評

前回確認された主要な論点は、本文内で適切に整理されている。中心課題を「課題仮説」として明示し、第一対象・協力者・提供を支える関係者を分離している。また、v1・milestone・release の定義、対象外、外部責任、セキュリティ境界、成功条件の証拠種別、OPEN と FUTURE の区分もコンセプトの責務に収まっている。

未検証の課題仮説や milestone の個別完了条件は残っているが、いずれも本文で OPEN として明示され、次フェーズへの引継ぎ方法も定義されている。現時点で要件定義へ進むことを妨げる `ERROR` はない。以下の指摘は、要件定義で取り落とさないための注意事項である。

## 指摘

### CS-001 — `WARN`: 中心課題の実証が未完了のまま要件定義を開始できる扱いになっている

- 対象本文: `docs/concept/concept-sheet.md:31-43`, `:235-239`, `:269-277`
- 根拠: 中心課題は明確に「課題仮説」と記載され、利用者調査・問い合わせ・事故記録による実証が不足していることも明示されている。一方、`OPEN-001` が未完了でも要件定義を開始できると定めている。
- 影響: 未検証の「一般ユーザーが判断しにくい」という仮説が、要件定義で確定した課題として扱われる可能性がある。課題が実在しない、または優先順位が異なる場合に、要件の中心を後から修正するコストが発生する。
- 対応または未決定理由: 現在の扱いはコンセプトとして許容できるが、要件定義の全成果物で `仮説 / 根拠あり / 未確認` の状態を追跡する。OPEN-001 を完了できない場合は、未確認事項を残したまま確定要求へ昇格させない。
- 参照資料: `docs/concept/concept-sheet.md:31-43,235-239,269-277`

### CS-002 — `WARN`: 成功条件の証拠種別は定義されているが、合否の判定単位は後工程へ残っている

- 対象本文: `docs/concept/concept-sheet.md:216-229`
- 根拠: 成功状態ごとに、利用者観察、受け入れ記録、セキュリティレビュー、統合確認などの証拠種別が対応付けられている。ただし、どの観測結果を成功とみなすか、観測対象の範囲、判定主体はまだ決めていない。本文は数値目標や具体的テストケースを後続工程で決定すると明示している。
- 影響: 要件定義で「証拠が存在すること」と「中核価値が成立したこと」が混同される可能性がある。特に「安全に判断できる」「共通接点を利用できる」は、記録を残すだけでは達成判定にならない。
- 対応または未決定理由: コンセプト段階で数値を追加する必要はない。要件定義では各成功状態について、観測する行動・対象範囲・判定主体・不合格時の扱いを定め、証拠種別から判定可能な受け入れ条件へ具体化する。
- 参照資料: `docs/concept/concept-sheet.md:216-229`

### CS-003 — `WARN`: 全体 v1 の完了条件と一般ユーザーの中核価値との関係を、各 milestone の判定で維持する必要がある

- 対象本文: `docs/concept/concept-sheet.md:11-21`, `:95-97`, `:126-137`, `:247-251`
- 根拠: 本文は、ブラウザ拡張機能で中核価値を最初に検証し、Android、iOS、Relay を後続 milestone とし、Relay 完了を全体 v1 完了と定義している。v1 と個別 release の用語は分離されているが、各 milestone が一般ユーザーの中核価値をどの条件で維持・拡張できたと判定するかは `OPEN-003` に残っている。
- 影響: milestone が単なる提供形態の追加や開発完了として扱われると、一般ユーザーの価値検証から離れたまま全体 v1 完了へ進む可能性がある。Relay 完了が全体 v1 の基準であること自体ではなく、その完了が中核価値の達成とどう結びつくかが論点である。
- 対応または未決定理由: `OPEN-003` で、各 milestone の利用者価値、責任境界、次段階へ進む条件、全体 v1 完了に寄与する理由を定義する。提供順序を変える必要があるという指摘ではなく、既に決めた順序を中核価値に追跡可能にするための引継ぎ事項である。
- 参照資料: `docs/concept/concept-sheet.md:11-21,95-97,126-137,247-251`

### CS-004 — `NIT`: 「dApp」と「dApp 開発者」の役割を下流の利用場面で明示的に分けると追跡しやすい

- 対象本文: `docs/concept/concept-sheet.md:65-71`, `:91-93`, `:105-108`, `:220-226`
- 根拠: dApp 開発者は主要な協力者として整理され、dApp は署名結果を利用する主体として記載されている。この区別は概ねできているが、成功条件では開発者の統合確認と dApp の結果確認が近接して記載されるため、人（協力者）とシステム上の外部主体（責任者）の関係が下流で混同される余地がある。
- 影響: 要件定義で、開発者が提供する統合と、dApp 実行時の署名結果検証・ネットワーク処理を同じ要求として扱う可能性がある。
- 対応または未決定理由: コンセプトの修正は必須ではない。要件定義では「dApp 開発者＝統合を行う協力者」「dApp＝署名要求と署名後処理を行う外部主体」として用語を固定する。
- 参照資料: `docs/concept/concept-sheet.md:65-71,91-93,105-108,220-226`

## 確認できた整合事項

- 中心課題を仮説として扱い、根拠不足を OPEN として明示しているため、未確認の事実を確定事項としていない。
- 一般ユーザーを第一対象とし、dApp 開発者を協力者、運用者を提供を支える関係者として優先順位を整理している。
- v1、milestone、release を定義し、対象範囲・非対象範囲・将来検討事項を分離している。
- Signer の責任、利用者の承認、dApp の独立検証・ネットワーク処理、Relay の受け渡し責任を本文内で区別している。
- API、データ形式、通信方式、暗号方式、状態遷移、実装ライブラリ、テスト手順をコンセプトで決定せず、下流工程へ適切に委ねている。
- 成功条件に証拠種別を対応付け、OPEN と FUTURE の判断時期・扱いを記載している。

## 要件定義への引継ぎ

1. OPEN-001 の課題仮説と根拠状態を要求ごとに追跡する。
2. 成功状態を観測単位、判定主体、合否条件へ具体化する。
3. OPEN-003 で各 milestone の価値、完了条件、依存関係を定義する。
4. dApp 開発者と dApp の役割を要求文書で用語分離する。
