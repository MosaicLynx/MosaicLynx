## 4. レビュー結果

**レビュー判定条件: `REVISE DESIGN`**

アーキテクチャは、dApp / SDK / ブラウザ拡張機能 / モバイル / Relay / wallet-core の大枠、Signer 信頼境界、秘密情報を通常の公開経路から分離する方針、Relay の内容を解釈しない受け渡し、SDK の dApp 側の境界、Symbol / NEM および Mainnet / Testnet の分離、バインディングと実行環境分離の区別を概ね正しく定義している。

一方、共通要件が明示する「利用者認証条件、Signer の署名可能な状態へのロック解除、対象プロファイル / チェーン / ネットワーク / アカウントの署名認可、明示的な承認」の 4 条件を、ブラウザとモバイルに共通する Signer の必須判定条件として責任主体・主要フローへ一貫して配置していない。この欠落は、署名可否を決める信頼 / セキュリティ境界のアーキテクチャレベルの欠落であるため、`REVISE DESIGN` とする。

## 5. 要約

- `DR-001`（重大）: CR-016 の 4 つの署名前提条件のうち、認証、署名可能な状態へのロック解除、アカウントの利用認可を共通 Signer の責務・フローへ明示的に割り当てていない。モバイルの個別記述に認証 / ロックはあるが、共通の署名判定条件とブラウザ / モバイル双方の責任主体にはなっていない。
- `DR-002`（主要）: アーキテクチャレベルの責任・制約・未決項目を、個別設計ごとの正本となる責任主体へ渡す追跡可能性表がない。大枠の実装可能性はあるが、cross-cutting なセキュリティ / 署名フロー / インターフェースと各プラットフォーム / Relay / SDK の重複責務をアーキテクチャだけから一意に確認できない。
- AR-001（バインディングメソッドの固定）と AR-002（バインディングと実行環境分離の区別）は再発していない。
- Relay は非署名・非承認・非意味上の解釈の受け渡し基盤、SDK は Signer ではない dApp 側の統合層として整理されており、これらの責任逆流は見つからなかった。
- Mainnet リリース判定は、`release-evidence` 境界と安全側での終了方針をアーキテクチャに置き、詳細なビルド / 根拠運用を下流へ委譲している。現時点でアーキテクチャレベルの責任逆流は見つからなかった。

## 7. 必須の修正

### DR-001 — 共通 Signer の認証・ロック解除・アカウントの利用認可判定条件がアーキテクチャに未配置

- **対象**: `docs/design/architecture.md` §6.3、§6.6、§10、§12（特に L131-L142、L166-L170、L294-L305、L319-L325）
- **事実 / 条件**: ブラウザ拡張機能の責務には許可、文脈、チェーン / ネットワーク / アカウント、意味上の内容検査、明示的な承認、生のペイロード対応関係は記載されているが、利用者認証条件、署名可能な状態へのロック解除、対象プロファイル / チェーン / ネットワーク / アカウントの署名認可が必須条件として列挙されていない。共通ドメインも許可 / 承認ポリシーまでである。主要フローも許可 / アカウントの確認と明示的な承認は含むが、4 条件を揃える判定条件がない。モバイルには認証 / ロックの記述があるものの、共通 Signer 契約としてブラウザ / モバイルの両方へ適用される位置づけがない。
- **根拠**: `docs/requirements/requirements.md` の CR-010、CR-011、CR-015、CR-016、CR-AC-017。CR-016 は、署名・結果返却に必要な条件として認証、署名可能な状態へのロック解除、プロファイル / チェーン / ネットワーク / アカウントの利用認可、明示的な承認の全てを要求し、dApp / SDK / Relay による確立・更新・迂回を禁止している。`architecture.md` §10 は最初の 3 条件を明示的な共通判定条件として表現していない。
- **問題**: 下流実装が「許可と明示的な承認が通ればコアを呼べる」と解釈し、wallet-core のパスワード / ストア処理だけを利用者認証やアプリケーションレベルのロック解除 / アカウントの利用認可の代替として扱う余地が残る。これによりブラウザとモバイルの Signer が異なる署名可否を持ち、古くなったロック解除 / 認可を含む未認証・未承認署名をアーキテクチャレベルのに排除できない。
- **影響**: Signer 信頼境界の必須条件が欠落し、CR-016 のセキュリティ要求、CR-AC-017 の受け入れ条件、安全側での終了の判定対象を共通フローから検証できない。外部信頼されていない文脈がそれらを作成・更新・迂回できないという責務も、SDK / Relay / dApp に対して共通に固定されない。
- **最低限必要な修正**: アーキテクチャの共通 Signer 責務と主要フローに、4 条件が全て成立した場合に限り承認済み生のペイロードをコアへ渡し、いずれかが存在しない / ロック済み / 不明 / 古くなった / 不整合なら署名も成功結果も返さない判定条件を追加する。ブラウザの特権を持つホストとモバイルアプリの信頼されたホストを、利用者認証、署名可能な状態へのロック解除、プロファイル / チェーン / ネットワーク / アカウントの利用認可、承認の責任主体として明示する。wallet-core のパスワード / ストア / 秘密情報処理とアプリケーションレベルの認証・ロック解除・アカウント署名認可を別責務として記述し、SDK / Relay / dApp が判定条件を設定・更新・迂回できないことを明記する。認証方式、API、エラーコード、具体状態遷移は下流へ委譲する。
- **再確認**: CR-016 / CR-AC-017 がアーキテクチャの共通 Signer 判定条件とブラウザ / モバイルの両方の責務へ一意に追跡でき、署名前再確認・ライフサイクル無効化・結果返却条件にも同じ 4 条件が適用されること。

### DR-002 — 個別設計へのアーキテクチャレベルの責務 / 追跡可能性が一意でない

- **対象**: `docs/design/architecture.md` §17〜§18（L367-L403）、および §6〜§16 の横断責務。
- **事実 / 条件**: §18 は上位資料、ADR、wallet-core 関連資料を列挙しているが、security-design、signing-flow、インターフェース、ブラウザ拡張機能、モバイルアプリ、Relay、SDK などの個別設計を、どの責務・不変条件・未決項目の正本となる責任主体とするかを表にしていない。§17 の未決項目列挙も、アーキテクチャレベルの受け渡し対象を全て下流設計へ一意に割り当てる形式ではない。
- **根拠**: `docs/requirements/requirements.md` の CR-011、CR-013、CR-015、CR-016、CR-OPEN-001、CR-OPEN-002、およびブラウザ / モバイル / Relay / SDK 要件の各受け渡し。`architecture.md` §7 はパッケージ / アプリの依存方向を示し、§18 は関連資料を示すが、設計成果物単位の責務対応表にはなっていない。
- **問題**: 共通セキュリティ / 署名フロー / インターフェースと、ブラウザ / モバイル / Relay / SDK の各設計が、どの不変条件を所有し、どの未決項目を解消するかをアーキテクチャだけから機械的に確認できない。個別設計が READY でも、同じ横断条件を別々に解釈した場合に差分を検出する正本となるな受け渡しが残らない。
- **影響**: 上位要件の追跡可能性と設計工程の完了条件を確認する際、責任の重複・未割当・仕様への逆流を見落としやすい。特に `DR-001` のような共通署名判定条件、古くなった / ライフサイクル、Mainnet 対応能力、Relay 内容を解釈しない性の維持をプラットフォーム別に分岐させるリスクがある。
- **最低限必要な修正**: アーキテクチャに、アーキテクチャ責務 / 不変条件 / 未決項目、正本となる下流設計または仕様、責任主体、下流へ委譲する境界を示す高位の追跡可能性表を追加する。少なくとも security-design、signing-flow、インターフェース、ブラウザ拡張機能、モバイルアプリ、Relay、SDK、チェーン / プロファイル / wallet-core、release-evidence の責務を対象にし、下流だけで扱う API / スキーマ / 暗号処理パラメーター / 具体的な状態遷移は詳細化しない。
- **再確認**: アーキテクチャレベルの各責務・不変条件・未決項目に一つの正本となるな委譲先があり、下流資料が API や暗号詳細を発明せず、アーキテクチャの責務境界を再定義していないこと。

## 10. 後続工程へ委譲する指摘

次の事項はアーキテクチャが明示的に下流へ委譲しており、今回のアーキテクチャ指摘にはしていない。

- Provider API、通信上の形式、スキーマ、バージョン、対応付け、タイムアウト、具体エラー、具体的な状態遷移。
- Symbol / NEM のトランザクション型、アグリゲート、メッセージ形式、ハッシュ / 署名バイト列、チェーン固有のパーサーと検証の詳細。
- KDF、AEAD、ソルト、ノンス、メモリ clearing、バインディングメソッドの API 詳細、ホスト統合、OS 安全な保存領域、モバイル実行環境の具体方式。
- Relay の HTTP / Redis、TTL、セッション / 世代レコード、頻度上限、認証形式、サイズ制限の詳細。
- ブラウザ / モバイルの UI 配置、認証メソッド、PIN / 生体認証 / OS セッション、バックアップ / 移行の具体方式。
- Mainnet リリース証跡の収集・署名・信頼された鍵・ビルド埋め込み・実行環境対応能力の運用詳細。

これらは対応する仕様 / 実装 / リリース資料で扱う。ただし `DR-001` の 4 条件と `DR-002` の委譲先を定める高位責務はアーキテクチャに残す必要がある。

## 15. 残存リスクと未決定事項

- `DR-001` が未修正の間は、ブラウザとモバイルの Signer が同じ署名可否条件を持つことをアーキテクチャから保証できない。
- `DR-002` が未修正の間は、cross-cutting なセキュリティ / 署名フロー / インターフェースとプラットフォーム / Relay / SDK の責任・不変条件の追跡をレビューごとに資料横断で再構成する必要がある。
- wallet-core のホスト統合、OS 保護、一時的な秘密情報ライフサイクル、エラー対応付け、移行、モバイルホストの具体方式は引き続き未決であり、詳細をアーキテクチャで決めるべきではない。
- Symbol / NEM の具体対応済みのトランザクション、メッセージ、アグリゲート、バイト列、パーサー、検証は下流仕様の責任である。
- Mainnet 対応能力のリリース証跡 / ポリシー / ビルド / 実行環境強制は、アーキテクチャの高位判定条件を維持したままリリース資料と実装レビューで確認する。

## 17. 最終判断

**`REVISE DESIGN`**

`DR-001` は Signer 信頼境界と共通署名可否条件に関わる重大指摘であり、下流設計だけへの委譲では解消できない。アーキテクチャに共通判定条件とブラウザ / モバイルの責任主体を追加し、`DR-002` の高位追跡可能性表を追加した後、アーキテクチャレビューを再実施すること。

AR-001 / AR-002 の再発はない。信頼境界、セキュリティ、責任分界について、Relay が Signer になる、SDK が Signer になる、wallet-core が承認を担う、バインディングが実行環境分離になる、といった重大な逆流は確認していない。ただし `DR-001` のため、現時点で「重大問題なし」とは判定しない。
