## 総評

前回の指摘 SD-REVIEW-001〜003 は、起動時状態、モバイルの機微な UI、Symbol / NEM のアカウント / 鍵識別情報責任分界として反映され、解消された。

共通設計は、ブラウザ拡張機能 / モバイルアプリを信頼されたホスト、wallet-core を秘密情報処理の正本、OS 安全な保存領域を限定的信頼、SDK / dApp / Web / ディープリンク / Relay / ノード / 外部 API を信頼されていないとする境界を明確にしている。外部入力の検証、署名前の意味上の内容検査、信頼された UI による表示と実ペイロードの一致、署名ごとの再認証、要求単位のリプレイ / 並行する分離、Relay の配送専任、ノードの非信頼、安全側での終了が相互に整合している。

今回追加された起動・再起動・再読み込み・プロセス再作成後の `LOCKED` MUST により、認証済み状態の自動復帰を下位設計が許す余地も解消された。モバイルの署名確認・認証画面を含む機微な UI についても、画面共有、録画、直近のアプリ、通知などの露出経路を評価し、OS の限界を誤認させない条件が下位設計へ引き継がれている。

Symbol / NEM の鍵については、共通セキュリティ設計が暗号方式を再実装せず、チェーンごとのアカウント / 鍵識別情報と対象チェーンを明示した導出契約を要求し、具体的な導出仕様を wallet-core / チェーン統合へ委譲している。関連するアーキテクチャ、プロファイル / アカウント、プロダクト、チェーン互換性の記述も同じ責任分界へ整合している。

SEC-OPEN-002 と SEC-OPEN-004 は、モバイルの具体的な生体認証対応能力と、メッセージ受け渡しの具体契約を下位資料へ委譲する未決として妥当である。いずれも、署名ごとの再認証、利用者存在、メッセージの表示・検証不能時拒否という共通 MUST を弱めるものではない。

## 最終判定

`READY`

ブラウザ拡張機能、モバイル、Relay、SDK およびチェーン統合の下位設計へ進めてよい。下位設計では、本書の MUST を受入条件として維持し、SEC-OPEN-002 / 004 の具体化時にも認証省略、自動署名、内容を確認しない署名、表示とペイロードの不一致を導入してはならない。

## SEC-OPEN-001〜004 の評価

| 未決         | 判定           | 評価                                                                                                                                                                                                                                                                                                                                                              |
| ------------ | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SEC-OPEN-001 | 解決済み       | プロファイル / アカウント仕様 §20 が `every-signature` に固定され、`while-unlocked` を署名時認証の有効条件から除外している。共通設計の署名ごとの再認証と一致する。                                                                                                                                                                                                |
| SEC-OPEN-002 | 未決継続が妥当 | モバイルで生体認証を利用可能とする共通方針と、具体的な対応能力、認証情報保管、代替経路、ライフサイクルは分離されている。モバイル未実装・下流仕様の将来対応能力記述は、共通 MUST と矛盾しない未決事項である。生体認証失敗時に認証なしへ落とさず、毎回の利用者存在 / 再認証を維持する条件は確定している。                                                           |
| SEC-OPEN-003 | 解決済み       | 共通設計は Symbol / NEM のアカウント / 鍵識別情報を分離し、対象チェーンを明示した導出契約を wallet-core / チェーン統合へ委譲している。関連するアーキテクチャ、プロダクト、プロファイル / アカウント、チェーン互換性も同じ方針であり、共通セキュリティ設計に残すべき未決ではない。                                                                                 |
| SEC-OPEN-004 | 未決継続が妥当 | §8.3 が呼び出し元 / オリジン、アカウント、チェーン / ネットワーク、目的、メッセージ内容、鮮度、ノンス、ドメイン分離とメッセージ単位の / 要求単位のリプレイの分離を原則化している。具体 API、通信上のスキーマ、エンコーディング、ノンス形式、シリアライズ済みのメッセージ形式はプロトコル / SDK / プラットフォーム下位設計へ委譲すべきで、共通設計の不足ではない。 |

## セキュリティ上の不変条件 12項目の確認

| #   | 結果 | 確認                                                                                                                                                                               |
| --- | ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 適合 | 秘密情報を SDK、dApp / Web、Provider、コンテンツスクリプト、ディープリンク、Relay、ノード、外部 API、URL、ログ / 遠隔計測データ / 診断情報等の信頼されていない外部境界に渡さない。 |
| 2   | 適合 | 秘密情報の平文永続保存を禁止し、wallet-core の暗号仕様を再実装しない。                                                                                                             |
| 3   | 適合 | 外部入力をすべて信頼されていない入力として扱う。                                                                                                                                   |
| 4   | 適合 | 解析・検証・表示できない署名対象を拒否する。                                                                                                                                       |
| 5   | 適合 | 利用者が確認した内容と実際の署名ペイロードを一致させる。                                                                                                                           |
| 6   | 適合 | 要求、確認、認証、署名を一対一に分離する。                                                                                                                                         |
| 7   | 適合 | 署名ごとの利用者認証を必須とし、自動署名を許可しない。                                                                                                                             |
| 8   | 適合 | 外部連携経路・補助サービス・信頼されていないコンポーネントの単独侵害で秘密情報取得または無確認署名に到達しない。                                                                   |
| 9   | 適合 | 秘密情報をログ / 遠隔計測データ / 異常終了報告書に出力しない。                                                                                                                     |
| 10  | 適合 | 安全性を確認できない場合は安全側での終了とする。                                                                                                                                   |
| 11  | 適合 | 認証・署名確認 UI を MosaicLynx 自身が制御する。                                                                                                                                   |
| 12  | 適合 | セキュリティ異常時に署名可能状態を解除し、以前の承認状態を再利用しない。                                                                                                           |
