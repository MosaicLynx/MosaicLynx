## 総評

共通セキュリティ設計は、後続のブラウザ拡張機能 / モバイル / Relay / SDK 設計へ進むための骨格を概ね満たしている。

特に、wallet-core と Signer ホストの責任分界、SDK / dApp / ディープリンク / Relay / ノード / 外部 API を信頼しない前提、秘密情報を外部へ渡さない方針、起動時ロック済み、署名ごとの再認証、内容を確認しない署名の禁止、署名前の解析・表示・ペイロード一致確認、要求単位のリプレイ / 並行する分離、Relay の内容を解釈しない通信経路、ノード応答の補助情報扱い、秘密情報のログ禁止、信頼された UI、安全側での終了および事故復旧は明確である。12 個のセキュリティ上の不変条件も、本文の中心原則を短く固定するものとして成立している。

一方、下位設計がこの文書だけを参照した場合に安全条件を弱く解釈し得る箇所がある。主なものは、署名確認フィールドの表示を `必要に応じて` としている点、wallet-core の警告 / 結び付けエラー / ストア検証失敗を安全側での終了と明示していない点、メッセージ署名の呼び出し元 / 目的 / 鮮度 / ドメイン分離の共通原則が本文に直接現れていない点、セキュリティ上の不変条件 1 の秘密情報の宛先列挙が本文より狭い点である。また、プロファイル仕様の `while-unlocked` との矛盾は、共通セキュリティ設計を弱めず、既存仕様を整合させる必要がある。

これらは暗号方式や具体 API を共通設計へ追加する要求ではない。共通 MUST の表現と、下位資料へ委譲する境界を明確にすれば、各コンポーネントの詳細設計へ進められる。

## 最終判定

`READY WITH CONDITIONS`

共通設計としての信頼境界、鍵ライフサイクル、認証、署名承認、Relay / ノード信頼、安全側での終了、事故復旧は成立しているため、条件を満たす範囲で下位設計へ進めてよい。ただし、次の条件を満たすまでは、下位設計が任意の警告迂回、while-unlocked 署名、wallet-core 警告の無視、メッセージの文脈欠落または秘密情報の Provider / Web 境界流出を許す仕様にならないことを確認できない。

## 良好な点

- wallet-core、ブラウザ拡張機能、モバイルアプリを信頼されたコンポーネントとしつつ、入力値や外部由来の戻り値は別途信頼されていないと扱っている。OS 安全な保存領域を Limited 信頼とした区別も適切である。
- SDK、dApp、ディープリンク、Relay、ノード、外部 API を信頼せず、Relay / SDK の侵害だけで秘密鍵取得や無確認署名へ直結しない構造を要求している。
- wallet-core の暗号、KDF、ウォレットストア、ゼロ化を本書で再設計せず、ホストの UI / 許可 / 意味上の内容検査 / 処理の調整と分離している。
- 起動時ロック済み、明示操作によるロック解除、署名ごとの再認証、ブラウザ拡張機能のパスコード必須、外部要求によるロック解除禁止、自動署名禁止が一貫している。
- 署名対象から確認情報を生成し、表示後および署名直前にペイロード、呼び出し元、アカウント、チェーン、ネットワークの変化を検出して再承認するため、TOCTOU への基本防御がある。
- 未知型、未対応バージョン、解析 / 検証不能、表示不能または生のペイロードの安全な解釈不能を拒否し、警告だけで迂回できる通常経路を禁止している。
- 接続許可と署名認可を分離し、アカウント、呼び出し元、セッション、許可、チェーン / ネットワークを要求ごとに結び付け、失効と並行する分離を要求している。
- `requestId`、`createdAt`、`expiresAt`、処理済み要求の再利用拒否、同一 ID の内容衝突拒否、結果の要求への紐付けを定めている。チェーンの期限とは別の application-layer リプレイ保護になっている。
- Relay を配送専用の信頼されていない通信経路とし、秘密情報、意味解釈、承認、署名、アナウンスを持たせていない。Relay 障害・侵害だけで資産移動に到達しない条件も明確である。
- ノード / 外部 API の手数料、メタデータ、名前空間、mosaic 等を補助情報に限定し、悪意あるノード応答や取得失敗を理由に署名確認を省略しない。
- 秘密情報 / 機微な / 公開の分類、ログ・遠隔計測データ・異常終了報告書への秘密情報出力禁止、トランザクションペイロード全文ログ禁止、最小保持、ロック / 失効 / 期限切れ時の無効化が定められている。
- エクスポートの明示操作・再認証・信頼された UI、秘密情報のクリップボード原則禁止、QR の高リスク扱い、モバイルの画面露出対策、ブラウザ拡張機能のスクリーンショット非保証が明記されている。
- 解析、検証、ネットワーク、許可、要求完全性、認証、wallet-core 検証、Relay / ノード / API 障害、結果不明を署名拒否へ倒す安全側での終了がある。
- 異常時に署名可能状態、セッション、一時認証、処理中要求を無効化し、再承認なしの再開を禁止する一方、秘密鍵の自動削除や Relay 侵害だけを理由とする鍵更新を要求していない。
- ソフトウェア完全性は正規配布、改ざん検出、wallet-core バージョン、依存関係 / 供給チェーン、厳格なセキュリティレビュー、移行の平文退避禁止、デバッグ / 本番環境分離までを原則として示し、CI の具体実装を過剰に固定していない。

### SD-SEC-001: 署名確認フィールドの MUST 性

**重要度:** `MEDIUM`

**根拠:** §8.1 は Signer 自身が署名対象から確認情報を生成し、未知・省略・取得不能な危険情報を隠さないことを定めている。しかし、表示対象の列挙が「必要に応じて、少なくとも」となっているため、下位設計が受信者、数量、手数料、期限、メッセージ、アグリゲート内部トランザクション、メタデータ、権限変更等のうち一部だけを表示しても、共通設計上の必須条件を満たすと解釈される余地がある。

`docs/requirements/requirements.md` の CR-002 / CR-007-TX、`docs/specifications/product-spec.md` §12、`docs/specifications/chain-compatibility-spec.md` §4〜§5 は、対応範囲内の全体と確認可能な影響を解析・表示できない場合は署名しない方向である。共通設計はスキーマや UI の詳細を決める必要はないが、適用可能な署名対象フィールドを表示できない場合の拒否条件は共通 MUST として持つべきである。

**推奨対応:** 「署名対象に存在するセキュリティに関わるフィールドは、対象チェーン / 操作に応じて全て確認可能な形で表示する。任意の適用フィールドを解析・表示できない場合は署名しない」と原則を明記する。具体的なフィールド表、表示順、UI はチェーン統合 / プラットフォーム設計へ委譲する。

### SD-SEC-002: wallet-core 失敗の安全側での終了明示

**重要度:** `MEDIUM`

**根拠:** §15.1 の列挙には `Wallet Core validation` があるが、wallet-core の警告、バインディングエラー、ストア検証失敗、署名前後のコアエラーを明示的に「無視・継続してはならない」としていない。§18 も wallet-core を正本として承認済みペイロードを渡す条件は示すが、コアの非成功結果の扱いを共通 MUST として独立に書いていない。

一方、共通要件 CR-NFR-004 は、wallet-core の失敗、警告、バインディングエラー、ストア検証失敗を無視して署名を継続してはならないと定めている。共通セキュリティ設計だけを参照する下位設計でもこの条件が見える必要がある。

**推奨対応:** 安全側での終了の確認項目に「wallet-core のエラー / 警告 / 結び付けエラー / ストア完全性失敗」を追加し、いずれも署名結果を返さず、秘密情報をエラー / 診断情報へ含めないことを明記する。wallet-core 内部のエラーコードや暗号仕様は追加しない。

### SD-SEC-003: メッセージ署名の共通セキュリティ原則

**重要度:** `MEDIUM`

**根拠:** §8 はメッセージの解析・表示・ペイロード一致と内容を確認しない署名禁止を含むが、メッセージ署名において、検証済み呼び出し元 / オリジン、アカウント、チェーン / ネットワーク、用途、ノンス、メッセージ自体の有効期限およびドメイン分離をどのようなセキュリティプロパティとして維持するかを直接述べていない。§10 の要求単位の `requestId` / `createdAt` / `expiresAt` はアプリケーション要求のリプレイ防止であり、署名されたメッセージの再利用・別用途への転用を防ぐメッセージ単位の文脈とは別である。

`docs/specifications/product-spec.md` §3 / §12.2 と `docs/specifications/web-transaction-handoff-spec.md` §5 / §7 は、構造化メッセージと `signData` の具体契約を既に定めている。したがって、SEC-OPEN-004 の「具体契約が未確定」は、現状ではメッセージのプラットフォーム表示受け入れ条件や既存受け渡しとの整合確認に絞るのが適切である。

**推奨対応:** 共通設計に「メッセージ署名は、操作に適用される呼び出し元 / オリジン、アカウント、チェーン / ネットワーク、用途、鮮度 / ノンスおよびドメイン分離を含む承認済みメッセージ意味を維持し、文脈を検証・表示できないメッセージは署名しない」と原則だけ追加する。具体 API、通信上のスキーマ、エンコーディング、ノンス形式、期限値はプロトコル / SDK / プラットフォーム設計へ委譲する。

### SD-SEC-004: セキュリティ上の不変条件の秘密情報境界の範囲

**重要度:** `MEDIUM`

**根拠:** §6.2 は平文秘密鍵を Provider、コンテンツスクリプト、URL、通知、長期キャッシュに保持してはならないとし、§12 は外部通信、URL、クリップボード、診断情報等への出力も禁止している。しかし不変条件 1 は「SDK / dApp / Relay / 外部 API」に限定され、不変条件 8 も侵害主体を Relay / ノード / SDK / dApp に限定している。不変条件単体を下位設計のチェックリストとして使うと、Provider / Web ページ / コンテンツスクリプト / ディープリンク / URL / ノードへの秘密情報流出や、外部 API / ディープリンクの侵害影響が列挙漏れに見える。

本文のより強い条件が存在するため、直ちに秘密情報を許可する矛盾ではない。ただし、下位設計へ逸脱不能な MUST として掲げる不変条件の表現は本文と同じ境界を指す必要がある。

**推奨対応:** 不変条件 1 を「SDK、dApp / Web ページ、Provider / コンテンツスクリプト、ディープリンク、Relay、ノード、外部 API、URL、ログ等の信頼されていない外部境界に渡さない」のような包括表現へ広げる。不変条件 8 も「外部連携経路・補助サービスの単独侵害」として本文の脅威モデルと一致させる。新しい不変条件を追加する必要はない。

### SD-SEC-005: プロファイルの `while-unlocked` との正本衝突

**重要度:** `MEDIUM`

**根拠:** §7.1 は署名ごとの再認証を MUST とし、接続許可、セッション、直前認証の流用を禁止している。§19 SEC-OPEN-001 も、プロファイル仕様 §20 の `while-unlocked` を有効な実装条件として扱わないと明記している。この共通方針は、今回の承認済み方針に適合し、安全側である。

しかし `docs/specifications/profile-account-spec.md` §20 は現在も `while-unlocked` / `every-signature` を設定可能な選択肢として記載している。共通設計が正本であることを下位設計が必ず知る仕組みがないままでは、プロファイル / アカウントの詳細設計で署名ごとの再認証を弱める余地が残る。

**推奨対応:** プロファイル / アカウント仕様または承認済み設計判断で、署名ごとの再認証を正本として `while-unlocked` を廃止・非適用にする。プロファイル仕様を本レビューで変更する必要はないが、整合が完了するまで下位設計は `while-unlocked` を採用してはならない。ブラウザ拡張機能のパスコード再入力 MUST とモバイルの毎回利用者の立ち会い / 認証条件は維持する。

## SEC-OPEN-001〜004 の評価

| 未決         | 評価           | 判定・必要な引継ぎ                                                                                                                                                                                                                                                                                                                                                                              |
| ------------ | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SEC-OPEN-001 | 条件付き解消   | `while-unlocked` を共通設計で無効な実装条件とした判断は正しい。共通方針を弱めず、プロファイル / アカウント仕様側を改訂するか正本優先の設計判断を記録する必要がある。整合完了まで `while-unlocked` は採用不可。                                                                                                                                                                                  |
| SEC-OPEN-002 | 未決継続が妥当 | モバイルで生体認証を利用可能とする共通方針と、具体的な OS 対応能力、認証情報保管、代替経路、ライフサイクルは分離できている。既存プロファイル §22 の「将来対応能力」は、共通方針を弱める根拠にせず、モバイル / プロファイルの対応能力位置付けを整合させる。生体認証が使えない場合に認証なしへ落ちることは許可しない。                                                                            |
| SEC-OPEN-003 | 未決継続が妥当 | 同一秘密鍵利用の可否やチェーン別アカウント対応は、共通セキュリティ設計で暗号設計を決める事項ではない。wallet-core、プロファイル / アカウントモデル、チェーン統合の責務として確定し、本書では Symbol / NEM の処理を暗黙に共通化しない原則を維持すればよい。共通設計から重大な暗号変更を提案する必要はない。                                                                                      |
| SEC-OPEN-004 | 範囲縮小が必要 | 具体 API / スキーマ / 通信上の形式はプロトコル / SDK / プラットフォーム設計へ委譲するのが妥当。ただし現行受け渡し仕様には `signData`、構造化されたメッセージ、要求 / 応答の具体契約が既にあるため、「具体契約が未確定」という表現は広すぎる。未確定範囲をプラットフォーム表示受け入れ条件・既存契約との整合・対応形式の詳細に絞り、共通設計には SD-SEC-003 のメッセージセキュリティ原則を残す。 |

## 下位設計への進行可否

条件付きで進行可能である。

- ブラウザ拡張機能の Provider / オリジン / 特権を持つ層、Relay の内容を解釈しない通信経路、SDK の受け渡し、チェーン統合の意味上の内容検査、モバイルの OS 統合へ進んでよい。
- 下位設計では、少なくとも SD-SEC-001〜005 の条件を設計受入条件へ取り込むこと。
- プロファイル / アカウントの認証仕様が `while-unlocked` を残したままの場合、署名フローの詳細確定と実装承認へは進めない。
- モバイルの生体認証、画面取得、OS 安全な保存領域、代替経路は具体方式を下位設計へ委譲してよいが、毎回の明示的利用者存在 / 認証、外部要求からの省略不可、失敗時安全側での終了を弱めてはならない。
- メッセージ署名の具体形式 / API / 通信上の契約はプロトコル / SDK / プラットフォーム設計へ委譲してよいが、メッセージの呼び出し元 / 目的 / 鮮度 / ドメイン分離と表示対象の一致を共通原則として扱うこと。
