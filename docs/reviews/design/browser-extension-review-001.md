## 2. 総評

`docs/design/browser-extension.md` は、ブラウザ拡張機能の基本設計として実装または下位仕様策定へ進められる品質に達している。

本書は、Web ページ / ページに公開する橋渡し / コンテンツスクリプト / 特権を持つホスト / 信頼された承認 UI / チェーン統合 / wallet-core バインディング / 保存領域・ブラウザアダプターの責務を分離し、Web ページを信頼されていないとする信頼境界を明示している。特に、ブラウザが観測した呼び出し元文脈によるオリジンとの結び付け、接続・公開アカウント情報公開・署名要求の分離、要求ごとの承認・認証、承認対象と実署名ペイロードの署名前再検証、結果不明と配送不明の区別、サービスワーカー・再読み込み・ページ遷移・文脈消失後の古くなった認可不使用が、基本設計上の判断として具体化されている。

また、共通セキュリティポリシー、署名意味、共通要求 / 応答、wallet-core の暗号・鍵管理契約、Relay / モバイルプロトコルをブラウザ拡張機能独自仕様として再定義せず、上位設計をブラウザの実行文脈、UI、ライフサイクルおよびローカル署名主体の責務へ適用する構成になっている。

実装不能性、上位設計との矛盾、信頼境界の破綻、オリジンとの結び付けまたは承認との結び付けの重大な不足は確認されなかった。マニフェスト、通信上のスキーマ、保存領域スキーマ、キューアルゴリズム、具体 API 等を下位仕様へ委譲している粒度も妥当である。

## 3. 判定

### ブラウザ拡張機能設計 READY

最終判定: `READY`

基本設計として必要な主要責務、境界、ライフサイクル、セキュリティ上の不変条件、安全側での終了方針が定まり、下位仕様策定および実装へ進めてよい。`LOW` / `NIT` を含め、今回のレビューで記録すべき指摘はない。

## 6. セキュリティ / 信頼境界評価

### 6.1 信頼境界

適合。§5〜§6 は、ページに公開する橋渡しとコンテンツスクリプトを経路選択 / 通信経路の信頼されていない境界として扱い、特権を持つホストに次の判断を集約している。

- ブラウザが観測した送信者、タブ / フレーム、文書、オリジンと要求の対応。
- 呼び出し元、許可、セッション、プロファイル / アカウント、チェーン / ネットワークおよび要求完全性。
- チェーン固有の内容検査、信頼された UI、承認、認証、ライフサイクルおよび応答配送。

信頼された承認 UI は Web アプリケーションの DOM、表示文言、CSS、ページ modal またはブランド表示から独立し、wallet-core は呼び出し元、許可、UI、利用者承認およびトランザクションの意味解釈を担わない。これにより、Web ページから特権を持つ署名判断権限へ直接到達する設計になっていない。

### 6.2 オリジンとの結び付け

適合。§7.2 の認可組は、オリジンだけでなく閲覧文脈、セッション、許可対象範囲 / リビジョン、プロファイル / アカウント、チェーン / ネットワーク、操作、署名対象、鮮度および完全性を含む。§7.3 は応答にも要求識別情報、セッション、オリジン、文脈、アカウント、チェーン / ネットワーク、対象を要求している。

特に、Web ページが自己申告するオリジン、タブ、アカウント、チェーン、ネットワークまたは requestId をブラウザで観測した文脈の代替にしていない。ページ遷移、文書 / フレーム変更、接続解除、許可変更、ペイロード変更、期限切れ、重複、リプレイ、古くなったセッションを旧認可の失効条件としており、オリジン spoofing、confused deputy、要求差し替え、オリジン間の応答漏えい、古くなったセッションおよび unsolicited 要求への基本的な防御方針が成立している。

### 6.3 承認との結び付け

適合。§10.3 は承認を単独真偽値ではなく、オリジン、セッション、許可リビジョン、プロファイル / アカウント、チェーン / ネットワーク、操作、対象、内容検査結果、鮮度および対応能力文脈に対する一回限りの認可としている。wallet-core 呼び出し直前に、ペイロード、親、埋め込み / 内部トランザクション、メッセージ、署名主体、期待される署名主体、許可、内容検査、正規化、期限および応答受信者を再検証する。

不変スナップショットやダイジェストの具体方式は下位仕様に委譲されているが、承認対象と実署名対象を一致させる不変性の概念は基本設計に表現されている。共通署名フローが要求する対象ダイジェストまたは同等の不変性確認情報、内容検査結果、認証状態との結び付けと矛盾しない。

### 6.4 セキュリティ上の不変条件

適合。§20 の 15 項目は、共通セキュリティ設計 §17 の不変条件をブラウザの文脈、UI、保存領域、ライフサイクル、応答配送、アグリゲート / 連署署名に適用している。共通方針の単なる重複ではなく、ブラウザで観測した文脈、ページ / コンテンツスクリプト、信頼された UI、サービスワーカー、ページ遷移、タブ / フレームおよび応答チャネルというブラウザ固有の適用条件が加わっている。

## 7. 上位設計との整合性

### コンセプト / 要件

[`concept-sheet.md`](../../concept/concept-sheet.md) のローカル署名主体、秘密情報と dApp の分離、利用者の明示判断、理解できない要求の安全な終了、Chrome を最初の提供形態とする方針に一致する。[`requirements/browser-extension.md`](../../requirements/browser-extension.md) の BR-001〜BR-013 および BR-AC-001〜BR-AC-013 に対して、オリジン、最上位の文脈、許可、信頼された UI、ページ / 拡張機能分離、ライフサイクル、wallet-core 境界、最小権限、更新安全性、Mainnet 判定条件が下流で実装可能な設計判断へ展開されている。

### アーキテクチャ

[`architecture.md`](../../design/architecture.md) §5.1、§6.3、§6.7〜§6.8、§7.2、§8、§11 と整合する。ブラウザ拡張機能はブラウザ文脈、アプリケーション許可、内容検査、承認、ライフサイクルおよび wallet-core アダプターを担い、SDK、Relay、モバイルおよび wallet-core の責務を取り込んでいない。特に wallet-core バインディングを API / データ所有責任境界とし、実行環境分離を自動保証しない点も §13 と一致する。

### セキュリティ設計

[`security-design.md`](../../design/security-design.md) §5、§7〜§10、§14〜§18 と整合する。オリジン単位許可、署名ごとの認証、`1 request = 1 confirmation = 1 authentication = 1 signing`、内容を確認しない署名禁止、安全側での終了、秘密情報の最小保持、事故 / ライフサイクル消失後の認可破棄がブラウザ固有の形で表現されている。

### 署名フロー

[`signing-flow.md`](../../design/signing-flow.md) §4〜§7、§10〜§13、§18〜§24 と整合する。要求文脈、承認との結び付け、状態遷移、`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN`、アグリゲート / 連署署名 / 部分トランザクションのチェーン固有の扱い、ノード照会による補完禁止および応答対応付けを再定義していない。

### インターフェース

[`interfaces.md`](../../design/interfaces.md) §4〜§9 と整合する。ブラウザで観測した呼び出し元文脈と SDK / Provider の自己申告を区別し、アカウントの公開識別情報と内部参照、TransactionSummary と署名対象、署名主体と wallet-core の検証責務を保っている。

### ADR

[`ADR 0001`](../../adr/0001-mainnet-evidence-lite.md) の Mainnet リリース証跡 / 判定条件をブラウザ拡張機能の独自判定へ置き換えず、§9、§19、§22、§23 からリリースポリシーへ委譲している。判定条件未達成または判定不能のビルドを Mainnet 署名有効として扱わない点も上位要求と整合する。

## 8. 基本設計粒度の評価

粒度は妥当である。

- 実装者が主要判断に迷わない範囲として、責務分担、信頼境界、オリジン / 許可 / セッション結び付け、要求状態、承認との結び付け、ロック / 再読み込み、失敗処理結果の区分、アグリゲート / 連署署名の確認条件を定めている。
- 下位仕様へ委譲すべき事項として、Provider API、通信上のスキーマ、マニフェスト JSON、ブラウザ許可名、実行環境メッセージプロトコル、オリジン正規化の具体形式、許可分類体系の細分、保存領域レコード、wallet-core DTO、チェーン固有のスキーマ、UI 配置、タイムアウト、キューアルゴリズム、E2E テストを列挙している。
- 共通セキュリティ設計、署名フロー、インターフェースの意味を上書きせず、ブラウザ固有の適用として整理している。

したがって、マニフェスト完全定義、保存領域スキーマ、JSON スキーマ、エラーコード全表、React コンポーネント、ブラウザ API 呼び出し順、キューアルゴリズム等の欠落を、この基本設計の不足とは判定しない。

## 9. 未決事項の評価

§23 の未決事項は、基本設計を確定不能にする阻害要因ではなく、下位仕様またはリリース操作へ適切に引き継がれている。

- Chrome の最低バージョン、配布チャネル、マニフェストバージョン、Mainnet 判定条件のビルド時の / 実行環境境界は、要求・ADR・リリースポリシーの範囲を超える下位運用事項である。
- Provider / SDK API、オリジン証明、セッションプロトコル、応答不明後の再配送・照会はインターフェース / プロトコル下位仕様の責務である。
- アグリゲート、連署署名、部分トランザクション、NEM マルチシグ、メッセージ署名の公開操作と対応済みの対象範囲は、共通の安全条件を維持したままチェーン / SDK / プラットフォーム下位設計へ委譲されている。
- wallet-core バインディング、秘密バイトの一時ライフサイクル、移行、許可の細分、キュー、auto-lock 時間、プロファイルバックアップ / 復元のブラウザ範囲は、上位設計の責任境界を弱めずに後続決定できる。

これらの未決事項を理由として内容を確認しない署名、許可による自動署名、オリジンとの結び付けの省略、古い承認の再利用、Relay / dApp への秘密情報移管または安全条件を満たさない継続復旧を許可していない点が明記されている。
