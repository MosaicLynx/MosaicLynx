## 4. Review Result

**Review Gate: `READY`**

Critical finding はなく、Major 2 件を次工程への必須引継ぎとして記録する。Design Review Skill は Critical が 1 件以上の場合だけ `REVISE DESIGN` とし、Critical がなく Major / Minor のみの場合は `READY` とするため、今回の正式 Gate は `READY` である。

現行本文は、Browser Extension privileged layer と Mobile trusted host を Signer-side owner とし、request validation、trusted display、明示承認、4 条件、署名前再検証、wallet-core raw signing、result validation、fail-closed、replay / duplicate 拒否および automatic fallback 禁止を一貫して定める。normal transaction、Aggregate、bonded / partial context、cosignature、NEM multisig、message signing も共通 gate と chain-specific inspection の下に置かれている。

一方、`SIGNING` 進入後の cancel と signing outcome の優先関係、および remote / handoff の intended recipient・device と response channel の binding・再検証が、本文だけからは一意に実装判断できない。下位の Signing Protocol、Mobile / Relay / Interfaces はより安全な条件を定めているが、共通 Signing Flow の control-flow boundary としては新規 Major finding とする。

## 8. Optional Improvements

`DR-SF-007`、`DR-SF-008` は Major の Open finding であり、Design Review Skill 上は Gate を不合格にしないため本 section に記録する。両件とも実装へ進む前に修正または設計上の明示確認を行うべき内容である。

### DR-SF-007: OPEN — `SIGNING` 中 cancel の outcome precedence

- Severity: `Major`
- Status: `OPEN`
- Location: [`docs/design/signing-flow.md`](../../design/signing-flow.md) §7.1〜§7.3（状態定義、遷移、lifecycle loss）、§21（retry / duplicate / replay）および §22（failure）。特に §7.2 の `SIGNING → SUCCEEDED` と「いずれの非 terminal state → terminal」の cancel 条件。
- Problem: 本文は cancel を非 terminal state から terminal へ遷移させ、`SIGNING → SUCCEEDED` を Wallet Core の成功時に許すが、`SIGNING` 中に cancel が受理された場合の outcome precedence を定めていない。そのため、同じ設計から、署名処理開始後の cancel を `CANCELLED` と先に確定する実装と、core の outcome を待って `RESULT_UNKNOWN` / `SUCCEEDED` とする実装の双方が合理的に導ける。`CANCELLED` とされた request が後から core signing を完了し得るか、また response をどの状態で返すかが本文だけでは一意でない。
- Impact: requester、Signer UI、transport の cancel と wallet-core signing の競合時に、cancel 済み request の後続署名、署名結果の誤分類、または `RESULT_UNKNOWN` の success / rejection への誤変換が発生し得る。これは `SIGNING` state の安全な one-way outcome と、cancel 後に signing へ進ませない invariant を下位実装が推測する責任 gap である。
- Evidence: 下位の [Signing Protocol §6.2](../../specifications/signing-protocol.md) と §19.2 は、`RECEIVED`〜`AUTHORIZED` の cancel、`SIGNING` 中の outcome unknown、署名未生成が確定した cancel、`SUCCEEDED` 後の delivery cancel を区別している。これは安全な補完根拠である一方、共通 Flow §7.2 に同じ high-level boundary がないことを示す。Requirements `CR-012`、`CR-NFR-009`、`CR-NFR-011`、`SDK-FR-010` も、cancel / expiry / result unknown 後の成功・追加署名を許さない意味を要求する。
- Affected transition: `AUTHORIZED → SIGNING`、`SIGNING → SUCCEEDED`、非 terminal state → `CANCELLED` / `RESULT_UNKNOWN`、および `SUCCEEDED` 後の response delivery。
- Violated requirement / invariant: `CR-012` の failure と success の分離、`CR-NFR-011` の追加署名防止、§23 の「terminal state から再開しない」「結果不明から自動署名しない」。本文の意図を直接破る実装を必ず許すと断定するものではないが、共通設計だけでは安全な競合結果を確定できない。
- Required correction at Signing Flow granularity: §7 の高位遷移として、署名開始前の accepted cancel は `CANCELLED` かつ core call なし、`SIGNING` 中に outcome が不明なら `RESULT_UNKNOWN`、署名が生成されていないことが確定した場合だけ `CANCELLED`、署名成功後の cancel は既存 result を取り消さず delivery disposition だけを扱う、という境界を明示する。`CANCELLED` の terminalization 後に core signing が開始・完了しないことも明示する。
- Scope boundary: lock、CAS、atomic primitive、queue、cancel API、core binding、timeout 値、error code または wire state の形式は要求しない。必要なのは state / outcome の一意な安全条件だけである。
- Completion / reconfirmation: `signing-flow.md` の state transition と failure / retry table に上記の precedence を追跡でき、cancel 競合の各時点で `CANCELLED`、`RESULT_UNKNOWN`、`SUCCEEDED + delivery disposition` を実装者が推測せず選べることを再確認する。

### DR-SF-008: OPEN — handoff recipient / response channel binding

- Severity: `Major`
- Status: `OPEN`
- Location: [`docs/design/signing-flow.md`](../../design/signing-flow.md) §5（request logical model）、§16（Authorization tuple と署名前再検証）、§19（Mobile / Relay Flow）、§20（result model）および §25（下位仕様への引継ぎ）。§4 と §23 には抽象的な `response channel` の isolation はあるが、intended recipient / device identity の明示的な binding と再検証がない。
- Problem: remote / handoff request について、本文は caller、session、generation、request identity、Profile、Account、Chain / Network、target integrity および permission を binding / revalidation するが、意図した response recipient / device と response channel の identity を同じ Authorization / result tuple の項目として明示していない。`response channel` という抽象語だけでは、valid session と request ID が一致することを intended recipient の確認まで意味するのか、どの Signer / delivery owner が wrong-device response を拒否するのかが一意に読めない。
- Impact: handoff または Relay の誤配送・別 recipient・stale channel に対し、request が意図しない device / Signer の approval UI に到達する、または別 recipient が取得した response を元 request の結果として受け取る責任 gap が残る。request ID、caller、session だけの相関では cross-recipient delivery を明示的に閉じられず、結果の誤帰属や response injection の防止条件を共通 Flow から実装へ安全に引き渡せない。
- Evidence: [`docs/design/interfaces.md` §6](../../design/interfaces.md) は wallet-core result、response recipient、response delivery context を同一 Profile-local context に binding し、§6.3〜§6.4 は concurrent request isolation と response recipient を要求する。[`docs/design/mobile-app.md` §12.3](../../design/mobile-app.md) は pre-sign に intended recipient / response channel を再検証し、[`docs/design/relay.md` §28](../../design/relay.md) は recipient identifier と cross-recipient routing を invariant にする。Requirements `RR-007`、`CR-NFR-012` および handoff specification §7.4 / §13 も wrong recipient と response correspondence を client-side に検証する前提である。
- Affected flow: handoff initiation、Relay fetch / response upload、Mobile validation、approval target、`AUTHORIZED → SIGNING` 前の再検証、result correlation、response delivery、wrong-device / late response handling。
- Violated requirement / invariant: `RR-007` の request / result separation、`CR-NFR-012` の元 request・signer・Account・Chain / Network への対応、Security Design / Relay の cross-recipient delivery 防止 invariant、および本文 §23 の request / response channel isolation。下位資料に recipient 条件があるため実際の全実装が欠陥になると断定するものではないが、共通 Flow の responsibility boundary が不十分である。
- Required correction at Signing Flow granularity: handoff を適用する共通 flow の logical request / Authorization / result correlation に intended recipient / device および response channel identity を含める責任を明示し、Signer が approval / pre-sign 前に recipient を検証し、Signer / SDK / Relay の各 delivery owner が wrong recipient、stale channel、別 request の response を拒否することを定める。exact public field を追加する必要はない。
- Scope boundary: recipient field 名、device attestation、Deep Link / App Link、HTTP / Redis routing、E2E encryption、ACK、transport credential、API signature または response schema は要求しない。必要なのは recipient identity をどの flow binding と ownership が守るかの明示である。
- Completion / reconfirmation: §5、§16、§19、§20、§25 と Interfaces / Mobile / Relay の traceability が同じ recipient / response channel invariant を示し、wrong-device request / response、concurrent handoff、stale response のいずれも UI、signing、success delivery へ進まないことを再確認する。

Mainnet release evidence、E2E secret / transport credential、ACK、retry、UI layout および platform lifecycle の具体化は、対象本文が指定した owner・下位仕様へ委譲されており、今回の formal finding ではない。

## 16. Remaining Risks and Open Decisions

- `DR-SF-007` が未解消のままでは、下位実装が `SIGNING` 中 cancel を `CANCELLED`、`RESULT_UNKNOWN` または `SUCCEEDED` のいずれに扱うかを本文から独立に推測し得る。Signing Protocol §19.2 の安全な区別を、共通 Design の outcome precedence として維持する必要がある。
- `DR-SF-008` が未解消のままでは、request / session / caller correlation が成立していても、handoff の intended recipient / device または response channel を独立に検証しない実装解釈が残る。Interfaces、Mobile、Relay、handoff specification の recipient invariant を共通 Flow の binding として維持する必要がある。
- SDK の public caller / Origin representation、platform lifecycle、Relay ACK / delivery contract、`RESULT_UNKNOWN` 後の lookup / resend、Chain-specific operation scope、wallet-core host integration および具体 UI は OPEN / delegated である。ただしそれらを理由に 4 条件、Profile binding、target inspection、replay rejection、recipient binding または cancel safety を弱めてはならない。
- Mainnet capability gate は Architecture §16、platform design、release evidence / policy および Signing Protocol §21.1 の owner に従う。Security Design の `DR-SEC-001` はこのレビューで再計上しないが、実装・release review で evidence missing / invalid / expired / unverifiable / unknown を fail-closed とすることは残存確認事項である。
- Relay E2E secret と transport credential の分離は Relay design、RR-008 および handoff specification の owner に従う。Security Design の `DR-SEC-002` はこのレビューで再計上しないが、Relay が opaque envelope を復号できず、transport status / ACK が approval や signing success の代替にならないことは維持する。
- 現在の workspace に Mobile App 実装は存在しない。今回の Mobile 評価は設計責任、共通 invariant、handoff flow および lower contract の整合性に限り、runtime 実装済み・検証済みとは扱わない。
