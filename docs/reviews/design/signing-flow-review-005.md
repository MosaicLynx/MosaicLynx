## 4. レビュー結果

**レビュー判定条件: `READY`**

重大指摘はなく、主要 2 件を次工程への必須引継ぎとして記録する。設計レビュースキルは重大が 1 件以上の場合だけ `REVISE DESIGN` とし、重大がなく主要 / 軽微のみの場合は `READY` とするため、今回の正式判定条件は `READY` である。

現行本文は、ブラウザ拡張機能特権を持つ層とモバイル信頼されたホストを署名主体側の責任主体とし、要求検証、信頼された表示、明示承認、4 条件、署名前再検証、wallet-core 生の署名、結果検証、安全側での終了、リプレイ / 重複拒否および自動代替経路禁止を一貫して定める。通常のトランザクション、アグリゲート、bonded / 部分トランザクション文脈、連署署名、NEM マルチシグ、メッセージ署名も共通判定条件とチェーン固有の内容検査の下に置かれている。

一方、`SIGNING` 進入後のキャンセルと署名結果の優先関係、およびリモート / 受け渡しの意図した受信者・端末と応答チャネルの結び付け・再検証が、本文だけからは一意に実装判断できない。下位の署名プロトコル、モバイル / Relay / インターフェースはより安全な条件を定めているが、共通署名フローの control-flow 境界としては新規主要指摘とする。

## 8. 任意の改善

`DR-SF-007`、`DR-SF-008` は主要の未決指摘であり、設計レビュースキル上は判定条件を不合格にしないため本節に記録する。両件とも実装へ進む前に修正または設計上の明示確認を行うべき内容である。

### DR-SF-007: 未決 — `SIGNING` 中キャンセルの結果優先順位

- 重要度: `Major`
- 状態: `OPEN`
- 対象箇所: [`docs/design/signing-flow.md`](../../design/signing-flow.md) §7.1〜§7.3（状態定義、遷移、ライフサイクル消失）、§21（再試行 / 重複 / リプレイ）および §22（失敗）。特に §7.2 の `SIGNING → SUCCEEDED` と「いずれの非終端状態 → 終端」のキャンセル条件。
- 問題: 本文はキャンセルを非終端状態から終端へ遷移させ、`SIGNING → SUCCEEDED` を wallet-core の成功時に許すが、`SIGNING` 中にキャンセルが受理された場合の結果優先順位を定めていない。そのため、同じ設計から、署名処理開始後のキャンセルを `CANCELLED` と先に確定する実装と、コアの結果を待って `RESULT_UNKNOWN` / `SUCCEEDED` とする実装の双方が合理的に導ける。`CANCELLED` とされた要求が後からコア署名を完了し得るか、また応答をどの状態で返すかが本文だけでは一意でない。
- 影響: 要求元、署名主体 UI、通信経路のキャンセルと wallet-core 署名の競合時に、キャンセル済み要求の後続署名、署名結果の誤分類、または `RESULT_UNKNOWN` の成功 / 拒否への誤変換が発生し得る。これは `SIGNING` 状態の安全な one-way 結果と、キャンセル後に署名へ進ませない不変条件を下位実装が推測する責任不足である。
- 根拠: 下位の [署名プロトコル §6.2](../../specifications/signing-protocol.md) と §19.2 は、`RECEIVED`〜`AUTHORIZED` のキャンセル、`SIGNING` 中の結果不明、署名未生成が確定したキャンセル、`SUCCEEDED` 後の配送キャンセルを区別している。これは安全な補完根拠である一方、共通フロー §7.2 に同じ上位の境界がないことを示す。要件 `CR-012`、`CR-NFR-009`、`CR-NFR-011`、`SDK-FR-010` も、キャンセル / 期限切れ / 結果不明後の成功・追加署名を許さない意味を要求する。
- 影響対象遷移: `AUTHORIZED → SIGNING`、`SIGNING → SUCCEEDED`、非終端状態 → `CANCELLED` / `RESULT_UNKNOWN`、および `SUCCEEDED` 後の応答配送。
- Violated 要求 / 不変条件: `CR-012` の失敗と成功の分離、`CR-NFR-011` の追加署名防止、§23 の「終端状態から再開しない」「結果不明から自動署名しない」。本文の意図を直接破る実装を必ず許すと断定するものではないが、共通設計だけでは安全な競合結果を確定できない。
- 必須修正 at 署名フロー granularity: §7 の高位遷移として、署名開始前の受け入れ済みキャンセルは `CANCELLED` かつコア呼び出しなし、`SIGNING` 中に結果が不明なら `RESULT_UNKNOWN`、署名が生成されていないことが確定した場合だけ `CANCELLED`、署名成功後のキャンセルは既存結果を取り消さず配送処理結果の区分だけを扱う、という境界を明示する。`CANCELLED` の terminalization 後にコア署名が開始・完了しないことも明示する。
- 対象範囲境界: ロック、CAS、不可分な基本機構、キュー、キャンセル API、コア結び付け、タイムアウト値、エラーコードまたは通信上の状態の形式は要求しない。必要なのは状態 / 結果の一意な安全条件だけである。
- 完了 / 再確認: `signing-flow.md` の状態遷移と失敗 / 再試行表に上記の優先順位を追跡でき、キャンセル競合の各時点で `CANCELLED`、`RESULT_UNKNOWN`、`SUCCEEDED + delivery disposition` を実装者が推測せず選べることを再確認する。

### DR-SF-008: 未決 — 受け渡し受信者 / 応答チャネル結び付け

- 重要度: `Major`
- 状態: `OPEN`
- 対象箇所: [`docs/design/signing-flow.md`](../../design/signing-flow.md) §5（要求論理的なモデル）、§16（認可組と署名前再検証）、§19（モバイル / Relay フロー）、§20（結果モデル）および §25（下位仕様への引継ぎ）。§4 と §23 には抽象的な `response channel` の分離はあるが、意図した受信者 / 端末識別情報の明示的な結び付けと再検証がない。
- 問題: リモート / 受け渡し要求について、本文は呼び出し元、セッション、世代、要求識別情報、プロファイル、アカウント、チェーン / ネットワーク、対象完全性および許可を結び付け / 再検証するが、意図した応答受信者 / 端末と応答チャネルの識別情報を同じ認可 / 結果組の項目として明示していない。`response channel` という抽象語だけでは、有効なセッションと要求 ID が一致することを意図した受信者の確認まで意味するのか、どの署名主体 / 配送責任主体が誤った端末応答を拒否するのかが一意に読めない。
- 影響: 受け渡しまたは Relay の誤配送・別受信者・古くなったチャネルに対し、要求が意図しない端末 / 署名主体の承認 UI に到達する、または別受信者が取得した応答を元要求の結果として受け取る責任不足が残る。要求 ID、呼び出し元、セッションだけの相関では受信者間の配送を明示的に閉じられず、結果の誤帰属や応答注入の防止条件を共通フローから実装へ安全に引き渡せない。
- 根拠: [`docs/design/interfaces.md` §6](../../design/interfaces.md) は wallet-core 結果、応答受信者、応答配送文脈を同一プロファイル内の文脈に結び付けし、§6.3〜§6.4 は並行する要求分離と応答受信者を要求する。[`docs/design/mobile-app.md` §12.3](../../design/mobile-app.md) は署名前に意図した受信者 / 応答チャネルを再検証し、[`docs/design/relay.md` §28](../../design/relay.md) は受信者識別子と受信者間の経路選択を不変条件にする。要件 `RR-007`、`CR-NFR-012` および受け渡し仕様 §7.4 / §13 も誤った受信者と応答対応関係をクライアント側のに検証する前提である。
- 影響対象フロー: 受け渡し initiation、Relay fetch / 応答アップロード、モバイル検証、承認対象、`AUTHORIZED → SIGNING` 前の再検証、結果対応付け、応答配送、誤った端末 / 遅延した応答処理。
- Violated 要求 / 不変条件: `RR-007` の要求 / 結果分離、`CR-NFR-012` の元要求・署名主体・アカウント・チェーン / ネットワークへの対応、セキュリティ設計 / Relay の受信者間の配送防止不変条件、および本文 §23 の要求 / 応答チャネル分離。下位資料に受信者条件があるため実際の全実装が欠陥になると断定するものではないが、共通フローの責務境界が不十分である。
- 必須修正 at 署名フロー granularity: 受け渡しを適用する共通フローの論理的な要求 / 認可 / 結果対応付けに意図した受信者 / 端末および応答チャネル識別情報を含める責任を明示し、署名主体が承認 / 署名前前に受信者を検証し、署名主体 / SDK / Relay の各配送責任主体が誤った受信者、古くなったチャネル、別要求の応答を拒否することを定める。厳密な公開フィールドを追加する必要はない。
- 対象範囲境界: 受信者フィールド名、端末証明、ディープリンク / App Link、HTTP / Redis 経路選択、E2E 暗号化、受領確認、通信経路認証情報、API 署名または応答スキーマは要求しない。必要なのは受信者識別情報をどのフロー結び付けと所有責任が守るかの明示である。
- 完了 / 再確認: §5、§16、§19、§20、§25 とインターフェース / モバイル / Relay の追跡可能性が同じ受信者 / 応答チャネル不変条件を示し、誤った端末要求 / 応答、並行する受け渡し、古くなった応答のいずれも UI、署名、成功配送へ進まないことを再確認する。

Mainnet リリース証跡、E2E 秘密情報 / 通信経路認証情報、受領確認、再試行、UI 配置およびプラットフォームライフサイクルの具体化は、対象本文が指定した責任主体・下位仕様へ委譲されており、今回の正式な指摘ではない。

## 16. 残存リスクと未決定事項

- `DR-SF-007` が未解消のままでは、下位実装が `SIGNING` 中キャンセルを `CANCELLED`、`RESULT_UNKNOWN` または `SUCCEEDED` のいずれに扱うかを本文から独立に推測し得る。署名プロトコル §19.2 の安全な区別を、共通設計の結果優先順位として維持する必要がある。
- `DR-SF-008` が未解消のままでは、要求 / セッション / 呼び出し元対応付けが成立していても、受け渡しの意図した受信者 / 端末または応答チャネルを独立に検証しない実装解釈が残る。インターフェース、モバイル、Relay、受け渡し仕様の受信者不変条件を共通フローの結び付けとして維持する必要がある。
- SDK の公開呼び出し元 / オリジン表現、プラットフォームライフサイクル、Relay 受領確認 / 配送契約、`RESULT_UNKNOWN` 後の照会 / 再送、チェーン固有の操作対象範囲、wallet-core ホスト統合および具体 UI は未決 / delegated である。ただしそれらを理由に 4 条件、プロファイル結び付け、対象内容検査、リプレイ拒否、受信者結び付けまたはキャンセル安全性を弱めてはならない。
- Mainnet 対応能力判定条件はアーキテクチャ §16、プラットフォーム設計、リリース証跡 / ポリシーおよび署名プロトコル §21.1 の責任主体に従う。セキュリティ設計の `DR-SEC-001` はこのレビューで再計上しないが、実装・リリースレビューで根拠欠落 / 無効な / 期限切れ / 検証不能の / 不明を安全側での終了とすることは残存確認事項である。
- Relay E2E 秘密情報と通信経路認証情報の分離は Relay 設計、RR-008 および受け渡し仕様の責任主体に従う。セキュリティ設計の `DR-SEC-002` はこのレビューで再計上しないが、Relay が内容を解釈しないエンベロープを復号できず、通信経路状態 / 受領確認が承認や署名成功の代替にならないことは維持する。
- 現在のワークスペースにモバイルアプリ実装は存在しない。今回のモバイル評価は設計責任、共通不変条件、受け渡しフローおよび下位の契約の整合性に限り、実行環境実装済み・検証済みとは扱わない。
