## 総評

署名フローの基本設計として、主要な安全境界と責任分担は十分に整理されている。特に、署名主体が対象全体から確認モデルを生成すること、解析不能・未対応・表示不能を警告付きで通過させないこと、アグリゲート / マルチシグの親全体を連署署名の署名対象とすること、ハッシュのみ署名を拒否すること、ノード照会を署名の前提にしないこと、wallet-core を生の署名と秘密情報処理に限定することは、`security-design.md` および既存要件と整合している。

また、`RESULT_UNKNOWN` からの自動再署名禁止、Relay 配送成功と署名成功の分離、サービスワーカー / モバイルプロセス / Relay 状態消失後の認可再利用禁止、Symbol / NEM のチェーン固有の意味の分離も明確である。既存の `SDK-OPEN-*`、`MR-OPEN-*`、`CR-OPEN-*` を公開 API やプラットフォーム対応能力の確定に使っていない点も適切である。

一方、下位設計へ進める前に、認可の結び付け組と実際に再検証する文脈の表現を一致させ、署名済み結果の配送失敗を `RESULT_UNKNOWN` と混同しない論理状態を補い、`1 signing operation` の安全上の単位を明文化する必要がある。いずれも現行本文に直ちに内容を確認しない署名や自動再署名を成立させる抜け道があるという判定ではないが、実装者の解釈差が安全性と回復性へ影響する。

## 良い点

- §4〜§5 は、要求識別情報だけでなく呼び出し元、セッション、許可、アカウント、チェーン、ネットワーク、対象、トランザクション文脈、鮮度、対応能力を署名判断の文脈として扱い、SDK / Relay / Provider / ノードの自己申告を最終根拠にしていない。
- §6 はアグリゲート完了 / Bonded、部分トランザクション、NEM マルチシグを共通基本機構として無理に増やさず、チェーン固有のトランザクション文脈と操作の関係に分離している。公開 API の範囲は `SDK-OPEN-002` 等へ適切に残している。
- §10〜§13 は、アグリゲートの外側 / 埋め込み全体、資産影響、権限変更、既存連署署名、期待される署名主体 / 役割を内容検査対象とし、完全な親を確認できない連署署名と NEM マルチシグを拒否する。ハッシュ、Relay、ノード、dApp の自己申告だけで進める経路を明示的に禁止している。
- §7、§19、§21 は、重複、リプレイ、遅延した配送、旧世代、ライフサイクル消失、要求期限切れ、メッセージ期限切れを署名再試行と混同せず、新しい要求と新しい承認を要求している。
- §14 はメッセージ署名をトランザクション署名から分離し、表示内容と署名バイト列の入力を分けないこと、メッセージ単位のリプレイ / ドメイン間の / 目的間の保護と要求単位の対応付けを別層として扱うことを明示している。
- §17〜§18 は、wallet-core に UI、呼び出し元検証、意味上の内容検査、承認を押し込まず、MosaicLynx 側が承認済み対象の処理の調整と再検証を担う境界を維持している。`_snwc` のバインディング / コア契約とも矛盾しない。

## 指摘一覧

### SDR-001

- 重要度: `MEDIUM`
- 対象: `docs/design/signing-flow.md` §5、§16.1〜§16.2、§23（特に行 90〜106、395〜415、552〜565）
- 内容: §5 の署名要求モデルには `permission context` と `protocol / capability context` が含まれ、§16.2 でも許可と対応能力を再検証している。一方、認可の中心的な論理組（§16.1）は呼び出し元、セッション、操作、アカウント、チェーン、ネットワーク、署名対象、トランザクション文脈、内容検査結果、鮮度だけで、許可と対応能力が明示されていない。§23 の認可失効条件にも許可 / 対応能力が直接列挙されていない。
- リスク: 実装者が §16.1 の組を認可の保存単位と解釈し、許可の失効 / 対象範囲変更または対応能力 / プロトコル文脈の変更を、単なる現在値の再確認で済ませると、承認時と署名時の権限境界・対応対応能力が一致しない状態を作り得る。これは直ちに迂回を意味しないが、TOCTOU の対象を実装解釈へ残す。
- 推奨対応: 認可組または同等の結び付け契約に、適用される許可対象範囲 / リビジョンとプロトコル / 対応能力文脈のスナップショットまたは不変識別子を明示的に含める。失効、対象範囲変更、対応能力 / プロトコル変更は認可を `INVALIDATED` にすること、再検証は現在値が存在することではなく承認時結び付けと一致することを明記する。具体的なフィールド名や通信上のスキーマは確定しなくてよい。
- 根拠: `docs/design/security-design.md` §8.1、§9、§10.2、§17（アカウント、チェーン、ネットワーク、呼び出し元、許可、セッションおよび要求の対応、署名ごとの承認、承認状態の再利用禁止）；`docs/requirements/requirements.md` の `CR-NFR-008`、`CR-NFR-009`、`CR-NFR-011`；`docs/requirements/sdk.md` の `SDK-SEC-005`〜`SDK-SEC-006`。

### SDR-002

- 重要度: `MEDIUM`
- 対象: `docs/design/signing-flow.md` §7.1〜§7.3、§20〜§22（特に行 135〜193、490〜548）
- 内容: 状態機械は `SIGNING → SUCCEEDED` を wallet-core の結果検証完了として定義し、後続に `Response` を置く。しかし、署名結果が確定した後に応答配送だけが失敗した場合の状態または外部から識別できる結果処理結果の区分がない。本文はその場合に自動再署名しないと述べる一方、`RESULT_UNKNOWN` は署名の成否自体が不明な状態として定義されている。
- リスク: 配送タイムアウトを `FAILED` / `RESULT_UNKNOWN` と誤分類して同じ対象の再署名を誘発する、または署名済み結果を安全に再配送できず利用者に新規署名を促す、という実装差が生じ得る。二重署名防止の禁止規則はあるが、既知の署名結果と署名成否不明をライフサイクル上で機械的に区別できない。
- 推奨対応: `SIGNED_RESULT_PENDING_DELIVERY`、`DELIVERY_UNKNOWN` 等の非署名復旧処理結果の区分を導入するか、状態名を増やさずとも「署名生成確認済み / 応答配送保留中の」と「署名生成不明」を明示的に区別する論理契約を追加する。前者は結果再送 / 照会のみ許可し、`SIGNING` への遷移・新しい署名生成を禁止する。結果照会 / 通信上の再試行の具体方式は既存未決と下位受け渡し仕様へ委譲できる。
- 根拠: 同設計 §7.3（行 192〜193）、§20.2（行 508〜516）、§21（行 525〜528）；`docs/requirements/relay.md` の `RR-NFR-002`、`RR-AC-011`、`RR-AC-012`；`docs/specifications/web-transaction-handoff-spec.md` の世代 / 状態消失 / 結果処理規則。

### SDR-003

- 重要度: `MEDIUM`
- 対象: `docs/design/signing-flow.md` §4、§6、§7、§23（特に行 82、112〜129、395〜402）
- 内容: `1 request = 1 confirmation = 1 authentication = 1 signing operation` は安全原則として適切だが、`signing operation` が論理的な利用者対応、プロトコル操作、wallet-core API 呼び出し、または署名バイト世代のどれを指すか定義されていない。本文は `Signing request` を一つの署名判断として定義し、操作をトランザクション / 連署署名 / メッセージの分類として扱っているが、両者の安全上の単位が明示的に同一化されていない。
- リスク: アグリゲートの初期署名と追加連署署名、wallet-core の内部呼び出し、結果再配送を実装ごとに異なる粒度で一つの認可と扱う可能性がある。認証の使い回し、意図しない一括処理化、または安全性を保つための過剰な API 制約につながる。
- 推奨対応: この不変原則における `signing operation` を「一つの論理的な署名対象に対する一回の署名判断・一回の使用済み認可」と定義する。wallet-core の内部 API 呼び出しや署名検証、結果配送は新しい署名操作ではない。別の親、連署者、アカウント、操作または対象は別要求 / 認可とし、複数の内部暗号学的な呼び出しを許すかどうかは下位契約で決めるが、承認済み対象の範囲を拡張しないことを明記する。
- 根拠: `docs/design/security-design.md` §7.1、§10.2、§17（毎回再認証、要求ごとの承認・認証・署名分離）；`docs/requirements/requirements.md` の `CR-AC-001`、`CR-AC-012`、`CR-NFR-011`。これは一括処理署名を許可する提案ではなく、既存の一回限り原則の適用単位を明確化する提案である。

### SDR-004

- 重要度: `LOW`
- 対象: `docs/design/signing-flow.md` §11.1〜§11.2（特に行 264〜294）
- 内容: ハッシュのみ連署署名の拒否と親全体の内容検査は明確であるが、「完全な親ペイロード、または下位仕様で承認された同等の全体表現」という表現が、何をもって親全体と同等とするかを下位仕様へ広く残している。
- リスク: 将来の下位仕様が、ハッシュ + 外部要約、ノード / Relay からの補完、または一部フィールドだけの commitment を「同等」と解釈すると、§11.2 のハッシュのみ禁止を実質的に迂回し得る。
- 推奨対応: 「同等の全体表現」は、署名主体が外部補助情報なしに親の全セキュリティに関わるフィールド、埋め込み / 内部トランザクション、既存署名・連署署名、選択済みの連署者、正規ハッシュ結び付けを再構成・検証・表示できる表現に限る、と基本設計上で条件付ける。ハッシュ、内容を解釈しない識別子、外部表示文言およびノード / Relay 照会は代替にならないことを再掲する。
- 根拠: 同設計 §4.1、§10.1、§11.1〜§11.2；`docs/specifications/product-spec.md` §12.3（完全な親ペイロード、ハッシュ / 部分トランザクションデータの拒否）；`docs/specifications/chain-compatibility-spec.md` §5〜§6（親ハッシュ / トランザクションハッシュの正規検証）。

## アグリゲート / 連署署名 / 部分トランザクション評価

総合評価は「安全条件は満たしているが、SDR-004 の結び付け表現を下位仕様へ引き継ぐ際に条件を固定すること」である。

- アグリゲート完了 / Bonded: 外側、埋め込み、署名主体、受信者、mosaic / 数量、手数料、期限、名前空間、メタデータ、判断権限 / 許可、トランザクションハッシュ、ペイロードサイズ、既存の連署署名、期待される役割まで内容検査対象に含め、部分解析や不明 / 未対応の警告迂回を拒否している。完了 / Bonded を独立共通操作にしない分類も妥当である。
- 連署署名: 署名対象を連署署名バイト列単体ではなく親全体と選択済みの連署者の関係として定義している。親内容、ハッシュ、チェーン / ネットワーク、期待される連署者、重複 / 既に署名済み、古くなった / 期限切れ、結果対応付けを要求し、ハッシュのみ、ノード / Relay / SDK / dApp の自己申告による省略を拒否している。SDR-004 の「同等表現」の条件だけ明文化が必要である。
- 部分トランザクション: 共通基本機構ではなくチェーン / ネットワーク / 受け渡し文脈として扱い、部分トランザクションであることだけで署名可能にせず、全体確認不能なら不合格終了済みとしている。ノードから検索・監視して補完する前提もない。Symbol と NEM の部分トランザクション意味を同一化していない。
- NEM マルチシグ: Symbol アグリゲートとトランザクションモデルを共有せず、ラッパー / 内部トランザクション、開始主体、内部署名主体、手数料支払者、連署署名意味、ハッシュ、アドレス、ネットワーク、署名バイト列を NEM 統合に残している。共通化はライフサイクル、承認、結び付け、対応付け、不合格終了済みに限定されている。

## 状態遷移評価

`RECEIVED → VALIDATED → INSPECTED → AWAITING_USER → AUTHORIZED → SIGNING → SUCCEEDED` の責任分担、`AUTHORIZED` の短寿命、署名前の再検証、終端状態からの再発 / 再署名禁止、サービスワーカー / モバイル / Relay ライフサイクル消失の安全側終了は適切である。`SIGNING` の自動再実行禁止も明示されている。

ただし、`SUCCEEDED` 後の応答配送失敗が状態遷移の外に残り、`RESULT_UNKNOWN`（署名成否不明）と同じ要求の結果配送問題を機械的に分ける状態がない。SDR-002 を条件として、署名結果の再配送と署名生成を分離する処理結果の区分を下位仕様へ確実に引き継ぐ必要がある。

## 認可 / TOCTOU 評価

requestId 単体への依存を避け、呼び出し元、セッション、操作、アカウント、チェーン、ネットワーク、対象、トランザクション文脈、内容検査結果、鮮度に結び付けし、wallet-core 呼び出し直前に対象、親、埋め込み / 内部、メッセージ、署名主体、期待される署名主体、許可、対応能力、正規化、署名状態を再検証する構成は十分に強い。確認モデルと実対象の不変性、ブラウザ観測された文脈、モバイル受け渡し文脈、Relay 世代も適切に扱われている。

SDR-001 のとおり、中心組に許可 / 対応能力を明示しない点だけが表現上の不整合である。現在値との比較ではなく、承認時の許可対象範囲 / 対応能力文脈との一致と、変更時の失効を明示すれば、TOCTOU の責任境界が一貫する。

## RESULT_UNKNOWN / 再試行評価

`RESULT_UNKNOWN` を成功とも未署名とも断定せず、自動再署名を禁止し、Relay 配送再試行と署名再試行を分離し、再起動 / 状態消失 / 古くなった / 重複 / リプレイ後に古い認可、セッション、暗号文、対象を再利用しない点は適合している。既知の署名結果を結果再送 / 照会と再署名から分ける方針も本文にある。

SDR-002 の状態表現を補えば、応答配送失敗と署名生成不確実性を外部契約へ安全に伝播できる。照会が未決であること自体は問題ではなく、照会がない場合でも自動再署名しないという現在の原則を維持すべきである。

## wallet-core / Relay / ノード境界評価

- wallet-core: MosaicLynx が呼び出し元検証、意味上の内容検査、確認、認可、認証、対象再検証、処理の調整、結果検証を担い、wallet-core がウォレットストア、鍵管理、秘密情報処理、生の署名を担う分離は適切である。KDF、AEAD、ストア形式、鍵導出、署名バイト列、秘密情報ライフサイクルを再実装していない。
- Relay: 内容を解釈しない / 信頼されていない通信経路とし、内容検査、承認、署名対象の生成・補完・差し替え、署名生成、アナウンス、意味上の成功判定を Relay に置いていない。世代、遅延した配送、状態消失、配送成功と署名成功の分離も適合している。
- ノード: 解析、検証、内容検査、確認、署名の必須条件にせず、ノード応答やメタデータを署名可否の単独根拠にしていない。部分トランザクション / アグリゲート親のノード照会を共通前提にしない点も適切である。
- ブラウザ拡張機能 / モバイル: Provider / コンテンツスクリプト / self-reported オリジンを信頼された署名主体とせず、特権を持つ層 / モバイルアプリがブラウザ観測された文脈または受け渡し文脈を再検証する。タブ / フレーム / 文書変更、ページ遷移、サービスワーカー再起動、モバイルプロセス消失の安全側扱いも要件と一致する。

## 未決事項

既存の未決事項は適切に引き継がれており、本レビューでは解決しない。

- `SDK-OPEN-002`、`SDK-OPEN-003`、`SDK-OPEN-004`、`SDK-OPEN-006`、`SDK-OPEN-007`: アグリゲート / 連署署名の公開範囲、通信経路、トランザクション組み立て、バージョンポリシー、呼び出し元 / オリジンとの結び付け、具体 API。
- `MR-OPEN-002`、`MR-OPEN-003`、`MR-OPEN-005`、`MR-OPEN-006`: モバイル受信経路、OS 保護、バインディング統合、ライフサイクル、バックアップ / 移行。
- `CR-OPEN-001`、`CR-OPEN-002`: wallet-core バインディングホスト統合、秘密バイトライフサイクル、OS 保護、エラー対応付け、移行。
- アグリゲート / Bonded、部分トランザクション、Symbol 連署署名、NEM マルチシグ / 連署署名の公開操作、形式、対応済みの対象範囲。
- `result unknown` 後の既存署名結果の照会 / 再送契約。既存署名を再配送する処理と、同じ対象の再署名は分離する。

SDR-002 と SDR-003 は新しい公開 API を決める指摘ではないが、下位仕様の前提として追跡すべき設計明確化である。SDR-004 の「同等の全体表現」の条件も、既存未決を解決せずに安全下限として追記できる。

## 最終判定

`READY WITH CONDITIONS`

阻害要因 / HIGH は確認されなかった。基本設計は、下位仕様へ進めるための主要な責任境界、安全不変条件、アグリゲート / 連署署名 / 部分トランザクションの安全側での終了方針、Symbol / NEM の分離、wallet-core / Relay / ノード境界を満たしている。

ただし、下位仕様化の前に次を反映することを条件とする。

1. 認可組と失効条件へ許可対象範囲 / リビジョンおよび対応能力 / プロトコル文脈の結び付けを明示する（SDR-001）。
2. 既知の署名結果の応答配送失敗と署名生成不確実性をライフサイクル / 結果処理結果の区分上で区別し、前者を結果再送 / 照会のみに限定する（SDR-002）。
3. `signing operation` を一回限りの認可の安全上の単位として定義する（SDR-003）。
4. 連署署名の「同等の全体表現」が親全体の再構成・正規ハッシュ結び付け・全フィールド内容検査を満たすことを固定する（SDR-004）。
