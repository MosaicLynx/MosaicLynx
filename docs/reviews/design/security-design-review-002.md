## 総評

前回レビューで指摘した SD-SEC-001〜005 は、対象設計書およびプロファイル / アカウント仕様への反映により解消された。

- 署名対象のセキュリティに関わるフィールドは全て確認可能でなければならず、表示不能時は拒否する MUST が追加された。
- wallet-core のエラー、警告、結び付けエラー、ストア完全性 / 検証失敗を無視せず安全側での終了とする条件が追加された。
- メッセージ署名の呼び出し元 / オリジン、アカウント、チェーン / ネットワーク、目的、鮮度、ノンス、ドメイン分離の共通原則が追加された。
- セキュリティ上の不変条件 1 / 8 の外部境界・侵害範囲が本文と一致する表現へ改訂された。
- `while-unlocked` はプロファイル / アカウント仕様から除外され、署名ごとの再認証が正本として固定された。

信頼境界、秘密情報の責任分界、署名承認、内容を確認しない署名禁止、許可分離、application-layer リプレイ保護、Relay / ノードの非信頼モデル、ログ・保持、バックアップ / エクスポート、総当たり攻撃、信頼された UI、安全側での終了、事故復旧、ソフトウェア完全性、および12個のセキュリティ上の不変条件は、共通セキュリティ設計として成立している。

残る条件は、起動時ロック済みを「原則」ではなく下位設計が逸脱できない MUST として明示すること、モバイルの署名確認・認証画面を含む画面露出リスクを共通原則から下位ポリシーへ確実に引き継ぐこと、Symbol / NEM の同一秘密鍵利用に関する既存資料間の正本と責任分界を整理することである。いずれも具体 API、暗号パラメーター、OS API または実装クラスを本書へ追加する指摘ではない。

## 最終判定

`READY WITH CONDITIONS`

ブラウザ拡張機能、Relay、SDK および共通のモバイル受け渡し / 承認境界の下位設計へ進めてよい。ただし、下記条件を満たすまで、モバイルの署名画面や起動直後の状態について下位設計が認証省略・古い状態の復帰・画面露出を許す仕様にならないことを確認できない。

### SD-REVIEW-001: 起動時ロック済みの MUST 化

**重要度:** `MEDIUM`

**根拠:** §7.1 は「アプリ / 拡張機能の起動時は原則ロック済み」と記載し、ブラウザ拡張機能のブラウザ再起動・拡張機能再ロード時ロックは明記するが、モバイルアプリを含む全 Signer が起動時に必ずロック済みであることを MUST としていない。

`docs/specifications/product-spec.md` §6.2 は保存済みプロファイルがある通常起動でロック解除画面を表示し、`docs/requirements/mobile-app.md` MR-005 / MR-006 は再起動後の自動再開および明示操作なしの認証完了を禁止している。共通設計の「原則」は、プラットフォーム固有設計で自動復帰を例外扱いできる余地を残す。

**推奨対応:** 「ブラウザ拡張機能 / モバイルアプリは起動、再起動、再読み込み、プロセス再作成後に MUST ロック済みとし、利用者の明示認証なしにロック解除済みまたは署名可能状態へ移行してはならない」とする。具体的なロック UI、OS 認証情報、サービスワーカー / プロセスライフサイクルは下位設計へ委譲する。

### SD-REVIEW-002: モバイルの画面露出範囲

**重要度:** `LOW`

**根拠:** §13.2 はモバイルの秘密情報表示画面についてスクリーンショット / 画面録画防止を要求し、直近のアプリプレビュー、通知、履歴、一時領域 UI に秘密鍵 / ニーモニックを残さないことを定めている。これは秘密情報保護として適切である。

一方、`docs/requirements/mobile-app.md` MR-011 / MR-AC-012 は秘密情報だけでなく、署名対象、承認画面、最近使ったアプリ一覧、通知表示の露出リスク評価を要求している。署名確認画面は秘密情報ではない場合でもトランザクション / メッセージ、呼び出し元、アカウント、資産移動情報を含む機微な UI であり、§18 のモバイル委譲表だけではその評価を必須の引継ぎ条件として読み取りにくい。

**推奨対応:** §13.2 または §18 のモバイル維持条件に「秘密情報入力・表示画面に加え、署名確認 / 認証画面、直近のアプリプレビュー、通知、画面共有・録画を機微な UI として評価し、プラットフォームポリシーと保護限界を明示する」と追加する。OS が防止できない範囲を完全防止と表示しない原則は維持し、具体的な対象画面や API はモバイル設計へ委譲する。

### SD-REVIEW-003: 同一秘密鍵利用の正本と責任分界

**重要度:** `MEDIUM`

**根拠:** `docs/specifications/profile-account-spec.md` §11、`docs/specifications/product-spec.md` §10.2 / §10.3、`docs/specifications/chain-compatibility-spec.md` §2.3 は、同じ秘密鍵から Symbol / NEM の識別情報を導出する互換性要求と、片方のチェーンまたは秘密鍵侵害時に両チェーンアカウントが影響を受ける共通リスクを記載している。

一方、`docs/design/architecture.md` §13 は「一つのアカウントの鍵を Symbol / NEM で共用する前提を本設計から除外する」と記載し、セキュリティ設計 §19 SEC-OPEN-003 も「旧来の共用前提を採用していない」と表現している。これは共通セキュリティ設計で鍵方式を勝手に変更すべきという意味ではないが、同一リポジトリ内で正反対に読めるため、下位のプロファイル / wallet-core / チェーン統合設計が異なる blast radius を前提にする。

**推奨対応:** 同一秘密鍵利用の採否を本書で暗号設計として決めず、承認済みのアカウントモデル / チェーン互換性 / wallet-core 外部契約のどれを正本とするかを ADR または責任分界表で明示する。共通セキュリティ設計は、採用された方式にかかわらずチェーン / ネットワーク / アカウントを混同しないこと、Symbol / NEM の処理を暗黙に共通化しないこと、同一鍵を採用する場合のチェーン間の blast radius を利用者へ示すことを保持する。

## 下位設計への進行可否

条件付きで進行可能である。

- ブラウザ拡張機能の Provider / オリジン / 特権を持つ層、Relay の内容を解釈しない通信経路、SDK の受け渡し、メッセージ / トランザクション内容検査は進めてよい。
- モバイルの詳細設計は、起動・再起動・プロセス再作成後のロック済み、毎回の利用者存在 / 再認証、署名確認・認証画面の露出ポリシーと限界を受入条件へ含めること。
- Symbol / NEM のアカウント / 鍵モデルとチェーン統合の詳細設計は、同一秘密鍵利用に関する正本とチェーン間の blast radius を整理してから確定すること。
- SEC-OPEN-002 は具体的モバイル対応能力の未決として保持できるが、認証省略や自動署名を許可する未決ではない。
- SEC-OPEN-004 は具体契約の再設計を意味せず、既存受け渡し契約に対する表示・対応形式の最終確認として扱うこと。

## 未解決事項

- SD-REVIEW-001: 起動時ロック済みを全 Signer 共通 MUST として明記すること。
- SD-REVIEW-002: モバイルの署名確認・認証画面、プレビュー、通知、録画・画面共有を含む機微な UI ポリシーの引継ぎ。
- SD-REVIEW-003 / SEC-OPEN-003: 同一秘密鍵利用の正本、アカウントモデル、wallet-core / チェーン統合の責任およびチェーン間の blast radius の整合。
- SEC-OPEN-002: モバイル生体認証の対応能力、代替経路、認証情報保管、ライフサイクル。
- アグリゲート / マルチシグ / 連署署名、プロファイル全体バックアップ / 復元、モバイルライフサイクル、OS 保護、リリース操作の具体詳細。これらを理由に共通 MUST を弱めてはならない。
