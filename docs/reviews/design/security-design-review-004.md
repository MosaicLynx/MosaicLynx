## 4. レビュー結果

**レビュー判定条件: `READY`**

現在のセキュリティ設計を本文、上位資料、アーキテクチャの確定内容および関連下流資料から独立に評価した結果、重大 / 主要 / 軽微の新規指摘は確認されなかった。信頼境界、共通署名ゲート、秘密情報 / 鍵ライフサイクル、安全側での終了、セキュリティ上の不変条件および設計フェーズ境界に、設計を差し戻す実質的な問題はない。

`SD-REVIEW-001`、`SD-REVIEW-002`、`SD-REVIEW-003` は、現在の本文に基づきそれぞれ `RESOLVED` と判定する。現在の `SEC-OPEN-*` は `SEC-OPEN-002` と `SEC-OPEN-004` であり、いずれも共通 MUST を弱めず、セキュリティ設計で無理に確定すべき内容を残しているものではない。

## 5. 要約

- ブラウザ拡張機能の特権を持つ文脈とモバイルアプリの信頼されたホストが Signer であり、Provider、コンテンツスクリプト、SDK、dApp / Web ページ、ディープリンク、Relay、ノード / 外部 API および OS は同じ信頼主体として扱われていない。信頼されたコンポーネントと信頼された入力の混同はない。
- アーキテクチャ §6.9 の共通4条件（認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認）は、セキュリティ設計 §16 で明示され、§3 / §5 / §7〜§9 / §15 / §17 で責任、結び付け、再確認および失敗条件へ接続されている。ブラウザ / モバイルの責任主体は一致し、接続 / 許可、ロック解除済み、wallet-core パスワード / ストア検証、SDK / Relay / dApp の動作は代替にならない。
- 秘密鍵、ニーモニック、パスワード / PIN 由来の秘密情報、復号済みストア、一時的な署名秘密情報、セッション / 認証秘密情報および通信経路認証情報について、ホスト / wallet-core 境界、短期保持、外部境界・ログ・遠隔計測データへの非開示、ロック / 失効 / 期限切れ / 事故時の無効化が基本方針として成立している。詳細なバイトライフサイクル、認証情報形式および OS 保護は正しく下位へ委譲されている。
- §7 は起動、再起動、再読み込み、プロセス再作成、拡張機能再読み込み、ブラウザ再起動後の `LOCKED` を全 Signer の MUST とし、署名ごとの再認証とロック時の一時秘密破棄を要求する。プロファイル §20 の `every-signature` と整合し、SD-REVIEW-001 の再発はない。
- §8〜§10 は Signer 自身が生成する信頼された UI、全セキュリティに関わるフィールドの確認可能性、ペイロードと表示内容の一致、ペイロード / 呼び出し元 / アカウント / チェーン / ネットワーク変更時の承認無効化、要求単位のリプレイ / 並行する分離を定める。内容を確認しない署名、不明 / 未対応の / 表示不能の要求は拒否される。
- Relay は内容を解釈しない通信経路 / 短期間のみ有効な状態 / 構造上の検証に留まり、SDK は dApp 側の統合 / 対応付け / 通信経路抽象化に留まる。両者とも Signer、認証、アカウントの利用認可、承認、意味上の内容検査または生の署名を代替しない。
- ノード / 外部 API は補助情報に留まり、チェーン / ネットワーク不一致、解析 / 検証失敗、ストア / バインディング失敗、Relay 失敗、結果不明等は安全側での終了へ接続される。Mainnet 対応能力はリリース証跡 / ポリシーを満たす場合だけ有効化される。
- §17 の12 セキュリティ上の不変条件は本文と矛盾しない。不変条件 6 の一対一対応は共通4条件の全てを列挙する代替表現ではなく、4条件自体は §16 と個別の §7〜§9 に別途 MUST として定義されているため、判定条件の欠落にはならない。

## 10. 後続工程へ委譲する指摘

正式な後続工程へ委譲指摘はない。以下はセキュリティ設計が高位の安全条件を固定したうえで、下位資料または運用へ委譲している事項であり、今回の指摘ではない。

- `SEC-OPEN-002` に関係するモバイルの生体認証対応能力、代替経路、認証情報保管およびライフサイクル。
- `SEC-OPEN-004` に関係する既存メッセージ署名受け渡し契約とプラットフォームの表示受け入れ条件の最終整合。具体 API、通信上のスキーマ、エンコーディング、ノンス形式、シリアライズ済みのメッセージ形式は対象外。
- `CR-OPEN-001` / `CR-OPEN-002` の wallet-core ホスト統合、React ネイティブ連携、OS 保護、秘密バイトの一時ライフサイクル、エラー対応付けおよび移行。
- `MR-OPEN-*`、`RR-OPEN-*`、`SDK-OPEN-*`、アグリゲート / マルチシグ / 連署署名、プロファイル全体バックアップ / 復元、プラットフォームライフサイクルおよびリリース操作の具体詳細。
- Symbol / NEM の対応型 / バージョン、意味上の内容検査、正規化、署名バイト列、Mainnet 根拠の収集・検証・運用詳細。

これらの未決・委譲は、認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認、秘密情報の分離、Relay の内容を解釈しない性、SDK の非特権性、wallet-core のアプリケーションレベルの認証 / 承認非担当および安全側での終了を弱める根拠にはならない。

## 15. 残存リスクと未決定事項

- `SEC-OPEN-002` は、プロファイル §22 の将来生体認証対応能力とセキュリティ設計 §7.2 のモバイル利用可能方針を、モバイル対応能力、代替経路、認証情報保管およびライフサイクルの下位決定で整合させるために残すことが妥当である。認証省略、自動署名または OS への無条件信頼を許す未決ではない。
- `SEC-OPEN-004` は、既存受け渡し / 署名プロトコルのメッセージ署名契約を前提に、プラットフォームの表示受け入れ条件と最終的な契約整合だけを残すことが妥当である。具体 API / 通信上の / エンコーディングをセキュリティ設計で再定義する必要はない。
- モバイル実装は現在のワークスペースに存在しない。モバイルの OS 保護、画面露出、ライフサイクル、バインディング統合、バックアップ / 移行およびリリース対応能力は、実装・下位設計時に本書の MUST として再確認する必要がある。
- Relay 認証情報、E2E 秘密情報、セッション識別子、公開アカウント情報は下位資料で分類・保持境界が具体化されるが、セキュリティ設計の `§12`、`§15`、`§18` がそれらを秘密情報・機微な情報・一時状態として安全側に扱う共通条件を既に固定している。
- Mainnet リリース証跡の期限、信頼された鍵、成果物、ポリシー、実行環境対応能力および事故操作はリリース資料で確定・検証する。セキュリティ設計は根拠不足時の安全側での終了を維持する。
