## 5. 要約

前回 `DR-001` の問題であった `Relay / remote handoff failure → result unknown` という直接対応は現在の SDK 設計から除去されている。§15 は通信経路 / Relay を通信経路レベルのエラー分類とし、`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` をエラー分類ではない Signer 側の処理結果の区分として分離している。§21 は Relay / Provider / 通信経路失敗だけでは両処理結果の区分が成立しないこと、SDK は取得済みの Signer が生成した処理結果の区分を対応付け後に意味不変で伝達するだけであることを明記している。

`RESULT_UNKNOWN` は Signer が署名生成自体の結果を確定できない場合、`DELIVERY_UNKNOWN` は Signer が既知の署名済み結果の配送処理結果の区分を確定できない場合に限定されている。Provider 失敗、Relay 失敗、ネットワーク / 通信経路失敗、タイムアウト、応答欠如、接続解除、受信者オフライン、再接続失敗、配送失敗、ページライフサイクル消失および SDK 内部状態から SDK が両処理結果の区分を生成・推測・確定する余地は、§4、§15〜§17、§21〜§22 で閉じられている。

既知の結果の再配送 / 再送 / 取得 / 照会は署名再試行と分離され、通信経路失敗、既知の結果配送失敗、`RESULT_UNKNOWN`、`DELIVERY_UNKNOWN`、利用者拒否、セキュリティ / 許可 / 認可失敗からの自動再署名 / 代替経路も禁止されている。新しい署名操作には新規要求と共通4条件が必要である。

修正による前回合格項目の回帰、明確な新規重大 / 主要 / 軽微指摘、設計工程境界逸脱は確認されなかった。`DR-001` は `Resolved`、新規指摘はなし、全8 レビュー判定条件は合格と判定する。

## 9. 解消済みの指摘

### DR-001: 解消済み — Relay / 通信経路失敗と Signer 側の処理結果の区分の判断権限分離

- 重要度: `Critical`
- 状態: `Resolved`
- 対象: [`docs/design/sdk.md`](../../design/sdk.md) §4.1〜§4.2、§14.2、§15.1〜§15.2、§16.3、§17、§21、§22、§25。前回中心箇所は旧 §21 行569、現行中心箇所は §21 行577〜586。
- 前回の確認条件: Relay / リモート受け渡し失敗を `transport failure / result unknown` とする直接対応があり、SDK が通信経路状態から Signer 側の `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` を生成・推測・確定する余地があった。
- 現在確認できた事実: §4.1 行81は Provider / Relay / 通信経路 / クライアント失敗の正規化が署名生成結果または Signer 側の配送処理結果の区分の確定を意味しないと定める。§4.2 行94〜95は SDK が署名生成結果、既知の署名済み結果の配送処理結果の区分、および指定された Provider / Relay / タイムアウト / 応答欠如 / ライフサイクル等からの両処理結果の区分の生成・推測・確定を担わないと定める。
- 現在の応答 / エラー境界: §15.1 行440〜442は SDK が受け取るのは Signer が生成した `RESULT_UNKNOWN` と Signer 側の `DELIVERY_UNKNOWN` であり、要求 / 応答対応付け後に意味不変で伝達するだけであること、両者の成立条件と通信経路状態からの生成禁止を明記する。§15.2 行457、462は通信経路 / Relay を通信経路レベルの分類とし、両処理結果の区分を通信経路 / エラー分類から分離する。
- 現在のライフサイクル / 抽象化境界: §16.3 行488はページライフサイクル消失を文脈消失した / 通信経路失敗分類とし、署名結果または配送処理結果の区分の証明にしない。§17 行502〜506はローカル / リモートの通信経路差異、Relay 利用不能、確定済みの結果復旧を両処理結果の区分の生成と分離する。
- 現在の失敗 / 復旧境界: §21 行577〜586は Relay / リモート受け渡し失敗を通信経路 / 受け渡し失敗分類として終了し、Signer が生成した `RESULT_UNKNOWN` / Signer 側の `DELIVERY_UNKNOWN` は対応付け後に意味不変で伝達する別行としている。通信経路失敗、既知の結果配送失敗、両処理結果の区分、許可 / 認可失敗から自動再署名 / 代替経路を行わず、新しい署名操作には新規要求、認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認が必要である。
- 現在の不変条件 / 追跡可能性: §22 行591、600、603〜605は SDK を署名結果正確性 / 処理結果の区分判断権限とせず、タイムアウト / キャンセル / ページライフサイクル消失、応答欠如、Provider / Relay / 通信経路状態を結果の根拠とせず、Signer が生成した処理結果の区分を意味不変に伝達することを固定する。§25 行647〜653は通信経路正規化、両処理結果の区分の分離、そのまま通過させる、確定済みの結果復旧、再署名の禁止をそれぞれ責任主体と下流受け渡しへ追跡する。
- 問題・影響の再確認: 旧 §21 の直接対応はなく、現行本文を単独で読んでも通信経路失敗が `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` に昇格しない。Signer 側の処理結果の区分と通信経路分類の意味が維持されるため、既知の結果の再配送と署名再試行、Signer が生成した不明の伝達と SDK ローカル失敗、セキュリティ失敗と通信経路再試行を誤って統合する下流リスクは解消されている。
- 最小修正の確認: 前回指摘が要求した判断権限分離、通信経路レベルの正規化、Signer が生成したそのまま通過させる、ページライフサイクルの非証明性、既知の結果復旧、no 自動再署名、no 自動代替経路、4条件の新鮮な署名および §25 追跡可能性が、具体 API / エラーコード / 通信上のスキーマを追加せずに実現されている。
- 完了条件 / 再確認: (1) 旧直接対応が残っていない、(2) 通信経路失敗が分類として扱われる、(3) SDK が `RESULT_UNKNOWN` を生成・推測・確定しない、(4) SDK が `DELIVERY_UNKNOWN` を生成・推測・確定しない、(5) `RESULT_UNKNOWN` 責任主体が Signer、(6) `DELIVERY_UNKNOWN` 責任主体が Signer、(7) そのまま通過させるが意味不変、(8) タイムアウト / キャンセル / ページ消失が結果を確定しない、(9) 既知の結果復旧と再署名が分離、(10) 自動再署名 / 代替経路禁止、(11) 通信経路再試行と署名再試行分離、(12) 詳細仕様を逆流させない、の全条件を確認した。`DR-001` は `Resolved` とする。
