## 5. Summary

`interfaces.md` は、共通 Interface の意味・責任・検証を platform transport、exact API、DTO、wire encoding および実装アルゴリズムから分離している。SDK / Provider / Browser / Mobile / Relay / wallet-core の authority は概ね分離され、Profile-local context、Account authority、Chain / Network、target-derived summary、四条件 gate、secret isolation、fail-closed、replay / duplicate rejection、`RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` の区別および concurrent request isolation は interface-level invariant として追跡できる。

Public operation についても、capability / discovery、connection、permission、public Account identity、disconnect / revoke、transaction / message signing、signing result、classified error および lifecycle を共通概念または責任分界としてカバーしている。Provider discovery や具体的な API 名を本書へ追加要求する必要はなく、SDK Design / Specification への委譲は適切である。

一方、Interfaces 自身には次の2件の contract gap が残る。

- `DR-006` Major / Open: cancellation を単なる error category として扱うだけで、cancel request、cancel の authority / scope、accepted / rejected acknowledgement、terminal 済み・SIGNING 中・署名済み後の意味および race outcome (`CANCELLED` / `RESULT_UNKNOWN` / `SUCCEEDED` + `DELIVERY_UNKNOWN`) が共通 interface contract として一意に定義されていない。
- `DR-007` Major / Open: caller / source、session、generation、response recipient の概念はあるが、handoff の intended recipient / participant、必要な device / signer identity および response channel / direction を request / response の binding として共通に表現・検証する責任が明示されていない。

これらは `DR-SF-007` / `DR-SF-008` を機械的に複製したものではない。Signing Flow の未確定事項が Interfaces 境界で表現可能になるために必要な、対象本文固有の semantic contract gap として分離した。具体的な operation 名、ack wire schema、device identifier の公開形式、channel 実装、lock / concurrency primitive は要求しない。

正式な Gate rule は `Critical` が1件以上なら `REVISE DESIGN`、`Critical` がなく `Major` / `Minor` のみなら `READY` である。今回の新規 Open finding は Major 2件で Critical は0件のため、追跡すべき follow-up は残るが Review Gate は `READY` とする。

## 8. Optional Improvements

### DR-006: Cancellation outcome contract

- Severity: `Major`
- Status: `Open`
- Location: [`interfaces.md`](../../design/interfaces.md) §6.4、§6.6、§7.6、§8、§9、特に行232〜255、276〜302、342〜353、355〜375、377〜403。
- Affected operation / actor: Signing request、SDK / Provider、Browser / Mobile Signer、handoff / Relay adapter。
- Problem: 本文は `cancelled` を Error / terminal の意味として記載し、SigningResponse の概念にも cancelled を含める一方、cancel 自体をどの actor がどの request に対して発行できるか、cancel request と cancellation acknowledgement をどの意味で扱うか、受理拒否・既に terminal・`SIGNING` 中・署名済みだが response 未配送の場合の結果をどう表現するかを共通契約として定めていない。§7.6 の common interface concepts と §8 の validation responsibility に cancellation operation / acknowledgement / race outcome の対応がない。
- Evidence: `interfaces.md` §6.4 は SigningResponse の result states と `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` を定義するが、cancel request の scope / authority / acceptance を定義しない。§6.6 は `cancelled` を分類するが、rejected、expired、timeout、in-progress signing、already signed との境界を cancel contract として固定しない。§7.6 は connection、permission、disconnect / revoke、signing、response、error の共通概念を列挙するが、cancel acknowledgement や race outcome を列挙しない。§8 の表にも cancellation validator がない。下位の SDK Design §14.2 は local wait の終了が wallet-side cancellation completion を意味せず、Signer が既に approval / signing している可能性を示しており、Signing Flow `DR-SF-007` も同じ境界を未確定としている。
- Problem impact: SDK、Signer、Browser / Mobile、handoff adapter が cancel の完了を異なる意味で扱うと、caller が `CANCELLED` を署名未生成の証明と誤認したり、`RESULT_UNKNOWN` / `SUCCEEDED` + `DELIVERY_UNKNOWN` を cancellation に潰したり、既に terminal / signing 済み request を再開・再署名したりする余地がある。これは error normalization、retry safety、response correlation および signing lifecycle の相互運用性を損なう。
- Required correction: Interface-level に、(1) cancel の発行主体と対象 request identity、(2) cancel が受理されたか・拒否されたか・既に terminal かを示す意味、(3) signing 前、`SIGNING` 中、署名済み・配送未確定、expiry / timeout との区別、(4) race 時に `CANCELLED`、`RESULT_UNKNOWN`、`SUCCEEDED` + `DELIVERY_UNKNOWN` または適用される既知 terminal outcome のどれを返すか、(5) terminal state を reopen / auto-resign しないことを固定する。具体的な API 名、ack field、transport、concurrency primitive、再送 wire protocol は下位仕様へ委譲する。
- Scope boundary: mutex、lock、queue、callback style、Promise / exception、HTTP status、JSON field、numeric error code、exact timeout、再送アルゴリズムを要求しない。Signing Flow の state machine 全体を本書へ複製せず、共通 boundary で誤解が生じない cancellation / outcome semantics のみを定義する。
- Reconfirmation: SDK、Signer、Browser / Mobile、handoff adapter が同じ request identity に対する cancel と terminal response を対応付け、cancel accepted / rejected、already terminal、in-progress signing、signed-but-undelivered および timeout / expiry を意味損失なく扱えることを確認する。

### DR-007: Handoff recipient and response channel binding

- Severity: `Major`
- Status: `Open`
- Location: [`interfaces.md`](../../design/interfaces.md) §4.1、§6.3〜§6.4、§7.3、§8、§9.2、特に行77〜88、197〜230、232〜255、320〜326、355〜375、401〜403。
- Affected operation / actor: Mobile handoff、Relay、SDK、Mobile Signer、response delivery。
- Problem: 本文は caller / source context、session、generation、request identity、`response recipient` および delivery context を binding 対象に含め、Mobile が verified handoff source を検証すると定める。しかし共通 SigningRequest / SigningResponse の semantic contract と validation table に、intended recipient / participant、必要な device / signer identity、response channel / direction を request / handoff session / generation / response correlation に binding する概念と責任が明示されていない。§7.3 は Relay を opaque とし Mobile に handoff source 等の再検証を委譲するが、recipient / channel mismatch を共通 interface outcome として固定していない。
- Evidence: `interfaces.md` §6.3 は producer / consumer と caller / source、session、signing context を列挙するが intended recipient / device / response channel の明示的な共通 concept がない。§6.4 は response recipient / delivery context を含めるが、response channel / direction と participant identity の対応を定義しない。§8 は Mobile caller / handoff context を Mobile、response を Signer に割り当てるが、recipient / channel binding の独立 validation responsibility がない。§9.2 は response recipient / delivery state の cross-request isolation を要求するが、recipient / channel の intended binding 自体を定義しない。下位 Relay Design §6、§8、§17 および Signing Flow `DR-SF-008` は participant / recipient / routing channel の重要性を示すが、下位記述だけでは共通 Interface の semantic boundary を一意に保証できない。
- Problem impact: handoff session や request identity が正しくても、別 device / signer participant または別 response channel が response を受け取る・返す解釈が adapter ごとに分かれると、response substitution、cross-device delivery、stale / wrong-channel result の誤適用が発生し得る。署名 authority 自体が Relay に移るわけではないが、request / response binding、delivery safety および signer identity の相互運用性が弱くなる。
- Required correction: Interface-level に、intended recipient / participant、device または Signer identity（公開が不要な場合は Signer-local identity を含む）、handoff session / generation、response channel / direction を、request identity、caller / source、operation、Account、Chain / Network、target、response correlation および expiry に結び付ける意味と検証責任を固定する。recipient、device、channel の mismatch、stale generation、wrong direction または別 request の response は fail-closed で terminal failure とし、response delivery の成功だけを signing success としないことを明記する。具体的な device identifier、channel field、Relay route、URI、暗号 envelope は下位仕様へ委譲する。
- Scope boundary: device fingerprint、OS identity、public API field の公開可否、Relay protocol、HTTP / WebSocket / Deep Link、cryptographic binding、routing algorithm を要求しない。`DR-SF-008` の flow 全体を重複レビューせず、Interfaces が recipient / channel semantics を表現できるかだけを補完する。
- Reconfirmation: Browser / Mobile / SDK / Relay adapter で、意図した recipient / participant と response channel / direction に限定して response を delivery し、別 device、別 session / generation、別 request または stale channel の response を fail-closed で拒否できることを確認する。

## 11. Deferred Findings

次の事項は本レビューの finding ではなく、Interfaces Design が semantic contract と責任境界を固定した上で、下位仕様・platform design・実装工程へ委譲する。

- API 名、function signature、公開 DTO / JSON Schema / field type、exact error code、numeric code、wire field、encoding、hex / Base64、byte serialization。
- 具体的な cancel method / acknowledgement schema、device identifier の wire 表現、response channel field、Relay route、HTTP / WebSocket / Deep Link、暗号 envelope、TTL、retry / lookup algorithm。ただし `DR-006` / `DR-007` の semantic boundary は委譲で失われないことが前提。
- mutex、lock、queue、callback / Promise style、state storage、Service Worker、Mobile OS lifecycle、native pointer、FFI、WASM ABI、Buffer / Uint8Array の具体実装。
- Symbol / NEM の transaction schema、canonical serialization、署名 bytes、aggregate / multisig / cosignature、message encoding および complete TransactionSummary。
- Node selection、Relay availability policy、Mobile runtime、未実装 Mobile App の E2E、release evidence および具体的な error mapping。
