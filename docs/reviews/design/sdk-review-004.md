## 5. 要約

現行 SDK 設計は、SDK を Web アプリケーションと同じ非特権文脈の要求調整役として扱い、秘密鍵 / ニーモニック / ウォレットストア / wallet-core へ直接到達させず、ブラウザ拡張機能 / モバイルアプリの信頼された Signer、信頼された UI、許可判断権限、オリジンの信頼性判断、共通4条件および署名判断権限を SDK へ移していない。この信頼境界、許可と署名承認の分離、Provider の信頼されていない検出、対応能力と認可の分離、Symbol / NEM と Mainnet / Testnet の明示、要求分離、応答対応付け、タイムアウト / ローカルキャンセルの非代替性、エラー正規化、Relay の内容を解釈しない通信経路、確定済みの結果復旧と再署名の分離、`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` の Signer 判断権限および wallet-core 境界は成立している。

一方、SDK の対応能力判定を外部アプリケーションが署名可能性と誤認しないための Mainnet リリース / 根拠判定条件の明示が、現在の SDK 設計の責任表・追跡可能性・不変条件にはない。これはセキュリティ設計の `DR-SEC-001` を SDK に複製するものではなく、SDK が経路 / 対応能力 / バージョンを見て公開利用可能性を扱う境界固有の追跡可能性不足である。

また、SDK は受け渡しの `session / intended recipient` を対応付け情報として挙げるが、端末 / Signer 参加者、応答チャネル / 方向およびそれらを選択済みの経路から応答まで保持・検証する SDK 調整役 / 対応付けの責任を一意に記述していない。共通インターフェース / 署名フローの `DR-007` / `DR-SF-008` は共通の契約の追加対応であり、今回の `DR-003` はその契約を SDK が失わず、最初に届いた応答を採用しないための SDK 固有の適用責任である。

## 8. 任意の改善

### `DR-002` — Mainnet 対応能力とリリース証跡判定条件の SDK 境界

- **重要度:** `Minor`
- **状態:** `New / Open`
- **対象箇所:** [`sdk.md`](../../design/sdk.md) §4.2、§7.3〜§7.4、§18、§22、§25（特に行69、75、161、258〜266、510〜526、588〜607、639〜655）
- **問題:** SDK 設計は Symbol / NEM と Mainnet / Testnet を明示的に区別し、Provider 対応能力 / バージョン / チェーン / ネットワークを確認する。しかし、Mainnet 署名対応能力が現在のリリースと適用リリース / 根拠ポリシーを満たした信頼された Signer だけで有効になること、SDK の利用可能性、経路、Provider 対応能力、接続、許可、バージョン互換性、Relay / モバイル利用可能性または応答がその判定条件の代替にならないことを、SDK の対応能力判定・不変条件・追跡可能性として明示していない。§23 の `release evidence` 委譲も具体的責任主体と Mainnet 安全側での終了の意味を SDK 側へ戻していない。
- **影響:** 下流実装者が SDK の対応能力 / 互換性判定を Mainnet 署名対応能力の有効化・広告条件として扱い、判定条件が欠落、無効な、期限切れ、不整合の、検証不能のまたは不明の経路を `available` と公開する余地が残る。信頼された Signer 側の最終署名判断権限が直ちに SDK へ移ることを示すものではないが、公開利用可能性と Mainnet リリース assurance の境界が曖昧になり、未達成判定条件の提供を利用者が署名可能と誤認し得るため軽微とする。
- **根拠:** [`docs/requirements/sdk.md`](../../requirements/sdk.md) §4.2 は Mainnet 対応能力をリリース判定を満たす Signer / ビルドに限定し、判定不能時を利用不能 / 未対応のとする。[`docs/specifications/sdk.md`](../../specifications/sdk.md) §3、§6.2、§6.5 は信頼された Signer / リリースセキュリティ判断権限を判定条件責任主体とし、経路 / 対応能力 / 接続 / 応答を代替にしないことを定義している。[`docs/adr/0001-mainnet-evidence-lite.md`](../../adr/0001-mainnet-evidence-lite.md) とアーキテクチャ §17.1 もリリース証跡の責任主体を SDK 外に置く。一方、対象 §25 の追跡可能性にはこの Mainnet 判定条件の行がなく、対象本文の対応能力 / バージョン記述から一意に追跡できない。最新 [`security-design-review-005.md`](./security-design-review-005.md) の `DR-SEC-001` はセキュリティ設計本文自身の同じ上位追跡可能性問題であり、今回の指摘は SDK の公開対応能力境界に限定する。
- **影響対象要件 / 不変条件:** `SDK-FR-001`、`SDK-PLAT-005`、`SDK-COMP-001`〜`004`、`SDK-NFR-004`、`SDK-AC-001`、`SDK-AC-010`、`SDK-AC-011`、および SDK セキュリティ上の不変条件 2〜4、13。
- **必須修正:** SDK 設計に、Mainnet 署名対応能力は適用されるリリース / 根拠判定条件を信頼された Signer / リリースセキュリティ判断権限が成立させた場合だけ有効であり、SDK は判定条件の判断権限 / 評価器 / enabler ではないことを追加する。SDK が経路、Provider 対応能力、バージョン、接続、許可、Relay / モバイル利用可能性または応答から Mainnet 対応能力を推測・補完・昇格・迂回してはならず、判定条件を確認できない場合は既存の利用不能 / 未対応の / Signer が生成した結果対応付けを維持することを明示する。Testnet 専用の安全な継続を不必要に禁止しないことも示す。
- **対象範囲境界:** 根拠スキーマ、信頼された鍵、ビルド埋め込み、評価器、リリースコマンド、実行環境実装、パッケージメタデータ、具体的エラーコードおよびプラットフォーム対応能力評価器は要求しない。これらはリリースポリシー、仕様およびプラットフォーム / Signer の下位責任である。
- **完了 / 再確認:** SDK の対応能力 / バージョン / 利用可能性説明、SDK セキュリティ上の不変条件および §25 追跡可能性から、Mainnet 判定条件の責任主体、代替禁止、判定不能時の安全側での終了、Testnet 専用の扱いおよび下位リリースポリシーへの委譲を確認できること。

### `DR-003` — 受け渡し受信者 / 端末 / 応答チャネルの SDK 対応付け責任

## 9. 解消済みの指摘

### `DR-001` — 解消済み

前回 `sdk-review-002` の `DR-001` は、Relay / リモート受け渡し失敗を `result unknown` と直接対応付け得る記述と、`DELIVERY_UNKNOWN` の責任主体不足を指摘した。現行 SDK 設計は次を満たす。

- §15.1〜§15.2 が通信経路 / Relay 失敗を通信経路レベルのエラー分類とし、`RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` を通常のエラー分類から分離している。
- §15.1、§17、§21〜§22 が、`RESULT_UNKNOWN` は Signer の署名生成不確実性、`DELIVERY_UNKNOWN` は Signer 側の既知の署名済み結果配送不確実性に限ることを明示している。

- 既知の署名済み結果の再配送 / 再送 / 取得 / 照会と署名再試行 / 再署名を分離し、通信経路失敗、不明、拒否、セキュリティ失敗、許可失敗から自動再署名 / 代替経路を行わない。

`DR-001` の再発はなく、状態は `Resolved` とする。過去 `sdk-review-001` の旧式の分類体系には正式な指摘 ID がないため、追加の解消済み / 再発状態は作成しない。

## 16. 残存リスクと未決定事項

- `DR-003` が未解消のままでは、共通の受け渡し契約が確定しても、SDK アダプター / 対応付けが意図した受信者、端末 / Signer 参加者、応答チャネル / 方向 / 世代を要求から応答まで保持する責任を実装者が再構成する必要がある。誤った応答の採用を防ぐため、下流設計・実装前に追跡する。
- `DR-002` が未解消のままでは、SDK の対応能力 / 利用可能性表示と Mainnet リリース証跡判定条件の関係が SDK 本文から追跡しにくい。信頼された Signer / リリースセキュリティ判断権限の判定条件を SDK の経路 / バージョン / 対応能力判定が代替しないことを明文化する。
- 共通 `DR-SF-007` / `DR-006` は署名中キャンセルの競合 / 受領確認 / 終端結果を確定していない。SDK はローカルキャンセルとウォレット側のキャンセル完了を混同しないが、公開終端対応付けは共通契約の解消に依存する。
- 共通 `DR-SF-008` / `DR-007` は意図した受信者 / 端末 / 応答チャネルの共通契約を未決としている。`DR-003` と併せて解消する必要があるが、SDK が厳密な通信上の / 証明 / OS 仕組みを決めるものではない。
- モバイル実装、実機ライフサイクル、OS 保護された保存領域、E2E、実行環境強制、provider 選択ポリシー、バージョン対応表、リリース証跡補助ツールは未検証または下位責任主体の範囲である。現在のワークスペースにモバイル実装がないことを実装済みとは扱っていない。
