## 5. Summary

現行 SDK Design は、SDK を Web Application と同じ非特権 context の request coordinator として扱い、private key / Mnemonic / Wallet Store / wallet-core へ直接到達させず、Browser Extension / Mobile App の trusted Signer、trusted UI、permission authority、Origin authority、共通4条件および signing authority を SDK へ移していない。この trust boundary、permission と signing approval の分離、Provider の untrusted discovery、capability と authorization の分離、Symbol / NEM と Mainnet / Testnet の明示、request isolation、response correlation、timeout / local cancellation の非代替性、error normalization、Relay の opaque transport、known-result recovery と re-sign の分離、`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` の Signer authority および wallet-core boundary は成立している。

一方、SDK の capability 判定を外部アプリケーションが署名可能性と誤認しないための Mainnet release / evidence gate の明示が、現在の SDK Design の責任表・traceability・invariant にはない。これは Security Design の `DR-SEC-001` を SDK に複製するものではなく、SDK が route / capability / version を見て公開 availability を扱う境界固有の traceability gap である。

また、SDK は handoff の `session / intended recipient` を correlation 情報として挙げるが、device / signer participant、response channel / direction およびそれらを selected route から response まで保持・検証する SDK coordinator / correlator の責任を一意に記述していない。共通 Interfaces / Signing Flow の `DR-007` / `DR-SF-008` は common contract の follow-up であり、今回の `DR-003` はその contract を SDK が失わず、最初に届いた response を採用しないための SDK 固有の適用責任である。

## 8. Optional Improvements

### `DR-002` — Mainnet capability と release evidence gate の SDK 境界

- **Severity:** `Minor`
- **Status:** `New / Open`
- **Location:** [`sdk.md`](../../design/sdk.md) §4.2、§7.3〜§7.4、§18、§22、§25（特に行69、75、161、258〜266、510〜526、588〜607、639〜655）
- **Problem:** SDK Design は Symbol / NEM と Mainnet / Testnet を明示的に区別し、Provider capability / version / Chain / Network を確認する。しかし、Mainnet signing capability が current release と適用 release / evidence policy を満たした trusted Signer だけで有効になること、SDK の availability、route、Provider capability、connection、permission、version compatibility、Relay / Mobile availability または response がその gate の代替にならないことを、SDK の capability 判定・invariant・traceability として明示していない。§23 の `release evidence` 委譲も具体的 owner と Mainnet fail-closed の意味を SDK 側へ戻していない。
- **Impact:** 下流実装者が SDK の capability / compatibility 判定を Mainnet signing capability の有効化・広告条件として扱い、gate が missing、invalid、expired、inconsistent、unverifiable または unknown の経路を `available` と公開する余地が残る。trusted Signer 側の最終署名 authority が直ちに SDK へ移ることを示すものではないが、公開 availability と Mainnet release assurance の境界が曖昧になり、未達成 gate の提供を利用者が署名可能と誤認し得るため Minor とする。
- **Evidence:** [`docs/requirements/sdk.md`](../../requirements/sdk.md) §4.2 は Mainnet capability を release gate を満たす Signer / build に限定し、判定不能時を unavailable / unsupported とする。[`docs/specifications/sdk.md`](../../specifications/sdk.md) §3、§6.2、§6.5 は trusted Signer / release security authority を gate owner とし、route / capability / connection / response を代替にしないことを定義している。[`docs/adr/0001-mainnet-evidence-lite.md`](../../adr/0001-mainnet-evidence-lite.md) と Architecture §17.1 も release evidence の owner を SDK 外に置く。一方、対象 §25 の traceability にはこの Mainnet gate の行がなく、対象本文の capability / version 記述から一意に追跡できない。最新 [`security-design-review-005.md`](./security-design-review-005.md) の `DR-SEC-001` は Security Design 本文自身の同じ上位 traceability 問題であり、今回の finding は SDK の公開 capability boundary に限定する。
- **Affected requirements / invariants:** `SDK-FR-001`、`SDK-PLAT-005`、`SDK-COMP-001`〜`004`、`SDK-NFR-004`、`SDK-AC-001`、`SDK-AC-010`、`SDK-AC-011`、および SDK Security Invariants 2〜4、13。
- **Required correction:** SDK Design に、Mainnet signing capability は適用される release / evidence gate を trusted Signer / release security authority が成立させた場合だけ有効であり、SDK は gate の authority / evaluator / enabler ではないことを追加する。SDK が route、Provider capability、version、connection、permission、Relay / Mobile availability または response から Mainnet capability を推測・補完・昇格・迂回してはならず、gate を確認できない場合は既存の unavailable / unsupported / Signer-originated result mapping を維持することを明示する。Testnet-only の安全な継続を不必要に禁止しないことも示す。
- **Scope boundary:** evidence schema、trusted key、build embedding、evaluator、release command、runtime implementation、package metadata、具体的 error code および platform capability evaluator は要求しない。これらは release policy、Specification および platform / Signer の下位責任である。
- **Completion / reconfirmation:** SDK の capability / version / availability 説明、SDK Security Invariants および §25 traceability から、Mainnet gate の owner、代替禁止、判定不能時の fail-closed、Testnet-only の扱いおよび下位 release policy への委譲を確認できること。

### `DR-003` — handoff recipient / device / response channel の SDK correlation 責任

- **Severity:** `Major`
- **Status:** `New / Open`
- **Location:** [`sdk.md`](../../design/sdk.md) §9.3 の Origin / handoff 表、§11.2、§12、§14、§17、§20、§22.9〜§22.10、§25（特に行305〜310、346〜378、430〜434、492〜510、598〜605、645〜653）
- **Problem:** SDK Design は `handoff session / intended recipient` を correlation 情報として扱い、Provider / session / connection context、request identity、operation、Account、Chain / Network、signer context、target binding を response correlation に要求している。しかし、handoff の intended recipient / participant、対象 device または signer identity、response channel / direction / generation を、SDK が selected transport の request context から response acceptance まで保持し、対応しない response を拒否するという SDK 固有の責任が一意に書かれていない。`§23` は具体 handoff schema を下位へ委譲するが、semantic binding を SDK coordinator / adapter / correlator が失わないという boundary まで定めていない。
- **Impact:** 同じ session や Provider context に属する複数の Mobile device、participant、response channel または direction が存在する実装で、意図した recipient 以外から届いた valid-looking response、古い channel の response または最初に届いた response を現在の request の結果として採用する余地が残る。これは request / response / signer / recipient binding と handoff integrity を弱め、外部アプリケーションへ誤った signed result または誤った terminal outcome を返し得るため Major とする。SDK が device identity の最終証明 authority になることを要求するものではない。
- **Evidence:** [`docs/requirements/sdk.md`](../../requirements/sdk.md) の `SDK-FR-008`、`SDK-PLAT-003`、`SDK-SEC-005`〜`007`、`SDK-AC-003`、`SDK-AC-005`〜`007` は元要求、Signer、Account、Chain / Network、handoff source、Relay、結果対応および context isolation を要求する。[`docs/design/interfaces.md`](../../design/interfaces.md) と [`interfaces-review-005.md`](./interfaces-review-005.md) の `DR-007` は common contract として intended recipient / participant、device / signer identity、response channel / direction の欠落を Open としている。[`docs/design/signing-flow.md`](../../design/signing-flow.md) と [`signing-flow-review-005.md`](./signing-flow-review-005.md) の `DR-SF-008` も同じ binding を共通 flow の follow-up としている。対象 §12 の相関最小列は Provider / connection / session、Account、Chain / Network、signer context、target であり、recipient / device / channel / direction の SDK applicability が欠けている。下流 [`web-transaction-handoff-spec.md`](../../specifications/web-transaction-handoff-spec.md) には generation、direction、session、recipient および response route の具体契約があるが、これを対象 Design の責務境界へ逆流させるのではなく、SDK がその意味を保持する必要性だけを確認した。
- **Affected requirements / invariants:** `SDK-FR-005`、`SDK-FR-008`、`SDK-FR-009`、`SDK-FR-010`、`SDK-PLAT-003`、`SDK-SEC-004`〜`007`、`SDK-AC-003`、`SDK-AC-005`〜`007`、および SDK Security Invariants 6、9、10、12、15。
- **Required correction:** SDK Design の request construction / transport / correlation boundary に、common contract が定める範囲の intended recipient / participant、必要な device / signer identity、response channel / direction / generation を logical request context として保持し、selected route へ binding して渡し、response acceptance でも request identity、session、generation、recipient、channel、direction、operation、Account、Chain / Network、target および freshness と照合することを追加する。対応を確認できない response、別 recipient / device / channel の response、ambiguous response、late response は success にせず安全側に終了し、「最初に返った response」を採用しない。最終的な recipient / source / device authenticity の検証 authority は Mobile / Signer / Relay の既存責任に残し、SDK は semantic context の保持・dispatch・correlation を担うことを明示する。
- **Scope boundary:** device attestation、recipient identifier の exact field、response channel の wire representation、direction encoding、cryptographic proof、Relay ACK / cancel API、Mobile OS API、queue / lock / Promise 実装および common Interfaces の contract 自体は要求しない。`DR-007` / `DR-SF-008` の共通契約を解消する作業と、SDK がその契約を消失させない作業を分離する。
- **Completion / reconfirmation:** SDK の logical request / correlation context、local / remote adapter boundary、invariant および traceability に recipient / participant、device / signer identity、response channel / direction / generation の保持・照合・不一致時の fail-closed が明記され、common `DR-007` / `DR-SF-008` の exact contract を独自に再定義していないこと。

## 9. Resolved Findings

### `DR-001` — Resolved

前回 `sdk-review-002` の `DR-001` は、Relay / remote handoff failure を `result unknown` と直接対応付け得る記述と、`DELIVERY_UNKNOWN` の owner 不足を指摘した。現行 SDK Design は次を満たす。

- §15.1〜§15.2 が transport / Relay failure を transport-level error category とし、`RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` を通常の error category から分離している。
- §15.1、§17、§21〜§22 が、`RESULT_UNKNOWN` は Signer の signing generation uncertainty、`DELIVERY_UNKNOWN` は Signer-side の known signed result delivery uncertainty に限ることを明示している。
- SDK / Provider / Relay / transport / timeout / response absence / disconnect / page lifecycle loss から両 disposition を生成・推測・確定せず、取得済みの Signer-originated disposition だけを correlation 後に意味不変で伝達する。
- known signed result の redelivery / resend / retrieval / lookup と signing retry / re-sign を分離し、transport failure、unknown、rejection、security failure、permission failure から automatic re-sign / fallback を行わない。

`DR-001` の再発はなく、Status は `Resolved` とする。過去 `sdk-review-001` の legacy taxonomy には formal finding ID がないため、追加の Resolved / Reopened status は作成しない。

## 10. Upstream Feedback

新規の上流 Requirements / Architecture / Security Design の欠落として扱う formal feedback はない。Mainnet gate は Requirements、Architecture、ADR、release evidence および SDK Specification に存在し、handoff recipient / channel は Interfaces / Signing Flow の `DR-007` / `DR-SF-008` として既に common follow-up 化されている。

最新の上位 review artifact にある次の Open finding は、SDK に機械的に複製していない。

- Security Design `DR-SEC-001` / `DR-SEC-002`: Security Design 本文の Mainnet traceability と Relay E2E / credential separation。SDK では `DR-002` を公開 capability boundary に限定した。
- Architecture `DR-003`: Message signing の Architecture open item と downstream Specification の同期。SDK の operation 分離は現行本文で成立している。
- Signing Flow `DR-SF-007` / `DR-SF-008`、Interfaces `DR-006` / `DR-007`: 共通 cancellation race と handoff binding contract。SDK では既存の非権威・correlation 境界を確認し、SDK 固有の binding 保持だけを `DR-003` とした。

## 11. Deferred Findings

- `DR-SF-007` / `DR-006` は、SIGNING 中 cancellation の authority、acknowledgement、already completed / already signing、terminal state と race outcome の共通 contract である。SDK は local wait の終了を wallet-side cancellation completion と同一視せず、late result を別 request へ適用しないため、共通 finding の内容を再指摘しない。exact public terminal mapping は common Interfaces / Signing Flow / downstream Specification の owner で確定する。
- `DR-SF-008` / `DR-007` は、recipient / participant、device / signer identity、response channel / direction の common contract である。`DR-003` はその exact contract を SDK が保持・correlate する責務の不足であり、common finding 自体の重複ではない。
- Provider の fake / conflicting / multiple selection policy、cancellation protocol、transport selection、exact timeout / expiry、retry timing、error code、version matrix、cache schema、runtime support、cosignature scope および handoff wire schema は Requirements の OPEN または下位 Specification へ委譲する。SDK Design は ambiguous provider / unsupported capability / stale state を安全側に扱うため、これらを新規 finding としない。
- request mutation については、SDK が request identity、target binding、operation、Account、Chain / Network、content change mismatch を correlation で確認し、identity collision / content change を安全側に終了する方針が §11〜§12 にある。exact immutable representation、digest、canonical serialization は下位 contract の責任であり、今回の Design finding にはしない。
- `DR-SEC-002` に関連する E2E secret と Relay transport credential の exact ownership / wire detail は Handoff / Relay Specification に委譲される。対象 SDK は secret、credential raw value、Relay privileged interface を要求・保持・出力しないため、SDK 固有 finding にはしない。
- concrete TypeScript API、class / function、Promise / event implementation、browser / OS API、cryptographic parameter、JSON / wire format、ABI、lock / queue / mutex および test case implementation は Design phase の対象外である。

## 16. Remaining Risks and Open Decisions

- `DR-003` が未解消のままでは、common handoff contract が確定しても、SDK adapter / correlator が intended recipient、device / signer participant、response channel / direction / generation を request から response まで保持する責任を実装者が再構成する必要がある。誤った response の採用を防ぐため、下流設計・実装前に追跡する。
- `DR-002` が未解消のままでは、SDK の capability / availability 表示と Mainnet release evidence gate の関係が SDK 本文から追跡しにくい。trusted Signer / release security authority の gate を SDK の route / version / capability 判定が代替しないことを明文化する。
- 共通 `DR-SF-007` / `DR-006` は SIGNING 中 cancellation の race / acknowledgement / terminal outcome を確定していない。SDK は local cancellation と wallet-side cancellation completion を混同しないが、公開 terminal mapping は共通 contract の解消に依存する。
- 共通 `DR-SF-008` / `DR-007` は intended recipient / device / response channel の共通 contract を Open としている。`DR-003` と併せて解消する必要があるが、SDK が exact wire / attestation / OS mechanism を決めるものではない。
- Mobile 実装、実機 lifecycle、OS protected storage、E2E、runtime enforcement、provider selection policy、version matrix、release evidence tooling は未検証または下位 owner の範囲である。現在の workspace に Mobile 実装がないことを実装済みとは扱っていない。
