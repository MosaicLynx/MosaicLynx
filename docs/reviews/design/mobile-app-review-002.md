## 4. レビュー結果

**レビュー判定条件: `REVISE DESIGN`**

現行モバイルアプリ設計は、外部入力を信頼されていないとする信頼境界、モバイル信頼された UI、Relay の内容を解釈しない通信経路、wallet-core の秘密・生の署名境界、ライフサイクル無効化、並行する要求分離、`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` および自動代替経路禁止を概ね維持している。

しかし、モバイル設計自身に、共通4条件を独立した判定条件として成立・再確認・結果帰属する記述、v1 `MESSAGE_SIGN` の構造化された契約、署名時4条件を含む成功結果との結び付け、Mainnet 判定条件の高位安全側での終了不変条件、および要求された責務単位の直接追跡可能性が不足している。重大 2件、主要 2件、軽微 1件を記録する。

## 5. 要約

- `DR-001: UNRESOLVED`。`Authentication`、`Signing-capable unlock`、アカウントの利用認可、利用者による明示的な承認の4条件が、モバイル信頼されたホストの独立した必須判定条件として本文に確定していない。`AUTHORIZED`、署名前、成功、ロック / ロック解除の各記述も4条件を一貫して表さない。
- `DR-002: UNRESOLVED`。モバイル v1 の `MESSAGE_SIGN` が操作として明示されず、構造化されたメッセージのドメイン、目的、ノンス、発行された / 期限切れ、メッセージ単位のリプレイおよび同一内容検査モデルの結び付け、生の / 内容検査できない代替経路禁止が確定していない。
- `DR-003: UNRESOLVED`。応答結び付けは要求、送信元、プロファイル / アカウント、チェーン / ネットワーク、操作、対象ダイジェストを含むが、署名主体識別情報、署名時点4条件および承認文脈を成功条件として明示していない。
- `DR-004: UNRESOLVED`。Mainnet 判定条件の存在・未達成時の対応能力無効化・判定不能時安全側での終了がモバイル設計のセキュリティ上の不変条件として明示されず、§3.3 / §27 で Mainnet 判定条件条件全体が未決に戻っている。
- `DR-005: UNRESOLVED`。§28 は8つの広い資料対応に留まり、呼び出し元の信頼性判断、4条件、アカウントの利用認可、構造化されたメッセージ、結果不明 / 配送不明、代替経路、wallet-core、Mainnet 等について、責務・不変条件・責任主体・下流境界の直接対応を網羅していない。

上記以外では、モバイル信頼されたホストを署名主体とする基本方向、外部アプリ / SDK / Relay / 受け渡しメタデータの判断権限を持たないこと、プロファイル / アカウントと wallet-core 識別情報の分離、意味上の内容検査、信頼された UI、ライフサイクル、画面露出の評価責任、安全な保存領域境界、並行する要求、不明結果、秘密情報の分離および代替経路禁止に重大な回帰は確認されなかった。

- `DR-001`: モバイル信頼されたホストを共通署名判定条件の唯一の署名主体側の処理の調整責任主体と明記し、4条件を独立必須として、同一要求 / 送信元 / セッション / プロファイル / アカウント / チェーン / ネットワーク / 操作 / 対象 / 鮮度に結び付けする。署名前、成功結果、失効・古くなった・不明・ロック済み時の安全側での終了、および接続、許可、対応能力、セッション、通常の `UNLOCKED`、前回認証、OS ロック解除、SDK / Relay、dApp 自己申告、wallet-core パスワード / ストア検証 / 署名成功の非代替を明記する。
- `DR-002`: モバイル v1 の `MESSAGE_SIGN` を構造化メッセージ署名として明示し、検証済み / 未検証の送信元状態、プロファイル / アカウント、チェーン / ネットワーク、操作、ドメイン、目的、メッセージ、ノンス、発行された / 期限切れ、要求鮮度、リプレイ状態および4条件を結び付けする。署名主体自身の同一信頼されたモデルから内容検査と署名入力を導出し、生の任意の / 内容検査できない代替経路、文脈間のリプレイ、期限切れ / 重複 / リプレイ署名を禁止する。厳密な形式は下流仕様に委譲してよい。
- `DR-003`: 成功結果の必要条件に元の要求、送信元、署名主体識別情報、プロファイル、アカウント、チェーン / ネットワーク、操作、厳密な対象 / 信頼されたダイジェスト、署名時点の4条件および承認文脈を追加する。文脈消失、古くなった、失効済み、ロック済み、不一致、不明は成功にせず、`RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` を維持し、配送失敗を再署名根拠にしないことを明記する。
- `DR-004`: Mainnet 対応能力は現在のリリースポリシー / 根拠判定条件の成立時だけ有効、判定条件未達成・期限切れ・不整合・判定不能時は Mainnet 署名を無効化する、と高位不変条件として固定する。厳密な OS 条件、根拠形式、実行環境強制は下流へ委譲し、Testnet 専用継続の余地は維持する。
- `DR-005`: §28 を、少なくとも呼び出し元 / オリジンまたは受け渡し送信元、判断権限を持たないこと、4条件、プロファイル / アカウントに関する判断権限、構造化されたメッセージ、チェーン / ネットワーク、アグリゲート / 連署署名、結果 / 不明、代替経路、wallet-core 境界、Mainnet 判定条件ごとに、上位要求 / 設計、本文適用箇所、下流契約および責任主体を対応付ける表へ補強する。

### DR-001: 未解消 — モバイルの共通署名ゲート4条件

- ID: `DR-001`
- 重要度: `Critical`
- 対象: [`mobile-app.md`](../../design/mobile-app.md) §4、§5.5〜§5.8、§10、§12.3、§14、§16、§24。
- 事実 / 条件: §4 は利用者の明示的な承認 / 拒否と端末認証を別条件として取得すると記載するが、認証、署名可能な状態へのロック解除、対象プロファイル / チェーン / ネットワーク / アカウントのアカウントの利用認可、利用者による明示的な承認の4条件を列挙していない。§14 の `AUTHORIZED` は署名意図の明示だけ、§16 の署名前条件は明示的な承認・端末認証・対象 / 文脈再検証だけであり、アカウントの利用認可と署名可能ロック解除の独立性が確認できない。§24 も端末認証と承認を分けるだけで、モバイル信頼されたホストが4条件の唯一の処理の調整責任主体であること、4条件を署名前と結果時に再確認することを一貫して定めていない。
- 根拠: [共通要件 CR-016 / CR-AC-017](../../requirements/requirements.md)、[アーキテクチャ §6.9](../../design/architecture.md)、[署名フロー §4 / §16 / §20](../../design/signing-flow.md)、[インターフェース §9](../../design/interfaces.md) は、4条件の独立性、同一結び付け、署名前、結果検証、失効時安全側での終了および接続 / 許可 / セッション / 通常の `UNLOCKED` / wallet-core 処理の非代替を要求する。
- 問題: モバイル設計の各フローが、端末認証、許可 / ペアリング、アカウント選択、通常の `UNLOCKED`、OS ロック解除、wallet-core パスワード / ストア検証または wallet-core 署名成功を、アカウントの利用認可・署名可能な状態へのロック解除・明示的な承認と取り違えないための共通判定条件契約を直接示していない。SDK、Relay、外部アプリ、OS 受け渡しメタデータまたは wallet-core が判定条件を成立・変更・免除・迂回できない境界も、モバイルの判定条件責任主体として明示されていない。
- 影響: 下流実装が「認証成功」「アプリがロック解除済み」「アカウントが選択された」「wallet-core が署名した」ことだけで署名可能と解釈し、別要求 / 呼び出し元 / プロファイル / アカウント / チェーン / ネットワーク / 操作 / 対象 / 鮮度に承認・認証・認可を流用するセキュリティ境界の不整合が生じる。

### DR-002: 未解消 — モバイル v1 の構造化された `MESSAGE_SIGN`

- ID: `DR-002`
- 重要度: `Critical`
- 対象: [`mobile-app.md`](../../design/mobile-app.md) §5.6、§12.2〜§12.3、§20、§24、§27。
- 事実 / 条件: 現行モバイル設計に `MESSAGE_SIGN` という操作名がない。§5.6 と§12.2 はトランザクション / メッセージを同じ一般的な列挙で扱い、メッセージのドメイン、目的、ノンス、発行された / 期限切れ、メッセージ単位のリプレイ、ドメイン間の / 目的間のリプレイまたはトランザクションとは別の結果契約を同一文脈として定めていない。署名主体自身が構造化されたメッセージから内容検査と署名入力を生成すること、解析失敗 / 内容検査できないメッセージの生の代替経路を禁止することも明記されていない。
- 根拠: [署名フロー §6.1 / §14](../../design/signing-flow.md) は v1 `MESSAGE_SIGN`、メッセージ文脈、署名主体内容検査、4条件、署名前、生バイト列代替経路禁止を定義する。[インターフェース仕様 §9.4](../../specifications/interfaces.md)、[署名プロトコル](../../specifications/signing-protocol.md) および [Web トランザクション受け渡し](../../specifications/web-transaction-handoff-spec.md) は構造化されたメッセージ、メッセージリプレイ、署名済み結果対応を下流契約として定める。厳密なノンス形式、シリアライズ、有効期間は今回要求していない。
- 問題: モバイルが一般的なメッセージペイロードを受け付けるだけの設計に留まり、ブラウザと共通の構造化メッセージ署名対応能力がモバイル v1 で確定していない。外部アプリの表示文言と実際の署名バイト列が分離したり、内容検査できない生バイト列、期限切れ・重複・リプレイまたはオリジン間の / ドメイン / 目的要求が署名可能になったりする余地がある。
- 影響: 利用者が確認した意味と実際に署名されるメッセージの対応を検証できず、トランザクション署名へ誤分類することによるリプレイ、意図外署名および同一メッセージの再利用が生じる。
- 最低限必要な修正: モバイル v1 の `MESSAGE_SIGN` を構造化されたメッセージ操作として明示する。検証済み / 未検証の送信元状態、プロファイル / アカウント、チェーン / ネットワーク、操作、ドメイン、目的、メッセージ内容、ノンス、発行された / 期限切れ、要求鮮度、リプレイ状態および共通4条件を同一メッセージ署名文脈に結び付けし、署名主体が同じ信頼されたモデルから内容検査と署名入力を導出することを定める。任意の生バイト列、解析失敗 / 内容検査できない生の代替経路、オリジン間の / ドメイン間の / 目的間のリプレイ、期限切れ / 重複 / リプレイ署名を禁止し、署名前と結果との結び付けを適用する。厳密なフィールド / 通信上の / シリアライズは下流へ委譲してよい。
- 再確認条件: モバイル設計に `MESSAGE_SIGN` の対応能力と構造化された契約が明記され、指定された全文脈が同一結び付けに含まれることを確認する。署名主体内容検査と署名入力が同一信頼されたメッセージモデルから導出され、生の / 内容検査できない代替経路がなく、期限切れ・重複・リプレイ・文脈間のリプレイが拒否され、4条件・署名前・結果検証が適用されることを確認する。

### DR-003: 未解消 — 成功結果の署名時の結び付け

- ID: `DR-003`
- 重要度: `Major`
- 対象: [`mobile-app.md`](../../design/mobile-app.md) §8.3、§12.3、§14、§15.4、§22。
- 事実 / 条件: §8.3 の応答はセッション、要求識別情報、送信元、プロファイル / アカウント、チェーン / ネットワーク、操作、対象ダイジェストを結び付けするが、署名主体識別情報、署名時点の認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認および承認文脈を成功条件として列挙していない。§14 の `SUCCEEDED` は署名結果と元要求の対応確認に留まる。一方、`RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` の分離、古くなった応答の別要求への配送禁止および配送失敗の再署名禁止は記載されている。
- 根拠: [署名フロー §20](../../design/signing-flow.md) は成功結果に元の要求、呼び出し元、署名主体、プロファイル、アカウント、チェーン / ネットワーク、対象識別情報、署名時4条件および承認文脈を要求する。[インターフェース設計](../../design/interfaces.md) と [インターフェース仕様](../../specifications/interfaces.md) は結果検証、受信者、不明 / 配送の意味を定める。
- 問題: Mobile-level 成功が wallet-core の返却結果または対象ダイジェストの確認だけで成立するように読め、署名時の判定条件文脈と信頼された承認の帰属を安全に検証できない場合の成功禁止が明確でない。
- 影響: 文脈消失した、プロファイル / アカウント切り替え、送信元不一致、ロック済み、認可失効、承認置き換えまたは wallet-core 結果の取り違え後に、別要求や別受信者へ署名成功を返す可能性がある。配送不明時の再署名禁止はあっても、生成済み結果自体の安全な帰属が不足する。
- 最低限必要な修正: 成功の必要条件に元の要求、検証済み送信元、署名主体識別情報、プロファイル、アカウント、チェーン / ネットワーク、操作、厳密な対象 / 信頼されたダイジェスト、署名時点の4条件および承認文脈を追加する。文脈消失、古くなった、失効済み、ロック済み、呼び出し元 / プロファイル / アカウント / チェーン / ネットワーク / 対象不一致、署名時の文脈不明または結果処理結果の区分不明は成功にしない。`RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` を維持し、配送失敗は既存結果の再送 / 照会以外の再署名根拠にしない。
- 再確認条件: モバイル信頼されたホストが wallet-core 結果をそのまま転送せず、上記全文脈と署名時の 4条件を結果検証で確認することを確認する。ページ遷移 / ライフサイクル / 送信元消失後に旧結果を別受信者へ返さず、`RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` を混同せず、配送失敗から同一対象を再署名しないことを確認する。

### DR-004: 未解消 — Mainnet 判定条件の高位安全側での終了不変条件

- ID: `DR-004`
- 重要度: `Major`
- 対象: [`mobile-app.md`](../../design/mobile-app.md) §3.3、§23、§27、§28。
- 事実 / 条件: §3.3 はハードウェアで保護された保護、非対応端末の代替経路、Mainnet 対応能力への適用条件を要件 / リリース判定の未決事項として扱い、§27 は「直接ハードウェア署名の対応能力および Mainnet 判定条件条件」を未決にしている。§23 と§28 は Mainnet 判定条件を参照するが、適用リリースポリシーの判定条件未達成・判定不能時にモバイル Mainnet 署名対応能力を無効化する高位必須条件をセキュリティ上の不変条件または責務表で明示していない。
- 根拠: [共通要件 CR-NFR-006 / CR-AC-008](../../requirements/requirements.md) は判定条件未達成・判定不能時の Mainnet 対応能力無効化を MUST とする。[アーキテクチャ](../../design/architecture.md) と [ADR 0001](../../adr/0001-mainnet-evidence-lite.md) はリリース証跡の判定条件と安全側での終了を定める。[Web トランザクション受け渡し](../../specifications/web-transaction-handoff-spec.md) はモバイル v1 の具体的な対応能力 / リリース条件を下流で具体化している。

- 最低限必要な修正: Mainnet 対応能力は適用中のリリースポリシー / 根拠判定条件が成立した場合だけ有効、必須根拠の欠落・不整合・期限切れ・署名検証失敗・信頼された鍵不備・ポリシー判定不能では Mainnet 署名を無効化する、とモバイルの高位不変条件として §23 / §24 / §28 に明記する。厳密な根拠形式、OS API、実行環境強制およびプラットフォーム対応表は下流に委譲し、Testnet 専用継続は許可する。
- 再確認条件: モバイル設計が Mainnet 判定条件の存在、リリース / 根拠責任主体、未達成・判定不能時の対応能力 disable および安全側での終了を明示し、§27 の未決が厳密なプラットフォーム / 根拠詳細に限定されていることを確認する。ADR、要件、リリースポリシーと矛盾せず、OS ロック解除、ハードウェア signal またはアプリストア配布成功だけで判定条件を代替しないことを確認する。

## 15. 残存リスクと未決定事項

- 共通4条件がモバイル設計の各状態・署名前・成功に明示されないまま下流へ進むと、端末認証、通常の `UNLOCKED`、許可、OS ロック解除、wallet-core パスワード / ストア検証または wallet-core 署名成功がアカウントの利用認可や明示的な承認の代替として実装されるリスクがある。
- `MESSAGE_SIGN` が一般的なメッセージとして残ると、トランザクションとメッセージの意味・リプレイ境界が混同され、表示モデルと署名入力の分離、生の / 内容検査できない代替経路、ドメイン間の / 目的間のリプレイの実装解釈が発生する。
- 成功結果が署名時の判定条件文脈と承認文脈を持たないと、wallet-core の成功結果または配送成功を Mobile-level 成功と誤帰属するリスクがある。
- Mainnet の厳密な OS / 根拠条件は下流で決定してよいが、Mainnet 判定条件の存在と未達成・判定不能時の対応能力 disable はモバイル設計で未決に戻してはならない。
- `docs/specifications/mobile-app.md` は存在しない。モバイル固有の後続仕様を新設する場合も、共通4条件、構造化されたメッセージ、結果との結び付け、ライフサイクル、Relay 内容を解釈しない、wallet-core 境界および Mainnet 判定条件を上位から直接引き継ぐ必要がある。
- 現在のワークスペースにモバイル実装がないため、本文で確認できた安全条件を実行環境 /実機対応能力の確認済み事実と扱ってはならない。

## 16. 自動変更

なし。レビュー中に変更するのは新規レビュー成果物 [`mobile-app-review-002.md`](./mobile-app-review-002.md) のみであり、モバイル設計、要件、仕様、ADR、共通設計、wallet-core、実装および既存レビューは変更していない。

## 17. 最終判断

`REVISE DESIGN`

現行モバイルアプリ設計は、信頼境界、Relay / wallet-core の責任分界、意味上の内容検査、信頼された UI、ライフサイクル / プロセス再作成、並行する要求分離、`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN`、自動代替経路禁止、秘密情報処理およびチェーン固有の境界に重大な回帰を起こしていない。しかし、共通4条件、v1 構造化された `MESSAGE_SIGN`、署名時の成功結果との結び付け、Mainnet 判定条件の高位安全側での終了不変条件および要求された直接の追跡可能性が不足している。`DR-001`〜`DR-005` を解消し、再レビューで各再確認条件を確認するまで、モバイルアプリ設計を `READY` と判定できない。
