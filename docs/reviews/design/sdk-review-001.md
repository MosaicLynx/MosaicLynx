## 2. 総評

`docs/design/sdk.md` は、SDK の基本設計として実装または下位仕様策定へ進められる品質に達している。

本書は SDK を Web アプリケーション / dApp と信頼されたウォレット文脈の間に置く非特権統合層として定義し、公開 SDK API、Provider 検出、Provider アダプター、対応能力 / バージョン協議、接続 / 許可クライアント、アカウント / ネットワーク照会、署名要求生成、要求調整役 / 応答対応付け、タイムアウト / キャンセル、エラー正規化処理、イベント / 状態通知およびシリアライズ / 検証境界の責務を分離している。SDK は Provider 検出、対応能力、接続 / 許可 initiation、公開情報取得、要求組み立て、振り分け、応答対応付け、タイムアウト / キャンセル、エラー正規化およびバージョン互換性を担う一方、オリジンの信頼性判断、許可判断権限、信頼された表示、利用者承認、端末認証、生の署名、トランザクション安全性 judgment、Relay 信頼判断および wallet-core を担わない。

特に、SDK が Web ページと同じ信頼ドメインに置かれ得ること、Provider の存在・対応能力・応答を信頼根拠にしないこと、SDK が自己申告または観測したオリジンをセキュリティ判断権限にしないこと、ブラウザ拡張機能 / モバイルアプリの信頼された文脈が最終的な呼び出し元 / オリジン / 許可 / 要求検証を担うことが明確である。SDK の早期検証は開発者 ergonomics とプロトコル robustness のためのものに限定され、Signer 側の意味上の検証、承認との結び付け、信頼された UI および wallet-core 署名を代替しない。

また、要求 / 応答の操作、Provider / 接続文脈、アカウント、チェーン / ネットワーク、対象結び付け、期限切れおよびライフサイクルによる対応付け、古くなった / 重複 / リプレイ応答の破棄、タイムアウトとウォレット側の署名状態の分離、キャンセルの非保証、結果不明の安全側処理、複数要求の独立管理、ページ / Provider / ブラウザライフサイクル後の古くなった状態不使用が基本設計として具体化されている。ローカル署名とリモート署名は意味を可能な範囲で共通化しつつ、遅延、利用可能性、セッション、キャンセル、結果不明および Relay involvement の差異を隠していない。

ブラウザ拡張機能、モバイルアプリ、Relay、wallet-core およびインターフェースとの責任分界も一貫しており、SDK 侵害単独で秘密情報資料の取得、承認迂回、オリジンの信頼性判断の奪取または unauthorized 署名が成立しない。実装不能性、信頼境界の破綻、上位設計との重大な矛盾は確認されなかった。

## 6. 信頼境界 / Provider 評価

適合。§3、§6、§7 は、Web アプリケーション / dApp、SDK コード、ページデータ、Provider 応答、Provider の自己申告値を信頼されていないとして扱い、SDK の解析、型確認、対応能力協議、対応付け、エラー正規化が信頼されたウォレット文脈の代わりにならないことを明示している。

- SDK は Provider を検出しても、信頼されたウォレット、許可済み、アカウント情報公開可、署名認可済みのまたは user-approved と判断しない。
- Provider 抽象化は利用可能性、対応能力、接続 / 許可振り分け、公開情報、署名要求振り分け、応答、接続解除、イベントの統合境界に留まり、拡張機能特権を持つ API、モバイル安全な保存領域、承認状態、wallet-core API を公開しない。
- 偽の、競合する、不正な形式の、部分トランザクション、旧または互換性のない Provider は利用不能 / 互換性のない / 検証失敗とし、意図しない Provider への自動送信を行わない。
- SDK 侵害単独で秘密鍵、ニーモニック、ウォレットストア、端末認証資料、E2E 秘密情報または生の署名 API に到達できない。

Provider 検出、Provider 応答、SDK 解消済み状態、接続イベントまたは対応能力イベントを信頼アンカーと扱う構造は確認されなかった。

## 7. オリジンの信頼性判断 / 許可評価

適合。§9 は SDK が観測したオリジン、ホスト、referrer、URL、呼び出し元名、アプリケーションラベル、自己申告文脈をセキュリティ判断権限にしない。ブラウザではブラウザで観測したオリジン / タブ / フレーム / 文書をブラウザ拡張機能 / ブラウザプラットフォームが最終検証し、モバイル / リモートフローでは受け渡しセッション、送信元、受信者、完全性、期限切れをモバイル / プラットフォームが検証する。SDK が渡す呼び出し元 / オリジンは Signer が信頼された文脈で検証するための補助的な要求文脈に留まる。

具体的なオリジン証明、ブラウザ API、OS API、ノンス、暗号学的な結び付け、プロトコルフィールドは `SDK-OPEN-007` と下位仕様へ委譲されているが、次の基本方針は未決事項へ戻されていない。

- SDK はオリジンの信頼性判断ではない。
- Web アプリケーションの自己申告のオリジンを信頼しない。
- 信頼されたブラウザ / モバイル文脈が最終結び付け / 検証を担う。
- 検証不能時に検証済みオリジン、呼び出し元検証済み、接続済みまたは署名成功と表明しない。

§8 は接続、account/address 情報公開、署名要求、利用者承認を分離し、許可の最終判断権限を Provider / ウォレット側に置いている。SDK のローカルキャッシュ、対応能力、公開アカウント、公開鍵、接続状態は許可、アカウント所有責任、署名許可または最新の Signer 状態の証明ではない。

## 8. 署名 / SDK 検証 / 表示境界評価

適合。§11 は SDK の責務を署名意図の組み立て、プロトコル境界への変換、振り分け、応答受付および早期検証に限定している。SDK はトランザクション / メッセージの安全性、意味上の内容検査、アグリゲート内部トランザクション、連署署名対象、表示可能性、内容を確認しない署名の可否、承認との結び付け、生の署名を確定しない。

SDK が行う不正な形式の入力、未対応の操作、明らかなチェーン / ネットワーク不一致、文脈欠落、サイズ / シリアライズ異常の検出は、開発者 ergonomics とプロトコル robustness のための早期検出である。SDK 検証通過後も Signer が呼び出し元、許可、アカウント、チェーン / ネットワーク、ペイロード完全性、意味上の安全性、信頼された表示、明示的な承認、wallet-core 入力を独立検証するため、`SDK validation passed = safe to sign` にはならない。

SDK / dApp の表示テキスト、ラベル、説明、アイコン、受信者名、数量説明は補足の / 信頼されていないメタデータであり、信頼された承認 UI がペイロードから再構成・検証する署名表現を置き換えない。未対応または意味を保てない要求を生の署名、警告付き内容を確認しない署名、別操作、別通信経路へ自動変換しない点も適合している。

## 9. 要求 / 応答対応付け評価

適合。§12〜§13 は、要求識別情報、操作、Provider / 接続 / セッション文脈、アカウント、チェーン / ネットワーク、Signer 文脈、対象結び付け、期限切れ、許可スナップショットおよびページライフサイクルを要求単位で管理する。成功を返す前に、応答が対象要求、操作、現在の文脈、アカウント、チェーン / ネットワーク、Signer、対象に対応することを確認する。

対応を確認できない応答、遅延応答、重複、古くなった、期限切れ、キャンセル済み、再送された、別要求、別セッションまたは旧接続の応答は適用せず、成功推測もしない。終端処理は一要求一回であり、重複完了を無視または安全な重複として扱う。SDK の対応付けは dApp による署名済み結果の独立検証を代替しない。

## 10. タイムアウト / キャンセル / エラー評価

適合。§14〜§15 は、タイムアウトを SDK のアプリケーション待機 / 応答アプリケーションの終了として扱い、Signer が要求を受信していない、承認が閉じた、端末認証が未実行、署名が未実行、署名済み結果が存在しないとは保証しない。タイムアウト後の再試行は、共通仕様に従う新しい要求と新しい検証 / 承認の境界を必要とする。

キャンセルはローカル待機 / 応答ハンドラー / 要求状態の終了と、Provider が提供するプロトコルキャンセル要求を区別する。送信・受理・配送をウォレット側のキャンセル完了と同一視せず、キャンセル後も Signer が既に承認・署名した可能性を否定しない。

エラー分類は利用者拒否、許可拒否、無効な、未対応の / 互換性のない、不一致 / 完全性 / リプレイ、タイムアウト / 期限切れ / キャンセル済み、通信経路 / Relay、ウォレット側の / 内部を区別し、利用者拒否、検証失敗、結果不明を自動再試行 / 代替経路で迂回しない。具体的なエラーコード、例外、メッセージ、再試行回数は下位仕様へ適切に委譲されている。

## 11. 並行処理 / 接続消失 / ページライフサイクル評価

適合。§16 はアカウント照会、接続、トランザクション署名、メッセージ署名、キャンセル、応答を単一のグローバル状態に混在させず、要求識別情報、操作、アカウント、チェーン / ネットワーク、Provider 文脈、タイムアウト、キャンセル、完了、エラー、許可スナップショットおよびページライフサイクル文脈を要求単位で分離する。

Provider 接続解除、拡張機能再読み込み、ブラウザ再起動、タブページ遷移、ページ再読み込み、SDK 再初期化、セッション有効期限後の再接続は、前回承認、認証、保留中の要求、署名済み結果、許可または旧応答の復元を意味しない。旧応答が新しい SDK インスタンス / 接続に到着した場合も識別情報、文脈、期限切れ、セッションを検証し、対応しなければ破棄する。BFCache、タブ終了、重複初期化を含むページライフサイクル後に古くなった要求 / 応答状態を危険に再利用しない。

## 12. ローカル / リモート署名抽象化評価

適合。§17 は次の二経路を可能な範囲で共通のアプリケーションに公開する意味として扱っている。

```text
ローカル:  SDK → Provider → ブラウザ拡張機能 → wallet-core
リモート: SDK → Provider / 受け渡しクライアント → Relay → モバイルアプリ → wallet-core
```

操作、要求識別情報、アカウント / チェーン / ネットワーク文脈、成功 / 拒否 / 失敗の意味および結果対応付けは共通化する一方、遅延、利用可能性、セッション establishment、利用者有効化、ページ / アプリライフサイクル、タイムアウト、キャンセル、結果不明は完全に同一視しない。Relay の内部プロトコル、認証情報、セッションストア、モバイルの特権を持つインターフェースを SDK API へ露出せず、Relay 利用不能やモバイル未提供を署名成功に変換しない。

ローカル失敗からリモート、リモート失敗からローカルへの無断代替経路は、拒否、不一致、完全性、呼び出し元、リプレイ失敗、結果不明を迂回し得るため禁止されている。明示的な通信経路選択や代替 UX は要件の未決事項として扱われている。

## 13. バージョン管理 / 互換性 / シリアライズ評価

適合。§18 は SDK、Provider / プロトコル、対応能力、Signer / モバイル / Relay バージョンの関係を操作、チェーン / ネットワーク、通信経路およびセキュリティプロパティと併せて確認し、バージョン一致だけを対応能力の根拠にしない。不明、未対応の、互換性のない、判定不能なバージョン、不明フィールド / アルゴリズム、非推奨の操作、古い許可モデル、曖昧または意味を保てない変換は安全側に拒否する。

SDK 内部モデル、アプリケーションに公開するモデル、共通プロトコル表現を分離し、シリアライズ前後で操作、要求識別情報、チェーン / ネットワーク、アカウント、ペイロード結び付けおよび期限切れの意味を変えない。インターフェースのプロトコル意味、通信上のスキーマ、正規シリアライズ、要求 ID 形式、署名形式およびエラーコードを SDK 独自に再定義していない。

## 14. 秘密情報 / wallet-core 境界評価

適合。§4、§6、§10、§19、§20、§22 は SDK が秘密鍵、ニーモニック、パスワード、ウォレットストア、復号済み秘密情報、端末認証情報、ロック解除トークン、E2E 秘密情報、認証情報生の値を要求・保持・復号・導出・出力・ログ出力しないことを定める。

wallet-core は信頼されたウォレットコンポーネント内部の暗号学的な境界とされ、SDK は生の署名 API、ウォレットストア復号、秘密情報操作 passthrough、Provider private 文脈、モバイル安全な保存領域または端末認証チャネルへ直接到達しない。署名済み結果は秘密情報ではない範囲で扱うが、署名結果の正当性は dApp / SDK が独立検証する責任分界を維持している。

ログ出力、例外、URL、照会、イベント、コールバック、Provider メッセージ、キャッシュ、デバッグ出力、遠隔計測データ、APM 相当の診断経路にも秘密情報、全体ペイロード、承認詳細、不要なオリジン / アカウント組み合わせ、セッション秘密情報、認証情報または内部スタック追跡を恒常的に記録しない設計である。

## 15. ブラウザ拡張機能 / モバイルアプリ / Relay との責任分界

適合。§20 と上位設計の照合により、次の境界が保たれている。

| 主体                        | 主な責任                                                                                                                                                | SDK が委譲・代替しない責任                                                                            |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Web アプリケーション / dApp | 署名意図、SDK 利用、結果の独立検証、必要なネットワーク処理                                                                                              | SDK や Provider 応答を信頼アンカーにしない。秘密情報を渡さない。                                      |
| SDK                         | 検出、対応能力 / バージョン、接続 / 許可クライアント、公開情報、要求組み立て、振り分け、対応付け、タイムアウト / キャンセル、エラー正規化               | ウォレット、オリジンの信頼性判断、承認判断権限、署名判断権限、トランザクション安全性 judge ではない。 |
| ブラウザ拡張機能            | ブラウザで観測したオリジン、許可 / アカウント情報公開判断権限、要求セキュリティ検証、信頼された UI、端末 / ロック解除、署名処理の調整、wallet-core 統合 | SDK は公開 Provider 境界だけを利用し、特権を持つ / private 文脈へ入らない。                           |
| モバイルアプリ              | 受け渡し / 送信元検証、OS セキュリティ、端末認証、信頼された承認、アカウント / ネットワーク、署名、応答世代                                             | SDK はモバイル特権を持つチャネル、Relay 検証、安全な保存領域、端末認証を直接制御しない。              |
| Relay                       | 内容を解釈しない通信経路、セッション / 経路選択、短期間のみ有効な配送、有効期限、接続ライフサイクル                                                     | SDK は Relay を信頼アンカー、認可バックエンド、意味上の検証器、結果判断権限として扱わない。           |
| wallet-core                 | 秘密情報処理、ウォレットストア、暗号学的な操作、生の署名                                                                                                | SDK / Web アプリケーションへ直接公開せず、信頼されたウォレットコンポーネント内部に置く。              |
| インターフェース            | 要求 / 応答意味、操作、識別情報 / 対応付け、バージョン管理、共通プロトコル                                                                              | SDK は独自通信上の契約、署名プロトコル、承認モデルを発明しない。                                      |

接続済み、対応能力あり、Relay 配送済み、Provider 成功または SDK 解消済みは、利用者承認、署名成功、オリジン検証済み、アカウント所有責任、トランザクション安全性または結果の独立検証完了を意味しない。

## 16. セキュリティ上の不変条件評価

適合。§22 は共通セキュリティ設計の単純な複製ではなく、SDK の Provider、ページ、対応付け、ライフサイクル、通信経路抽象化、診断情報へ次のように適用している。

- SDK は秘密情報資料、ウォレットロック解除、端末認証、ウォレットストア、生の署名に関与しない。
- SDK はウォレット、署名判断権限、承認判断権限、トランザクション検証器、オリジンの信頼性判断、信頼アンカーではない。
- Provider 検出は接続、許可、アカウント情報公開、ロック解除、承認、署名対応能力の確定を意味しない。
- 対応能力は認可、アカウント所有責任、利用者承認、個別要求の成功を意味しない。
- 接続、account/address 情報公開、署名要求、利用者承認を分離し、許可の最終判断権限を Provider / ウォレット側に置く。
- オリジン / 呼び出し元の最終結び付けはブラウザ / モバイルの信頼された文脈が担い、SDK の自己申告・観測情報だけで検証済みとしない。
- SDK 検証、表示メタデータ、Provider 応答、SDK 解消済み状態はウォレット側のセキュリティ検証、信頼された表示、承認、署名結果検証の代替ではない。
- 要求 / 応答、操作、アカウント、チェーン / ネットワーク、Provider 文脈、対象結び付け、期限切れを一意に対応付けし、古くなった / 重複 / リプレイ / 別要求応答を適用しない。
- タイムアウトはウォレット側のキャンセル、未署名、署名済み結果不存在を保証せず、キャンセルは署名 definitely did not happen を保証しない。
- 再接続、Provider 再読み込み、ブラウザ再起動、ページ再読み込み、SDK 再初期化は古くなった承認、許可、保留中の要求、署名済み結果の復元を意味しない。
- 互換性のないプロトコル / 対応能力 / 実行環境は安全でない代替経路せず、利用者拒否、不一致、完全性、呼び出し元、リプレイ失敗、結果不明を自動再試行 / 代替経路で迂回しない。
- Relay 配送、Provider 応答、接続イベント、SDK 解消済み状態を署名成功・安全性・オリジン検証済みの根拠にしない。

本文のコンポーネント、ライフサイクル、失敗 / 復旧、責務境界と矛盾する不変条件は確認されなかった。

## 18. 基本設計粒度の評価

粒度は妥当である。

- 実装者が主要判断に迷わない範囲として、SDK の非特権境界、Provider 検出 / 対応能力、接続 / 許可、オリジンの信頼性判断、アカウント情報公開、要求組み立て、検証境界、対応付け、ライフサイクル、タイムアウト / キャンセル、エラー、並行処理、ローカル / リモート、互換性、秘密情報の分離、失敗復旧を定めている。
- TypeScript の具体 API、クラス / 関数、Provider オブジェクト名、メソッド署名、要求 ID 形式、通信上のスキーマ、エラーコード、タイムアウト秒数、キャンセルプロトコル、パッケージエクスポート、バンドラー、基盤アダプター、ブラウザ対応表、キューアルゴリズム等は下位仕様へ委譲している。
- 未決事項は Provider 選択、キャンセルプロトコル、通信経路選択、アグリゲート / マルチシグ / 連署署名公開範囲、実行環境 / バージョンポリシー、オリジン証明の具体方式に限定され、確定済みのセキュリティ原則を未決に戻していない。

したがって、具体 API、メソッド署名、Provider オブジェクト名、スキーマ、エラーコード、タイムアウト値、React フック、パッケージエクスポート対応表の欠落を基本設計の不足とは判定しない。

## 19. 未決事項の評価

§24 の未決事項は、基本設計を確定不能にする阻害要因ではなく、要件の `SDK-OPEN-002`〜`SDK-OPEN-007`、Provider 契約、受け渡し / プロトコル仕様、プラットフォーム / リリースポリシーへ適切に引き継がれている。

- Provider 検出の具体仕組み、偽の / 競合する Provider の選択ポリシー、複数 Provider の明示選択は、検出を信頼としない不変条件を維持したまま決定できる。
- キャンセルがローカル待機のみか Provider / Signer へのプロトコル要求を含むかは未決だが、いずれの場合も SDK が non-signing を強く保証しない基本境界は確定している。
- ローカル / リモート通信経路選択、明示的代替 UX、アグリゲート / マルチシグ / 連署署名の公開範囲、実行環境、バージョン管理、互換性は下流で具体化できる。
- ブラウザで観測したオリジン、モバイル受け渡し送信元、呼び出し元証明、許可結び付けの具体仕組みは未決だが、SDK が判断権限ではなく、信頼された文脈が最終検証 / 結び付けを担うことは確定している。

未決事項を理由に、SDK がオリジンの信頼性判断、承認エンジン、ウォレット、Relay 信頼アンカー、生の署名 API または安全でない代替経路を持つ余地は残されていない。
