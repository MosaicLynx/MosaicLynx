## 4. Review Result

`REVISE DESIGN`

## 5. Summary

現行の `relay.md` は、Relay を短期 opaque transport / delivery coordination に限定し、private key、Wallet Store、semantic inspection、approval、account authorization、signing、result correctness authority を持たせないという基本方向を広範囲に明記している。session / generation / request-response binding、stale / duplicate の transport-level 処理、bounded retention、secret 非保持、DoS / overload の安全側処理、automatic fallback の禁止も確認できる。

しかし、次の2点は基本設計として修正が必要である。

- Relay の outage、partition、overload、full outage、reconnect failure を `RESULT_UNKNOWN` と分類し得る記述があり、Signer が署名生成の結果を不確定とした `RESULT_UNKNOWN` と、既知の結果が届かない `DELIVERY_UNKNOWN`、単なる transport unavailable / pending / expiry を Relay が分離できていない (`DR-001`)。
- Relay は opaque envelope を復号・意味解釈しないとしながら、unsupported operation / format や operation / capability を Relay が reject すると読める記述がある。下流 handoff では operation が暗号化 request の内部にあるため、Relay の structural validation と Signer の operation / semantic validation の責務が衝突する (`DR-002`)。

また、trust-boundary 図の SDK と Browser / Mobile のまとめ方、および traceability table の責務単位が、本文の正しい境界を一読で検証するには弱い (`DR-003`, `DR-004`)。これらは Critical / Major Gate を単独で失敗させるものではないが、上記 Critical finding の修正時に同時に明確化すべきである。

## 7. Required Changes

### DR-001: Transport failure と signing-result disposition の混同

- Severity: `Critical`
- Status: `New`
- Target: [`relay.md`](../../design/relay.md) §10（行279〜285）、§12.2（行323〜327）、§14.2（行368〜370）、§20（行449〜455）、§25（行517〜533）、§30（行594〜603）。
- Facts / conditions: §10 は Relay が application / approval / signing / result を観測しないと定める一方、§14.2 は reconnect failure を「期限切れまたは delivery unknown 等」とまとめ、§20 は instance / storage / network partition、overload、full outage を transport failure、timeout、expiry または `result unknown` に分類し得る。§12.2 は timeout、restart、state loss 後の retry に fresh envelope と new approval を要求するが、どの unknown が署名生成結果の unknown で、どれが配送・transport の unknown かを定義していない。
- Evidence: [`signing-flow.md`](../../design/signing-flow.md) §7.3〜§7.4、§20〜§21 は `RESULT_UNKNOWN` を signing generation の結果が安全に確定できない場合に限定し、既知の signed result の配送不確実性を `DELIVERY_UNKNOWN` と区別する。[`interfaces.md` specification](../../specifications/interfaces.md) §10.3、[`signing-protocol.md`](../../specifications/signing-protocol.md) §19 も、transport failure、known-result resend / lookup、`RESULT_UNKNOWN`、`DELIVERY_UNKNOWN`、re-sign を別の意味として扱う。[`docs/requirements/relay.md`](../../requirements/relay.md) RR-004、RR-NFR-002、RR-NFR-005 は、Relay outage を signing success / failure と推測せず、result unknown を success とせず、retry を fresh request と区別することを要求する。Mobile Design §14〜§15 も同じ分離を定める。
- Problem: Relay は signer の signing generation を観測しないため、Relay の outage / state loss / response 未取得だけから `RESULT_UNKNOWN` を成立させる authority を持たない。Relay が `RESULT_UNKNOWN` を自ら選べると、response 未取得が「未署名」と誤認され、known result の resend / lookup と新しい signing operation が混同される。反対に、signer process loss 中の本当の `RESULT_UNKNOWN` を transport failure として扱う場合も、責任 owner が不明確になる。
- Impact: Relay compromise、outage、partition、restart、recipient offline、delivery timeout が、外部 caller の retry / re-sign 判断に影響する。既存の automatic fallback prohibition があっても、公開 disposition の意味が曖昧なままでは、Relay / SDK / Mobile の実装が「応答がない = 未署名」または「result unknown = 再署名可能」と解釈する余地が残り、共通4条件と result correctness authority の境界を侵食する。
- Minimum correction: `relay.md` の failure / lifecycle / retry / delegation を、次の authority 分離が読み取れるよう修正する。`RESULT_UNKNOWN` は signer が signing generation の結果を確定できない場合だけ、`DELIVERY_UNKNOWN` は signer が既知の結果を持つが response delivery を確定できない場合だけとし、Relay 自身はこれらの signing outcome を生成・推測しない。Relay outage、state loss、recipient unavailable、response 未取得は transport-level disposition のまま扱い、known result の resend / lookup と re-sign を分離し、state loss は re-sign の根拠にしない。signer-originated disposition を Relay が運ぶ場合も、Relay はその意味の authority にならないことを明記する。具体 code、timeout、retry 数および wire representation は下位へ委譲してよい。
- Reconfirmation criteria: signing generation 中の Mobile process loss、signer が結果を既知にした後の Relay response loss、signer が応答を返す前の Relay outage、Relay state loss、recipient offline、request expiry の各ケースについて、Relay が署名成功 / failure / `RESULT_UNKNOWN` を推測しないこと、`RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` を signer-side authority に結び付けること、known result の resend / lookup が re-sign を開始しないこと、security failure / user rejection / authorization failure が transport retry に変換されないことを設計本文から追跡できること。

### DR-002: Opaque envelope と operation-specific reject の責務矛盾

- Severity: `Critical`
- Status: `New`
- Target: [`relay.md`](../../design/relay.md) §3.1（行38〜40）、§8.1〜§8.2（行221〜247）、§27（行546〜552）。
- Facts / conditions: §3.1 は Relay が E2E opaque envelope を復号・解釈・表示・変更しないと宣言する一方、「未対応 operation / format」を安全に拒否すると記述する。§8.1 は unknown kind / version / capability / structure に加えて operation を Relay が reject するよう読め、§27 も operation conversion / downgrade をしない代わりに unsupported item を Relay が reject する構造である。対象本文は operation-specific な reject と transport envelope の structural reject の境界を定義していない。
- Evidence: [`docs/requirements/relay.md`](../../requirements/relay.md) RR-003 は Relay validation を operation-independent metadata、envelope shape / size / expiry / version / session / request-response correspondence 等の structural validation に限定する。[`web-transaction-handoff-spec.md`](../../specifications/web-transaction-handoff-spec.md) §7.1、§9.2 は `CreateHandoffRequest` の外側に protocol / generation / session / request / expiry 等があり、transaction signing / message signing の operation payload は暗号化された request 内にあると定める。同仕様 §8.2 は Relay が plaintext を扱わないとする。[`mobile-app.md`](../../design/mobile-app.md) §8.2、[`architecture.md`](../../design/architecture.md) §6.5 は operation / semantic validation を Mobile / Signer 側に置く。Chain Compatibility Specification も Symbol / NEM、Mainnet / Testnet、MESSAGE_SIGN / transaction semantics の最終検証を chain integration / Signer 側の責務としている。
- Problem: Relay が operation-specific unsupported / format を reject するには、暗号化 payload の operation / message / transaction semantics を可視化するか、別の operation authority を信頼する必要がある。前者は opaque / non-Signer boundary を破壊し、後者は Relay metadata を semantic authority に昇格させる。逆に Relay を完全 opaque と実装すれば、現在の本文が期待する operation-specific reject を実行できず、下流の責務契約と矛盾する。
- Impact: 実装者が Relay に plaintext inspection、untrusted operation hint の authority、operation downgrade / conversion、または Relay-originated semantic rejection を追加する余地が生じる。MESSAGE_SIGN の domain / purpose / replay meaning、transaction recipient / amount、Chain / Network、Account、approval といった Signer-only semantics が Relay の protocol admission に逆流し、Relay compromise 時に拒否・許可の authority を誤って持つ可能性がある。
- Minimum correction: Relay が見える transport envelope の protocol version、envelope kind、shape / size、generation、session、direction、correlation、expiry、transport credential、routing eligibility のみを structural validation 対象として明記し、operation-specific unsupported、message / transaction format、domain / purpose、Chain / Network、Account、approval は decrypt 後の Mobile / Signer 側へ戻す。「未対応 operation / format」は transport-visible protocol kind / version と、Signer-only operation / semantic format に分けて記述する。operation hint を外側に置くかどうか、またその wire schema は本設計で決める必要はないが、hint が Signer の最終 authority を代替しないことは明記する。
- Reconfirmation criteria: Relay の validation list から operation / transaction / message / account / Chain / Network / approval の意味解釈を除外し、下流 handoff の暗号化 request に含まれる signTransaction / signData / MESSAGE_SIGN 等を Relay が読まずに搬送できること。unknown transport version / envelope structure は Relay が fail-closed し、unknown operation / semantic format は Signer 側の結果として扱われること、Relay が operation conversion / downgrade / semantic reject を生成しないことを確認すること。

## 8. Optional Improvements

### DR-003: SDK と Browser / Mobile Signer の trust-boundary 表現が曖昧

- Severity: `Minor`
- Status: `New`
- Target: [`relay.md`](../../design/relay.md) §5（行147〜170）および §29（行575〜585）。
- Facts / conditions: §5 の trust-boundary 図は egress 先を「`Mobile App or SDK / Browser Extension`」とまとめ、その同じ説明範囲に semantic inspection、user approval、signing を置いている。§29 の責任表も Browser Extension と SDK を同一行へまとめている。一方、同じ本文 §15 は SDK に approval、semantic inspection、signing、secret を持たせず、SDK Design §20 と Architecture §6.2〜§6.5 は SDK / Relay と Browser / Mobile Signer を別責務にしている。
- Evidence: [`sdk.md`](../../design/sdk.md) §17、§20〜§22 は SDK を non-Signer の transport orchestration / correlation 層とし、Browser host / Mobile が approval / signing authority を持つ。[`architecture.md`](../../design/architecture.md) §6.2〜§6.5 も SDK、Browser Extension、Mobile、Relay を別 component としている。関連する Browser / Mobile Design は trusted host、caller / source、semantic inspection、four-gate、wallet-core の責務を SDK / Relay から分離する。
- Problem: 本文の個別節を読めば intended boundary は推測できるが、trust-boundary と責任表の grouping だけを参照する実装者には、SDK が Signer-side semantic / approval / signing に関与できるように見える。これは dependency direction と final authority の説明を弱める。
- Impact: SDK への semantic authority、approval state、signing capability、または Browser / Mobile の境界を跨ぐ retry / response interpretation が追加される余地がある。Relay はその結果として SDK 経由の signing authority と誤認され得る。
- Minimum correction: §5 の trust-boundary と §29 の責任表を、SDK、Browser Extension、Mobile trusted host の別ノード / 別行として表現し、SDK は transport orchestration / correlation まで、Browser Extension / Mobile Signer はそれぞれの local / remote signing gate と trusted UI まで、Relay は opaque transport までと明記する。
- Reconfirmation criteria: 図・責任表だけを読んでも SDK が Authentication、Signing-capable unlock、Account authorization、Explicit user approval、semantic inspection、signing、secret handling の authority を持たず、Browser local signing に Relay を不要に挿入せず、remote handoff でも Mobile trusted host が final authority であることが確認できること。

### DR-004: 責務単位の traceability と OPEN の既決事項の明示不足

- Severity: `Minor`
- Status: `New`
- Target: [`relay.md`](../../design/relay.md) §31（行605〜617）および §32（行619〜633）。
- Facts / conditions: §32 の traceability table は opaque / non-Signer、structural vs client semantic、session / generation / correlation、result unknown / duplicate、retention / logging、horizontal consistency、component boundary の7行である。本文には automatic fallback prohibition、retry / redelivery、explicit `DELIVERY_UNKNOWN`、source / caller authority、DoS / abuse、MESSAGE_SIGN、Mainnet release / evidence gate が記述されているが、それぞれを上流 requirement / common Design / downstream owner へ直接追跡する行がない。さらに Requirements の RR-OPEN-001 は operation scope 自体ではなく external handoff contract / milestone completion / SDK-Mobile boundary を open とし、transaction signing と message signing は既決であるが、§31 の表現だけではその区別が明示されない。
- Evidence: [`docs/requirements/relay.md`](../../requirements/relay.md) RR-003〜RR-011、RR-NFR-002〜RR-NFR-005、RR-OPEN-001〜RR-OPEN-002 は、opaque validation、DoS、result / delivery failure、fresh retry、operation scope の既決範囲を分けている。[`signing-flow.md`](../../design/signing-flow.md) §21〜§23 は automatic fallback、retry / redelivery、unknown disposition を定める。[`mobile-app.md`](../../design/mobile-app.md) §23.1、§25、[`0001-mainnet-evidence-lite.md`](../../adr/0001-mainnet-evidence-lite.md) および release evidence policy は Mainnet capability を Relay でなく release / evidence gate と Signer 側へ置く。[`architecture.md`](../../design/architecture.md) §6.9 は4条件 gate を Signer 側へ置く。
- Problem: 本文を更新する際、traceability table を見ても重要な禁止事項と owner を網羅したか確認しにくく、OPEN-001 が下流で決まった operation scope や common security boundary を再び未決に戻したように解釈される余地がある。Mainnet health、delivery success、Relay connection が signing capability / release gate ではないことも、Relay Design 単独の trace からは明示的に確認できない。

## 15. Remaining Risks and Open Decisions

- RR-OPEN-001 は、transaction signing と message signing の operation scopeを未決に戻すものではない。既決の operation scopeを維持したまま、external handoff contract、milestone completion、SDK / Mobile boundary の残余条件を open として扱う必要がある (`DR-004`)。
- RR-OPEN-002 は external failure classification の具体 code、mapping、timing、retry / lookup contract を下位で決める open として残せる。ただし signing-generation `RESULT_UNKNOWN`、known-result `DELIVERY_UNKNOWN`、transport failure、no re-sign の意味分離は open に戻せない (`DR-001`)。
- Transport credential、pairing representation、persistence / multi-instance consistency、retention / deletion / logging detail、multi-relay、admin governance は具体 protocol / operations の open として妥当である。これらが transport auth を signing gate、Relay metadata を source authority、Relay health を Mainnet gate に昇格させないことが前提である。
- Mainnet capability は ADR、release evidence policy、Signer / Mobile の release gate に属し、Relay の connection / availability は代替しない。対象本文に直接矛盾はないが、次回 traceability table で owner を明示する必要がある (`DR-004`)。
- 現在の workspace に Mobile App 実装は存在しないため、本レビューは Mobile Design との責務整合を確認したもので、Mobile runtime / E2E の完了を意味しない。

## 17. Final Decision

`REVISE DESIGN`

`DR-001` と `DR-002` は、Relay を non-Signer / opaque transport に限定するための result authority と semantic validation authority の基本境界に関わる Critical finding である。これらが解消され、Relay 障害から signing outcome を推測せず、operation-specific semantics を Relay が扱わないことを本文から一意に追跡できるまで、Relay Design を `READY` と判断できない。`DR-003` と `DR-004` は、修正後の責務を誤読なく維持するための Minor improvement である。
