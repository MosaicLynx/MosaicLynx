`REVISE DESIGN`

## 5. 要約

現行の `relay.md` は、Relay を短期内容を解釈しない通信経路 / 配送調整に限定し、秘密鍵、ウォレットストア、意味上の内容検査、承認、アカウントの利用認可、署名、結果正確性判断権限を持たせないという基本方向を広範囲に明記している。セッション / 世代 / request-response 結び付け、古くなった / 重複の通信経路レベルの処理、上限のある保持、秘密情報非保持、DoS / 過負荷の安全側処理、自動代替経路の禁止も確認できる。

しかし、次の2点は基本設計として修正が必要である。

- Relay の障害、分割、過負荷、全体障害、再接続失敗を `RESULT_UNKNOWN` と分類し得る記述があり、署名主体が署名生成の結果を不確定とした `RESULT_UNKNOWN` と、既知の結果が届かない `DELIVERY_UNKNOWN`、単なる通信経路利用不能 / 保留中の / 期限切れを Relay が分離できていない (`DR-001`)。
- Relay は内容を解釈しないエンベロープを復号・意味解釈しないとしながら、未対応の操作 / 形式や操作 / 対応能力を Relay が拒否すると読める記述がある。下流受け渡しでは操作が暗号化要求の内部にあるため、Relay の構造上の検証と署名主体の操作 / 意味上の検証の責務が衝突する (`DR-002`)。

また、信頼境界図の SDK とブラウザ / モバイルのまとめ方、および追跡可能性表の責務単位が、本文の正しい境界を一読で検証するには弱い (`DR-003`, `DR-004`)。これらは重大 / 主要判定条件を単独で失敗させるものではないが、上記重大指摘の修正時に同時に明確化すべきである。

## 7. 必須の修正

### DR-001: 通信経路失敗と署名結果処理結果の区分の混同

- 重要度: `Critical`
- 状態: `New`
- 対象: [`relay.md`](../../design/relay.md) §10（行279〜285）、§12.2（行323〜327）、§14.2（行368〜370）、§20（行449〜455）、§25（行517〜533）、§30（行594〜603）。
- 事実 / 条件: §10 は Relay がアプリケーション / 承認 / 署名 / 結果を観測しないと定める一方、§14.2 は再接続失敗を「期限切れまたは配送不明等」とまとめ、§20 はインスタンス / 保存領域 / ネットワーク分割、過負荷、全体障害を通信経路失敗、タイムアウト、期限切れまたは `result unknown` に分類し得る。§12.2 はタイムアウト、再起動、状態消失後の再試行に新鮮なエンベロープと新規承認を要求するが、どの不明が署名生成結果の不明で、どれが配送・通信経路の不明かを定義していない。
- 根拠: [`signing-flow.md`](../../design/signing-flow.md) §7.3〜§7.4、§20〜§21 は `RESULT_UNKNOWN` を署名生成の結果が安全に確定できない場合に限定し、既知の署名済み結果の配送不確実性を `DELIVERY_UNKNOWN` と区別する。[`interfaces.md` 仕様](../../specifications/interfaces.md) §10.3、[`signing-protocol.md`](../../specifications/signing-protocol.md) §19 も、通信経路失敗、確定済みの結果再送 / 照会、`RESULT_UNKNOWN`、`DELIVERY_UNKNOWN`、再署名を別の意味として扱う。[`docs/requirements/relay.md`](../../requirements/relay.md) RR-004、RR-NFR-002、RR-NFR-005 は、Relay 障害を署名成功 / 失敗と推測せず、結果不明を成功とせず、再試行を新鮮な要求と区別することを要求する。モバイル設計 §14〜§15 も同じ分離を定める。
- 問題: Relay は署名主体の署名生成を観測しないため、Relay の障害 / 状態消失 / 応答未取得だけから `RESULT_UNKNOWN` を成立させる判断権限を持たない。Relay が `RESULT_UNKNOWN` を自ら選べると、応答未取得が「未署名」と誤認され、既知の結果の再送 / 照会と新しい署名操作が混同される。反対に、署名主体プロセス消失中の本当の `RESULT_UNKNOWN` を通信経路失敗として扱う場合も、責任責任主体が不明確になる。
- 影響: Relay 侵害、障害、分割、再起動、受信者オフライン、配送タイムアウトが、外部呼び出し元の再試行 / 再署名判断に影響する。既存の自動代替経路禁止があっても、公開処理結果の区分の意味が曖昧なままでは、Relay / SDK / モバイルの実装が「応答がない = 未署名」または「結果不明 = 再署名可能」と解釈する余地が残り、共通4条件と結果正確性判断権限の境界を侵食する。
- 最低限必要な修正: `relay.md` の失敗 / ライフサイクル / 再試行 / 委譲を、次の判断権限分離が読み取れるよう修正する。`RESULT_UNKNOWN` は署名主体が署名生成の結果を確定できない場合だけ、`DELIVERY_UNKNOWN` は署名主体が既知の結果を持つが応答配送を確定できない場合だけとし、Relay 自身はこれらの署名結果を生成・推測しない。Relay 障害、状態消失、受信者利用不能、応答未取得は通信経路レベルの処理結果の区分のまま扱い、既知の結果の再送 / 照会と再署名を分離し、状態消失は再署名の根拠にしない。署名主体が生成した処理結果の区分を Relay が運ぶ場合も、Relay はその意味の判断権限にならないことを明記する。具体コード、タイムアウト、再試行数および通信上の表現は下位へ委譲してよい。
- 再確認条件: 署名生成中のモバイルプロセス消失、署名主体が結果を既知にした後の Relay 応答消失、署名主体が応答を返す前の Relay 障害、Relay 状態消失、受信者オフライン、要求期限切れの各ケースについて、Relay が署名成功 / 失敗 / `RESULT_UNKNOWN` を推測しないこと、`RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` を署名主体側の判断権限に結び付けること、既知の結果の再送 / 照会が再署名を開始しないこと、セキュリティ失敗 / 利用者拒否 / 認可失敗が通信経路再試行に変換されないことを設計本文から追跡できること。

### DR-002: 内容を解釈しないエンベロープと操作固有の拒否の責務矛盾

- 重要度: `Critical`
- 状態: `New`
- 対象: [`relay.md`](../../design/relay.md) §3.1（行38〜40）、§8.1〜§8.2（行221〜247）、§27（行546〜552）。
- 事実 / 条件: §3.1 は Relay が E2E 内容を解釈しないエンベロープを復号・解釈・表示・変更しないと宣言する一方、「未対応操作 / 形式」を安全に拒否すると記述する。§8.1 は不明種別 / バージョン / 対応能力 / 構造に加えて操作を Relay が拒否するよう読め、§27 も操作変換 / 格下げをしない代わりに未対応の項目を Relay が拒否する構造である。対象本文は操作固有のな拒否と通信経路エンベロープの構造上の拒否の境界を定義していない。
- 根拠: [`docs/requirements/relay.md`](../../requirements/relay.md) RR-003 は Relay 検証を操作に依存しないメタデータ、エンベロープ構造 / サイズ / 期限切れ / バージョン / セッション / request-response 対応関係等の構造上の検証に限定する。[`web-transaction-handoff-spec.md`](../../specifications/web-transaction-handoff-spec.md) §7.1、§9.2 は `CreateHandoffRequest` の外側にプロトコル / 世代 / セッション / 要求 / 期限切れ等があり、トランザクション署名 / メッセージ署名の操作ペイロードは暗号化された要求内にあると定める。同仕様 §8.2 は Relay が平文を扱わないとする。[`mobile-app.md`](../../design/mobile-app.md) §8.2、[`architecture.md`](../../design/architecture.md) §6.5 は操作 / 意味上の検証をモバイル / 署名主体側に置く。チェーン互換性仕様も Symbol / NEM、Mainnet / Testnet、MESSAGE_SIGN / トランザクション意味の最終検証をチェーン統合 / 署名主体側の責務としている。
- 問題: Relay が操作固有の未対応の / 形式を拒否するには、暗号化ペイロードの操作 / メッセージ / トランザクション意味を可視化するか、別の操作判断権限を信頼する必要がある。前者は内容を解釈しない / 署名主体ではないこと境界を破壊し、後者は Relay メタデータを意味上の判断権限に昇格させる。逆に Relay を完全内容を解釈しないと実装すれば、現在の本文が期待する操作固有の拒否を実行できず、下流の責務契約と矛盾する。
- 影響: 実装者が Relay に平文内容検査、信頼されていない操作参考情報の判断権限、操作格下げ / 変換、または Relay-originated 意味上の拒否を追加する余地が生じる。MESSAGE_SIGN のドメイン / 目的 / リプレイ意味、トランザクション受信者 / 数量、チェーン / ネットワーク、アカウント、承認といった署名主体のみの意味が Relay のプロトコル受け入れ判定に逆流し、Relay 侵害時に拒否・許可の判断権限を誤って持つ可能性がある。
- 最低限必要な修正: Relay が見える通信経路エンベロープのプロトコルバージョン、エンベロープ種別、構造 / サイズ、世代、セッション、方向、対応付け、期限切れ、通信経路認証情報、経路選択 eligibility のみを構造上の検証対象として明記し、操作固有の未対応の、メッセージ / トランザクション形式、ドメイン / 目的、チェーン / ネットワーク、アカウント、承認は decrypt 後のモバイル / 署名主体側へ戻す。「未対応操作 / 形式」は transport-visible プロトコル種別 / バージョンと、署名主体のみの操作 / 意味上の形式に分けて記述する。操作参考情報を外側に置くかどうか、またその通信上のスキーマは本設計で決める必要はないが、参考情報が署名主体の最終判断権限を代替しないことは明記する。
- 再確認条件: Relay の検証一覧から操作 / トランザクション / メッセージ / アカウント / チェーン / ネットワーク / 承認の意味解釈を除外し、下流受け渡しの暗号化要求に含まれる signTransaction / signData / MESSAGE_SIGN 等を Relay が読まずに搬送できること。不明通信経路バージョン / エンベロープ構造は Relay が安全側での終了し、不明操作 / 意味上の形式は署名主体側の結果として扱われること、Relay が操作変換 / 格下げ / 意味上の拒否を生成しないことを確認すること。

## 8. 任意の改善

### DR-003: SDK とブラウザ / モバイル署名主体の信頼境界表現が曖昧

- 重要度: `Minor`
- 状態: `New`
- 対象: [`relay.md`](../../design/relay.md) §5（行147〜170）および §29（行575〜585）。
- 事実 / 条件: §5 の信頼境界図は egress 先を「`Mobile App or SDK / Browser Extension`」とまとめ、その同じ説明範囲に意味上の内容検査、利用者承認、署名を置いている。§29 の責任表もブラウザ拡張機能と SDK を同一行へまとめている。一方、同じ本文 §15 は SDK に承認、意味上の内容検査、署名、秘密情報を持たせず、SDK 設計 §20 とアーキテクチャ §6.2〜§6.5 は SDK / Relay とブラウザ / モバイル署名主体を別責務にしている。
- 根拠: [`sdk.md`](../../design/sdk.md) §17、§20〜§22 は SDK を署名主体ではないことの通信経路処理の調整 / 対応付け層とし、ブラウザホスト / モバイルが承認 / 署名判断権限を持つ。[`architecture.md`](../../design/architecture.md) §6.2〜§6.5 も SDK、ブラウザ拡張機能、モバイル、Relay を別コンポーネントとしている。関連するブラウザ / モバイル設計は信頼されたホスト、呼び出し元 / 送信元、意味上の内容検査、four-gate、wallet-core の責務を SDK / Relay から分離する。
- 問題: 本文の個別節を読めば意図した境界は推測できるが、信頼境界と責任表のグループ化だけを参照する実装者には、SDK が署名主体側の意味上の / 承認 / 署名に関与できるように見える。これは依存関係方向と最終判断権限の説明を弱める。
- 影響: SDK への意味上の判断権限、承認状態、署名対応能力、またはブラウザ / モバイルの境界を跨ぐ再試行 / 応答解釈が追加される余地がある。Relay はその結果として SDK 経由の署名判断権限と誤認され得る。
- 最低限必要な修正: §5 の信頼境界と §29 の責任表を、SDK、ブラウザ拡張機能、モバイル信頼されたホストの別ノード / 別行として表現し、SDK は通信経路処理の調整 / 対応付けまで、ブラウザ拡張機能 / モバイル署名主体はそれぞれのローカル / リモート署名判定条件と信頼された UI まで、Relay は内容を解釈しない通信経路までと明記する。
- 再確認条件: 図・責任表だけを読んでも SDK が認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認、意味上の内容検査、署名、秘密情報処理の判断権限を持たず、ブラウザローカル署名に Relay を不要に挿入せず、リモート受け渡しでもモバイル信頼されたホストが最終判断権限であることが確認できること。

### DR-004: 責務単位の追跡可能性と未決の既決事項の明示不足

- 重要度: `Minor`
- 状態: `New`
- 対象: [`relay.md`](../../design/relay.md) §31（行605〜617）および §32（行619〜633）。
- 事実 / 条件: §32 の追跡可能性表は内容を解釈しない / 署名主体ではないこと、構造上の vs クライアント意味上の、セッション / 世代 / 対応付け、結果不明 / 重複、保持 / ログ出力、horizontal 整合性、コンポーネント境界の7行である。本文には自動代替経路禁止、再試行 / 再配送、明示的な `DELIVERY_UNKNOWN`、送信元 / 呼び出し元の信頼性判断、DoS / 悪用、MESSAGE_SIGN、Mainnet リリース / 根拠判定条件が記述されているが、それぞれを上流要求 / 共通の設計 / 下流責任主体へ直接追跡する行がない。さらに要件の RR-OPEN-001 は操作対象範囲自体ではなく外部受け渡し契約 / マイルストーン完了 / SDK-Mobile 境界を未決とし、トランザクション署名とメッセージ署名は既決であるが、§31 の表現だけではその区別が明示されない。
- 根拠: [`docs/requirements/relay.md`](../../requirements/relay.md) RR-003〜RR-011、RR-NFR-002〜RR-NFR-005、RR-OPEN-001〜RR-OPEN-002 は、内容を解釈しない検証、DoS、結果 / 配送失敗、新鮮な再試行、操作対象範囲の既決範囲を分けている。[`signing-flow.md`](../../design/signing-flow.md) §21〜§23 は自動代替経路、再試行 / 再配送、不明処理結果の区分を定める。[`mobile-app.md`](../../design/mobile-app.md) §23.1、§25、[`0001-mainnet-evidence-lite.md`](../../adr/0001-mainnet-evidence-lite.md) およびリリース証跡ポリシーは Mainnet 対応能力を Relay でなくリリース / 根拠判定条件と署名主体側へ置く。[`architecture.md`](../../design/architecture.md) §6.9 は4条件判定条件を署名主体側へ置く。
- 問題: 本文を更新する際、追跡可能性表を見ても重要な禁止事項と責任主体を網羅したか確認しにくく、OPEN-001 が下流で決まった操作対象範囲や共通のセキュリティ境界を再び未決に戻したように解釈される余地がある。Mainnet 正常性、配送成功、Relay 接続が署名対応能力 / リリース判定ではないことも、Relay 設計単独の追跡からは明示的に確認できない。
- 影響: 仕様化・実装・リリースレビューで、通信経路利用可能性を Mainnet 判定条件、再試行を再署名、Relay メタデータを呼び出し元の信頼性判断と誤接続する回帰を検出しにくくなる。本文の実質的な禁止事項が失われるわけではないが、変更時の検証可能性と下流受け渡しの精度が下がる。
- 最低限必要な修正: §32 に、少なくとも自動代替経路禁止、再試行 / 再配送、`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN`、送信元 / 呼び出し元の信頼性判断、DoS / 悪用、MESSAGE_SIGN 内容を解釈しない処理、Mainnet リリース / 根拠判定条件の責任主体を責務単位で追跡する行を追加する。§31 の OPEN-001 はトランザクション署名 / メッセージ署名の操作対象範囲が既決であることを明示し、残る外部受け渡し保証 / マイルストーン契約だけを未決とする。RR-OPEN-002 は厳密な分類 / コード / タイミングの未決としてよいが、署名結果と delivery-result の意味分離は未決に戻さない。
- 再確認条件: 追跡可能性表だけから、Relay が4条件判定条件、送信元検証、意味上の内容検査、MESSAGE_SIGN 意味、Mainnet 根拠判定条件、自動代替経路 / 再署名、DoS 責任主体、秘密情報境界の判断権限を持たないことと、SDK / モバイル / 署名主体 / リリースポリシーの責任主体を追跡できること。OPEN-001 / 002 が下位スキーマ / タイミングの未決に限定され、既決の操作対象範囲、内容を解釈しない境界、不明処理結果の区分、no-fallback 不変条件を再び未決にしていないこと。

## 15. 残存リスクと未決定事項

- RR-OPEN-001 は、トランザクション署名とメッセージ署名の操作対象範囲を未決に戻すものではない。既決の操作対象範囲を維持したまま、外部受け渡し契約、マイルストーン完了、SDK / モバイル境界の残余条件を未決として扱う必要がある (`DR-004`)。
- RR-OPEN-002 は外部失敗分類の具体コード、対応付け、タイミング、再試行 / 照会契約を下位で決める未決として残せる。ただし signing-generation `RESULT_UNKNOWN`、確定済みの結果 `DELIVERY_UNKNOWN`、通信経路失敗、再署名の禁止の意味分離は未決に戻せない (`DR-001`)。
- 通信経路認証情報、ペアリング表現、永続化 / 複数インスタンス整合性、保持 / 削除 / ログ出力詳細、multi-relay、管理者 governance は具体プロトコル / 操作の未決として妥当である。これらが通信経路認証を署名判定条件、Relay メタデータを送信元判断権限、Relay 正常性を Mainnet 判定条件に昇格させないことが前提である。
- Mainnet 対応能力は ADR、リリース証跡ポリシー、署名主体 / モバイルのリリース判定に属し、Relay の接続 / 利用可能性は代替しない。対象本文に直接矛盾はないが、次回追跡可能性表で責任主体を明示する必要がある (`DR-004`)。
- 現在のワークスペースにモバイルアプリ実装は存在しないため、本レビューはモバイル設計との責務整合を確認したもので、モバイル実行環境 / E2E の完了を意味しない。

## 17. 最終判断

`REVISE DESIGN`

`DR-001` と `DR-002` は、Relay を署名主体ではないこと / 内容を解釈しない通信経路に限定するための結果判断権限と意味上の検証判断権限の基本境界に関わる重大指摘である。これらが解消され、Relay 障害から署名結果を推測せず、操作固有の意味を Relay が扱わないことを本文から一意に追跡できるまで、Relay 設計を `READY` と判断できない。`DR-003` と `DR-004` は、修正後の責務を誤読なく維持するための軽微改善である。
