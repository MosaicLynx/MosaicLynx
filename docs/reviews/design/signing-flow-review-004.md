## 4. レビュー結果

**レビュー判定条件: `READY`**

`DR-SF-001`〜`DR-SF-006` は、現行の署名フロー本文でそれぞれの完了条件を満たしており、すべて `RESOLVED` と判定する。ブラウザ拡張機能特権を持つ層とモバイルアプリ信頼されたホストが共通署名ゲートの責任主体であり、認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認の4条件がトランザクション、メッセージ、アグリゲート、連署署名を含むフロー全体へ適用される。

プロファイルは公開通信上のフィールドではなく Signer 内部のセキュリティ文脈として要求、承認、認証、署名、結果に結び付けされ、プロファイルネットワーク、チェーン固有のアカウント / 鍵識別情報および wallet-core 文脈の対応、切り替え / ロック / 関連付け変更による失効が明示されている。結果返却時の署名時の判定条件文脈、要求分離、`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` の分離、セキュリティ失敗後の自動代替経路禁止および新鮮な再試行も確認できる。

過去 `SDR-001`〜`SDR-004` の再発、新規重大 / 主要指摘、信頼境界・wallet-core 責務・SDK Signer ではないこと境界・Relay 内容を解釈しない境界・意味上の内容検査・信頼された UI・内容を確認しない署名禁止・リプレイ / 重複・ライフサイクル消失・安全側での終了の重大回帰は確認されなかった。

- 対象箇所: `signing-flow.md` §2.1、§2.2、§3、§4、§7.1〜§7.3、§8、§9、§10、§11、§13、§14、§16、§17、§18、§19、§20、§22、§23、§25。
- 確認できた事実: ブラウザ拡張機能とモバイルアプリが Signer であり、両者が認証、署名可能な状態へのロック解除、アカウントの利用認可、利用者による明示的な承認を独立した4条件として成立・再確認する。`AWAITING_USER → AUTHORIZED` は4条件すべてを要求し、`AUTHORIZED → SIGNING` 前にも4条件を再確認する。トランザクション、アグリゲート、連署署名、NEM マルチシグおよびメッセージの各フローに同じ判定条件が適用される。成功結果も署名時の4条件と承認文脈の安全な帰属を要求する。
- 既存の根拠: 共通要件 `CR-016`、`CR-AC-017`、アーキテクチャ §6.3、§6.4、§6.9、セキュリティ設計 §7〜§8、署名プロトコル §8および§22。
- 問題と影響: 前回の「4条件が承認・署名成立条件として一体化されていない」問題は、現行本文では解消されている。未成立、ロック済み、不明、古くなった、失効済みまたは不一致では署名・成功結果を返さず、接続、許可、対応能力、セッション、単なる `UNLOCKED`、過去の認証、wallet-core パスワード / ストア検証および Relay 配送成功を代替にしない。
- 必要な最小修正または確認: 現行の §4、§7、§16、§20、§22、§23 による共通判定条件と責任主体の維持。
- 完了条件または再確認方法: 両 Signer が判定条件責任主体として一意に記載され、`AWAITING_USER → AUTHORIZED`、`AUTHORIZED → SIGNING`、`SIGNING → SUCCEEDED`、各操作および失敗意味に4条件が追跡できること。現行本文で充足している。

### DR-SF-002: 解消済み — プロファイルの内部セキュリティ文脈結び付け

- 対象箇所: `signing-flow.md` §3、§5、§7.1〜§7.3、§9、§14、§15、§16、§18、§19、§20、§23、§25、§26。
- 確認できた事実: プロファイルは公開フィールドではなく Signer 内部文脈であり、プロファイルネットワーク、チェーン固有のアカウント / 鍵識別情報および wallet-core 文脈を一意に解決する。要求、呼び出し元、セッション、プロファイル、アカウント、チェーン、ネットワーク、操作、対象の関係が論理モデルと認可組に含まれ、承認、認証、署名、結果にわたり同じプロファイル文脈を使う。プロファイル切り替え、ロック、関連付け変更、アカウント / チェーン / ネットワーク切り替えは旧認可を失効させ、プロファイル A の状態をプロファイル B に流用しない。
- 既存の根拠: 共通要件 §4.2、`CR-013`、`CR-016`、ブラウザ拡張機能要件 BR-003、BR-008、BR-011、モバイルアプリ要件 MR-005〜MR-007、プロファイル / アカウント仕様 §10、§20、§26。
- 問題と影響: 前回の「プロファイルが要求 / 承認 / 認証 / 署名 / 結果との結び付けと変更時失効条件から欠落している」問題は解消されている。公開 SigningRequest、SDK API または Relay エンベロープへの `profileId` 追加を要求せず、Signer 内のな解決と結び付けを維持している。
- 必要な最小修正または確認: プロファイルの内部結び付け、プロファイルネットワークの固定、チェーン固有のアカウント / 鍵識別情報と wallet-core 文脈の一意性、切替・ロック・関連付け変更時の失効を下位仕様が維持すること。
- 完了条件または再確認方法: 要求から結果までプロファイルを含む文脈組を追跡でき、プロファイル A の承認 / 認証 / 結果をプロファイル B に流用できないこと、公開通信上のフィールドを増やさずに実装へ引き渡せること。現行本文で充足している。

### DR-SF-003: 解消済み — 成功結果の署名時の文脈

- 対象箇所: `signing-flow.md` §7.1〜§7.4、§20.1〜§20.3、§21、§22、§23。
- 確認できた事実: `SIGNING → SUCCEEDED` は wallet-core の成功だけでなく、要求、呼び出し元、プロファイル、アカウント、チェーン / ネットワーク、操作、対象、Signer、署名済みペイロード、アグリゲート / マルチシグ親またはメッセージ文脈、署名時の4条件および承認文脈の対応確認を要求する。結果文脈が消失した、不明、古くなった、失効済み、ロック済みまたは不一致の場合は成功としない。
- 既存の根拠: 共通要件 `CR-006`、`CR-NFR-012`、`CR-AC-004`、`CR-AC-017`、アーキテクチャ §6.9、セキュリティ設計 §15、インターフェース §6.4。
- 問題と影響: 前回の「暗号学的な結果と対象の対応だけで成功を返せる」問題は解消されている。Signer が判定条件文脈を安全に帰属できない場合に成功結果を返す余地は現行本文から除かれている。
- 必要な最小修正または確認: 成功結果の内部検証に署名時の 4条件と承認文脈を維持し、文脈を確認できない場合は成功とせず、自動再署名もしないこと。
- 完了条件または再確認方法: `SIGNING → SUCCEEDED`、結果検証、応答、`DELIVERY_UNKNOWN` を確認し、署名生成の成否不明と配送成否不明を混同しないこと。現行本文では `RESULT_UNKNOWN` は署名生成自体に限定され、確定済み結果の配送失敗は `DELIVERY_UNKNOWN` とされている。

### DR-SF-004: 解消済み — 並行する要求分離

- 対象箇所: `signing-flow.md` §4、§5、§7.3、§15、§16、§18、§19、§20、§21、§23。
- 確認できた事実: 複数有効な要求は独立したセキュリティ文脈として扱い、要求識別情報、呼び出し元 / 送信元、セッション、プロファイル、アカウント、チェーン / ネットワーク、操作、対象、意味上の内容検査、承認、認証および結果 / 応答チャネルを共有・統合しない。ブラウザの複数タブ / フレームとモバイルの複数ディープリンク / Relay 受け渡しが明示対象であり、複数対象の一括処理署名と暗黙の統合も禁止される。
- 既存の根拠: セキュリティ設計 §10.2、モバイル設計 §21、Web トランザクション受け渡し仕様 §5.3、共通要件 `CR-NFR-009`、`CR-NFR-011`、`CR-AC-013`、`CR-AC-014`。
- 問題と影響: 前回の「同時要求の最低限の独立性が共通フローに固定されていない」問題は解消されている。1 要求の承認、認証、内容検査、対象または結果チャネルが別要求へ流用される余地を、設計不変条件として閉じている。
- 必要な最小修正または確認: 各有効な要求の文脈とチャネルの独立性、同時要求の暗黙の承認統合禁止を維持する。キュー、排他制御、並列アルゴリズム、公平性、同時数および UI の具体方式は下位へ委譲する。
- 完了条件または再確認方法: ブラウザタブ / フレーム、モバイルディープリンク / Relay 受け渡しの複数要求について、要求ごとの識別情報、承認 / 認証 / 内容検査 / 結果との結び付けが独立していることを確認し、現行本文で充足している。

### DR-SF-005: 解消済み — セキュリティ失敗後の自動代替経路禁止

- 対象箇所: `signing-flow.md` §2.3、§7.2、§8、§9、§14、§21、§22、§23、§26。
- 確認できた事実: 利用者拒否、ロック済み、認証失敗、署名可能な状態へのロック解除失敗、アカウントの利用認可失敗、許可失敗、呼び出し元不一致、完全性失敗、リプレイ / 重複失敗、意味上の内容検査失敗、チェーン / ネットワーク不一致、セキュリティに関わる文脈不一致および `RESULT_UNKNOWN` の後に、別通信経路、Provider または Signer 経路へ自動代替経路して署名を試みない。明示的再試行は新鮮な利用者有効化、新鮮な要求、新鮮な検証、新鮮な認証、新鮮な署名可能な状態へのロック解除、新鮮なアカウントの利用認可、新鮮な利用者による明示的な承認を伴う新しいフローである。
- 既存の根拠: アーキテクチャ §5.2、SDK 要件 §6、§11、Web トランザクション受け渡し仕様 §6、署名プロトコル §19、共通要件 `CR-007`、`CR-012`、`CR-AC-007`、`CR-AC-015`。
- 問題と影響: 前回の「セキュリティ判断の拒否・失敗・不明を代替の経路が迂回できる」問題は解消されている。通信経路復旧を理由に呼び出し元、認証、承認、鮮度または署名結果不明の境界を自動的に越えない。
- 必要な最小修正または確認: 自動代替経路と署名再試行を禁止し、利用者が明示的に開始する新鮮なフローの条件を維持する。通信経路選択順序、Provider 検出および再試行アルゴリズムの詳細は下位へ委譲する。
- 完了条件または再確認方法: 指定された全セキュリティ失敗の後に同一要求を別経路へ自動送信・署名しないこと、明示再試行が全新鮮な条件を満たすことを確認し、現行本文で充足している。

### DR-SF-006: 解消済み — `SDK-OPEN-007` の対象範囲

- 対象箇所: `signing-flow.md` §2.1、§2.3、§5、§9、§18、§19、§20、§23、§25、§26。
- 確認できた事実: `SDK-OPEN-007` に残るのは SDK が呼び出し元 / オリジン文脈を要求・伝播・対応付けする公開契約、対応付け、通信経路固有の表現、バージョンおよび API 詳細である。呼び出し元検証の最終責任は Signer にあり、ブラウザ観測された呼び出し元 / オリジンはブラウザ特権を持つ層、モバイル検証済み受け渡し文脈はモバイル信頼されたホストが判断権限とする。SDK、Provider、dApp、Relay の自己申告値は信頼された呼び出し元の信頼性判断ではなく、SDK は Signer の検証を代替しない。
- 既存の根拠: SDK 要件 `SDK-SEC-004`、`SDK-OPEN-007`、SDK 設計 §11〜§12、アーキテクチャ §6.9、インターフェース §7、Web トランザクション受け渡し仕様 §7。
- 問題と影響: 前回の「未決が Signer 判断権限まで未決に見える」問題は解消されている。公開 API / 通信経路の未決を残したままでも、呼び出し元の信頼性判断、検証責任主体および SDK Signer ではないこと境界は一意に読める。
- 必要な最小修正または確認: `SDK-OPEN-007` の判断権限境界を維持し、下流公開契約の決定時に観測された / 検証済み文脈を自己申告値へ置換しないこと。
- 完了条件または再確認方法: §26 の未決対象範囲と §2、§9、§18、§19、§23 の判断権限が一致し、下流が SDK を呼び出し元検証の代替として解釈できないこと。現行本文で充足している。
