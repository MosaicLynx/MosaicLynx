## 2. 総評

IF-001〜IF-003 は、いずれも前回の指摘内容を満たす形で解消されている。公開アカウントの識別情報と Signer 内部のアカウント参照、署名結果と配送状態、ネットワーク文脈と Relay / ノードの役割が、それぞれ基本設計上の概念として区別された。

修正後も、秘密情報を共通モデルへ含めない原則、Signer を最終的な署名判断権限とする境界、外部入力を信頼されていないとする扱い、TransactionSummary を署名対象の判断権限としない原則、およびチェーン / ネットワークの分離は維持されている。今回の修正による新たな阻害要因 / HIGH または下位設計を妨げる問題は確認されなかった。

### IF-001: アカウントの公開識別情報とアカウントの内部参照

- **判定:** `RESOLVED`
- **対象箇所:** [`interfaces.md` §6.2](../../design/interfaces.md)（アカウント、公開識別情報と内部参照、特に行 135–170）、§6.3（SigningRequest、行 172–192）
- **前回の課題:** 公開アカウントの識別情報とアプリケーション / Signer 内部のアカウント参照が同じ共通モデル内で区別されず、外部要求元が内部参照を鍵選択へ利用できる余地があった。
- **根拠:** `Account` はチェーン、ネットワーク、アドレス、公開鍵、表示情報を持つアカウントの公開識別情報と定義され、アカウントの内部参照はプロファイル、許可、wallet-core の鍵枠等を Signer 内部で解決する内部文脈と明記された。内部参照は秘密鍵そのものでも導出秘密でもなく、Signer 信頼境界内でプロファイル、許可、アカウントの識別情報、署名文脈と照合して解決・検証される。外部 Web アプリ / dApp / 要求元が任意に指定して鍵を直接選択する対応能力ではなく、公開 API、Relay、dApp、Web アプリへ不要に出さない原則も示されている。
- **推奨事項対応確認:** 内部参照の形式や保存方式を未確定のまま下位設計へ委譲しつつ、外部要求元から提供された参照は補助情報にとどまり、Signer の選択・認可判断権限にならない契約が追加されている。秘密鍵、ニーモニック、シード、復号された秘密情報等を `Account` に含めない原則も維持されている。

### IF-002: 署名結果不明と配送不明の共通結果モデル

- **判定:** `RESOLVED`
- **対象箇所:** [`interfaces.md` §6.4](../../design/interfaces.md)（SigningResponse の結果の状態、行 194–217）、§6.6（エラー、行 238–255）、§9（セキュリティ考慮事項、行 323–334）
- **前回の課題:** `RESULT_UNKNOWN` と `DELIVERY_UNKNOWN` が共通結果モデルに明示されず、`failed` への畳み込みや、二重署名・危険な再試行を防ぐ契約が不十分だった。
- **根拠:** `failed` は処理失敗が確定した状態、`RESULT_UNKNOWN` は成功 / 利用者拒否済み / 失敗のいずれも安全に確定できない処理結果、`DELIVERY_UNKNOWN` は要求 / 応答の配送状態を確定できない処理結果の区分として定義されている。`RESULT_UNKNOWN` は成功として返さず同一要求の自動再署名を行わない。署名生成済みで配送だけ不明な場合は概念上 `success + DELIVERY_UNKNOWN` とし、同じ対象の再署名ではなく既存結果の再送・照会だけを候補とする。要求の配送不明についても、未送信・失敗と推測した同一要求の自動再送を禁止している。
- **推奨事項対応確認:** `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` を `USER_REJECTED`、`SIGNING_FAILED`、`RELAY_ERROR` または相互の別状態へ自動変換しないことがエラーとセキュリティ考慮事項にも反映されている。再試行回数、タイムアウト、受領確認、冪等性、通信上のプロトコルの詳細は下位プロトコル設計へ委譲されており、基本設計として必要な安全上の区別は成立している。既存の [`signing-flow.md` §7.3–§7.4](../../design/signing-flow.md) および §20.3 の責務とも整合する。

### IF-003: ネットワーク文脈と Relay / ノードの意味上の判断権限

- **判定:** `RESOLVED`
- **対象箇所:** [`interfaces.md` §4.1–§4.2](../../design/interfaces.md)（行 75–100）、§6.1（ネットワーク、行 122–133）
- **前回の課題:** ネットワークの生成主体に Relay / ノードを含める表現が、内容を解釈しない通信経路とネットワークの意味上の判断権限の境界を曖昧にしていた。
- **根拠:** ネットワーク文脈を要求へ申告・通信経路する生成主体と、ペイロード・プロファイル・アカウント・対象チェーンと照合して Signer 内のな信頼された文脈を導出・確定する Signer / チェーン固有の統合が明示的に分けられた。Relay とブロックチェーンノードはネットワークメタデータの信頼されていないな搬送元・観測元・候補提供元にとどまり、ネットワークモデルを生成・確定・上書きする判断権限ではない。未確定、誤ったネットワーク、またはチェーン / ネットワーク不一致は署名へ進めないため、Relay が Signer の検証を代替する構造にもなっていない。
- **推奨事項対応確認:** ノード検出、ノード選択、チェーン検証、ネットワーク fingerprinting などの方式をこの基本設計へ過剰に追加せず、検証の最終責任を Signer / チェーン固有の統合に置く整理ができている。[`security-design.md` §11.1–§11.2](../../design/security-design.md) および [`signing-flow.md` §2.4–§2.5](../../design/signing-flow.md) の Relay / ノード信頼モデルとも矛盾しない。

## 4. 回帰確認

| 確認項目                               | 判定     | 確認結果                                                                                                                              |
| -------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 秘密情報の分離                         | 回帰なし | `Account`、`SigningRequest`、`SigningResponse` 等に秘密鍵、ニーモニック、シード、復号された秘密情報等を含めない原則が維持されている。 |
| 安全側での終了                         | 回帰なし | 不明 / 不一致のチェーン・ネットワーク、未検証の内部参照、結果不明・配送不明を成功として扱わない。                                     |
| Signer が最終署名判断権限              | 回帰なし | 内部アカウント解決、ネットワーク検証、署名結果の確定は Signer / チェーン固有の統合側に残っている。                                    |
| Relay がセキュリティ判断権限にならない | 回帰なし | Relay は内容を解釈しない / 信頼されていないな通信仲介であり、署名判断・ネットワーク確定・利用者承認を代替しない。                     |
| 外部入力は信頼されていない             | 回帰なし | 外部要求元、Relay、ノード由来の参照・メタデータ・要約は無条件に信頼されたとされない。                                                 |
| TransactionSummary の位置付け          | 回帰なし | 要約は表示・確認用の導出された情報であり、実署名対象の判断権限ではない。                                                              |
| チェーン / ネットワークの概念分離      | 回帰なし | Symbol / NEM と各ネットワークを別概念として扱い、不一致は署名前に拒否する。                                                           |
| 基本設計と詳細設計の責務分離           | 回帰なし | 再試行、冪等性、通信上のプロトコル、ノード検証等の詳細は下位設計へ委譲されている。                                                    |
