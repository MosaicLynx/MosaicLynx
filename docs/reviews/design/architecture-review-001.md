## 総評

アーキテクチャは、今回の再整理によって全体の基本設計として概ね成立している。

特に、ブラウザ拡張機能とモバイル / Relay の経路を分離し、拡張機能 / モバイルを署名主体、Relay を信頼しない内容を解釈しない通信経路、SDK を公開接続境界、wallet-core を鍵管理・秘密情報処理・生の署名の正本として整理した点は、確定済み要件に適合している。秘密情報、利用者承認、トランザクション / メッセージの意味解析、チェーン / ネットワークの整合性、結果対応、サービスワーカー / モバイルライフサイクル、オンラインノード処理の責任も、基本設計として追跡できる。

一方、下流設計へ進む前に、wallet-core の既に固定されたバインディング方式と MosaicLynx 側で未決のプラットフォーム統合方式を区別し、WASM バインディングが実行コンテキストから秘密情報を隔離するものではないことをアーキテクチャ上で明確にする必要がある。いずれも責任分界の方向を変更する指摘ではなく、下流実装の誤解を防ぐための限定的な修正である。

## 良好な点

- v1 の対象と対象外を分け、アナウンス、ノード選択、残高・履歴、継続的ネットワーク状態、内容を確認しない署名、プロファイル全体バックアップ / 復元の共通必須化、MPC / ハードウェアウォレット / enterprise カストディ等を現行必須設計から除外している。これは共通要件 `CR-014`、`FUTURE-001` およびコンセプトの製品境界に整合する。
- ブラウザ拡張機能の Provider / コンテンツスクリプトを秘密情報を扱わない搬送境界とし、特権を持つ層でブラウザ文脈、許可、チェーン / ネットワーク / アカウント、要求完全性、承認および結果対応を扱っている。`BR-002`〜`BR-008`、`CR-NFR-008`〜`CR-NFR-011` に対応する。
- サービスワーカーの停止・再起動・更新・タブ / 文書変更を、秘密鍵、ロック解除済みセッションまたは承認済み要求の安全な自動再開の前提にしていない。失われた文脈や承認を安全側に無効化する方針は `BR-007`、`BR-008`、`CR-NFR-010`、`CR-NFR-011` に適合する。
- モバイルアプリを拡張機能の単純な移植とせず、ドメイン、要求モデル、承認ポリシーおよび wallet-core 境界を共有し、OS ライフサイクル、受け渡し、OS 保護、認証、モバイル UI をホスト固有責任としている。`MR-001`〜`MR-007`、`MR-OPEN-002`〜`MR-OPEN-006` の扱いと整合する。
- Relay を内容を解釈しないエンベロープ、最小限の通信経路メタデータ / 認可、短期間のみ有効な状態、世代 / 古くなった / 重複の構造上の検証に限定し、意味上の内容検査、表示、承認、署名、秘密情報処理、アナウンスおよび長期履歴を担わせていない。`RR-003`、`RR-006`、`RR-008`、`RR-009` と整合する。
- SDK を dApp と署名主体の通信経路非依存な公開境界として位置付け、秘密鍵、ニーモニック、Vault 復号、生の署名、承認 UI、最終的な意味解析およびノード処理を担わせていない。拡張機能経路とモバイル / Relay 経路の操作、結果、失敗分類を共通化しつつ、危険な自動代替経路を禁止している点は `SDK-FR-009`、`SDK-SEC-001`、`SDK-SEC-007`、`SDK-ERR-001` に適合する。
- wallet-core と MosaicLynx の責任分界が明確である。wallet-core はウォレットストア、ニーモニック / ソフトウェア鍵、鍵導出、公開識別情報、暗号、生の署名を担い、MosaicLynx はプロファイル / アカウントのアプリケーション管理、許可、意味解析、表示、承認、ホスト / Relay 統合および処理の調整を担う。`CR-013`、`CR-AC-010`、`BR-009`、`MR-007` と整合し、旧来の MosaicLynx 側独自鍵導出・暗号・生の署名・同一秘密鍵共有の前提を再導入していない。
- Symbol / NEM は要求 / 承認 / ライフサイクルの共通モデルと、トランザクションスキーマ、メッセージ形式、アドレス、ネットワーク定数、意味上の内容検査、署名対象バイト列等のチェーン固有責務を分けている。`CR-005`、`CR-NFR-005` および wallet-core のチェーン互換性契約に適合する。
- 外部ノードへの問い合わせなしに要求検証、解析・表示、承認、wallet-core 署名、結果検証を完了できるローカル境界を示し、air-gapped 初回ウォレットと混同していない。MosaicLynx がノード / アナウンスを担わない点も `CR-006`、`CR-011`、`CR-AC-004` に整合する。
- `apps/mobile` が現行ワークスペースに存在しないことを明示し、モバイルの構成を実装済み・検証済みと誤認させていない。`apps/link-fallback`、`packages/*`、`apps/*` の対応付けも、実装の古さをアーキテクチャの責任として取り込まず、移行対象として扱っている。
- Mainnet 対応能力の安全側での終了方針をアーキテクチャに残し、`docs/adr/0001-mainnet-evidence-lite.md` と共通要件 `CR-NFR-006` の存在を壊していない。

## 指摘事項

### AR-001

- ID: `AR-001`
- 重要度: `MEDIUM`
- 対象: `docs/design/architecture.md` §5.2、§6.4、§6.8、§15、§17
- 問題: アーキテクチャは `CR-OPEN-001` / `CR-OPEN-002` の説明として、wallet-core の「バインディング、FFI / WASM / ネイティブ」を未決事項として列挙している。MosaicLynx 側のプラットフォーム統合、React ネイティブ連携、秘密情報の一時受け渡し、OS 保護との組み合わせ、エラー対応付けが未決であることは正しい。一方、wallet-core 側の v1 バインディング方式そのものは `_snwc/docs/decisions/binding-implementation.md` と `_snwc/docs/specifications/specification.md` §13 で、WASM は `wasm-bindgen`、ネイティブは C ABI と既に固定されている。現記述のままでは、MosaicLynx の後続設計が wallet-core の v1 バインディング方式まで自由に再選択できるように読める。
- 根拠: 共通要件 `CR-013`、`CR-OPEN-001`、`CR-OPEN-002` は責任境界を確定したうえでアプリケーションからの具体的統合方式を後続設計へ委ねている。採用済み外部決定 `_snwc/docs/decisions/binding-implementation.md` §決定、`_snwc/docs/specifications/specification.md` §13 は wallet-core の v1 バインディング方式を固定している。アーキテクチャ §6.8、§17 はこの二層を分けずに記述している。
- 影響: コンポーネント設計がネイティブ / WASM の再選択や独自バインディングの追加を前提に進み、wallet-core の公開契約・所有権・エラー / 警告境界と競合する可能性がある。MosaicLynx 側でバインディングに鍵管理・暗号・署名を再実装する誘因にもなる。
- 推奨対応: 「wallet-core v1 のネイティブ / WASM バインディング方式は外部決定に従い固定済み」と明記し、未決範囲を「各ホストがどの固定済みバインディングを利用するか、必要なアダプター / React ネイティブ連携、OS 保護との組み合わせ、秘密バイトの一時ライフサイクル、エラー対応付け、既存 TypeScript 実装からの移行」に限定する。方式を変更する場合は `_snwc` の決定・仕様更新が先行することも示す。

### AR-002

- ID: `AR-002`
- 重要度: `MEDIUM`
- 対象: `docs/design/architecture.md` §8、§9、§11、§15
- 問題: wallet-core を「独立した秘密情報境界」と表現しているが、wallet-core の WASM バインディングは JavaScript と同じ実行文脈で動作し、WASM 自体は JavaScript から秘密情報を隔離するセキュリティ境界ではない。現アーキテクチャは Web ページ / Provider / コンテンツスクリプトから wallet-core へ直接到達させない構成を別途示しているため、直ちに要件違反ではない。しかし、論理的な責任・API 境界と、実行コンテキスト・プロセスによるセキュリティ分離が区別されていない。
- 根拠: `_snwc/docs/decisions/binding-implementation.md` §WASM / ブラウザセキュリティ契約は、WASM が同じ JavaScript 実行文脈にあり、ページ文脈へ wallet-core を直接公開すべきでないと明記する。`BR-006`、`BR-011`、`CR-NFR-002` はページ / 拡張機能の分離と秘密情報の不要な複製・出力禁止を要求する。アーキテクチャ §5.1、§8、§11 はページ / コンテンツスクリプト分離を示す一方、wallet-core の境界を独立した秘密情報分離と読める表現である。
- 影響: ブラウザ拡張機能の WASM バインディングをページ文脈やコンテンツスクリプトに公開しても wallet-core が隔離してくれる、またはバインディング内のゼロ化が JavaScript 側のコピーを消去する、という誤った脅威モデル・実装判断につながる。秘密情報の最終保護責任、信頼されたホストの範囲、WASM とネイティブの保証差のレビューが不十分になる。
- 推奨対応: 図と本文を「wallet-core は秘密情報処理の正本であり、MosaicLynx との論理/API 責任境界。ただしバインディング自体がホスト実行環境から秘密情報を隔離するとは限らない」と明確化する。ブラウザではバインディングをページ / コンテンツスクリプトに公開せず特権を持つ拡張機能文脈だけから呼ぶこと、モバイルでは選択したホスト / OS 保護境界の保証範囲を別途定義すること、WASM の入力バッファーや実行環境コピーの完全消去を保証しないことを、信頼境界の前提として残す。

## 下流設計への影響

このアーキテクチャを基に、Relay の具体通信上の / 保存領域、Provider と受け渡しの契約、チェーン固有の意味上の内容検査、モバイルホストの詳細、プロファイル / アカウントの対応、wallet-core アダプターの設計へ進むことはできる。

ただし、次の二点はコンポーネント設計の開始前または並行してアーキテクチャの記述を限定的に修正すべきである。

1. wallet-core の v1 バインディング方式を固定済みの外部契約として扱い、MosaicLynx 側の未決対象範囲をホスト統合に限定する。
2. wallet-core の論理的な秘密情報責任境界と、WASM / ネイティブ / ホスト実行環境の実際の分離を分けて記載する。

これらを修正しても、既存の `packages/chain-symbol` / `packages/chain-nem` の重複処理、現行 Relay 実装、モバイル未実装、既存受け渡し仕様の古い詳細を直ちに変更する必要はない。要件を満たす下流仕様・移行計画・実装レビューで別途扱うべき事項であり、今回のアーキテクチャレビューの判定を下流実装の現状だけで変更していない。

## 最終判定

`READY WITH CONDITIONS`

基本設計としては成立しており、全体構成、責任分界、依存方向、信頼境界、秘密情報境界、署名フロー、Relay、SDK、ブラウザ拡張機能、モバイル、Symbol / NEM、オンライン / ローカル境界および対象外範囲を、確定済み要件に適合する形で判断できる。

ただし、`AR-001` と `AR-002` の二点は、wallet-core アダプターとホストセキュリティの下流設計を開始する前に、アーキテクチャ上で明示しておく必要がある。いずれも限定的な記述修正であり、阻害要因または HIGH に相当する根本的不整合、Relay の信頼境界破綻、秘密情報のページ / Relay 直接露出、または要件自体の矛盾は確認されなかった。
