## レビュー結果

**REVISE 設計**

## 要約

ブラウザ拡張機能の基本的な信頼境界、ブラウザ観測オリジン、Provider / コンテンツスクリプトの非権限化、信頼された UI、ページ遷移・再読み込み・サービスワーカーライフサイクル、要求分離、`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN`、自動代替経路禁止、wallet-core との暗号学的な責務分離は、上位資料と概ね整合している。

ただし、共通署名ゲート4条件をブラウザ署名主体の独立した必須条件として明記できておらず、メッセージ署名の構造化文脈 / リプレイ不変条件と、署名成功結果に必要な署名時の文脈が不足している。また、上位で必須化済みのメッセージ署名を `OPEN` のまま残している。これらは下位 API の不足ではなく、ブラウザ特権を持つ層の責務・セキュリティ上の不変条件・下流実装の成立条件に関わる。

## 必須の修正

### DR-001 — 重大

- 対象: [`browser-extension.md §4, §5.3, §10, §12, §15, §20`](../../design/browser-extension.md:48)
- 事実 / 条件:
  - ブラウザ設計は `Authentication` と `Explicit approve/reject` を記載するが、`Account authorization` を責務・条件として明示していない。
  - `§12` の `AUTHORIZED` は「利用者承認 + 要求ごとの認証」の2要素として記載され、`Signing-capable unlock` と `Account authorization` が同じ要求の独立条件として含まれていない。
  - `§15` は一時的な署名可能な状態を扱うが、それが共通ゲートの必須条件であること、ブラウザ特権を持つ層が責任主体であること、他の状態が代替にならないことを確定していない。
  - `§10` の署名前再検証はプロファイルと4条件それぞれの署名時の文脈を明示せず、`§20` の不変条件も要求固有の認証と承認のみを明示する。
- 根拠:
  - 共通アーキテクチャは特権を持つ層が `Authentication`、`Signing-capable unlock`、対象プロファイル / チェーン / ネットワーク / アカウントの `Account authorization`、`Explicit approval` の全4条件を所有し、全て必須とする [`architecture.md §6.9`](../../design/architecture.md:210)。
  - 署名フローは4条件を独立かつ同時に要求し、接続、許可、対応能力、セッション、通常の `UNLOCKED`、過去の認証、wallet-core パスワード / ストア成功を代替にしない [`signing-flow.md §4`](../../design/signing-flow.md:74)。
  - インターフェースもアプリケーションのアカウントの利用認可と特権を持つ署名主体の4条件判定条件を分離している [`interfaces.md §8–9`](../../design/interfaces.md:350)。
- 問題: ブラウザ拡張機能の最終署名主体が、4条件を同一署名要求に対する独立した必須判定条件として成立・再確認・無効化・成功結果へ引き継ぐ設計になっていない。`Account authorization` の責任主体もブラウザアプリケーション / 特権を持つ層として確定していない。
- 影響: 実装が許可、アカウント選択、セッション、通常のロック解除、以前の認証、wallet-core パスワード / ストア復号成功を認可や署名可能な状態へのロック解除の代替として扱い、dApp / Provider / コンテンツスクリプトが判定条件の成立・変更・免除へ影響できる余地が残る。プロファイル / アカウント切り替え後の保留中の認可、署名前、成功結果が同じ4条件へ結び付かない場合、誤ったアカウントからの署名や承認迂回につながる。
- 最低限必要な修正: ブラウザ特権を持つ層を4条件の唯一の処理の調整責任主体として明記し、同一要求・プロファイル・アカウント・チェーン / ネットワーク・対象に対して `Authentication`、`Signing-capable unlock`、`Account authorization`、`Explicit user approval` の全てを独立に必須とする。接続 / 許可 / 対応能力 / セッション / 通常の `UNLOCKED` / 前回認証 / wallet-core パスワードまたはストア検証は代替でないこと、署名前に全てを再確認し、変化時に認可 / 承認を失効させ、成功結果に署名時の 4-condition 文脈を必須化することを追加する。具体的な認証方式、状態名前、通信上のスキーマは下位へ委譲してよい。
- 再確認条件: ブラウザ設計のフロー、ライフサイクル、セキュリティ上の不変条件、責務表に4条件と特権を持つ責任主体が明示され、署名前と成功結果が4条件を全て同じ要求 / プロファイル / アカウント / 対象へ結び付けする。Provider / コンテンツスクリプト / SDK / dApp と wallet-core が判定条件を成立・変更・免除できないこと、および4条件のいずれかの失効が安全側での終了になることを確認できる。

### DR-002 — 重大

- 対象: [`browser-extension.md §10.1–10.3, §16, §20, §23`](../../design/browser-extension.md:268)
- 事実 / 条件:
  - ブラウザ設計はトランザクションの一般的な内容検査項目と `message` の存在には触れるが、メッセージ署名固有のドメイン / 目的 / ノンス / 発行された・期限切れ / メッセージリプレイ結び付け / 目的間の分離を必須不変条件として定めていない。
  - `§16` はアグリゲート / 連署 / 部分トランザクションと NEM マルチシグを詳述する一方、構造化されたメッセージの呼び出し元・ドメイン・目的・ノンス・有効期限を独立した署名対象・表示対象として扱わない。
  - `§23` はメッセージ署名の公開操作と対応済みの対象範囲を未決として残している。
- 根拠:
  - 共通要求は v1 でメッセージ署名を必須とし、内容を利用者が確認でき、生の / 内容検査できないメッセージ代替経路を許さない [`requirements.md CR-007-MSG`](../../requirements/requirements.md:175)。
  - 署名フローはメッセージをトランザクションと別の `MESSAGE_SIGN` 文脈とし、呼び出し元 / プロファイル / アカウント / チェーン / ネットワーク / 目的 / ドメイン / ノンス / 発行された・期限切れ / 鮮度 / リプレイを結び付けする [`signing-flow.md §14`](../../design/signing-flow.md:359)。
  - ブラウザ仕様は構造化されたメッセージの公開操作、同じメッセージモデルからの表示・署名バイト列、リプレイ防止、生の任意のメッセージ禁止を既に適用している [`browser-extension.md §16`](../../specifications/browser-extension.md:427)。
- 問題: ブラウザの基本設計がメッセージ署名をトランザクション署名と同じ共通判定条件へ接続するだけでなく、メッセージ固有の文脈分離とリプレイ不変条件を要求していない。`message` を任意ペイロードと解釈する余地があり、下流が構造化されたメッセージ契約を省略しても設計違反を検出できない。
- 影響: 同じメッセージの再利用、別オリジン / 目的 / ドメインへの文脈間のリプレイ、表示内容と署名バイト列の不一致、生のまたは表示不能のメッセージの署名をブラウザ署名主体が拒否できない設計になり得る。共通要求およびメッセージ署名 v1 の相互運用性を満たせない。
- 最低限必要な修正: ブラウザ設計に `MESSAGE_SIGN` を既存の構造化されたメッセージ契約として適用することを明記し、ブラウザ観測された呼び出し元、プロファイル / アカウント、チェーン / ネットワーク、ドメイン / 目的、メッセージ内容、ノンス、発行された・期限切れ、要求鮮度 / リプレイを内容検査、承認、署名前、結果に結び付けする。同一信頼されたモデルが UI と署名入力の根拠であること、生の任意の / 内容検査できないメッセージ代替経路がないことも明記する。ノンスのバイト長や具体通信上のスキーマは仕様へ委譲してよい。
- 再確認条件: メッセージ署名の独立したブラウザフロー / 不変条件として、文脈分離、メッセージ単位のリプレイ保護、構造化された内容検査、4条件、署名前再検証、結果との結び付け、安全側での終了が追跡できる。トランザクションとメッセージの対応付けが操作の混同や生の代替経路を許さないことを確認できる。

### DR-003 — 主要

- 対象: [`browser-extension.md §7.3, §10.2, §12, §20`](../../design/browser-extension.md:221)
- 事実 / 条件:
  - 応答結び付けは要求識別情報、セッション、オリジン、閲覧文脈、操作、アカウント、チェーン / ネットワーク、対象を列挙するが、プロファイルと署名時の 4-condition 文脈を列挙していない。
  - `SUCCEEDED` は「署名結果を検証し、要求結び付け」とするのみで、署名時点の認証、署名可能な状態へのロック解除、アカウントの利用認可、明示的な承認の全てを成功条件として要求していない。
  - `§20` の結果不変条件もオリジン / セッション / 文脈 / 対象 / 操作までで、プロファイルと署名主体、4条件の時点付き文脈が欠ける。
- 根拠: 署名フローは成功結果の概念に元要求 / 呼び出し元、署名主体、プロファイル / アカウント、チェーン / ネットワーク、厳密な対象ダイジェスト、署名時の 4-condition 文脈、承認文脈を含め、全て検証できなければ成功としない [`signing-flow.md §19`](../../design/signing-flow.md:500)。
- 問題: ブラウザ設計の結果との結び付けが、署名対象を正しい要求へ戻す相関だけでなく、正しいプロファイルと署名時点の全判定条件が成立した結果であることまで保証していない。
- 影響: プロファイル切り替え、アカウント関連付け変更、ロック、許可リビジョン、approval/authentication 状態の変化を一般的な要求結び付けが捕捉できない場合、署名自体が cryptographically 有効なでもブラウザが誤った文脈の成功として返し得る。配送失敗と署名時の認可失敗の境界も下流実装へ不適切に残る。
- 最低限必要な修正: ブラウザの成功不変条件に、元要求、呼び出し元、タブ / フレーム / 文書、プロファイル、アカウント、チェーン / ネットワーク、操作、厳密な対象またはダイジェスト、署名時の4条件、承認文脈を必須化する。これらの一つでも再検証不能、古くなった、文脈消失、不明なら成功を返さず、`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` の既存区分へ接続する。具体応答スキーマは下位へ委譲してよい。
- 再確認条件: 署名前から wallet-core 結果検証、元の受信者への配送まで、プロファイルと4条件を含む同一結び付け組が明示され、別文書への返却・古い認可の成功化・配送失敗の再署名が拒否されることを確認できる。

### DR-004 — 主要

- 対象: [`browser-extension.md §23`](../../design/browser-extension.md:550)
- 事実 / 条件: ブラウザ設計は `message signing public operation and supported scope` を未決事項としている。しかし共通要求ではメッセージ署名 v1 がブラウザを含む各クライアントの必須能力であり、現行ブラウザ仕様では `signMessage` / `MESSAGE_SIGN` と構造化されたメッセージの境界が定義済みである。
- 根拠:
  - 共通要求はブラウザ / Android / iOS のトランザクション署名とメッセージ署名を v1 の提供対象として固定している [`requirements.md OPEN-003`](../../requirements/requirements.md:455) および [`CR-007-MSG`](../../requirements/requirements.md:175)。
  - ブラウザ仕様は `MESSAGE_SIGN`、構造化されたメッセージ、呼び出し元 / チェーン / ネットワーク / 目的 / ノンス / 期限切れの結び付けを下位契約として固定している [`specifications/browser-extension.md §16`](../../specifications/browser-extension.md:427)。
  - 署名プロトコルはメッセージのリプレイ / ドメイン間の / 目的間の防止と生の代替経路禁止を定めている [`signing-protocol.md`](../../specifications/signing-protocol.md:475)。
- 問題: 既に上位要求・共通設計・下流仕様で対応能力の存在とセキュリティ境界が決まっている事項を設計の `OPEN` に戻している。実装者がメッセージ署名自体を v1 外、任意対応能力、または後続対象範囲と解釈する余地がある。
- 影響: `DR-002` の不足を固定化し、ブラウザと SDK / 署名プロトコルの追跡可能性を切断する。メッセージ署名を有効化しない、またはトランザクションと異なる弱い承認 / リプレイ意味で実装するリスクがある。
- 最低限必要な修正: `OPEN` をメッセージ署名対応能力の有無ではなく、既定の構造化されたメッセージ契約をブラウザ API / 通信上の / 有効期限フィールドへどう接続するかという下位統合事項へ限定する。v1 で `MESSAGE_SIGN` を提供し、DR-002 の不変条件に従うことは設計で確定する。API 名、フィールド名、厳密な期限切れ window は仕様へ委譲してよい。
- 再確認条件: §23 の未決事項を上位決定と矛盾しない粒度へ修正し、ブラウザのメッセージ署名対応能力、構造化された内容検査、リプレイ / ドメイン分離、共通4条件、結果意味が `requirements`、`signing-flow`、`browser-extension specification` へ追跡できる。

## 任意の改善

### DR-005 — 軽微

- 対象: [`browser-extension.md §2, §22, §24`](../../design/browser-extension.md:9)
