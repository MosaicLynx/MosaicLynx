## 5. 要約

SDK の署名主体ではないこと、Provider 検出 / 対応能力、接続 / 許可、呼び出し元 / オリジン、4条件の署名主体所有責任、プロファイル / アカウント / チェーン / ネットワークの非権威的な搬送、トランザクション / `MESSAGE_SIGN` の操作分離、対応付け、タイムアウト / キャンセル、秘密情報 / wallet-core、ローカル / リモートの自動代替経路禁止および Mainnet 判定条件非代替は、基本的に現在の共通設計と整合する。

一方、[`sdk.md`](../../design/sdk.md) §21 行569は `Relay / remote handoff failure` を `transport failure / result unknown` とすると記載している。最新の署名フロー、インターフェースおよび Relay 設計が確定した `RESULT_UNKNOWN`（署名生成自体の成否不明）と `DELIVERY_UNKNOWN`（既知の署名済み結果の配送処理結果の区分不明）は署名主体側の処理結果の区分であり、SDK / Relay の Provider、通信経路、タイムアウト、応答欠如、接続解除、オフライン、状態消失または配送失敗から生成・推測・確定してはならない。この判断権限が SDK 設計本文で明確に分離されておらず、`DELIVERY_UNKNOWN` の扱いも明記されていないため、下流実装者が通信経路失敗を署名主体側の処理結果の区分へ昇格させる余地が残る。

この1件は通信経路失敗、署名結果、配送処理結果の区分、再試行 / 再配送 / 再署名の安全境界を横断し、4つのレビュー判定条件を不合格にするため重大と判定する。正式指摘は今回新規の `DR-001` のみであり、旧 SDK レビューの ID は捏造していない。

## 7. 必須の修正

### DR-001: Relay / 通信経路失敗と署名主体側の処理結果の区分の判断権限混同

- 重要度: `Critical`
- 状態: `New`
- 対象: [`docs/design/sdk.md`](../../design/sdk.md) §15.1〜§15.2（行438、453）、§16.3（行482）、§17（行496）、§21（行569〜572）、§22（行589）、§25（行635）。中心は §21 行569。
- 確認できた事実: §21 は `Relay / remote handoff failure` の SDK 処理を `transport failure / result unknown とする` と記載する。§15 は SDK が `result unknown` を受け取ることを記載するが署名主体が生成した処理結果の区分として限定せず、§16.3 はページライフサイクル消失を `unknown / failure` と外部へ伝えるとしている。SDK 設計全体に `DELIVERY_UNKNOWN` の責任主体、署名主体が生成したそのまま通過させる、または通信経路状態からの生成禁止を明示した箇所はない。
- 正本となるな対照: 署名フローは `RESULT_UNKNOWN` を署名生成自体の成否不明、`DELIVERY_UNKNOWN` を既知結果の配送不明として分離し、配送失敗を `RESULT_UNKNOWN` にしない。インターフェースは通信経路 / Relay 失敗と両処理結果の区分の相互変換を禁止する。最新 Relay 設計 §29 は SDK の責務を通信経路 / Provider / Relay エラー正規化、通信経路レベルの失敗分類の公開、署名主体が生成した処理結果の区分の意味不変伝達に限定し、SDK / Relay に両処理結果の区分の生成・推測・確定判断権限を与えていない。
- 問題: 現行文言を単独で実装へ引き渡すと、Relay 障害、リモート受け渡し失敗、タイムアウト、応答欠如、Provider 接続解除、ページライフサイクル消失、受信者オフライン、再接続失敗または配送失敗を、署名生成の成否不明である `RESULT_UNKNOWN`、または既知署名済み結果の配送不明である `DELIVERY_UNKNOWN` として SDK が確定する解釈が成立する。これは通信経路失敗と署名主体側の結果 / 配送処理結果の区分の判断権限を混同する。
- 影響: SDK が署名結果正確性判断権限を持つことになり、既知の結果の再配送 / 取得と署名再試行を誤って選択し、`RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` 後の再署名禁止または新鮮な要求条件を誤適用する。Relay / SDK の可用性やページライフサイクルが署名結果の意味へ昇格し、署名主体、dApp、利用者への結果伝達とコンポーネント間の復旧が不安全になる。
- 最小修正: §21 の該当行を通信経路 / 受け渡し / ライフサイクル失敗のみとして扱うよう修正し、SDK は Provider / Relay / 通信経路状態、タイムアウト、応答欠如、接続解除、オフライン、再接続失敗、配送失敗またはページ消失から `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` を生成・推測・確定しないことを明記する。`RESULT_UNKNOWN` は署名主体が署名生成自体を確定できない場合、`DELIVERY_UNKNOWN` は署名主体が既知署名済み結果の配送処理結果の区分を確定できない場合だけとし、署名主体が生成した処理結果の区分は SDK が意味を変更せず対応付けして伝達する。既知結果の配送処理は再送 / 取得 / 照会の候補に限り、再署名しない。§15、§16、§17、§22、§25 の関連記述もこの判断権限分離と一貫するようにする。具体 API、エラーコード、通信上の形式、タイムアウト値および再試行回数は追加要求しない。
- 完了条件 / 再確認: SDK 設計を単独で読んだとき、通信経路レベルの失敗分類と署名主体が生成した `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` が区別され、前者から後者を生成・推測・確定できないこと、署名主体が生成した処理結果の区分は意味不変に伝達するだけであること、既知の結果の再配送と再署名が分離されることを確認する。§21 行569に通信経路失敗 → `result unknown` の直接対応が残らないことを再確認する。

## 15. 残存リスクと未決定事項

- `DR-001` が解消されるまで、Relay / リモート受け渡し失敗、タイムアウト、ページライフサイクル消失、応答欠如および配送失敗のアプリケーションに公開する分類を、署名主体側の処理結果の区分と同一視して実装してはならない。
- Provider 検出ポリシー、具体的なキャンセルプロトコル、通信経路選択、実行環境サポート、互換性対応表、厳密なタイムアウト / 再試行、エラーコード、受け渡しスキーマ、結果取得 API は既存の要件 / 仕様の未決または下位委譲に残る。ただし `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` の意味、通信経路失敗との分離、no 自動再署名 / 代替経路は既決であり、未決に戻らない。
- Mainnet リリース証跡の収集、署名、信頼された鍵、ビルド埋め込み、実行環境強制およびリリース操作は別の責任主体で確認する。SDK / Relay 正常性は Mainnet 判定条件ではないという責務境界は追跡可能である。

## 17. 最終判断

`REVISE DESIGN`

`DR-001` は、Relay / Provider / 通信経路失敗と署名主体が生成した `RESULT_UNKNOWN` / `DELIVERY_UNKNOWN` の判断権限を SDK 設計が明確に分離できていないという重大指摘である。したがって、SDK 基本設計は最新共通設計と整合するよう §15〜§25 の関連記述を補正するまで、次の設計 / 実装受け渡しへ進めない。

指摘集計: `Critical 1 / Major 0 / Minor 0`。旧 SDK レビューの `READY` は継承していない。
