## 総評

Relay を Signer から分離し、障害、改ざん、差し替え、リプレイ、重複配送、遅延配送、認証情報漏えいおよび結果不明を意図しない署名へつなげない責任境界は、前回レビューより明確になっている。`RR-008` の署名秘密情報と通信経路認証情報の分離、`RR-NFR-003` の上限のある保持、`RR-NFR-005` の安全側失敗分類、受け入れ条件および追跡可能性の追加も適切である。

ただし、現状は仕様化へ進めない。共通要件がトランザクション署名とメッセージ署名を v1 の確定 MUST としているのに対し、Web トランザクション受け渡し仕様はメッセージ署名を v1 対象外としており、下流文書の不整合が未解消である。また、Relay が E2E の内容を解釈しない暗号文だけを扱うべきことが、Relay 要件自身の検証可能な MUST として明示されていない。さらに、Relay の状態消失後に古い要求を同じセッション / 要求識別情報で再登録できないことが、要件として十分に閉じていない。

## 指摘事項

### RREQ2-001 — `ERROR` — メッセージ署名の v1 受け渡し契約が下流仕様と未整合

- 状態: `OPEN`
- 対象: `docs/requirements/relay.md:23-25,52-66,212-217,244-250,261-267`、`docs/requirements/requirements.md:156-183,401,418-423`、`docs/specifications/web-transaction-handoff-spec.md:11-38,102-117`
- 根拠: 共通要件 `CR-007` / `CR-007-MSG` はトランザクション署名とメッセージ署名を各 Signer の v1 共通能力として確定し、Relay に必要な要求・結果の受け渡しを要求している。Relay 要件も `RR-001`、`RR-002`、`RR-AC-007`、`RR-AC-008`、`RR-AC-010` で両操作を必須としている。一方、Web トランザクション受け渡し仕様の v1 対象外には「メッセージ署名」が残っている。同仕様の公開 API には `signData()` が存在するため、文書内でも対象範囲が一致していない。Relay 要件がこの不整合を認識し、下流仕様の修正を引き継いでいることは確認できるが、レビュー時点では契約が確定していない。
- 影響: Relay マイルストーンが v1 適合となる操作範囲、メッセージ署名のモバイル受け渡し、dApp の共通結果・失敗処理および完了判定を一貫して検証できない。トランザクション署名だけを実装した下流仕様を、現行の Relay 要件と同時に適合扱いできる余地が残る。
- 必要な修正: メッセージ署名を Relay v1 の確定必須範囲として維持するなら、Web トランザクション受け渡し仕様の対象外記載、対応範囲表、受け入れ条件、エラー / 結果契約および関連テストを `CR-007-MSG`、`RR-001`、`RR-002`、`RR-AC-010` に整合させる。メッセージ署名を除外する場合は Relay 要件だけでなく共通要件、共通受け入れ条件、モバイル / プロダクトの v1 範囲を同時に変更する必要があり、下流仕様を根拠に本要件を弱めてはならない。

### RREQ2-002 — `WARN` — Relay が E2E の内容を解釈しない暗号文を扱う要求と受け入れ条件が不足

- 状態: `OPEN`
- 対象: `docs/requirements/relay.md:23-27,38-48,54-58,62-72,184-200,206-217,221-240`、`docs/specifications/product-spec.md:91-95,554`、`docs/specifications/web-transaction-handoff-spec.md:456-498,500-513`
- 根拠: プロダクト仕様はモバイル Relay がトランザクションを解析せず E2E 暗号文だけを短時間保管し、Relay 侵害への対策を E2E AEAD と対応能力分離で行う前提を置いている。下流受け渡し仕様も要求 / 応答を暗号化エンベロープとし、Relay は暗号文を復号しないと定める。しかし Relay 要件の「意味を解釈、解析、表示しない」「秘密情報を扱わない」は、平文のトランザクション / メッセージ / 要求 / 結果を受信したうえで解釈だけしない実装も排除しない。`RR-AC-006` は署名秘密情報と認証情報の保護を確認するが、暗号文のまま扱うこと、平文ペイロードを Relay の API・保存領域・ログ・診断へ出さないことを直接確認しない。
- 影響: Relay が侵害された場合に、署名秘密情報ではないトランザクション内容、メッセージ内容、オリジン、アカウント等の受け渡しペイロードが Relay 運用者やログ基盤へ露出する実装でも、Relay 固有要件だけでは不適合と判定しにくい。Relay の責任境界とプロダクト仕様の「E2E Relay」前提が要求段階で閉じない。
- 必要な修正: Relay は要求 / 応答の意味内容を復号・解釈せず、暗号化された内容を解釈しないエンベロープと必要最小限の安全なメタデータだけを扱うことを `MUST` として明記する。平文ペイロード、復号結果、暗号文の復元可能な記録を API 応答、有効な保存領域、バックアップ、ログ、診断情報、利用状況分析 / 遠隔計測データへ出さないことを要求し、`RR-AC-002`、`RR-AC-006`、`RR-AC-011` 等から確認できる受け入れ条件を追加する。暗号アルゴリズム、ノンス、KDF 等の具体方式は本要件で固定する必要はない。

### RREQ2-003 — `WARN` — Relay 状態消失後の古い要求識別情報再登録に対する保証が不十分

- 状態: `OPEN`
- 対象: `docs/requirements/relay.md:74-86,99-109,150-158,206-217,252-257`、`docs/requirements/requirements.md:397-400`、`docs/specifications/web-transaction-handoff-spec.md:534-545,579-594`
- 根拠: `RR-004`、`RR-006`、`RR-NFR-003` は再起動・内部状態消失後の古い保留中の要求、リプレイ、再利用および追加署名を禁止し、`RR-AC-003`、`RR-AC-011` も再起動後の古い状態の再出現・再利用不能を受け入れ条件にしている。しかし、状態消失後に同じ `session ID`、`request ID`、認証情報または暗号化要求を新規作成 APIへ再送した場合に、それを新しい受け渡しとして受理してよいのか、また参加者側が必ず新しい署名要求として扱えるのかは明記されていない。下流仕様のセッション作成時の一意性拒否は、有効な状態が消失した後の再登録を単独では防がない。
- 影響: Relay 再起動・Redis 状態消失の直後に、古い暗号化要求が同じ識別情報で再登録され、モバイル側の状態や利用者の意図に依存して再処理される余地が残る。`RR-004` の「新しい署名要求として扱う」と `RR-006` の「古い要求の再利用禁止」を、実装・障害注入テストで一貫して判定できない。
- 必要な修正: Relay または dApp / モバイルが、状態消失後に旧識別情報を再利用できないこと、再試行時は新しい要求識別情報と新しい署名承認を必要とすることを、方式非依存の MUST として明記する。状態を失った Relay が旧セッションを受理しない、または参加者が旧セッションを署名対象として再承認しないことを含む受け入れ条件を追加し、再起動・状態消失後の再登録、遅延配送、同一暗号文の再送を障害注入 / 競合テストで確認できるようにする。具体的な世代、削除記録、ノンス、永続保存領域の方式は後続仕様へ委ねてよい。

### RREQ2-004 — `NIT` — `MAY` の適用主体と Relay マイルストーンの完了判定の関係が曖昧

- 状態: `OPEN`
- 対象: `docs/requirements/relay.md:13-17,242-267`
- 根拠: `MAY` は「v1 の成立条件ではないが許容される事項」と定義されているが、Relay の対象範囲、運用者、モバイル / dApp の実装上の任意事項のいずれに適用されるかが明示されていない。また `RR-OPEN-001` は Relay マイルストーンの個別完了条件を後続判断へ委ねている。
- 影響: `MAY` の事項を Relay の適合条件に含めるのか、許容される実装差異として扱うのかをレビュー・リリース判定で再現しにくい。
- 必要な修正: `MAY` は適用主体の要求を緩和せず、追加機能・実装選択に限ることを明記するか、Relay 要件では `MUST` / `SHOULD` のみを使用する。`RR-OPEN-001` では、少なくとも `RR-AC-001`〜`RR-AC-012` と共通 `CR-AC-004`〜`CR-AC-016` を満たすことが Relay マイルストーン完了の下限であると追跡する。

## 確認できた整合事項

- `RR-008` は署名秘密情報と通信経路認証情報を分離し、認証情報の生の値・セッション秘密情報・導出鍵の露出禁止を明示している。
- `RR-NFR-003` と `RR-AC-011` は、長期履歴化を避け、終端後の要求 / 結果 / 認証情報 / メタデータの再利用を禁止する方向で整合している。
- `RR-NFR-005` と `RR-AC-012` は、利用者拒否、未対応の、要求元・内容不一致、期限切れ、リプレイ、チェーン / ネットワーク / アカウント不一致、検証失敗、結果不明等を成功と区別する最低保証を追跡している。
- `RR-AC-009` と `RR-AC-010` により、トランザクション署名とメッセージ署名の正常受け渡しと、署名者・アカウント・チェーン・ネットワーク・操作の対応を受け入れ条件へ追加している。
- 追跡可能性表は上流根拠、適用主体、整合確認資料、下流引継ぎ、受け入れ条件を要求単位で追跡できる構成になっている。
- Relay の署名、意味解釈、利用者承認、アナウンス、ノード選択および長期履歴サービスを対象外とする責任境界は、共通要件と概ね整合している。

## 未決事項

- メッセージ署名を v1 必須とする共通要件と Web 受け渡し仕様の対象外記載を、下流仕様の修正としていつ閉じるか。
- 内容を解釈しないエンベロープの最低限の外部観測条件（Relay が扱えるメタデータと禁止される平文情報の境界）。
- Relay 状態消失後の旧セッション / 要求識別情報の再利用不能を、Relay 単体・SDK・モバイルのどの責任主体で保証するか。
- Relay マイルストーンの個別完了条件と Mainnet リリース判定への接続。具体的な API、暗号方式、保存領域方式を本要件で固定する必要はない。
