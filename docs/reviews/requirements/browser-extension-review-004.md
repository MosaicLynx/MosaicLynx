## 5. 要約

ブラウザ拡張機能は、共通の要件を Chrome ブラウザ拡張機能固有の制約へ適切に具体化している。特に、拡張機能管理下の確認領域、ブラウザで観測した最上位のオリジン、接続許可と要求ごとの署名承認の分離、オリジン / プロファイル / アカウント / チェーン / ネットワークの対象範囲、Web ページ / ページ文脈 / コンテンツスクリプトの非署名境界、ライフサイクル変化時の承認再利用禁止、wallet-core 境界、最小権限、リモートコード非依存、更新時の安全側での終了および Mainnet 判定条件が MUST と外部から判定可能な受け入れ条件に対応している。

共通の `CR-015`（SDK 境界）、`CR-016`（署名可能状態の共通前提）および `CR-NFR-013`（セキュリティ保証境界）はブラウザ文書へ重複して再定義する必要はない。共通のがブラウザを含む全 Signer へ適用し、ブラウザ側の `BR-003`、`BR-004`、`BR-006`、`BR-007`、`BR-008`、`BR-011` および各 BR-AC が外部側からの迂回・再利用を禁止しているため、継承関係は回復している。

過去のブラウザ指摘は再発していない。バックアップ / 復元は v1 共通の MUST ではなく、初回ブラウザマイルストーンへ不要な要求を逆流させていない。トランザクション署名、メッセージ署名、内容を確認しない署名禁止、dApp の独立検証、アナウンス非包含、Symbol / NEM、Mainnet / Testnet、Relay 非署名、wallet-core 境界および一般ユーザー中心の価値にも回帰はない。

## 9. 解消済みの指摘

過去の指摘について、現行文書で次を確認した。

- `BREQ5-001` / `BREQ6-003`: 未検証入力、XSS、注入およびリモートコードが確認表示、承認、署名権限または秘密情報を変更できないこと、リモート fetched 実行ファイルコードに署名処理を依存させないことが `BR-011`、`BR-AC-009` にある。防御方式は下流へ委譲されている。
- `BREQ5-002`: 更新後に既存プロファイル、アカウント、許可またはウォレットストアを無断で別対象へ置換せず、安全性・互換性・wallet-core 境界を確認できない場合に署名可能状態を継続しないことが `BR-012`、`BR-AC-006` にある。
- `BREQ5-003`: 未許可オリジンの接続要求、利用者の明示操作による許可作成および接続後も要求ごとに承認が必要であることが `BR-003`、`BR-004`、`BR-AC-010`、`BR-AC-011` にある。
- `BREQ5-004`: ブラウザで観測したオリジンの保証範囲、最上位の閲覧文脈、HTTPS / ループバック、iframe / 子フレームおよび不透明なオリジンの扱いが `BR-004`、`BR-AC-012` にある。
- `BREQ6-001`: バックアップ / 復元を初回ブラウザマイルストーンの共通の MUST として追加せず、将来の個別プラットフォーム / リリースに委譲する共通の `CR-014` とプロダクト仕様に整合している。
- `BREQ6-002`: 許可対象範囲のプロファイル / アカウント / チェーン / ネットワーク結び付け、プロファイル A / B の分離、作成・変更・撤回および古くなった / uncertain 許可の不使用が `BR-004`、`BR-AC-001`、`BR-AC-004`、`BR-AC-011` にある。
- `BREQ6-004`: 初回ブラウザ拡張機能マイルストーンの提供・サポート対象が Chrome のみであることが `BR-001`、`BR-AC-013` にある。最低バージョン等は下流へ委譲されている。
- `BREQ6-005`: Mainnet 判定条件の評価時点、公開後の根拠期限切れ・失効・検証不能およびビルド時の / 実行環境の詳細を `BR-013` がリリース操作 / Mainnet 根拠ポリシーへ引き継いでいる。これはブラウザ要件の阻害要因ではない。
