## 総評

クリーンアップの大部分は semantic-preserving である。要求 ID、v1 のトランザクション / メッセージ署名範囲、Mainnet 判定条件、署名主体 / SDK / Relay / wallet-core の責務境界、受け入れ条件の ID と本文、未決の集合および上流追跡可能性は維持されている。表の圧縮、仕様レベルの詳細、レビュー経緯および重複するメタ説明の削除も、原則として要求の意味を変えていない。

ただし、`SDK-NFR-003` では提供開始前の検証結果を存在するものとして報告してはならないという禁止条件が、「通信経路間の対応を完了扱いにしてはならない」へ弱まっている。さらに `RR-006` では再試行時に新しい通信経路認可文脈を伴うという明示が削除され、受け入れ条件には残るものの要求本文からは判定しにくくなった。前者は要求強度の回帰、後者は安全境界の明示性低下であり、後処理の修正が必要である。

## 後処理差分確認

- **要求 ID**: 6 ファイルについて親コミットと現行コミットの ID 集合を比較した。ID の欠落、再利用、renumbering、本文との入れ替えは確認されなかった。`SDK-OPEN-001` も復活していない。
- **MUST / SHOULD / MAY**: 規範的な keyword の要求本文における意味は、上記 2 件を除き維持されている。ブラウザ拡張機能の `MUST` 件数差は、削除された来歴情報文中の語を含むメタ説明の差であり、要求本文の弱体化ではない。モバイル、Relay、共通要件および SDK の他の keyword の適用主体・条件は維持されている。
- **対象範囲**: ブラウザ拡張機能、Android / iOS、Relay の v1 マイルストーン、SDK のブラウザ拡張機能優先と将来モバイル / Relay 連携、Mainnet 判定条件、トランザクション署名 / メッセージ署名の必須範囲は維持されている。モバイル未提供時の完了扱い禁止も `SDK-AC-006` に残っている。
- **セキュリティ境界**: 内容を確認しない署名防止、未解析・未対応時の安全側失敗、チェーン / ネットワーク / アカウント不一致、要求 / 結果対応関係、鮮度 / リプレイ、古くなった承認、利用者拒否、結果不明、秘密情報漏えいおよび Mainnet 安全側での終了の要求と AC は維持されている。`SDK-NFR-003` と `RR-006` の本文については、下記指摘のとおり明示性または強度が低下した。
- **責務**: ブラウザ拡張機能がブラウザで観測したオリジン / 文脈を検証し、モバイル / プラットフォームが受け渡し呼び出し元結び付けを最終検証し、Relay が最終呼び出し元検証・承認・署名を担わず、SDK が署名主体 / wallet-core を代替しない責務分担は維持されている。Relay サーバーのログ出力、保持、診断情報、認証情報処理は SDK の直接保証から移されていない。
- **AC**: 6 ファイルの受け入れ条件の ID と本文は後処理前後で維持されている。圧縮された追跡可能性表からも、各要求と AC の対応は追跡できる。`SDK-AC-006` は提供前の E2E / 契約テスト / 対応済み報告禁止を、`RR-AC-011` は通信経路認証情報の再利用禁止を、それぞれ維持している。
- **未決**: 後処理による誤削除、解決済み未決の復活、参照先の破壊は確認されなかった。現行の一覧は下記のとおりである。
- **追跡可能性**: コンセプト、共通要件、プラットフォーム要件および確定済み ADR を上流根拠とする構造は維持され、アーキテクチャ、仕様、wallet-core、SNIF、実装およびレビューは整合確認または下流引継ぎに留まっている。長い来歴情報の削除により、必要な上流 ID と AC 対応が失われた箇所は確認されなかった。

## 指摘事項

### CLN-001

- ID: `CLN-001`
- 重要度: `ERROR`
- 状態: 未解消
- 対象: `docs/requirements/sdk.md:437-443`（`SDK-NFR-003`）
- 後処理前: `Mobile App が未実装の期間は、Mobile / Relay の実装済み検証結果が存在するものとして報告してはならない。`
- 後処理後: `Mobile / Relay の提供開始前は、その cross-transport 対応を完了扱いにしてはならない。`
- 影響: 現行の MUST 本文では、モバイル / Relay の提供開始前に E2E または契約テストの検証結果が存在するものとして報告しても、「対応完了」と表示しなければ適合し得る。後処理前にあった検証結果の存在・報告そのものに対する禁止条件が失われている。`SDK-AC-006` には旧来の禁止条件が残るが、要求本文と AC の下限が一致せず、要求単体の適合判定では強度が弱くなる。
- 必要な修正: `SDK-NFR-003` に、モバイル / Relay の提供開始前は実装済み検証結果が存在するものとして報告してはならないという同等の MUST 条件を復元する。具体的なテスト基盤や E2E 手順は追加しない。

### CLN-002

- ID: `CLN-002`
- 重要度: `WARN`
- 状態: 未解消
- 対象: `docs/requirements/relay.md:107-119`（`RR-006`）および `RR-AC-011`
- 後処理前: 再試行は `fresh generation context`、`new request identity`、`new session identity`、`必要な新しい transport authorization context`、`fresh encrypted envelope` および新しい利用者承認を伴う。
- 後処理後: 再試行は `fresh generation context`、`新しい identity`、`fresh encrypted envelope` および新しい利用者承認を伴う。`transport authorization context` の明示がない。
- 影響: `RR-AC-011` には古い通信経路認証情報を有効な受け渡しとして再利用しない条件が残るため、受け入れ条件の安全下限は直ちには失われていない。しかし `RR-006` 本文だけでは、状態消失後の新しい受け渡しが新しい通信経路認可文脈に結び付くことを独立に判定できず、世代 / 鮮度と通信経路認可の境界を仕様へ引き継ぐ際に旧認証情報の再利用を許す読み方が生じる。
- 必要な修正: `RR-006` の再試行条件に、新しい通信経路認可文脈を伴うこと、または同じ保証を明示する抽象表現を復元する。認証情報の形式、生成方式、結び付け方式は本要件で固定しない。

未解決の細部は確認されなかった。

## 確認できた事項

- 意味上の変更: 大部分は確認されなかったが、`CLN-001` は要求強度の変更、`CLN-002` は要求本文の明示性低下である。

- 要求 ID: 欠落、再利用、renumbering なし。
- AC: ID・本文は維持され、正常系・安全側失敗・外部判定可能性の主要条件も維持されている。ただし `SDK-NFR-003` と `SDK-AC-006` の本文下限を一致させる必要がある。
- 責務: ブラウザ拡張機能 / モバイルアプリ / Relay / SDK / wallet-core / 署名主体 / dApp の責任境界は維持された。
- セキュリティ境界: 主要な fail-safe、呼び出し元 / オリジン、対応付け、リプレイ、秘密情報、Mainnet 判定条件は維持された。`RR-006` の通信経路認可文脈は復元が必要である。
- 追跡可能性: 上流根拠、プラットフォーム要件、AC、下流引継ぎの主要な対応は維持された。
- specification-level 詳細の整理: API、スキーマ、保存領域、暗号方式、DB / Redis、プロトコル、実装方式などの削除は、要件適合の最低保証を残した範囲で妥当である。
- meta 情報の削除: 来歴情報の詳細、レビュー経緯、既存実装状況の重複説明、外部資料が上流根拠でないことの反復説明は原則妥当である。モバイルの未決定事項節も、正式要求・MR-OPEN-*・追跡可能性に意味が残っているため、削除自体は回帰と判定しない。

## SNIF 整合確認

`_sns/packages/symbol-nem-interchange-format/doc/requirements.md`、`doc/spec-format.md`、`doc/spec-api.md` を整合確認資料として参照した。SNIF は通信経路非依存の形式 / interchange として `id` / `replyTo`、チェーン / ネットワーク、接続、トランザクション署名要求 / 応答等を搬送できるが、次を担わない境界が維持されている。

- 対応付けの搬送は SDK / 署名主体 / プラットフォームの要求存在、鮮度、リプレイ、使用済み管理およびセッション結び付けを代替しない。
- dApp / 接続情報の存在は呼び出し元真正性、オリジン検証、認証 / 認可を成立させない。
- SNIF の通信経路非依存性はブラウザ Provider、ディープリンク / App Link、Relay の安全境界を消去しない。
- 署名要求 / 応答の形式は、利用者承認、署名生成、署名検証、署名主体検証およびトランザクション意味上の検証を代替しない。

SDK 要件は SNIF を上位要求として扱わず、SNIF の使用自体も本後処理で確定していない。
