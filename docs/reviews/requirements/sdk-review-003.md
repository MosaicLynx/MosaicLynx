## 5. 要約

SDK は dApp 側の署名要求・結果の連携層であり、署名主体ではないことが目的、主体表、対象範囲、責務境界および対象外に一貫して定義されている。秘密情報の保管・復号・利用、署名、承認 UI および利用者の最終承認を SDK に移していない。

共通の要件の `CR-015` に対しては、SDK を署名主体の信頼境界外とし、SDK 経由の入力を署名主体が無条件に信頼しない境界が `SDK-FR-005`、`SDK-SEC-003`〜`SDK-SEC-005`、`SDK-PLAT-002`〜`003`、責務境界表および `SDK-AC-003` に追跡できる。`CR-016` に対しては、接続許可と署名承認を分離し、プロファイル / ロック / ロック解除 / 認証操作を外部アプリケーションへ移さず、署名主体の署名前提を弱める記述はない。`CR-NFR-013` に対しても、SDK の保証を各プラットフォーム / 署名主体の検証結果を越えない範囲へ置き、管理境界外の入力、配布物、実行環境および Relay を無条件に信頼しない要求になっている。

トランザクション署名とメッセージ署名は SDK v1 の必須操作として区別され、未対応・未解析・表示不能・生の署名への暗黙代替経路を成功扱いしない。要求、操作、署名主体、アカウント、チェーン / ネットワーク、承認対象および結果の対応付け、成功と失敗分類、結果不明、リプレイ、ライフサイクル変更および利用者に知らせない再試行 / 格下げ禁止は、要求と受入条件から外部判定可能である。

ブラウザのブラウザで観測したオリジン / ブラウザ文脈と、モバイル / Relay の受け渡しセッション / 呼び出し元検証を混同していない。Relay の配送成功や接続済み状態は署名成功・呼び出し元検証済み・最終承認の代替にならない。Symbol / NEM、Mainnet / Testnet、Mainnet 判定条件、wallet-core とアプリケーションの責任も維持されている。

過去 `RREQ1-001`〜`RREQ1-005` の再発はなく、現行の要件レベルで採用すべき新規指摘もない。`SDK-OPEN-002`〜`SDK-OPEN-007` は、最低限の安全条件を固定したうえで API、通信経路、実行環境、バージョンおよび呼び出し元結び付けの具体化を下流へ委譲しており、未決であること自体は阻害要因ではない。

## 10. 後続工程へ委譲する指摘

現行の SDK 要件に対する正式な後続工程へ委譲指摘はない。以下は SDK 要件が安全下限を定めたうえで下流へ引き継ぐ `SDK-OPEN-*` であり、未決であることだけを理由に阻害要因とはしない。

- `SDK-OPEN-002`: アグリゲート / マルチシグ / 連署署名の SDK 公開範囲。対応しない操作は対応能力上利用不能とし、通常のトランザクション署名やメッセージ署名へ変換しない。
- `SDK-OPEN-003`: 拡張機能 / モバイル / Relay の通信経路選択、明示的代替経路、利用不能 / タイムアウトおよび第三者通信経路の具体契約。利用者拒否、完全性 / 呼び出し元 / リプレイ失敗、結果不明後の自動再試行 / 代替経路禁止は確定済みである。
- `SDK-OPEN-004`: トランザクション組み立て補助処理の責務。SDK がノード、アナウンスまたは継続的ネットワーク状態を担わない制約は確定済みである。
- `SDK-OPEN-005`: 正式対応実行環境、ブラウザ文脈、Node.js / SSR / Web ワーカー等および配布形態のサポート対応表。宣言外の実行環境を署名可能・呼び出し元検証済みと扱わない下限は確定済みである。
- `SDK-OPEN-006`: バージョン管理、後方互換性および非推奨化ポリシー。意味を維持できない組み合わせを別操作の成功へ格下げしない制約は確定済みである。
- `SDK-OPEN-007`: ブラウザオリジンとモバイル / Relay 受け渡しの具体的呼び出し元結び付け。最終検証主体、保証上限および検証不能時の成功を確定しないは確定済みで、証明や API の方式を下流へ委譲している。

共通の要件レビューに記録された `REQ4-001`〜`REQ4-003` 等の後続工程へ委譲項目は上位レビューの管理対象であり、本レビューの SDK 正式な指摘へ重複計上していない。メッセージ署名、形式 / エンコーディング、wallet-core 参照および UI 詳細の具体化は、要件の安全下限を弱めない範囲で下流へ引き継ぐ。
