## 5. 要約

Relay は dApp / モバイル署名主体間の受け渡しだけを担い、署名主体の信頼境界外に置かれる。Relay は署名、トランザクション / メッセージの意味解釈・表示、利用者の最終承認、署名秘密情報の処理、アナウンス、長期履歴サービスを担わない。モバイル署名主体が復号・意味上の検証・確認・承認・署名を行い、dApp が結果を独立検証する責任分界は共通の要件と整合している。

`RR-001` / `RR-002` と `RR-AC-009` / `RR-AC-010` により、トランザクション署名とメッセージ署名の両方が Relay マイルストーンの必須受け渡し範囲として明確である。`connect`、`refreshActiveAccount`、`disconnect` は SDK / モバイル契約、`cosignTransaction` は任意 / 既存の SDK 契約として Relay マイルストーンの必須範囲から分離されている。

`RR-003` と `RR-AC-006` は、Relay が内容を解釈しないエンベロープの外形、サイズ、期限切れ、バージョン、認可、対応付け、ライフサイクル等を構造上の / 通信経路検証として扱える一方、平文の復号、トランザクション / メッセージ意味、署名主体表示内容、意味上の検証、承認および署名を扱わない境界を直接判定可能にしている。

`RR-006`、`RR-NFR-003`、`RR-AC-003`、`RR-AC-011` は、世代 / 状態消失後の旧状態・識別情報の復活を禁止し、旧暗号文の一時保存自体を Relay に過去履歴で検出させず、アプリの E2E 検証による no-approval / 署名しない / 成功を確定しないと新鮮な再試行を要求する。永続的なペイロード / 暗号文履歴は要求されていない。

`RR-008`、`RR-NFR-004`、`RR-AC-006` は署名秘密情報、Relay エンドポイント認可認証情報、E2E セッション秘密情報 / 導出された暗号化資料、検証済みクライアント側の受け渡しを別分類し、認証情報 / 秘密情報の不要な URL、ログ、診断情報、利用状況分析、遠隔計測データ、永続的な履歴への露出を防ぐ。`RR-NFR-005` と `RR-AC-012` は失敗、結果不明、Relay 利用不能、再試行を成功と混同しない最低保証を定める。

未決事項は厳密な受け渡し契約、失敗の分類粒度、具体的なプロトコル / API / 暗号処理 / 保存領域 / 保持 / 操作の実装契約に限定され、最低保証を弱めない形で下位フェーズへ委譲されている。Relay 要件は READY と判定するが、要件フェーズ全体は継続中であり、SDK の復元後レビューが残っている。

## 9. 解消済みの指摘

過去 `RREQ1-*`〜`RREQ6-*` は、現行文書において次の要件境界が確認できるため再発なし・解消済みと扱う。

- メッセージ署名は Relay v1 の必須受け渡し範囲であり、下流仕様の対象範囲と一致する。
- Relay は E2E 内容を解釈しないエンベロープと必要最小限のメタデータ / 通信経路認可情報のみを扱い、構造上の検証とモバイル / dApp の意味上の / クライアント側の検証を分離する。

- 上限のある保持、終端後の再利用不能、永続的なペイロード / 暗号文履歴を要求しない状態消失境界が MUST / 受け入れ条件へ追跡されている。
- 世代 / 状態消失後の旧識別情報 / セッションの復活禁止、旧暗号文の一時保存とアプリの署名前拒否の責任分離、新鮮な再試行 / 新鮮な承認が明記されている。

- 追跡可能性表により、各 `RR-*` / `RR-NFR-*` が上流、適用主体、整合確認資料、下流引継ぎ、受け入れ条件へ追跡される。
