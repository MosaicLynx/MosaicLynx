## 5. 要約

現行の共通要件は、一般ユーザーの安全な署名判断を中心に、ブラウザ拡張機能 / Android / iOS を署名主体、Relay を非署名の受け渡し基盤として区別している。明示的承認、内容を確認しない署名の禁止、秘密情報分離、Symbol / NEM、Mainnet / Testnet、署名結果の dApp 独立検証、Mainnet 判定条件、v1 マイルストーン、バックアップ / 復元の共通非包含、API 等の下位フェーズ委譲は概ね適切である。

一方、コンセプトで明示された SDK の責任境界が共通要件の主体・信頼境界・秘密情報要求へ引き継がれていない。また、認証条件が満たされ、署名主体がロックされておらず、対象アカウントの認可が成立していることを署名の共通前提として要求していない。現在の `CR-010` は認証失敗時の安全側終了を述べるだけで、認証・ロック解除・アカウントの利用認可の成功を署名前提として固定していない。このため、共通要件を満たしているだけでは、ロック中・未認証・未認可アカウントの署名を全署名主体で排除できない。

さらに、MosaicLynx の保証を管理下の署名主体 / 承認境界へ限定し、OS、端末、ブラウザ、dApp / Web ページ、配布成果物等の完全侵害まで保証しないというコンセプトの境界が、共通要件の成功条件・セキュリティ要求へ明示的に移されていない。これらは下位のパスワード / PIN / 生体認証、API、状態遷移、脅威モデルを要求する指摘ではなく、要件レベルで必要な共通責任・前提・保証範囲の不足である。

以上のため、品質ゲートを通過させる前に `RR-001`〜`RR-003` の修正が必要である。`OPEN-004` の欠番は、現在の未決事項を創作せずに履歴上の欠番であることを明記すればよい任意改善である。

## 7. 必須の修正

### RR-001: SDK の共通責任・信頼境界が未定義

- 対象箇所: `docs/requirements/requirements.md:5-11,34-43,74-89,185-219,249-259,383-400`
- 発生条件・確認できた事実: 共通要件は dApp、署名主体、Relay をエンドツーエンドの主体として列挙するが、`SDK` を主体として列挙していない。SDK への要求文書リンクもなく、`CR-008` / `CR-NFR-001` / `CR-NFR-002` / `CR-011` の秘密情報・入力・承認境界にも SDK が明示されていない。
- 既存の根拠: コンセプトは、SDK を dApp 側の連携接点であり署名主体ではないと定め（`docs/concept/concept-sheet.md:53-55`）、SDK を含む Web / dApp 側を署名主体の信頼境界外に置き、SDK は秘密情報を保管・復号・利用せず、署名と最終承認を担わないと定めている（`docs/concept/concept-sheet.md:208-218`）。`docs/requirements/sdk.md:3-9,64-70,223-281` には SDK 固有要求があるが、これは共通要件の上流境界欠落を代替しない。
- 問題: SDK 要件を別文書に適用すれば詳細責任は読めるものの、共通要件単体の責任表・信頼境界・秘密情報分離・承認境界では SDK が dApp 側の非署名主体であることを検証できない。後続のプラットフォーム / 受け渡し要件が SDK のクライアント側のアダプターを署名主体の一部、秘密情報を扱う層、または承認を成立させる層として誤って実装・検証する余地が残る。
- 影響: コンセプトの主要な責任境界と共通要求の追跡可能性が不完全になり、SDK を経由した入力検証、秘密情報分離、利用者承認の迂回禁止を全提供形態で同じ共通原則として判定できない。
- 要件レベルで必要な最小修正方針: 共通要件の対象範囲 / 主体表に SDK を dApp 側の連携接点として追加し、署名主体ではないこと、秘密情報を保管・復号・利用しないこと、署名しないこと、利用者の最終承認を担わないこと、署名主体の信頼境界外であることを共通要求として明記する。`CR-NFR-001`、`CR-008`、`CR-NFR-002`、`CR-011` および必要な受け入れ条件へ共通不変条件を追跡し、SDK 固有の要求文書へリンクする。
- 下位フェーズへ委譲する事項: SDK の API、通信経路、呼び出し元結び付け、ペイロード、エラーコード、実行環境、実装方式および SDK 固有の受け入れ試験は `docs/requirements/sdk.md` と後続設計 / 仕様へ委譲する。
- 完了条件・再確認方法: 共通要件に SDK の責任・非責任・信頼境界が追加され、秘密情報・入力・最終承認の共通要求と SDK 要件の `SDK-SEC-*` / `SDK-FR-*` が相互に追跡できること。CR-AC の適用主体に SDK を含めるべき箇所が漏れていないことを再確認する。

### RR-002: 認証・ロック・アカウントの利用認可が署名前提として固定されていない

- 対象箇所: `docs/requirements/requirements.md:91-100,193-205,207-227,315-323,383-400`
- 発生条件・確認できた事実: 共通要件は、アカウントを確認・選択すること（`CR-009`）、認証に失敗した場合の安全側終了（`CR-010`）、要求元の許可範囲（`CR-NFR-008`）を定めている。しかし、認証条件が満たされていること、署名主体がロックされていないこと、対象アカウントの署名認可が成立していることを署名前の必須条件として定めていない。`requirements.md` には `lock` / `ロック` の共通要求がない。
- 既存の根拠: コンセプトは、認証条件、署名主体の非ロック状態、対象アカウントの認可が成立した場合だけ秘密情報を使用でき、dApp / SDK / Relay はそれらを成立・迂回できないと定めている（`docs/concept/concept-sheet.md:172-178`）。モバイル要件では同原則が `MR-006` と `MR-AC-005` に具体化されている（`docs/requirements/mobile-app.md:60-64,139-150`）。これはモバイル固有の下位要求だけに置くべき事項ではなく、全署名主体共通の安全不変条件である。
- 問題: `CR-010` の「認証に失敗した場合」は、認証成功を署名前提にする要求ではない。`CR-009` のアカウント選択や `CR-NFR-008` の dApp の許可範囲も、署名主体のロック解除状態と対象アカウントの利用認可を表さない。そのため、認証・ロック・アカウントの利用認可を確認せずに署名する実装でも、現行の共通 MUST との不適合を明確に判定できない。
- 影響: 全署名主体に共通する利用者承認の前提が欠け、ロック中、未認証、認可されていないアカウント、または外部主体が成立させたと主張する認証状態で署名が成立する回帰を防げない。dApp / SDK / Relay がその条件を成立・迂回しないことも共通受け入れ条件で検証できない。
- 要件レベルで必要な最小修正方針: 各署名主体は、利用者の認証条件が成立し、署名主体がロック解除状態で、現在のプロファイル / チェーン / ネットワークと対象アカウントの署名認可が成立している場合に限り秘密情報を使用して署名できることを共通 MUST とする。ロック中、未認証、認可不成立、確認不能時は署名結果を返さず安全側に終了し、dApp / SDK / Relay はこれらの条件を成立・更新・迂回できないこと、および受け入れ条件を追加する。
- 下位フェーズへ委譲する事項: パスワード、PIN、生体認証、セッションの選択、ロック解除の状態表現、再認証頻度、OS API、API、エラーコード、詳細状態遷移はプラットフォーム要件の補足と設計 / 仕様へ委譲する。
- 完了条件・再確認方法: 共通要件と CR-AC に、認証済み・ロック解除・対象アカウントの利用認可の三条件、各条件の不成立時の署名しない / 成功を確定しない、dApp / SDK / Relay の非迂回を追跡できること。ブラウザ拡張機能、Android、iOS の各プラットフォーム要件がこの共通 MUST を参照していることを再確認する。

### RR-003: セキュリティ保証境界が共通要件へ引き継がれていない

- 対象箇所: `docs/requirements/requirements.md:24-45,74-100,185-191,249-305,379-400`
- 発生条件・確認できた事実: 共通要件は秘密情報分離、入力非信頼、Mainnet 判定条件、署名主体 / Relay / dApp の責任を MUST としているが、MosaicLynx が保証する範囲を「MosaicLynx が管理する署名主体 / 承認境界の正常動作範囲」に限定する記述がない。`CR-AC-007` の秘密情報分離と第8節の成功条件も、外部環境の完全侵害を除外する条件を明示していない。
- 既存の根拠: コンセプトは保証の中心を MosaicLynx が管理する署名主体 / 承認境界の正常動作に限定し、OS、端末、ブラウザ、dApp / Web ページ、正規配布成果物等の管理境界外の完全侵害まで防ぐことを意味しないと定めている（`docs/concept/concept-sheet.md:220-224`）。コンセプト review-003 でもこの境界の整合を確認している（`docs/reviews/concept/concept-sheet-review-003.md:54,168-169`）。
- 問題: 現行の共通要求・成功条件は保証の前提を置かずに秘密情報分離や承認不在署名の達成を要求しているため、正常な管理下の保証と、OS / 端末 / ブラウザ / Web ページ / 配布成果物の完全侵害を含む絶対保証の境界が外部から判定できない。外部入力を信頼しない要求だけでは、MosaicLynx の保証範囲を定義したことにならない。
- 影響: セキュリティレビュー、リリース判定、プラットフォーム対応能力表示および利用者向け説明が、MosaicLynx の管理責任を越える環境まで保証すると読める。逆に、外部主体の侵害を理由に MosaicLynx 管理下の署名主体 / 承認境界の要求を免除する誤解も防げない。
- 要件レベルで必要な最小修正方針: セキュリティまたは対象範囲に、共通セキュリティ要求と成功条件は MosaicLynx が管理する署名主体 / 承認境界が正常に動作する範囲の保証であること、OS、端末、ブラウザ、dApp / Web ページ、外部配布成果物等の完全侵害まで保証しないことを明記する。外部境界からの入力は引き続き検証前に信頼せず、管理境界内で満たすべき no-secret / explicit-approval / 安全側での終了を受け入れ条件へ追跡する。
- 下位フェーズへ委譲する事項: 詳細脅威モデル、攻撃者能力、OS / ブラウザ / 配布の個別脅威、セキュリティテスト、リリース証跡の具体手順および緩和策は設計 / 仕様 / リリースセキュリティ文書へ委譲する。
- 完了条件・再確認方法: 共通要件の保証境界と非保証範囲がコンセプトと同じ意味で明記され、第8節の成功条件・`CR-NFR-002`・`CR-AC-007` がその条件付き保証と矛盾しないことを再確認する。OS、端末、ブラウザ、dApp / Web ページ、配布成果物の完全侵害を保証する文言がないことも確認する。
