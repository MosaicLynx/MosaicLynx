# MosaicLynx 共通要件定義書レビュー

- 対象: `docs/requirements/requirements.md`
- 確認日: 2026-08-24
- 判定: `REVISE REQUIREMENTS`
- レビュー種別: 要件定義レビュー（修正版）

## 実施方法

`requirements-review` Skill と `.agents/project-context.md` を適用した単独レビュー。サブエージェントは使用していない。

判定の主な根拠は、対象要件自身の内部整合性・外部可視性・検証可能性と、上流の `docs/concept/concept-sheet.md` への追跡性とした。下流仕様との不一致は、要件が誤っている根拠として扱っていない。下流資料は、要件が仕様化へ進んだ場合の引継ぎ先を把握する目的に限って参照した。

## 総評

前回から、Signer と Relay の責任境界、Mainnet の fail-closed、要求の完全性・鮮度・replay 防止、要求単位の受け入れ条件、Profile backup の共通要件からの非包含が整理された。特に `CR-014` は、共通要件から外すことと個別 platform で提供する可能性を区別できている。

一方、共通要件の適用対象に Relay を含めるのか、Signer を経由する End-to-End の境界だけを定めるのかが冒頭の位置付けと本文で一致していない。また、セキュリティ要求の一部と wallet-core の named component 化は、コンセプトからの導出または承認済み制約であることを本文上で十分に追跡できない。これらを整理してから仕様化へ進める。

前回レビューで下流資料との競合として扱った message signing と Profile backup の論点は、今回のレビューでは下流資料を根拠にした要件不備として再掲していない。

## 指摘事項

### REQ3-001 — `ERROR` — 共通要件の適用対象に Relay を含める範囲が不明確

- 状態: `OPEN`
- 根拠: 5行目は本書をブラウザ拡張機能とスマホアプリに適用する共通要求と位置付けている。一方、39〜43行目では Relay を責任主体として列挙し、49〜66行目では Relay を v1 milestone として共通境界へ含め、72〜83行目、100行目以降および CR-NFR / 受け入れ条件では End-to-End と Relay を共通要求の適用主体に含めている。
- 影響: Relay 自身が共通要求を満たす主体なのか、Signer と dApp の間の受け渡しに関する境界要求だけを負うのかを、要求単位・受け入れ条件単位で一貫して判定できない。Relay に「表示・承認・署名を担わない」責任を定めること自体は明確だが、文書の適用範囲と矛盾する。
- 必要な修正: 冒頭の位置付けを「Signer と End-to-End に適用し、Relay には受け渡し境界の要求を適用する」などと明記するか、Relay を共通要求の対象から外して Relay 固有要件への引継ぎだけを定める。どちらを採用するかを決めたうえで、各 CR / CR-AC の適用主体を同じ分類へそろえる。

### REQ3-002 — `WARN` — セキュリティ要求の根拠がコンセプトの記述を越えている

- 状態: `OPEN`
- 根拠: CR-NFR-008〜011（309〜339行目）は、要求元・許可範囲、要求内容の完全性、期限・失効、replay・重複・遅延配送を共通 MUST としている。しかしコンセプトの根拠箇所は、外部入力を検証前に信頼しないこと、利用者が確認した対象と署名前後の要求・結果の対応を保つこと、安全側に終了することまでは示すが、これらの具体的な脅威条件・判定単位までは定めていない。コンセプト自身も、具体的な脅威モデル、入力検証、通信仕様は後続で決定するとしている。
- 影響: これらをコンセプトから直接追跡できる確定要求として扱うのか、上流のセキュリティ判断から導出した追加制約として扱うのかが不明で、要求の必要性と優先度を第三者が再確認できない。
- 必要な修正: 各要求について、コンセプトの安全原則から必須化した理由と対象脅威を要求本文または承認済みセキュリティ判断へ追跡する。まだ判断前なら、未決事項として扱う範囲と、仕様化前に確定すべき安全条件を分ける。ここで具体的な暗号方式や通信方式を新たに固定する必要はない。

### REQ3-003 — `WARN` — 共通署名操作の確定範囲と OPEN-003 の関係が不明確

- 状態: `OPEN`
- 根拠: コンセプトはメッセージまたはトランザクションへの署名、提供形態を越えた共通の署名接点を示しているが、120行目では「方向性」と表現し、OPEN-003 では各 milestone の外部要求・完了条件・依存関係を未決としている。一方、CR-007、CR-007-TX、CR-007-MSG および CR-AC-005 / 006 / 015 は、Browser Extension、Android、iOS の全 Signer が transaction signing と message signing を v1 の共通能力として提供することまで MUST 化している。
- 影響: CR-007 が v1 全体で既に確定した共通能力なのか、各 milestone の完了条件で決める範囲を先取りしているのかを判定できない。未実装の Mobile を実装済みと扱う問題ではなく、要件上の共通能力と milestone 別の提供条件の境界が不明確である。
- 必要な修正: 全 Signer の両操作を v1 共通 MUST とする判断を確定事項として明記し、OPEN-003 を個別完了条件だけに限定する。まだ確定していない場合は、CR-007 を共通の安全な署名接点と未対応時の安全側結果に限定し、operation / platform の対応表を OPEN-003 へ移す。

### REQ3-004 — `WARN` — wallet-core の named component 化が「実装方式を確定しない」と併記されている

- 状態: `OPEN`
- 根拠: 13行目は Application 側の実装ライブラリや実装方式を確定しないとしている。一方、43行目、183行目、225〜229行目、418〜427行目では `symbol-nem-wallet-core` を鍵管理、Wallet Store、秘密情報を使用する暗号処理、raw byte signing の正本として MUST で固定している。本文はこれを「承認済み外部コンポーネント」と記載するが、その承認済み制約を示す MosaicLynx 側の上流判断は本文の参照資料に現れていない。
- 影響: wallet-core との責任境界を製品上の外部制約として確定したのか、設計上の採用候補を要件へ昇格させたのかが不明になる。「実装方式を確定しない」という自己制約との関係も第三者には判定しにくい。
- 必要な修正: wallet-core の採用と正本範囲が確定済みなら、承認根拠と固定する責任範囲を要件から追跡可能にする。そのうえで「未確定なのは Application からの統合方式」と明記する。採用自体が未決なら、named component を能力・責任境界の要求へ戻し、具体的なコンポーネント選択は設計へ委ねる。

## 確認できた整合事項

- `CR-001`〜`CR-012` で Signer、Relay、dApp、End-to-End の責任を分け、Relay が利用者判断や署名を担わないことを明記している。
- `CR-NFR-006`、`CR-AC-008`、`OPEN-005` で Mainnet gate の fail-closed と、未達成・判定不能時の扱いを要求として追跡できる。
- `CR-AC-001`〜`CR-AC-016` により、主要な MUST と成功・拒否結果の対応を確認できる。
- `CR-014` と対象外範囲により、Profile backup を共通要件へ含めないことと、個別 platform で提供し得ることを区別している。
- `OPEN-001`、`OPEN-002`、`OPEN-003`、`OPEN-005` および `CR-OPEN-001` / `CR-OPEN-002` により、未決事項を確定要求と混同しない構成になっている。

## 未決事項

1. 共通要件の適用対象を Signer、Relay、End-to-End のどの単位で定義するか。
2. CR-NFR-008〜011 のセキュリティ要求を、コンセプトからの必須導出とするか、承認済みのセキュリティ判断として別途追跡するか。
3. CR-007 の transaction / message signing を全 Signer の v1 共通 MUST として確定済みとするか。
4. `symbol-nem-wallet-core` の採用・正本範囲と、未確定の統合方式の境界。
