## 3. 前回指摘への対応確認

### CLN-001

- 判定: **解消済み**
- 対象: `docs/requirements/sdk.md:437-443`、`SDK-NFR-003`
- 修正前: モバイル / Relay の提供開始前に通信経路間の対応を完了扱いにしてはならない、という下限のみだった。
- 修正後: `Mobile / Relay の提供開始前は、実装済み検証結果が存在するものとして報告してはならない。検証が完了していない状態で、検証済み、確認済み、保証済みまたは対応済みであるかのように報告してはならない。`

修正後は、`SDK-NFR-003` の `MUST` 要求の文脈に、未検証の結果を検証済み・確認済み・保証済み・対応済みとして報告することを禁止する明確な規範的な要求がある。単なる `SHOULD`、注意事項または運用助言への弱体化ではない。`SDK-AC-006` の「E2E 済み、契約テスト済みまたは対応済みと報告しない」という既存条件とも整合する。

復元内容は報告禁止の要求に限定されており、テスト基盤、E2E 手順、証跡形式、実装状態管理などの新しい設計詳細は追加されていない。前回後処理前の禁止範囲を回復したものであり、要求強度の弱体化は解消された。

### CLN-002

- 判定: **解消済み**
- 対象: `docs/requirements/relay.md:107-119`、`RR-006`
- 修正前: 再試行の新鮮な世代、識別情報、暗号化されたエンベロープおよび承認は残っていたが、通信経路認可文脈の扱いが本文から失われていた。
- 修正後: 再試行は `必要な新しい transport authorization context` を伴い、`transport authorization context は retry によって暗黙に別の認可境界へ置き換えず、必要な場合は維持または再検証しなければならない` と明記された。

修正後は、再試行 / 再接続により認可境界を暗黙に変更・迂回しないこと、通信経路認可文脈を無条件に別のものへ置換しないこと、必要な場合に維持または再検証することが要求本文から判定できる。`RR-AC-011` の通信経路認証情報再利用禁止および世代 / リプレイの安全側条件とも整合する。

追加されたのは既存の認可境界の意図を復元する抽象的な要求だけであり、トークン形式、セッション ID、通信経路プロトコル、再試行アルゴリズム、再接続実装、認証プロトコルの具体方式は固定していない。要件定義の粒度を逸脱していない。

## 6. SDK / Relay / 署名主体 / SNIF の責務境界確認

- **SDK**: 外部アプリケーションとの連携、要求・結果の対応および失敗の伝達を担う。署名主体の表示・承認・署名、wallet-core の秘密情報処理、Relay サーバーの内部実装を代替していない。
- **Relay**: 内容を解釈しない受け渡しの通信経路 / 構造上の境界を担う。今回の認可文脈要求によって、Relay がトランザクション / メッセージの意味解釈、利用者承認、署名または呼び出し元識別情報の最終検証主体になる変更はない。
- **署名主体**: 利用者確認・承認、トランザクション / メッセージの意味確認、署名および安全側失敗の責任を維持している。
- **SNIF**: `_sns` の要件、spec-format、spec-api と照合した。SNIF は形式と `id` / `replyTo` 等の対応付け情報を搬送する資料であり、認証、認可、リプレイ防止、鮮度、セッション状態、利用者承認、署名生成、署名検証またはトランザクション意味上の検証を担わない。この責務境界は今回の修正で変更されていない。SNIF は MosaicLynx の上位要求として扱われておらず、SDK が SNIF を使用することも確定されていない。
