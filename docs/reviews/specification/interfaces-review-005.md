## 7. 必須の修正 — 新規指摘 / 再発した指摘

今回は実装開始を妨げる主要も本章に含める。ユーザー指定判定条件による扱いであり、主要を重大に変更してはいない。

### SR-006 — 正式 wallet-core 委譲と秘密鍵付き SDK 署名の規範が競合する

- 重要度: 重大
- 状態: 新規
- 影響対象: interfaces.md §2.2 / §9.2〜§9.6 / §16、chain-compatibility-spec.md §6.1〜§6.3。
- 説明: インターフェースは署名基本機構と秘密情報処理を wallet-core に委譲する一方、署名バイト列の参照先チェーン互換性 §6 は symbol-sdk ファサード / アカウントを唯一の生成実装とし、`createAccount(privateKey)`、アカウント `signTransaction` / `cosignTransaction`、`keyPair.sign` を本番経路に指定する。同 §2 / §9 の wallet-core 所有責任とも競合する。正式コアの公開署名 API は生の `sign` のみで、秘密鍵付きアカウントを返す API はない。`export_private_key` は別の明示的エクスポート操作であり通常署名の鍵取得 API ではない。
- リスク: 実装者が旧 §6 を満たすため署名ごとに秘密鍵をエクスポート・保持し、SDK 側で生の署名を行う合理的解釈が成立する。不要な秘密情報露出と暗号学的な責務の二重化を招き、今回の信頼境界を破る。
- 必須変更: 同一フェーズの参照契約を正式コアの生の署名委譲へ統一する。解析、公開ハッシュ、検証、署名済みペイロード組立てと秘密鍵を使う署名基本機構を区別し、通常署名に秘密鍵エクスポートを必要としない契約を固定する。コア自体を変更しない。
- 受け入れ条件: トランザクション / 連署署名 / メッセージの全経路が承認済み厳密なバイト列をコア `sign` に渡し、MosaicLynx、チェーンアダプター、SDK が秘密鍵を取得・導出・使用せず同じ期待署名と公開結果を作れる。秘密鍵付き SDK アカウントは本番環境署名の前提に存在しない。

### SR-007 — 完成コアの正式 DTO・同期 API・エラーへの統合契約が固定されていない

- 重要度: 主要
- 状態: 新規
- 影響対象: interfaces.md §5.3 / §9.6〜§9.7 / §10 / §11 / §16、プロファイル / チェーン / ブラウザ / モバイルの wallet-core 参照境界。
- 説明: 論理責任は規定されるが、正式パッケージ / 状態、`sign(store, request, password_utf8)`、`SigningRequest.target { profile_id, key_id, context }`、`payload: Uint8Array`、`approval.status`、`SignatureResult.value.signature` の接続先が規範的に固定されていない。コアは生の 64-byte 署名と警告だけを返し、SignedTransaction、ハッシュ、signerPublicKey、要求 ID、配送処理結果の区分を返さない。コアの同期 throw、初期化エラー、操作エラーの正確な対応付けもない。アプリケーションプロファイルは単一チェーン、コアプロファイルはネットワーク固定・鍵ごとチェーン固定であり、両 ID を同一の意味と仮定できない。
- リスク: hex 通信上のペイロードを生の署名バイト列と誤認する、数値の列挙型と DTO の文字列列挙型を混同する、未認証一覧索引を識別情報判断権限とする、存在しないロック解除 / トランザクション API を想定する、BindingFailure を未実行確定と誤認するなどの実装差が生じる。正式コアの利用だけでは共通インターフェースを実装できない。
- 必須変更: 責任主体を定めた規範的統合契約を固定し、外部通信上のとコア DTO の明示対応付け、内部アカウント → プロファイル / 鍵解決、操作固有の厳密なバイト列、結果組立て・独立検証、警告ポリシー、秘密情報入力 / 出力許容範囲、同期呼び出しと初期化、エラーの安全な分類を定める。ロック解除は Signer 内の判定条件として扱い、コアに未公開 API を要求しない。
- 受け入れ条件: 三つのバックエンドで同じ DTO / 結果契約を適用できる。`AuthenticationFailed`、`ProfileNotFound`、`SoftwareKeyNotFound`、`NetworkMismatch`、`BindingFailure`、初期化失敗、未知エラーと結果変換失敗の公開分類 / 終端 / 不明の扱いが判定できる。例外だけで未署名を推測しない。通常署名でニーモニック / 秘密鍵エクスポートを呼ばず、パスワードや内容を解釈しないストアをページ / SDK / Relay に返さない。

### SR-008 — 連署署名の公開応答と不確定結果が定義済み要求に対応しない

- 重要度: 主要
- 状態: 新規
- 影響対象: interfaces.md §6.2〜§6.3 / §9.3 / §9.6 / OPEN-006、sdk.md §5 / OPEN-SDK-004、受け渡し §5 / §7。
- 説明: `cosignTransaction`、Symbol の `detached`、NEM の `payload / parentPayload` は要求共用体にあるが、正規 RelayResponse は `signedTransaction` と `signedData` しか定義しない。連署署名厳密なフィールドを下位へ委譲する §9.6 に対し SDK / 受け渡しは既存 `Promise<MosaicLynxCosignature>` と未決を維持し、不明 / 配送共用体の適用を未決としている。コアは連署署名 DTO を返さず生の署名のみを返す。
- リスク: 分離された連署署名を SignedTransaction へ詰める、別フィールドを発明する、不確定結果を通常例外にするなど互換性と安全性が分岐する。要求 / 親ハッシュ / 連署者 / ネットワークと結果を独立検証する契約が成立しない。
- 必須変更: 対象リリースで提供するチェーン / 方式を確定し、その公開結果、署名 / 親ハッシュ / 連署者の表現、要求対応付け、不明 / 配送処理結果の区分を規定する。今回公開しないなら対応能力・受付を無効 / 未対応のとすることを明示し、成功応答を発明しない。
- 受け入れ条件: 全体親の解析・表示、Signer による親ハッシュ再計算、既存の署名 / 連署署名検証、連署者 / ネットワーク一致に加え、attached / 分離された / NEM の許可結果と禁止結果が一意である。ハッシュのみ外部要求は拒否し、不確定時に再署名しない。

### SR-009 — メッセージの正規期限切れと確認可能なバイナリ形式が未確定

- 重要度: 主要
- 状態: 新規
- 影響対象: interfaces.md §9.4 / OPEN-001、受け渡しの RelayDataSigningRequest、プロダクト構造化されたメッセージ契約。
- 説明: 署名バイト列は接頭辞 + JCS(StructuredMessage) と定まるが、StructuredMessage の `expiresAt` と Relay 要求の `messageExpiresAt` の変換責任主体 / 対応付けは明示的未決であり、暗黙別名も禁止されている。`encoding: 'hex'` は許可される一方、「生バイト列の羅列だけでは承認不可」に対し、確認可能なバイナリ形式の範囲と undecodable 入力の具体的受付条件がない。
- リスク: 別実装が異なる JCS オブジェクトを署名・検証する、要求期限切れとメッセージ期限切れを取り違える、hex 表示を意味確認と誤認する。ドメイン / オリジン接頭辞があっても内容を確認しない署名防止の成立は証明できない。
- 必須変更: メッセージ署名の対象リリースを決め、正規オブジェクト / 期限切れ対応付けの責任主体を確定する。人が読める / バイナリの対応形式と表示可能性の受入条件を固定し、意味を確認できない任意のバイト列は未対応のにする。安全な契約を閉じない場合は MVP の MESSAGE_SIGN を無効とする判断を上流で承認する。
- 受け入れ条件: SDK / 拡張機能 / モバイル / 独立した検証者が同じ正規メッセージと署名バイト列を得る。観測された / proven 要求元オリジンと署名オリジンが一致する。UTF-8、NFC 不正、未対応のエンコーディング、解釈不能 hex、期限切れ不一致、ノンスリプレイが署名前に拒否される。UI 配置の固定は不要。

### SR-010 — 信頼されていない JS DTO の安定した値と検証前リソース上限が未固定

- 重要度: 主要
- 状態: 新規
- 影響対象: interfaces.md §6.4 / §11 / §12、ブラウザページ → Provider / ホスト境界、モバイル復号後境界。
- 説明: JSON 型検証、不明フィールド拒否、トランザクション 256 KiB、メッセージ 16 KiB、チェーン収集上限はある。しかし SDK が受ける JS オブジェクトの継承したフィールド / accessor / ゲッター / Proxy と、承認・署名の間で同じ値を維持する境界契約はない。Relay 側受け渡し §13 はプロトタイプ pollution / 過剰 depth を拒否するとするが厳密な結び付いたがなく、ブラウザも含めたエンベロープ / 文字列 / nesting の検証前上限・拒否条件が一意でない。コアファサードは自身のデータプロパティスナップショットを規定するが、その時点は承認後であり上流の表示・承認の同一性を保証しない。Proxy trap の副作用・原子的スナップショットは保証対象外である。
- リスク: ゲッターが表示用と署名用に異なる値を返す入力や、サイズ超過の / deeply nested オブジェクトが、実装ごとに異なる検証・JCS・内容検査を誘発する。コアの安全な変換だけでは Signer の TOCTOU とリソース枯渇を防げない。
- 必須変更: 外部 JS / JSON → Signer が所有する validated 値の許可・拒否条件と、同じ対象 / 要約 / core-call バイト列の結び付けを契約化する。ゲッター / 継承した / 読み取り不能な入力を判断権限としないこと、不正な形式の / dangerous keys の扱い、pre-parse / pre-copy の必要なリソース制限を責任主体付きで固定する。具体的パーサーや clone ライブラリは指定しない。
- 受け入れ条件: 継承した必須フィールド、accessor による置換、descriptor trap 失敗、dangerous 鍵、過剰文字列 / バイト列 / depth / elements を入力した時の拒否と wallet-core 未呼出しを独立判定できる。Proxy を無副作用で検出できるという不可能な保証は置かず、信頼されていない realm のオブジェクトを直接承認判断権限にしない。

### SR-003 — 受け渡しのタイムアウト / アプリ終了が未署名確定へ縮退する

- 重要度: 主要
- 状態: 再発
- 影響対象: interfaces.md §10.3 / §13.1 と参照する受け渡し §11、署名プロトコル §19.2。
- 説明: review-004 で解決した共通の結果 / 配送共用体は維持されている。しかし受け渡し §11 の「拒否、アプリ終了、タイムアウトは署名されていない状態として完了する」は、署名中のタイムアウト / 終了と signed-result 配送前の終了を未署名と断定する。署名プロトコルは署名生成が確定しない時だけ RESULT_UNKNOWN、生成済みなら既知結果を保持すると規定し、共通契約と異なる結果を要求する。
- リスク: 呼出し元がタイムアウトを未署名の証明として扱い、新たな要求・アナウンスを重ねる。不確定な署名生成と既知結果の配送不明を区別できない。自動再試行禁止だけでは誤った確定情報を訂正できない。
- 必須変更: 同 ID の既存区別を失わないこと条件を受け渡し §11 にも適用し、拒否、署名前キャンセル、処理中の不明、既知の結果 / 配送、通信経路タイムアウトを区別する。SDK / Relay が RESULT_UNKNOWN / DELIVERY_UNKNOWN を合成しない条件を維持する。
- 受け入れ条件: 承認前タイムアウト、署名呼出し中プロセス消失、署名成功後応答消失、SDK タイムアウト、成功後キャンセルに対して未署名を推測しない。既知結果は再生成せず、Signer のみの不明と通信経路失敗を維持する。旧重要度は重大だったが今回はユーザーのエラー / 不明状態基準で主要とし、状態解釈が実装を妨げるため判定条件阻害要因とする。

## 12. 対象範囲と追跡可能性 — Wallet-core 互換性評価

### 公開 API と DTO の実態

### エラー / バックエンド評価

コアは18の安定したコードを `WalletCoreError` として throw し、`name` / `code` / `message` は固定契約。実行環境 `WalletCoreError` クラスエクスポートはない。`instanceof` の専用クラスを前提にしない。別名前空間の `WalletCoreBackendInitializationError` はコードを持たず、固定メッセージ `backend initialization failed` を返す。

`InvalidArgument` / `InvalidStore` / 未対応のスキーマ / `ProfileNotFound` / `SoftwareKeyNotFound` / `AuthenticationFailed` / `NetworkMismatch` / `CryptoFailure` / `BindingFailure` 等を Signer の公開エラーと結果確定性へ写像する必要がある。コアは失敗 / RESULT_UNKNOWN / DELIVERY_UNKNOWN、ロック済み、呼び出し元許可を判断しない。秘密・スタック・生のバックエンド詳細・警告をページに公開するエラーにそのまま転送しない。正確な対応付けは `SR-007`。

| バックエンド        | 正式契約                                                                                                                          | 統合評価                                                                                                                                |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| ネイティブ / ノード | node-addons 条件、同期関数。有効なマニフェストにネイティブ対象がない場合だけ package-local WASM へ初期選択可能                    | ネイティブ負荷 / 操作失敗後に再試行しない。Signer を切り替える代替経路とは別                                                            |
| ブラウザ WASM       | モジュール初期化は非同期になり得る。evaluation 後の16 API は同期                                                                  | モジュールインポート失敗と署名操作失敗を区別。保証署名 API を前提にしない                                                               |
| React ネイティブ    | react-native 条件、新規アーキテクチャ TurboModule / JSI provider、同じ同期 DTO / エラー。実行環境 / 登録簿 / ライフサイクル無効化 | npm install だけでは成立しない。provider / ライフサイクル失敗時 WASM / ノード代替経路禁止。モバイルワークスペースが存在する証拠ではない |

バックエンドの共通仕様は存在するためコア自体の非互換を指摘していない。MosaicLynx が利用する境界の採用・対応付けが未固定である。

### トランザクション / セキュリティ確認の補足

- Transfer、アグリゲート埋め込み、NEM ラッパー / 内部 / 連署署名はチェーン互換性の許可リストと全フィールド表を確認した。手数料、期限、受信者、mosaic、数量、トランザクションハッシュ、署名者役割、既存の署名 / 連署署名、ネットワーク、正規バイト列を検証する契約がある。
- 名前空間 / メタデータ / マルチシグ modification / アカウント・mosaic・名前空間 restrictions / ロック / 秘密情報トランザクションは現行許可リスト外。不明 / 将来型とともに未対応のとし、「それらしい要約」で承認しない。対応する意味上のパーサーを新たに要求しない。
- 世代ハッシュは固定 SDK ネットワークのシード、NEM の署名バイト列は non-verifiable シリアライズに追跡される。コアはその情報を付加しない。
- 外部アグリゲートハッシュだけでは拒否する。検証済み全体親から Signer が計算した連署バイト列を生のコアに渡すことはハッシュのみ内容を確認しない連署と同義ではない。
- 要求差し替え、アカウント / ネットワーク差し替え、confused deputy、重複承認 / 署名、古くなった / リプレイ、TOCTOU はオリジン / 許可 / プロファイル / 対象範囲 / 対象 / 鮮度 / 四条件 / ダイジェストと直前再検証で禁止される。入力値の安定性を成立させる契約が SR-010。
- 秘密情報漏えい / 例外漏えいは不変条件と公開エラーポリシーが禁止。クリップボードを認可 / 受け渡し標準として使わず、独自の方式は追加契約なしに受理しない。
- オリジン証明は要求元鍵と要求完全性の証明であり、dApp の善性の証明ではない。compromised dApp の要約を信用しない。compromised 特権を持つ Signer / コア realm をコアファサードが安全化する保証はない。
- Relay 侵害に対して E2E 機密性 / 完全性は要求されるが、通信経路利用可能性は保証されない。Relay 失敗を署名失敗 / 不明判定へ変換しない。
